📇 概念卡 #1:连接池 —— 账房门口固定几位伙计,轮流接待

① 一句话大白话: 连接池是应用里预先准备好的一组数据库连接。请求来了从池子里借一个,查完还回去,下一个请求接着用;池子满了,后来的请求排队等。这样既省掉了每次新建连接的开销(PostgreSQL 每个连接是一个进程,Day 22),也给数据库的总连接数加了一个上限。

② 生活类比:门口固定几位伙计

Day 22 说过:每来一个办事的人,账房总管就专门派一个伙计陪他,直到他离开。如果分店每接一单就派一个人去账房、办完就走,账房要不停地招人、遣散人,高峰期一下子来两百个人,账房就挤爆了。连接池的做法是:门口固定站 5 位伙计,谁来了就找一位空闲的,办完伙计留在门口等下一位;5 位都忙时,后来的人排队,而不是再招第 6 位。

比喻真实组件nest-lab 里

在 Nest 里,池子是一个 Provider:Day 12 的带类型 token PG_POOL + Day 9 的 useFactory(从 ConfigService 读连接串、池大小、schema 名),DatabaseModule 实现 onModuleDestroy,在 app.close() 时把所有连接还给数据库(不关的话进程会因为还有打开的 socket 退不出去)。pg.Pool 创建时不会连数据库,第一次 query 才真正建连接,所以内存模式下它只是一个闲置的对象。

⑤ 动手验证:池子上限设为 5,同时发 20 个请求,每个请求占用连接 300 ms(SELECT pg_sleep(0.3))。✍️ 预测(先写再运行):总用时大约多少?pg_stat_activity 里 nest-lab 的连接数最多是几?请求结束后连接会立刻消失吗?真实结果(npm run day27 第 1 幕):

========== 第 1 幕:20 个请求同时到达,每个占用连接 300 ms;池子最多 5 个连接 ==========
20 个请求全部返回:是,总用时 1283 ms(串行要 6000 ms,不限连接数约 300 ms)
它们一共用到了 5 个不同的后端进程:12151, 12153, 12154, 12155, 12156
观察期间 pg_stat_activity 里 nest-lab 的连接数最多是 5
✅ 并发 20 个请求时,连接数始终不超过池大小 5
请求结束后,池子里还留着 5 个空闲连接(idleTimeoutMillis=10000,空闲 10 秒才关)

20 个请求分 4 轮,每轮 5 个,4 × 300 ms ≈ 1.2 秒,加上开销就是 1283 ms。只用到 5 个后端进程,后来的请求复用的是同一批连接。请求结束后连接没有断,还在池子里等下一批,这正是池子省掉的开销。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「伙计越多,办得越快」——池子不是越大越好。数据库的 CPU、磁盘是固定的,同时干活的连接一多,反而在争锁、争 CPU、来回切换上浪费时间,总吞吐量可能下降。HikariCP(Java 最常用的连接池)文档里有个经验公式:连接数 ≈ CPU 核数 × 2 + 磁盘数,意思是池子通常比想象的小得多。真正的答案靠压测(Week 17 / Week 19)。
  2. 「一个账房一支伙计队伍」——多副本时要乘以副本数。Day 4 讲过 cluster 开多个进程,部署时还会开多个副本:4 个副本 × 每个池 10 = 40 个连接,再加上后台任务、迁移脚本、你自己开的 psql。PostgreSQL 默认 max_connections 是 100(Day 22 实测),很容易超。连接数太多时,要在数据库前面放 PgBouncer 这类「共享的伙计队伍」(Week 6)。
  3. 「伙计办完就还回来」——忘了还,队伍就借空了。pool.query() 会自动借还;pool.connect() 拿到的连接必须在 finally 里 release()。漏一次 release,池子就少一个人;漏 5 次,所有请求都会卡在「等待空闲连接」,3 秒后报超时。
④ 真实术语: connection pool;pg.Pool / pg.Client / PoolClient;max / idleTimeoutMillis / connectionTimeoutMillis;connection acquisition / release;pool exhaustion(池子被借空);application_name;PgBouncer(外部连接池,Week 6);graceful shutdown(onModuleDestroy + pool.end())。

📇 概念卡 #2:参数化查询 —— 客人的话只写进「填写栏」

① 一句话大白话: SQL 注入:把用户输入拼进 SQL 字符串,用户就能在输入里写 SQL,改掉你的语句本来的意思。参数化查询:SQL 文本固定写成 … WHERE body LIKE '%' || $1 || '%',用户输入作为参数单独发给数据库,数据库只把它当成一个值,永远不会把它当 SQL 解析。数据和指令走不同的通道。但列名、表名、排序方向这类「SQL 结构」不能参数化,只能从白名单里选。

② 生活类比:单子上的填写栏和操作栏

账房的单子印着两栏:操作栏是印好的,「查询 alice 的笔记,内容包含【 】」;填写栏就是那对括号,客人只能往里面写字。伙计只照着操作栏办事,客人在括号里写「或者把所有人的笔记都给我,再把保险柜打开」,伙计会老老实实地去找「内容包含『或者把所有人的笔记都给我……』」的笔记,当然一条也找不到。拼接字符串则相当于让客人自己在空白纸上写整张单子,前半句由你写好、后半句由客人接着写,他想写什么操作都行。

⑤ 动手验证:先亲手注入一次。sql/day27/01-injection-demo.sql 建了两张实验表:day27_demo.notes(alice 两条、bob 一条私人笔记)和一张接口不该碰到的 day27_demo.api_keys。src/db-demo/db-demo.controller.ts 里有一个故意写错的接口,只查 alice 的笔记:

// ❌ 永远不要这样写
const sql = `SELECT id, body FROM day27_demo.notes WHERE owner = 'alice' AND body LIKE '%${q}%'`;
await this.pool.query(sql);

✍️ 预测:q = ' OR 1=1 -- 会返回谁的笔记?q = ' UNION SELECT id, secret FROM day27_demo.api_keys -- 呢?q = '; DROP TABLE day27_demo.api_keys; -- 会怎样?真实结果(第 2 幕):

❌ 拼接 · 正常搜索:q = SQL
   实际执行的 SQL:SELECT id, body FROM day27_demo.notes WHERE owner = 'alice' AND body LIKE '%SQL%'
   → SELECT:[{"id":2,"body":"周二:学 SQL 注入"}]

❌ 拼接 · 永真条件:q = ' OR 1=1 --
   实际执行的 SQL:SELECT id, body FROM day27_demo.notes WHERE owner = 'alice' AND body LIKE '%' OR 1=1 --%'
   → SELECT:[{"id":1,"body":"周一:买菜"},{"id":2,"body":"周二:学 SQL 注入"},{"id":3,"body":"Bob 的私人笔记:银行卡密码提示"}]

❌ 拼接 · UNION 偷别的表:q = ' UNION SELECT id, secret FROM day27_demo.api_keys --
   实际执行的 SQL:SELECT id, body FROM day27_demo.notes WHERE owner = 'alice' AND body LIKE '%' UNION SELECT id, secret FROM day27_demo.api_keys --%'
   → SELECT:[{"id":1,"body":"周一:买菜"},{"id":1,"body":"DEMO-SECRET-not-a-real-key"},{"id":2,"body":"周二:学 SQL 注入"}]

❌ 拼接 · 多语句:删表:q = '; DROP TABLE day27_demo.api_keys; --
   实际执行的 SQL:SELECT id, body FROM day27_demo.notes WHERE owner = 'alice' AND body LIKE '%'; DROP TABLE day27_demo.api_keys; --%'
   → SELECT:[{"id":1,"body":"周一:买菜"},{"id":2,"body":"周二:学 SQL 注入"}]
   → DROP:[]

多语句注入之后,day27_demo.api_keys 还在吗?不在了

三次攻击全部成功:永真条件让 OR 1=1 绕过了 owner = 'alice'(AND 比 OR 优先,-- 把后面的 %' 注释掉),读到了 Bob 的私人笔记;UNION 把另一张表的密钥拼进了结果;多语句直接删掉了一张表。最后一种能成功,是因为这个接口调用 pool.query(sql) 时没有传参数,pg 驱动走「简单查询协议」:整段文本原样交给数据库,里面有几条语句就执行几条,驱动返回的是一个「每条语句一个结果」的数组(上面的 SELECT 和 DROP 两行)。

   SQL 文本永远是:SELECT id, body FROM day27_demo.notes WHERE owner = 'alice' AND body LIKE '%' || $1 || '%'
   → 200:[]
✅ 参数化 · UNION 偷别的表 …  → 200:[]
✅ 参数化 · 多语句:删表 …     → 200:[]
(正常搜索 q = SQL → 200:[{"id":2,"body":"周二:学 SQL 注入"}])

带参数时塞两条语句:42601 cannot insert multiple commands into a prepared statement

同样的四个输入,参数化之后都只是「要搜的文字」:没有哪条 alice 的笔记里包含 ' OR 1=1 -- 这串字符,所以结果是空的。最后一行:带参数时驱动走「扩展查询协议」,SQL 文本和参数分开发送,一段文本里只能有一条语句,这又多了一层保护(但不要依赖它,真正的保护是「值不进 SQL 文本」)。

排序字段为什么不能参数化:ORDER BY $1 里的 $1 会被当成一个值(比如字符串 'title'),对每一行都一样,等于没排序;它不能变成列名。所以 PgTasksRepository 里有一张白名单:

// src/tasks/pg-tasks.repository.ts
const SORT_SQL: Record<SortField, { expr: string; cast: string }> = {
  id: { expr: 't.id', cast: 'bigint' },
  createdAt: { expr: 't.created_at', cast: 'timestamptz' },
  title: { expr: 't.title COLLATE "C"', cast: 'text' },
};
// 用户的 ?sort=-createdAt 只用来「选」哪一项;拼进 SQL 的永远是代码里写死的字符串
const orderBy = sort.map((s) => `${SORT_SQL[s.field].expr} ${s.dir === 'desc' ? 'DESC' : 'ASC'}`).join(', ');

Day 19 的 DTO(@IsIn)是第一道墙,这张表是第二道。同样的道理也用在 DATABASE_SCHEMA 上:schema 名会拼进连接参数 search_path,所以 env schema 用正则限制它只能是小写字母、数字、下划线(env.schema.spec.ts 里测了 'app; DROP TABLE tasks' 会被拒绝)。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「有了填写栏就万事大吉」——参数化只保护「值」。列名、表名、排序方向、LIMIT 以外的 SQL 结构(比如 IN (…) 里有几个元素)都不能用 $n。动态生成这些部分时,只能用白名单,或者 pg 的 escapeIdentifier 这类函数,并且要非常小心。ORM 也一样:Prisma 的 $queryRawUnsafe、EF Core 的 FromSqlRaw 拼字符串,照样能被注入(第 6 节)。
  2. 「客人填写栏里写的只是文字」——对数据库是,对下一个读它的人不一定。参数化防的是 SQL 注入。用户存进去的 <script>… 依然是一段字符串,如果前端拿它去拼 HTML,那是 XSS(Week 20)。每一层都要按自己的语法转义:SQL 用参数,HTML 用转义 / 框架的自动转义,shell 用参数数组(Day 4 的 shell 注入)。
  3. 「伙计会检查填写栏里写的是不是合理」——参数化不做校验。q 可以有 1 MB 长,可以全是 %(没转义时就变成「匹配一切」)。长度、格式仍然是 DTO 的事(Day 16),LIKE 通配符要自己转义(escapeLike)。
④ 真实术语: SQL injection(OWASP Top 10 的 Injection 类);tautology attack(OR 1=1);UNION-based injection;stacked queries(多语句);parameterized query / prepared statement;bind parameter($1);PostgreSQL 的 simple query protocol vs extended query protocol;identifier vs literal(escapeIdentifier / escapeLiteral);allowlist;LIKE escaping。

「只改一行」兑现了吗?

差一点。Day 9 的接口是同步的:findById(id: number): Task | undefined。内存数组伸手就有,同步没问题;数据库在另一个进程里,每次读写都是网络 I/O,在 Node 里只能是异步的(Day 1–3 的 event loop)。所以今天第一件事是把接口改成 Promise<Task | undefined>。这就是所谓的抽象泄漏:接口本该只描述「能做什么」,却悄悄带上了「数据就在手边」这个实现细节。改完以后,TypeScript 编译器把所有没 await 的地方一个个指了出来(单元测试里的假仓储、pagination.e2e-spec.ts 里直接调 Service 的地方、day19 观察脚本),改掉它们就好;业务规则一行都没动。教训:设计会碰 I/O 的接口时,从第一天就写成异步的,哪怕第一个实现是内存版。

第二处是 tasks.module.ts:不是改 useClass 那一行,而是把它换成一个按配置选择的 useFactory(为了让默认的内存版不需要数据库):

{
  provide: TASKS_REPOSITORY,
  useFactory: (seed: Task[], pool: pg.Pool, config?: ConfigService<Env, true>): TasksRepository => {
    if (config?.get('TASKS_STORAGE', { infer: true }) !== 'postgres') return new InMemoryTasksRepository(seed);
    return new PgTasksRepository(pool, config.get('DB_RESET_ON_START', { infer: true }) ? seed : null);
  },
  inject: [TASKS_SEED, PG_POOL, { token: ConfigService, optional: true }],
}

回答 Day 21 留下的思考题:「换成 PG 后,85 个 e2e 用例还应该全部通过吗?」应该,而且实测确实全部通过,一条断言都没改。e2e 测的是 HTTP 契约(状态码、响应体、错误格式),不是存储方式;如果哪条挂了,说明两种实现的行为不一样,那正是 bug 所在。但让它们通过,需要三处测试基础设施的调整,都和「测试假设了什么」有关:

  1. 每个测试都假设「开店时只有两条样品任务,下一个 id 是 3」。内存版每创建一个 app 就是一个新数组;PG 版的数据会留在库里。所以加了 DB_RESET_ON_START:创建 app 时 TRUNCATE … RESTART IDENTITY 并写入同样的样品数据(样品的 createdAt 来自注入的 CLOCK,所以 rest.e2e 里写死的 2026-01-01 也对得上)。生产环境禁止打开这个开关。
  2. 内存版每个测试文件各有各的数组,可以并行;PG 版共用一个库,所以 fileParallelism: false,表放在独立的 schema app_test。
  3. 直接调用 Service 的测试(pagination.e2e-spec.ts)要加 await:这是接口改成异步带来的,编译器会指出来。另外,有两个用例(tasks.e2e 的「覆盖配置」、openapi.e2e 的「关闭文档」)整个替换了 ConfigService,里面没有 TASKS_STORAGE,在 PG 版里它们实际上还是用内存仓储。不影响结论,但要知道。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「换了仓库,菜的味道一模一样」——两种实现的行为并不完全相同。观察脚本第 6 幕就是一个真实的例子:PATCH {"title": null} 能通过 DTO(PartialType 加的 @IsOptional 会放过 null),内存版把标题改成了 null 并返回 200;PG 版被 NOT NULL 约束拦下,返回 422("pointer":"#/title")。数据库约束替 DTO 补了一个漏洞,这正是 Day 24 说的「最后一道校验」;但它也说明 DTO 有一个真 bug(习题 3)。其他差异:排序规则(用 COLLATE "C" 对齐)、时间精度(PG 是微秒,这里写入的都是 JS 的毫秒)、bigint 被驱动读成字符串(仓储里 Number())。这些差异 85 个用例都没覆盖到,所以「e2e 全过」不等于「行为完全一致」。
  2. 「一起送到就万无一失」——今天的事务只保证「两张表一起成功或一起失败」。Service 的 replace / update 是「先查(检查 409 规则)、再改」两次往返,中间如果另一个请求改了同一条任务,检查的结论就过时了;两个请求同时 PATCH 同一条,后写的会覆盖先写的。并发下读到什么、怎么加锁、隔离级别,是 Week 6 的内容。
  3. 「仓库会告诉你哪里不对」——约束只认识它自己的规则。Day 15 的「已完成的任务不能改标题」、Day 16 的「清单最多 20 项」,数据库都不知道,仍然靠 Service 和 DTO。约束错误的翻译表(pg-errors.ts)也只登记了 API 能碰到的约束;没登记的数据库错误一律当 500,并且不暴露原文。
④ 真实术语: repository pattern;dependency inversion;leaky abstraction(抽象泄漏);transaction(BEGIN / COMMIT / ROLLBACK,同一个连接);atomicity(ACID 的 A,Week 6);SQLSTATE mapping / error translation;keyset pagination(row value comparison vs expanded OR);collation(COLLATE "C");fail fast;test fixture / database reset;contract test(同一套测试验证两个实现)。

🎤 面试翻译练习: 面试官问:"What is SQL injection and why do parameterized queries prevent it? Can you parameterize ORDER BY? How do you size a connection pool?"(或者:「什么是 SQL 注入?参数化为什么能防?ORDER BY 能参数化吗?连接池大小怎么定?」)你可以答:
"SQL 注入是把用户输入拼进 SQL 字符串,输入里的引号、OR、UNION、分号会改变语句本来的结构,轻则读到别人的数据,重则删表。参数化查询把 SQL 文本和参数分开发给数据库,文本先被解析成固定的结构,参数只作为值代入,不会再被当成 SQL 解析,所以不管输入是什么都改不了语句结构;在 PostgreSQL 里带参数的查询走扩展查询协议,一段文本里也只能有一条语句。但参数只能代替值,列名、表名、排序方向这类结构不能参数化,ORDER BY 必须用白名单把用户的选择映射成代码里写死的列名。连接池的作用是复用连接,PostgreSQL 每个连接是一个进程,建连接很贵,而且 max_connections 有限,所以池子要有上限;大小不是越大越好,数据库能同时有效干活的连接数大约和 CPU 核数同一个量级,还要乘以应用的副本数,不能超过数据库的上限,最终靠压测确定。连接数需求很大时会在前面加 PgBouncer。"

今天带走的 4 句话

  1. 连接池复用连接、给总连接数封顶:实测池上限 5 时,20 个并发请求只用了 5 个后端进程、总用时约 1.3 秒。池子不是越大越好,多副本时要乘以副本数;pool.connect() 借的连接必须 release();关店时 pool.end()。
  2. SQL 注入是「数据被当成了指令」:拼接字符串时,永真条件、UNION、多语句删表全部实测成功;参数化后同样的输入都只是值。参数只能代替值,ORDER BY 的列名和方向必须走白名单;LIKE 的通配符要转义。
  3. 换仓储靠的是 Day 9 的「依赖接口」:业务规则、Controller、DTO、错误格式都没改,同一套 85 个 e2e 在内存版和 PG 版上都通过;唯一的泄漏是同步接口,改成 Promise 后由编译器指出所有调用点。两张表一起写要用同一个连接的事务;约束违反按 SQLSTATE 翻译成 problem+json,不暴露原文。
  4. 两种实现的行为不完全一样:{"title": null} 内存版 200、PG 版 422;排序规则、时间精度、bigint 也要对齐。e2e 全过不等于行为一致,数据库约束会替上层兜住漏掉的规则。配置缺失和数据库连不上都在启动时失败。
