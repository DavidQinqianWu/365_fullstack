🗺️ 第一件事:画出「一次列表请求的一生」,从调用方拿到 openapi.json 开始(约 25 min)

Week 1 复盘你画的是「一个 HTTP 请求在 Node 服务器里的一生」,Week 2 复盘把它往上盖了一层,画的是同一个请求在 Nest 管线里经过哪些站。今天再往上盖一层:管线还是那条管线,但每一站现在都承担着一条对外承诺。这次的主角也不再只是服务器,还包括调用方:他从拿到契约开始,到翻完第二页为止。

场景(主线)

# 第 0 步:调用方先拿契约

# 第 2 页:把 nextCursor 原样传回

要覆盖这些环节(顺序你自己排):

  • 调用方在发请求之前,从 openapi.json 里知道了什么(有哪些参数、limit 的范围、响应形状、可能的错误);生成的类型里 nextCursor 是什么类型
  • 请求 ID 从哪来、存在哪、最后出现在响应的哪两个地方(成功时和失败时各是哪里)
  • 谁检查 Accept,不满足时回什么
  • /v2 这个前缀是谁认出来的,为什么不带版本号的 /tasks 也能到同一个 Controller
  • 这个接口要不要钥匙,是谁、根据什么决定的
  • done=false、limit=10、sort=-createdAt 从字符串变成什么,在哪一站变的;非法值在哪一站被拦下
  • cursor 在哪里被解码、它里面装了什么、为什么换了 sort 旧 cursor 就不能用了
  • 为什么要多取 1 条;排序为什么要补 id;这一段如果换成 SQL 长什么样
  • 内部的 Task 在哪一步变成对外的字段,谁决定哪些字段出门
  • 响应为什么是 { items, nextCursor } 而不是 { data, timestamp };计时头在哪里写

再写四条支线(模板里已列好):cursor 被改坏;limit=500 / sort=password / foo=1;换成 /v1/tasks;Accept: text/html 与不带版本号的 /tasks。

为什么这张图值 25 分钟

Week 2 那张图回答的是「框架怎么组织代码」;今天这张图回答的是「调用方能依赖什么」。面试里问「你怎么设计一个列表接口」,能从契约讲到 pipe、从 cursor 讲到 SQL、从错误体讲到 requestId 的人,说明他知道每一条承诺是在哪一站兑现的。

这张图在 ASP.NET Core 和 Spring 里结构也几乎一样:内容协商 → 路由与版本 → 鉴权 → 参数绑定与校验 → Controller → Service / Repository → 响应映射 → 异常处理成 ProblemDetails。你画的是「一个 REST API 的契约在服务端怎么兑现」,不是「NestJS 的用法」。

一句话总结 Week 3

你现在知道一个 REST API 不只是「能返回数据的路由」,而是一份对外契约:方法和状态码的语义、进门和出门的报关单、统一的错误格式、翻页和换版本的规矩,以及一份从代码生成、会自动报警的机器可读文档。

Week 1 是「服务器怎么收发字节」,Week 2 是「框架怎么组织代码」,Week 3 是「写出去的东西怎么让别人放心依赖」。从 Week 4 开始,数据要真的落进数据库,这份契约不能因为换了存储就变。
