📇 概念卡 #1:主键 —— 会员卡号由总部统一发

① 一句话大白话: 主键是一行的身份证号:不能为空、不能重复、最好永远不变,别的表靠它来指向这一行。用业务里本来就有的东西当主键(邮箱、身份证号、ISBN)叫自然键;另外发一个和业务无关的编号叫代理键。业务系统通常用代理键,因为业务数据会变。代理键可以由数据库按顺序发(IDENTITY),也可以用 UUID(随机生成的 128 位编号)。

② 生活类比:会员卡号由总部统一发

如果用手机号当会员卡号,会员换了手机号,他所有的订单、积分记录都要跟着改(Day 23 里 Alice 换邮箱就是这个问题)。所以卡号由总部统一发:一台发号机,每按一下吐出下一个号。号码印在卡上,一辈子不变。发号机吐出的号如果没用上(办卡办到一半客人走了),这个号也就作废了,不会再发给下一个人。还有一种做法是每张卡印一串很长的随机码,任何分店自己就能印,不用问总部,而且别人猜不到下一张卡的号码。

  • BY DEFAULT / serial 的撞车是真实的线上事故来源:有人用脚本导入了一批带 id 的数据,之后应用正常插入就开始随机报「主键重复」。ALWAYS 从源头上不许这样做;真要导入(比如数据迁移),写 OVERRIDING SYSTEM VALUE 是一个显式的、看得见的动作,导完再用 setval 把序列调到最大值之后。
  • serial 是旧写法:序列是一个单独的对象,给应用账号授权时除了表的 INSERT,还要记得给序列 USAGE,复制表结构时也容易漏掉它。IDENTITY 是 SQL 标准写法(PostgreSQL 10 起支持),序列和列绑在一起管理。新表一律用 IDENTITY。
  • 为什么用掉的号不还回去:如果序列也参与事务,事务 A 拿了 4 还没提交时,事务 B 就得等着,看 A 是提交(4 被用了)还是回滚(4 可以给 B)。所有插入都会排成一队。所以 PostgreSQL 让序列不参与回滚,每个人拿到号立刻走人。代价就是号码会有空洞,而且失败的插入(比如违反约束)也会用掉号。这不是 bug:主键只保证唯一,不保证连续。需要「连续的发票号」这类业务要求时,要用别的办法,不能指望主键。

(← 的说明是我加的。)v7 的前 12 个十六进制字符 01a1a6a3… 就是毫秒时间戳,后面每隔 2 毫秒递增(29be → 29c1 → 29c3…);第 15 个字符 7 是版本号。PG 16 下的 uuid_v7() 是我们自己写的 SQL 函数(在 03-uuid.sql 里,有逐段注释):48 位毫秒时间戳 + 版本号 + 12 位「毫秒以下的时间」+ 借用一个 v4 的随机后半段。另外两种办法是在应用层生成(比如 Node 的 uuid 包 v7()),或者装第三方扩展 pg_uuidv7(本课程环境没装,未实测)。升级到 PG 18 以后,换成内置的 uuidv7() 即可。

怎么读这组数字(只看量级):我把同一个脚本连跑了 4 次,插入耗时 bigint 约 450–575 ms、v4 约 800–1480 ms、v7 约 550–865 ms,波动很大;主键索引大小很稳定:bigint 4408 kB、v4 8344–8616 kB、v7 6184 kB。耗时受机器负载影响,不足以下结论;索引大小的差别是稳定的,而且能用下面的比喻解释。v7 比 bigint 大,主要因为 UUID 本身是 16 字节而 bigint 是 8 字节。v4 比 v7 又大了约 37%,这多出来的部分就是随机插入留下的半空页。

还有一个我在写这个函数时踩到的坑,如实记下:第一版函数只用了毫秒时间戳,毫秒内部完全随机。一次插 20 万行时,每毫秒要生成几百个,同一毫秒里的几百个彼此是乱序的。那一版测出来 v7 的主键索引是 9408 kB,比 v4 还大。加上「毫秒以下的时间」那 12 位之后,同一毫秒里的也基本有序了,才降到 6184 kB。这说明「v7 有序」是有前提的;PG 18 内置的 uuidv7() 也用了毫秒以下的精度来保证这一点。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「发号机发的号是连续的,可以拿来数人数」——主键不保证连续。回滚、失败的插入、数据库重启后的序列缓存,都会留下空洞。max(id) 不等于行数;「第 1000 号会员」也不代表他是第 1000 个注册的。需要连续编号(比如发票号)时,要另外设计,通常要在事务里加锁,代价很高。
  2. 「随机码只是长一点,和卡号没区别」——随机 UUID 会让 B-tree 索引变大变慢。主键自带一个 B-tree 索引(Day 22 的 tasks_pkey),它就像一本按号码排好的名册,每页写满了就要撕开分成两页。按顺序发号时,新号永远写在最后一页,写满就开新页,前面的页都是满的;随机号会插到名册的任意一页中间,各页不停地「写满 → 撕成两半」,留下大量半空的页,要读进内存的页也更多。上面的 8448 kB 对 6184 kB 就是这个效果。真正的测量方法(EXPLAIN (ANALYZE, BUFFERS)、缓存命中)是 Week 5 的内容。
  3. 「卡号印在卡上,随便给人看」——对外暴露自增 id 会泄露信息。/v2/tasks/1042 告诉别人:你们大概有一千多个任务;把 1042 改成 1041 就能试着看别人的任务(这叫 IDOR,越权访问,Week 20 的主题;鉴权不能靠「id 猜不到」,但也不该主动帮攻击者)。常见做法是内部用 bigint 关联,对外暴露一个 UUID:04-constraints.sql 的 users 有一列 public_id uuid。nest-lab 的 API 现在用的是自增 id,要不要改、怎么改,Day 27 接回 nest-lab 时决定(改 API 里 id 的类型是破坏性变更,Day 19 讲过)。
④ 真实术语: primary key;natural key vs surrogate key;sequence(nextval / setval);serial / bigserial;identity column(GENERATED ALWAYS | BY DEFAULT AS IDENTITY,OVERRIDING SYSTEM VALUE);integer overflow;UUID(RFC 9562:v4 随机,v7 Unix 毫秒时间戳 + 随机);B-tree page split;index locality;IDOR(Insecure Direct Object Reference)。

📇 概念卡 #2:约束 —— 账房的铁规矩

① 一句话大白话: 约束是写进表定义里的规矩,数据库在每一次插入和修改时都会检查,不合规矩就整条拒绝。常用的有五种:NOT NULL(必须有值)、UNIQUE(不能重复)、CHECK(值要满足一个条件)、PRIMARY KEY(= NOT NULL + UNIQUE)、FOREIGN KEY(指向的行必须存在,并规定被指向的行删除时怎么办:ON DELETE)。

② 生活类比:贴在账房墙上的铁规矩

账房墙上贴着:「姓名栏不许空着」(NOT NULL);「一个邮箱只能办一张卡,大小写不同也算同一个」(UNIQUE);「会员等级只能写普通或金卡」「截止日期不能早于下单日期」(CHECK);「订单上写的会员号,名册里必须有这个人」(外键)。还有一条:会员注销的时候,他的东西怎么办:附在订单上的小清单跟着订单一起销毁(CASCADE);名下还有订单的会员不许直接注销(RESTRICT);或者订单保留、只把「会员号」那一栏划掉(SET NULL)。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「什么规矩都能贴上墙」——约束只能表达「单行 / 唯一性 / 引用存在」这几类规则。「每人最多 10 个未完成任务」「已完成的任务不能改标题(Day 15 的 409 规则)」这种要看别的行或修改前的状态的规则,约束表达不了。CHECK 只能看同一行的列,不能引用别的表。这类规则要放在应用的 Service 里(还要考虑并发,Week 6),或者用触发器。
  2. 「规矩越多越安全,没有代价」——每条约束都要在写入时检查。唯一约束和外键尤其需要查索引;插入一条任务,数据库要去 users 里确认负责人存在。约束越多,写入越慢,但这个代价通常值得,因为坏数据进了库以后的清理成本高得多。另外一个容易被忽略的点:PostgreSQL 不会自动给外键列建索引(主键和唯一约束会自动带索引,外键不会)。tasks.owner_id 没有索引时,删除一个用户要扫描整张 tasks 来检查 RESTRICT。这是 Week 5 的第一批实验之一。
  3. 「账房会告诉你哪里不对、怎么改」——约束报错是给程序看的,不是给最终用户看的。violates check constraint "tasks_title_check" 对用户毫无意义,更不能原样塞进 API 响应(会泄露表结构,Day 17 讲过 500 里不能有内部细节)。友好的、字段级的错误提示仍然是 DTO 的工作,下一张卡讲两层怎么分工。
④ 真实术语: integrity constraint;NOT NULL / UNIQUE / CHECK / PRIMARY KEY / FOREIGN KEY;referential integrity;referential actions(ON DELETE / ON UPDATE:CASCADE、RESTRICT、SET NULL、SET DEFAULT、NO ACTION);expression index(lower(email));citext;DEFERRABLE / INITIALLY DEFERRED;transactional DDL。

📇 概念卡 #3:两层校验与错误码 —— 前台查过了,账房为什么还要再核

① 一句话大白话: DTO 校验(Day 16)站在 API 门口,防的是「格式不对的请求」,能给调用方友好的、字段级的错误;数据库约束站在数据旁边,防的是「任何来源的坏数据」:别的服务、手工 SQL、迁移脚本、以及两个请求同时进来时的竞态。两层不是重复劳动,各防各的。数据库拒绝时会给一个 5 位的 SQLSTATE 错误码,应用据此翻译成 HTTP 状态码。

② 生活类比:前台和账房

前台接待员看表格,发现邮箱格式写错了,当场就能指着那一栏说「这里填错了」,客人马上改,体验很好。账房不负责跟客人解释,但它守着最后一道门:如果有人不经过前台、拿着一张单子直接来账房(别的分店的系统、老板半夜手工改账),或者两个前台在同一秒给同一个邮箱各收了一张表(两边各自查名册:「没这个人,可以办」),只有账房能拦下第二张。账房拦下时只会说一句「第 23505 条规矩」,由前台把它翻译成客人听得懂的话。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「账房会核,前台可以偷懒」——有了约束,DTO 校验也不能省。数据库的错误是给程序看的,一次只报一个(第一个违反的约束),没有字段级的 pointer,还可能泄露表结构。用户填错三个字段,DTO 一次告诉他三处;数据库只会说「23514」。两层一起用:DTO 负责体验,约束负责底线。
  2. 「前台先查一下,就不会撞了」——先查后插在并发下必然有窗口期。上面的实验把窗口拉到了 1 秒,真实系统里窗口可能只有几毫秒,但流量一大总会撞上。同样的道理适用于「库存够不够再扣」「余额够不够再转账」,这些是 Week 6 的超卖 / 丢失更新实验。
  3. 「错误码一对一对应状态码」——同一个错误码在不同场景下意思不同。23503 在插入时是「你引用的东西不存在」(422),在删除时是「还有别的东西引用着它」(409)。映射要结合「这是什么操作」来做,Day 27 的仓储里会按约束名分别处理。
④ 真实术语: defense in depth(纵深防御);check-then-act race condition(先检查后执行的竞态,TOCTOU 的一种);SQLSTATE(SQL 标准的 5 位错误码,class 23 = integrity constraint violation);unique_violation 23505 / foreign_key_violation 23503 / not_null_violation 23502 / check_violation 23514;constraint name(驱动里通常是 err.constraint);error translation。

✅ 总结与自测

今天带走的 4 句话

  1. 主键用代理键,默认 bigint GENERATED ALWAYS AS IDENTITY:自然键会变;integer 会在 21 亿处用完;ALWAYS 拒绝手写 id,BY DEFAULT / serial 允许手写但会和序列撞车。序列不参与回滚,id 有空洞是正常的,主键只保证唯一、不保证连续。
  2. UUID v4 完全随机,v7 前面是毫秒时间戳;随机主键让 B-tree 索引页频繁分裂,实测主键索引 v4 约 8.4 MB、v7 约 6.2 MB(20 万行)。PG 16 没有 uuidv7(),用 SQL 函数、应用层或扩展替代。对外暴露 id 时考虑「内部 bigint + 对外 UUID」。
  3. 约束是数据库层的最后一道校验:NOT NULL、UNIQUE(邮箱用 lower(email) 唯一索引)、CHECK(只能看同一行)、外键(ON DELETE CASCADE / RESTRICT / SET NULL / NO ACTION 表达业务含义)。约束要命名,外键不会自动建索引。
  4. 两层校验各防各的:DTO 给友好的字段级错误,约束防任何来源的坏数据和并发竞态(先查后插拦不住并发注册)。违反时按 SQLSTATE 和约束名翻译:23505 → 409,23503 插入时 → 422、删除时 → 409,23502 / 23514 → 422 并记警告。
