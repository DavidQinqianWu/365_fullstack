Day 8–12 的观察脚本都是一个请求跑完再发下一个,日志整整齐齐。真实线上不是这样:几十个请求同时在店里,Day 1–2 讲过,服务员在每个 await 处都会放下手里这桌、先去招呼别桌。于是日志变成这样(今天观察脚本的真实输出,截取一段):

   ④ Kitchen 开始做菜(要等 60 ms)
   ④ Kitchen 查完库存
   ④ Kitchen 出菜
  ⑤-1 Interceptor(后) 计时结束:正常返回(handler 21.6 ms,从进门算起 22.3 ms)
← ⑥ Middleware 出门:200(25.6 ms)
   ④ Kitchen 查完库存
   ④ Kitchen 查完库存
   ④ Kitchen 查完库存
   ④ Kitchen 出菜

连着三行「查完库存」分别是谁的?出错时你根本没法回答「这一行属于哪个请求」。

最直接的办法是给每个请求一个编号(requestId),每打一行日志都带上它。可是编号要怎么送到 Service 深处?Day 11 的 @RequestId() 能把它交给 Controller,但从 Controller 到 Service 再到仓储,每一层都加一个 requestId 参数太难看了,而且第三方库的回调里你根本加不了参数。

💡 生活翻译: 客人一进门,门口就发一张桌号牌。后厨每道工序都在小票上写桌号,出了问题拿着桌号一查,这桌的所有小票都能找出来。但如果桌号要靠「前台喊给后厨、后厨喊给配菜、配菜喊给打荷」口口相传,迟早会传错。今天的 AsyncLocalStorage 像一张隐形的桌号牌:它跟着这桌客人的单子走,谁经手这张单子,抬头就能看到桌号,不用任何人喊。

今天的另一件事:Day 10 的全局计时 interceptor 和异常 filter 是用 app.useGlobalXxx(new X()) 挂的,它们在 DI 容器外面,拿不到桌号牌服务。今天把它们搬进容器(APP_INTERCEPTOR / APP_FILTER)。最后把 Week 2 的能力串成一张表,给 Day 14 复盘铺路。

📇 概念卡 #1:请求 ID —— 每桌一张桌号牌

① 一句话大白话: 给每个请求发一个唯一编号,这个请求产生的每一行日志都带上它;并发时日志再乱,按编号一筛就能把同一个请求的日志全找出来。

② 生活类比:桌号牌 + 小票上写桌号

门口发牌:客人自己带了会员卡号(上游传来的 x-request-id)就沿用,没带就现发一张;结账时把桌号印在收据上(回写响应头),客人投诉时报桌号,店长就能调出这桌从进门到出门的所有记录。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「发了桌号牌,各桌就互不干扰了」——桌号牌只是标签。它不会让请求变成排队执行,也不隔离任何数据。并发问题(两个请求同时改同一条任务)照样存在,那是 Week 7 事务和锁要解决的事。
  2. 「客人报的会员卡号一定是真的」——x-request-id 谁都能伪造。它只用来串日志,不能用来做任何权限判断。生产环境还应该限制它的长度和字符(否则有人塞一段换行符进来,就能在你的日志里伪造假记录,叫 log injection)。今天为了简单没做,Week 20 安全周会补上。
  3. 「所有小票都会自动写上桌号」——只有用 ctxLog 打印的才会。第三方库自己 console.log 的内容不会带前缀;要做到「所有日志都带」,需要换成支持上下文的结构化 logger(pino、Nest 的 Logger 接口),Week 15 可观测性会讲。
④ 真实术语: request ID / correlation ID(关联 ID):把一次请求在一个服务里、甚至跨多个服务的所有日志关联起来;常见请求头 X-Request-ID / X-Correlation-ID;分布式追踪(OpenTelemetry)里更完整的版本叫 trace ID,标准请求头是 W3C 的 traceparent(Week 15)。

📇 概念卡 #2:AsyncLocalStorage —— 跟着这桌客人走的隐形桌号牌

① 一句话大白话: als.run(store, fn) 开一条「异步链」,fn 里面的代码,以及它衍生出来的所有异步操作(await 之后的部分、setTimeout、Promise 回调、流事件),调用 als.getStore() 都拿到这一份 store。不同的 run 之间互不干扰。

② 生活类比:隐形桌号牌

桌号牌不挂在服务员身上(服务员只有一个,一会儿招呼这桌、一会儿招呼那桌),而是挂在这桌的单子上。单子被拆成几张小单交给不同工位(异步操作),每张小单都自动带着同一张隐形桌号牌。服务员拿起哪张单子,就看到哪个桌号。

// src/common/request-context/request-context.middleware.ts(核心一行)
this.context.run({ requestId, startedAt: performance.now() }, () => next());
// next() 之后的整条管线 —— guard、interceptor、pipe、controller、service、filter,
// 以及它们里面所有的 await —— 都在这条链上

// src/request-context-demo/kitchen.service.ts —— 方法签名里没有 requestId
async cook(ms: number) {
  ctxLog(`④ Kitchen 开始做菜(要等 ${ms} ms)`);  // ctxLog 自己去 ALS 里拿桌号
  await sleep(ms / 2);
  ctxLog('④ Kitchen 查完库存');                 // await 回来,还是同一个桌号
  ...
  return { requestId: this.context.requestId, ms };
}

比喻真实组件

给这桌的单子挂上牌als.run(store, fn)
拆成小单后都带着牌Node 在创建每个异步资源(Promise、定时器、socket 回调)时,把当前的 store 一起记下来;回调执行时再恢复它

🖥️ 前端翻译: React Context 解决的是同一个痛点 ——「不用一层层传 props(prop drilling)」:<Provider value> 下面的任何组件都能 useContext 拿到值。区别是:React Context 沿着组件树(空间结构)传,ALS 沿着异步调用链(时间先后)传。写过 Angular 的话,Zone.js 更像 ALS:它也是追踪「从这里衍生出来的所有异步操作」,Angular 靠它知道什么时候该刷新视图。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「店里任何人都能看到这桌的牌」——只有从这桌单子衍生出来的工作才看得到。开店时(任何请求之外)注册的定时器、在别处订阅的事件总线、Day 5 的 worker_threads(另一个线程)、消息队列另一头的消费者(另一个进程、另一台机器),都不在这条链上,拿到的是 undefined。跨线程、跨进程、跨服务要传 ID,只能把它显式放进消息里(消息头、HTTP 头)。
  2. 「它就是一个全局变量」——ALS 实例是全局的,但它装的值不是。getStore() 返回的是「当前这条异步链」的 store,每个请求各一份。真正的全局变量(或者单例 Service 的字段,Day 9 警告过)存 requestId 会串号:今天的 BadKitchenService 就是活教材(见下方第 2 幕)。
  3. 「牌子挂上就免费」——有开销。ALS 建立在 async_hooks 之上,Node 要在每个异步资源上多记一份上下文,有少量 CPU 开销(新版 Node 已经优化了很多,通常可以接受)。store 里只放小东西(ID、用户、租户),别塞大对象:它会跟着链上每个还没执行的回调一起活着,晚一点才能被回收。
④ 真实术语: AsyncLocalStorage(node:async_hooks):run(store, fn) / getStore();async context propagation(异步上下文传播);底层的 async_hooks 在每个异步资源创建 / 执行前后触发钩子;TC39 有一个让 JS 语言原生支持这件事的提案 AsyncContext。
现成方案:nestjs-cls(continuation-local storage)把今天手写的这套封装成了模块、装饰器和插件。Week 7 讲事务传播时会用到它的 @Transactional()(@nestjs-cls/transactional):事务对象也是靠 ALS「跟着请求走」,不用把 tx 一层层传进每个仓储方法。OpenTelemetry 的 Node SDK 也是用 ALS 传 trace 上下文的。

第 1 幕:三个请求在 await 之前都写了一遍全局变量,最后写的是 C,于是 A、B 醒来后读到的都是 C。第 3 幕最后一行值得多看一眼:ALS 跟的是「谁注册了这个回调」,不是「请求是否还在进行」。在请求里随手 setTimeout 一个后台任务,它会一直带着那个请求的 store,可能在请求结束后才执行。

再看 Nest 里的同一个坑:BadKitchenService 是单例,它把 requestId 存在字段 this.currentRequestId 上(npm run day13 第 2 幕,连跑 3 次结果相同):

========== 第 2 幕:BadKitchenService 把 requestId 存在单例字段上(3 个并发请求) ==========
bad-1(等 90 ms):字段里读到 bad-3 ❌ 串号了 | ALS 读到 bad-1 ✅
bad-2(等 30 ms):字段里读到 bad-3 ❌ 串号了 | ALS 读到 bad-2 ✅
bad-3(等 60 ms):字段里读到 bad-3 ✅ | ALS 读到 bad-3 ✅

同一个对象、同一个方法里,字段错了两次,ALS 一次都没错。e2e 里也把这件事写成了断言(慢请求的字段被快请求覆盖)。

📇 概念卡 #3:全局切面的 DI 版 —— 外包临时工 vs 编制内员工

① 一句话大白话: app.useGlobalInterceptors(new X()) 是你自己 new 出来的对象,在 DI 容器外,拿不到任何注入的依赖;改成在模块里写 { provide: APP_INTERCEPTOR, useClass: X },它就由容器创建,能注入 ConfigService、RequestContextService 等,而且只要 imports 这个模块就自动生效。

② 生活类比:外包临时工 vs 编制内员工

Day 10 的计时员和投诉台是外包临时工:店长在门口直接拉进来上岗,他们只能用自己带来的工具,领不到总部配发的东西(桌号牌查询机、配置手册)。今天把他们转成编制内员工:写进总部编制表(AppModule 的 providers),由人事部(Day 9 的容器)派来,入职时就配齐了需要的设备。而且编制表跟着总部走,在测试店、演示店(e2e、观察脚本)开张时也会自动到岗。

// src/app.module.ts
providers: [
  { provide: APP_GUARD, useClass: DemoKeyGuard },            // Day 11 就是这么做的
  { provide: APP_INTERCEPTOR, useClass: TimingInterceptor },  // Day 13:搬进容器
  { provide: APP_FILTER, useClass: AllExceptionsFilter },     // Day 13:搬进容器
],
configure(consumer: MiddlewareConsumer) {                     // 模块级 middleware:按 apply 顺序执行
  consumer.apply(RequestContextMiddleware).forRoutes('*');    // 先发桌号牌
  if (this.config.get('LOG_REQUESTS', { infer: true })) consumer.apply(requestLogger).forRoutes('*');  // 再登记
}

// src/common/all-exceptions.filter.ts
@Injectable()
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  constructor(private readonly context: RequestContextService) {}   // ← 外包临时工版做不到
  catch(exception, host) { /* ... */ body.requestId = this.context.requestId ?? null; }
}

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「写在哪个部门的编制表上,就只在那个部门上岗」——不是。APP_INTERCEPTOR 这些不管写在哪个模块里,都是全局生效的,写在 TasksModule 里也会作用到 AppController。所以惯例是统一写在根模块(或者一个专门的 CoreModule)里,别散落各处让人找不到。
  2. 「临时工版已经没用了」——它还有自己的位置。不需要依赖的简单切面、只在某个脚本里临时加一层、或者需要用到「只有 bootstrap 时才拿得到的对象」时,useGlobalXxx(new X()) 依然最简单直接。今天 configureApp 留成空壳,就是给 Week 3 的 swagger 这类「只能在 app 实例上做的事」留位置。
  3. 「换了注册方式,顺序不变」——middleware 的顺序变了。app.use() 挂的 middleware 比模块里 configure() 注册的先执行。如果登记员还用 app.use 挂,它就会跑在发牌员之前,「进门」那一行就没有桌号。所以今天把两者都放进 configure(),并按 apply 的先后排好。
④ 真实术语: APP_GUARD / APP_INTERCEPTOR / APP_PIPE / APP_FILTER(@nestjs/core 导出的特殊 token,本质就是 Day 9 的 useClass provider);functional vs class middleware;NestModule.configure() + MiddlewareConsumer.apply().forRoutes()(还可以 .exclude() 排除某些路由)。

📌 Go 为什么偏要显式传?取舍是「可见性 vs 便利」。隐式上下文(ALS、ThreadLocal、AsyncLocal)让函数签名干净,但依赖是看不见的:读代码看不出这个函数需要 requestId,测试时也要记得先「开一条链」。Go 选择让每个函数都把 ctx 写在参数里:啰嗦,但一眼能看出谁需要上下文,跨 goroutine 也不会丢,还顺便承担了超时和取消的传递(ctx.Done())。Node 生态里,超时 / 取消用的是 AbortSignal,它也是显式传的。

🎤 面试翻译练习: 面试官问:"How do you correlate logs for a single request in a Node.js service that handles many requests concurrently?"(或者 Java 面试:「MDC 是什么?用线程池时有什么坑?」)你可以答:
"Node 是单线程 event loop,并发请求会在 await 处交错执行,所以日志天然是混在一起的。我会在最前面的 middleware 里读取或生成一个 request ID,沿用上游传来的 X-Request-ID,并回写到响应头,然后用 AsyncLocalStorage 的 run 把后续整条处理链包起来。这样同一个请求衍生出来的所有异步操作都能通过 getStore 拿到这个 ID,不用一层层传参;logger 自动把它加进每一行日志,错误响应里也带上它,用户报错时可以直接按 ID 查日志。要注意 ALS 只跟着这条异步链走,worker 线程、消息队列这些边界要把 ID 显式放进消息;也绝不能把请求级数据存在单例的字段上,会串号。这和 Java 的 MDC 基于 ThreadLocal、.NET 的 AsyncLocal 是同一个思路,而 Go 选择用 context.Context 显式传递。"

✅ 总结与自测

今天带走的 4 句话

  1. 并发请求的日志天然交错(event loop 在 await 处切换),所以每个请求要有一张桌号牌(request ID):沿用上游的 x-request-id 或现生成,回写响应头,写进每行日志和错误体。
  2. AsyncLocalStorage = 跟着异步链走的隐形桌号牌:run 里衍生出来的所有异步操作都能 getStore(),不用传参;请求外注册的回调、worker 线程、消息队列拿不到,跨边界要显式传。
  3. ALS 实例是全局的,值不是;全局变量、单例 Service 的字段存请求级数据一定会串号。
  4. 全局切面优先用 APP_* 注册:在容器里能注入依赖,imports 模块就自动生效;useGlobalXxx(new X()) 适合无依赖、临时的场景。middleware 注册在哪里决定执行顺序。
