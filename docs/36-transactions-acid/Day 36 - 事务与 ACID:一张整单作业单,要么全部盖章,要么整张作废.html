📇 概念卡 #1:事务与原子性 —— 一张整单作业单

① 一句话大白话: 事务把几条 SQL 绑成一个整体:要么全部生效(COMMIT),要么全部当没发生过(ROLLBACK)。这就是 ACID 的 A(原子性)。PostgreSQL 里,事务中只要有一条语句出错,整个事务就进入 aborted 状态,之后的语句全部被拒绝,只能 ROLLBACK;想只撤回一部分,要事先设一个 SAVEPOINT。不写 BEGIN 时,每条语句自己就是一个事务(autocommit)。

② 生活类比:整单作业单

账房办「转账」这种事,从不一步一步地直接改账本,而是先开一张整单作业单:第一步给 Bob 加 130,第二步从 Alice 扣 130。两步都办完了,才在作业单上盖章,账本上的改动一起生效;中间任何一步办不了(Alice 只有 100),整张作业单作废,前面办过的也当没发生过。作业单中途出了错,就被红笔划掉,在正式作废之前,账房拒绝在这张单子上再办任何事。复杂的单子上可以有「阶段签字」:办到某一步签个字,后面出错时可以撤回到那个签字处继续,而不用整张作废。

  • 不用事务时,Bob 的加款已经单独提交了,凭空多出 130 元。这就是「扣款失败、加款成功」的经典事故。
  • 用事务时,第二条失败后,整个事务进入 aborted 状态:原话是 current transaction is aborted, commands ignored until end of transaction block。这时你发 COMMIT,PostgreSQL 也只会回滚,psql 显示的命令标签是 ROLLBACK。
  • 观察脚本第 7 幕用 nest-lab 的 pg 驱动做了同样的事:第一条 23514(CHECK 违反),同一事务里接着 SELECT 1 得到 25P02 current transaction is aborted…,再发 COMMIT,驱动拿到的命令标签是 ROLLBACK。所以应用里一出错就必须 ROLLBACK:不 ROLLBACK 就把连接还回池子,下一个借到它的请求一开口就是 25P02。

  • 保存点相当于事务里的「部分回滚」。psql 的 \set ON_ERROR_ROLLBACK interactive 就是在每条语句前自动设一个保存点,让交互式操作打错一条不至于整个事务作废。
  • 序列不回滚(Day 24 说过 id 会有空洞):序列要支持很多事务同时取号,如果回滚要把号「还回去」,所有人都得互相等。
  • DDL 是事务性的,这是 PostgreSQL 的一个强项:Day 24 的 SET NULL 实验、Day 34 在事务里 DROP INDEX 再回滚,都靠它。迁移脚本可以「要么整套结构改完,要么一点不改」。MySQL 的 DDL 会隐式提交当前事务(见跨语言对照)。
  • now() 在整个事务里不变:同一事务写进去的 created_at 都是同一个时刻。要「真正的这一刻」用 clock_timestamp(),比如在一个长事务里记录每一步的耗时。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「作废了就当没发生过」——只对数据库里的改动成立。事务里如果发了邮件、调用了支付接口、往消息队列里推了消息、写了本地文件,ROLLBACK 不会把它们撤回来。所以事务里不要做外部调用(概念卡 #3);真要「数据库改了才发消息」,要用 Week 13 的 Outbox 模式。
  2. 「作废了,单号也收回」——序列号、事务号不会收回。id 出现空洞是正常的。
  3. 「红笔划掉」是 PostgreSQL 的做法,不是所有数据库都这样。MySQL(InnoDB)和 SQL Server(默认 XACT_ABORT OFF)在很多错误下只回滚出错的那一条语句,事务还能继续、还能提交。从这些数据库转过来的人,常常在 PostgreSQL 里第一次看到 25P02。
④ 真实术语: transaction;atomicity;BEGIN / START TRANSACTION、COMMIT、ROLLBACK;autocommit;aborted transaction(SQLSTATE 25P02 in_failed_sql_transaction);SAVEPOINT / ROLLBACK TO SAVEPOINT / RELEASE SAVEPOINT(subtransaction);transactional DDL;now() = transaction_timestamp()、statement_timestamp()、clock_timestamp();pg_current_xact_id()。

📇 概念卡 #2:一致性、隔离性、持久性 —— 盖章前先记流水日记

① 一句话大白话: C(一致性):事务结束时,你告诉数据库的规则(约束)全部成立;可延迟的约束允许事务中间暂时不成立,COMMIT 时再检查。但「转账前后合计不变」这类规则数据库不知道,一致性大部分是应用的责任。I(隔离性):别的会话看不到你还没提交的修改(细节留给 Day 37)。D(持久性):COMMIT 返回之前,这次事务的改动已经写进磁盘上的 WAL;之后哪怕崩溃,重启时照着 WAL 重放就能补回来。

② 生活类比:规矩、关着门办事、流水日记

账房盖章前要核对规矩:余额不能为负、每件物品都得放在一个存在的箱子里。有的规矩允许「办的过程中暂时不满足」:先把物品登记上、再去建箱子,只要盖章那一刻箱子已经在了就行。但账房只核对写在墙上的规矩;「两人合计不能变」没写在墙上,他就不管。

每张作业单都关着门办:作业单还没盖章,隔壁窗口的人看不到它改过的账。

最重要的一条:账房盖章之前,先在一本流水日记(WAL)上记下「这张单子改了什么」,并且确认墨水干了(写到磁盘上)。真正的账本可以慢慢誊抄。半夜停电,第二天早上照着流水日记从上次誊抄的地方往后补,所有盖过章的单子都能补回来,没盖章的就当没发生过。

  • 可延迟约束适合「要么同时存在、要么都不存在」的互相引用(比如两张表互相指向、或者批量导入时顺序不好保证)。代价是:错误要到 COMMIT 才报,定位更难;只有 UNIQUE、PRIMARY KEY、FOREIGN KEY、EXCLUDE 能设成可延迟,CHECK 和 NOT NULL 不行。
  • ③ 说明了一致性的边界:数据库能保证「你声明过的约束」在每个事务结束时成立,但「转账要一加一减」「库存不能超卖」是业务规则,要靠应用把相关操作放进同一个事务、写对逻辑,必要时再加约束或锁(Day 40)。所以有人说 ACID 里的 C 更像是应用的目标,而 A、I、D 是数据库提供的工具。

⑤ 动手验证 B:隔离性的最小演示。✍️ 预测:A 开事务把 Alice 改成 70、还没提交,B 读到多少?B 也去改同一行会怎样?真实结果(观察脚本第 4 幕,两个连接;手动版在 04-isolation-two-sessions.sql):

  A:BEGIN; UPDATE … -30          A 自己看到 70.00
  B:SELECT(A 还没提交)          B 看到 100.00
  B:UPDATE 同一行 → 卡住了:wait_event_type=Lock, wait_event=transactionid, state=active
  A:COMMIT → B 的 UPDATE 立刻继续   B 再看 71.00(100 - 30 + 1)

B 看不到 A 没提交的修改;B 想改同一行时,要等 A 结束(它在等 A 的事务号,wait_event=transactionid)。A 提交后,B 是在A 改过的值上再加 1。这几件事背后是 MVCC(Day 38)和行锁(Day 39);不同隔离级别下读到的东西不一样,两个窗口会出现哪些「怪现象」,是 Day 37 的内容。

⑤ 动手验证 D:synchronous_commit 的取舍。✍️ 预测:关掉 synchronous_commit 以后提交会快多少?崩溃时会丢数据吗?会损坏数据吗?真实结果:

-- 2000 次单行提交(一个 DO 块里每行 COMMIT 一次),各跑 3 次、脚本跑 3 遍
  synchronous_commit = on   269.6 – 818.0 ms
  synchronous_commit = off   27.6 –  41.3 ms

-- 一个连接不停地单行提交,300 毫秒后 kill -9 它的后端进程,恢复后数一数(手动 3 轮 + 观察脚本 --crash 1 轮)
  synchronous_commit = off  客户端收到「成功」 1838 / 1935 / 2043 / 1554 次,恢复后 1814 / 1869 / 2022 / 1508 行 → 丢了 24 / 66 / 21 / 46 行
  synchronous_commit = on   客户端收到「成功」  572 /  750 /  412 /  523 次,恢复后 572 / 750 / 412 / 523 行 → 丢了 0 行
  • on(默认):每次 COMMIT 都要等 WAL 写到磁盘才返回。本机 2000 次提交要 0.27–0.82 秒,一次 0.1–0.4 毫秒,大部分花在等磁盘上。
  • off:COMMIT 写进内存里的 WAL 缓冲区就返回,由后台的 WAL writer 过一会儿(wal_writer_delay 默认 200 ms,最坏约 3 倍)再写盘。快了 7–30 倍,代价是崩溃时会丢掉最近一小段「已经告诉客户端成功了」的提交,实测丢了 21–66 次。
  • 但它不会损坏数据:丢掉的是最后一段完整的事务,不会出现「一个事务只恢复了一半」,也不会让表结构坏掉(fsync = off 才会有损坏的风险,永远不要在生产上关它)。
  • 可以只对某些事务关掉:SET LOCAL synchronous_commit = off 适合「丢几条也无所谓」的数据,比如访问日志、点击统计;转账、订单不要关。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「账房会核对所有规矩」——一致性不是数据库自动给的。它只检查你声明过的约束;业务不变量(合计不变、不超卖)要靠应用写对,数据库只提供原子性、隔离性这些工具。
  2. 「关着门办事,就不会互相影响」——隔离不是完全的。默认的 Read Committed 下,同一个事务里两次读同一行,可能读到别人中间提交的不同的值;两个事务同时「先读后改」还会丢更新。这些都是 Day 37 和 Day 40 的内容。
  3. 「记了流水日记就一定不丢」——持久性取决于配置和硬件。synchronous_commit = off 会丢最近的提交;fsync = off 或者磁盘缓存骗了操作系统,崩溃后可能损坏;机器整个坏了,本地的 WAL 也救不回来,要靠备份和复制(Week 9 / Phase 3)。持久性是「在这台机器的磁盘还在的前提下」。
④ 真实术语: consistency;deferrable constraint:DEFERRABLE INITIALLY DEFERRED / IMMEDIATE、SET CONSTRAINTS;isolation(Day 37 详讲);durability;WAL(write-ahead logging)、LSN、fsync、checkpoint、crash recovery / redo;synchronous_commit(on / off / local / remote_write / remote_apply,后三个和复制有关)、wal_writer_delay、SET LOCAL。

📇 概念卡 #3:应用里的事务 —— 出错的伙计不能直接放回门口

① 一句话大白话: 应用里的事务要做到三件事:同一个事务的所有语句用同一个连接(Day 27);出错一定 ROLLBACK,而且 ROLLBACK 本身也失败时,要保住原来的错误、把这个连接丢掉而不是还回池子;事务尽量短,里面不做外部调用和长计算,因为事务开着的时候,它占着一个连接,还可能锁着一些行。

② 生活类比:出错的伙计不能直接放回门口

门口站着几位伙计(连接池,Day 27)。一位伙计接了一张整单作业单,办到一半出了事:账房那边突然把他的窗口关了。按规矩他应该去把作业单作废(ROLLBACK),可窗口已经关了,作废也办不了。以前的做法有两个毛病:

  • 他回来只说一句「窗口关了」,真正出了什么事(哪一步、为什么)没人知道;
  • 不管他现在是什么状态,都直接放回门口继续接客。如果他手里还攥着一张没作废的单子,下一位客人一开口,就会听到「这张单子已经划掉了,什么都不能办」。

修好以后:先报告真正的原因,作废失败这件事另外记一笔;作废都没办成的伙计,直接请回家,门口换一位新伙计。

  await client.query('BEGIN');
  const result = await work(client);
  await client.query('COMMIT');
  return result;
} catch (err) {
  try {
    await client.query('ROLLBACK');
  } catch (rollbackErr) {
    broken = rollbackErr instanceof Error ? rollbackErr : new Error(String(rollbackErr));
    logger.error(`ROLLBACK 失败,丢弃这个连接(原来的错误照常抛出):${broken.message}`);
  }
  throw translatePgError(err);           // 原来的错误优先
} finally {
  client.release(broken);                // 传了错误 → 池子销毁这个连接,下次新建一个
}

事务的边界:放在哪一层、包多大

  • 不放在 Controller:Controller 管 HTTP,不该知道数据怎么存。
  • nest-lab 现在放在仓储方法里(一次 insert / update 一个事务)。够用,因为每个业务操作只调用一次仓储。
  • 一个业务操作要调用好几个仓储方法(比如「建任务 + 扣用户的配额」)时,事务要上移到 Service 层,所有仓储方法共用同一个连接。怎么在不层层传 client 参数的情况下做到,就是 Week 7 的「事务传播」(nestjs-cls + @Transactional(),对照 Spring 的 REQUIRED / REQUIRES_NEW)。
  • 「一个 HTTP 请求一个事务」是一些框架的默认做法(比如 EF Core 的一个请求一个 DbContext),简单,但容易让事务包住不该包的东西。
  • 不管放在哪一层,事务里都不要:调外部 HTTP(对方慢 10 秒,你就占着一个连接、锁着几行 10 秒)、发邮件(回滚撤不回来)、做长计算、等用户输入。先算好、调好,再开事务写库;或者先写库,提交后再做外部动作。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「把伙计请回家就安全了」——丢掉连接只保护了下一个请求,这一个请求还是失败了。调用方会收到 500(连接断开)或 422(约束违反)。要不要自动重试,取决于这个操作是不是幂等的(Day 15):创建任务的 POST 不幂等,重试可能建出两条。Week 12 的 Idempotency-Key 解决这个问题。
  2. 「ROLLBACK 失败了,事务就没回滚」——不一定。连接断开时,PostgreSQL 服务器那边会自动回滚这个没提交的事务。ROLLBACK 失败只说明「客户端没能确认」,数据库里的数据是安全的;不安全的是那个连接。
  3. 「一张作业单别办太久」听起来像建议,其实是硬性要求。长事务会一直占着连接(池子被借空,Day 27),一直锁着改过的行(别人卡住,今天第 4 幕),还会挡住 VACUUM 清理旧版本(表膨胀,Day 38)。Day 41 会讲 idle_in_transaction_session_timeout,让数据库主动掐掉开着事务又不干活的连接。

Spring @Transactional 什么时候不回滚(面试高频):

  • 默认只在抛出 RuntimeException(及其子类)和 Error 时回滚;抛出受检异常(checked exception,比如 IOException)时不回滚,照常提交。要改就写 @Transactional(rollbackFor = Exception.class),反过来用 noRollbackFor。
  • 异常在方法里被 catch 住、没有抛出来,Spring 不知道出错了,照常提交。
  • 同一个类里的方法互相调用(this.doSomething())不经过 Spring 的代理,被调用方法上的 @Transactional 不生效;非 public 方法上的注解在默认的代理模式下也可能不生效。

🎤 面试翻译练习: 面试官问:"What is ACID? Why do all subsequent statements fail after an error inside a PostgreSQL transaction? When does Spring's @Transactional not roll back?"(或者:「什么是 ACID?事务里出错了为什么后续语句都失败?Spring @Transactional 什么时候不回滚?」)你可以答:
"ACID 是事务的四个保证。原子性:一个事务里的修改要么全部生效、要么全部撤销,比如转账的扣款和加款。一致性:事务结束时数据库声明过的约束都成立,PostgreSQL 还支持可延迟的约束,到提交时才检查;但业务规则,比如转账前后合计不变,数据库并不知道,要靠应用保证。隔离性:并发的事务互相看不到对方没提交的修改,具体看到什么由隔离级别决定。持久性:提交返回之前改动已经写进磁盘上的预写日志,崩溃后可以重放恢复;我实际 kill -9 过 PostgreSQL 的后端进程,提交过的数据在,没提交的没了。如果关掉 synchronous_commit,提交会快一个数量级,但崩溃时会丢最近的一小段提交,只是不会损坏数据。PostgreSQL 里事务中一条语句出错后,整个事务进入 aborted 状态,之后的语句都会报 current transaction is aborted,连 COMMIT 也只会回滚,只能 ROLLBACK,或者事先用 SAVEPOINT 回到保存点;这和 MySQL、SQL Server 默认只回滚出错的那条语句不同。所以应用里出错必须 ROLLBACK,ROLLBACK 失败时还要保住原来的错误,并把这个连接从池子里丢掉。Spring 的 @Transactional 默认只在 RuntimeException 和 Error 时回滚,受检异常会照常提交,要用 rollbackFor 改;异常被 catch 住没抛出、或者同一个类里自调用不经过代理时,也不会回滚。"

✅ 总结与自测

今天带走的 4 句话

  1. 原子性:不用事务时,「加款成功、扣款失败」让合计从 150 变成 280;用事务就整体回滚。PostgreSQL 里事务中出错后进入 aborted(current transaction is aborted, commands ignored until end of transaction block),连 COMMIT 都变成 ROLLBACK;想部分回滚要用 SAVEPOINT。序列号不回滚,DDL 能回滚。
  2. 一致性:数据库只保证你声明过的约束,可延迟外键要到 COMMIT 时才检查;「合计不变」这类业务规则要靠应用。隔离性:别人看不到你没提交的修改,改同一行要排队(Day 37 详讲)。
  3. 持久性:COMMIT 返回前 WAL 已落盘;真的 kill -9 之后,PostgreSQL 照着 WAL 重放,提交过的行在、没提交的没了。synchronous_commit = off 快 7–30 倍,崩溃时丢了 21–66 次已确认的提交,但不会损坏数据。
  4. 应用里的事务:同一个连接、出错必 ROLLBACK、ROLLBACK 失败时保住原错误并 release(err) 丢掉连接、事务里不做外部调用。nest-lab 的 transaction() 已按这几条修好,新增的 5 个测试里有 2 个能抓住旧代码的问题。
