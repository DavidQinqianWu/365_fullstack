🧑‍🍳 接上回:后厨是谁招来的?

Day 8 我们开了一家连锁店:Module 是部门编制表,Controller 是前台,Service 是后厨。观察脚本第 2 幕还偷看到一张便利贴:

但有个问题一直没回答:TasksController 的构造函数写着 constructor(private readonly tasksService: TasksService),全项目没有任何地方写过 new TasksService()。那这个后厨是谁招来的?

💡 生活翻译: 街边小店里,老板缺人就自己去门口贴招聘、自己面试、自己发工资。连锁店不这样:前台只填一张用人申请单「我需要一名后厨」,交给总部人事部。人事部翻开登记簿,看「后厨」这个岗位登记的是谁、他自己又需要什么(冰箱、挂钟),把这些先备齐,再把人派到前台手里。前台从头到尾不知道也不关心后厨是怎么招来的。
这就是今天的两个词:依赖注入(DI)是「前台交申请单、等人派来」这个动作;控制反转(IoC)是「招人这件事的控制权,从前台手里交给了总部」。

今天最关键的一个文件 —— 登记簿:

// src/tasks/tasks.module.ts
@Module({
  controllers: [TasksController],
  providers: [
    TasksService,                                                     // 简写 = { provide: TasksService, useClass: TasksService }
    { provide: TASKS_REPOSITORY, useClass: InMemoryTasksRepository }, // Week 4 换 PostgreSQL:只改这一行
    { provide: CLOCK, useValue: systemClock },                        // 现成的对象直接放进去
    {
      provide: TASKS_SEED,                                            // 开业样品菜
      useFactory: (clock: Clock): Task[] => [ /* 两条任务,createdAt = clock.now() */ ],
      inject: [CLOCK],                                                // 先把 CLOCK 造好,传给工厂函数
    },
  ],
})
export class TasksModule {}

// src/tasks/tasks.service.ts
@Injectable()
export class TasksService {
  constructor(
    @Inject(TASKS_REPOSITORY) private readonly repo: TasksRepository,  // 申请单:我要一个「仓储」
    @Inject(CLOCK) private readonly clock: Clock,                      // 申请单:我要一个「时钟」
  ) {}
  create(title: string): Task {
    return this.repo.insert({ title, done: false, createdAt: this.clock.now().toISOString() });
  }
}

📇 概念卡 #1:依赖注入 —— 前台只交「用人申请单」,不自己招人

① 一句话大白话: 一个对象需要别的对象帮忙时,不自己 new,而是在构造函数里说「我需要一个 X」,由外面的人造好递进来。

② 生活类比:用人申请单

对比两种开店方式:

街边小店:自己 new连锁店:依赖注入
代码private service = new TasksService(new InMemoryTasksRepository(seed), systemClock);constructor(private readonly tasksService: TasksService) {}
前台要知道什么后厨叫什么、后厨需要冰箱和挂钟、冰箱要放什么样品菜……整条依赖链只知道「我需要一名后厨」
两个前台都要后厨各招各的,各自一台冰箱,A 前台收的单 B 前台看不到人事部派同一个后厨(默认单例),数据只有一份
测试 / 换实现改前台的代码只改登记簿(或在测试里 overrideProvider)

比喻 ↔ 真实 对照

比喻真实组件
用人申请单构造函数的参数列表(依赖声明)
「招人」这件事创建依赖对象(new)并把它交给使用者
招人的权力从前台交给总部Inversion of Control:创建和组装对象的控制权从业务代码移交给框架
人事部把人派到前台Dependency Injection:框架调用构造函数时把依赖作为参数传进去
进货合同(只认合同,不认供应商)接口 TasksRepository:Service 只依赖接口,不依赖具体实现
🖥️ 前端翻译: React Context 就是一种轻量的依赖注入:组件不 import 一个全局 store,而是 useContext(ThemeContext) 说「我要主题」,由树上方的 <ThemeContext.Provider value={...}> 提供。测试时包一个不同的 Provider,组件代码不用改 —— 和今天的 overrideProvider 一个道理,连 Provider 这个词都一样。Angular 的 DI 则和 Nest 几乎一字不差(providers、useClass、useValue、useFactory、InjectionToken)。区别:React Context 按组件树的位置找提供者,Nest 按模块的登记簿找。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「人事部一直坐在办公室里,随叫随到」——不是。对默认的单例来说,人事部只在开业那一刻工作一次:扫描所有登记簿、排好依赖图、把人全部造好、派到位,然后就「下班」了。之后请求来了,前台手里早就有后厨,不会再去申请。所以缺人在开业当天就会报错(Nest can't resolve dependencies...,启动直接失败),而不是等第一个客人进门才发现。
  2. 「有了 DI,换任何人都不用改前台」——前提是前台依赖的是「岗位」,不是「某个具体的人」。今天 TasksService 依赖的是 TASKS_REPOSITORY 这个岗位(接口 + token),所以换实现只改登记簿;如果它写的是 constructor(repo: InMemoryTasksRepository),虽然也是注入,但它已经和「内存实现」这个具体的人绑死了。
  3. 「DI 必须有人事部」——不必。你在 main 函数里手动 new 好所有对象、再通过构造函数传进去,这同样是依赖注入(Go 圈就这么干)。容器只是把「手动接线」自动化了。DI 是一种设计方式,IoC 容器是实现它的一种工具。
④ 真实术语: Dependency(依赖):一个对象完成工作需要用到的另一个对象;Dependency Injection(DI):依赖由外部传入,而不是自己创建,最常见的是构造函数注入(constructor injection);Inversion of Control(IoC):控制权反转,Day 8 说过框架「调用你」,今天是框架「替你创建并组装对象」;依赖倒置原则(DIP,SOLID 里的 D):高层(Service)和低层(内存仓储 / PG 仓储)都依赖抽象(接口)。
DI 带来的两件实在好处:可替换(Week 4 换 PostgreSQL 只改一行登记)和可测试(测试里把时钟换成固定时间、把仓储换成假的)。

📇 概念卡 #2:IoC 容器 —— 总部人事部的登记簿和工牌号

① 一句话大白话: IoC 容器就是一本登记簿 + 一个按簿派人的流程:先登记「要 X 时怎么造」,开业时顺着「谁需要谁」把所有对象按正确顺序造好、塞到位。

② 生活类比:人事部的四步工作

  1. 登记:各部门编制表(@Module 的 providers)里每一行都是「某个工牌号的岗位,怎么找人」。
  2. 排依赖图:翻看每个人的用人申请单(构造函数),画出「谁需要谁」的关系图。
  3. 造人:按图从最底层开始造:挂钟没有依赖,先造;冰箱要样品菜,样品菜要挂钟……最后才是前台。
  4. 派人:把造好的对象作为构造函数参数递进去,并记在花名册上(单例缓存),下次有人要同一个工牌号就直接给这个人。

比喻 ↔ 真实 对照

比喻真实组件nest-lab 里
工牌号(岗位编号)injection token:登记簿里的 key。可以是类本身、Symbol、字符串TasksService、TASKS_REPOSITORY、'TASKS_SEED'
「这个岗位招 X 类型的人」useClass:要这个 token 时 new 这个类TASKS_REPOSITORY → InMemoryTasksRepository
「直接配送一台校准好的挂钟」useValue:现成的值,不用造CLOCK → systemClock
「按配方现场组装,配料清单写在旁边」useFactory + inject:先解析 inject 里的依赖,再调工厂函数TASKS_SEED(要用 CLOCK 标开业时间)
用人申请单上写「我要工牌号 X」@Inject(TOKEN):构造函数参数上明确写要哪个 tokenTasksService 的两个参数
申请单上只写了「职业」design:paramtypes:tsc 根据参数的类自动写的元数据TasksController 要 TasksService
花名册容器里的实例缓存(默认单例)app.get(TasksService) === app.get(TasksService)
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「人事部看得懂申请单上写的职业」——只看得懂「类」,看不懂「接口」。TypeScript 的 interface 编译后完全消失,所以 constructor(repo: TasksRepository) 被 tsc 写进 design:paramtypes 的只是一个 Object。人事部拿到「Object」就懵了 —— 所以接口类型的依赖必须配一个 token,并用 @Inject(TOKEN) 写清楚。观察脚本第 2 幕能亲眼看到这一点。
  2. 「申请单是人写的」——其实是编译器写的。design:paramtypes 只有开着 emitDecoratorMetadata 的 tsc 会生成。tsx / esbuild 不生成,所以 src/09-di-ioc/ 里的迷你容器改用显式声明:类上写 static inject = [TASKS_REPOSITORY, CLOCK]。这和 @Inject(TOKEN)、useFactory 的 inject: [...] 是同一个思路:把「我需要谁」变成运行时看得见的数据。
  3. 「两个岗位互相等对方先到岗,总能商量出来」——容器商量不出来。A 的构造函数要 B,B 的构造函数要 A:谁都没法先造,容器只能报循环依赖。Nest 提供 forwardRef(() => B) 当「先给个占位工牌」的补丁,但循环依赖通常说明职责没拆清楚,优先改设计(比如抽出第三个 Service),不要先上 forwardRef。
④ 真实术语: IoC container / injector:负责创建对象和接线的组件;provider:登记簿里的一行「token → 怎么造」;injection token:provider 的 key;custom provider:useClass / useValue / useFactory(还有 useExisting 起别名,今天不展开);dependency graph(依赖图)与拓扑顺序(依赖先造)。
字符串 token vs Symbol token:字符串简单直观('TASKS_SEED'),但全应用里两个模块恰好起了同名字符串就会互相覆盖;Symbol('CLOCK') 每次创建都独一无二,更安全。
模块可见性:每个 Module 有自己的登记簿,别的模块想用这里的 provider,要在这里 exports、在那边 imports。今天所有东西都在 TasksModule 里,所以还用不到。

容器的核心就是 resolve 里这几行(完整版在 src/09-di-ioc/mini-container.ts,约 50 行):

resolve(token, path = []) {
  if (this.instances.has(token)) return this.instances.get(token);       // 花名册上有:直接给
  if (path.includes(token)) throw new Error(`循环依赖:...`);              // 自己等自己:死结
  const p = this.providers.get(token);                                   // 翻登记簿
  if (!p) throw new Error(`没有注册 ...`);
  const deps = (list = []) => list.map((d) => this.resolve(d, [...path, token]));  // 递归:先造依赖
  let instance;
  if ("useValue" in p) instance = p.useValue;
  else if ("useFactory" in p) instance = p.useFactory(...deps(p.inject));
  else instance = new p.useClass(...deps(p.useClass.inject));            // 注入 = 当参数传进去
  this.instances.set(token, instance);                                   // 记花名册(单例)
  return instance;
}

📇 概念卡 #3:作用域 —— 制冰机、每桌一套餐具、每人一把刀

① 一句话大白话: 作用域回答「同一个 provider,容器要造几个」:全店一个、每个请求一个,还是每个要它的人各一个。

② 生活类比:三种东西的配发规则

  • 制冰机(singleton,默认):全店就一台,开业时装好,所有员工共用。
  • 每桌一套餐具(request):每来一桌客人,发一套新的;客人走了就收掉。这桌的东西不会混到别的桌。
  • 每人一把刀(transient):不管是不是同一桌,只要有一个员工要刀,就给他一把新的。两个员工同时要,就是两把。

麻烦在于「传染」:如果后厨某个岗位要用「这桌的餐具」,这个岗位就没法全店共用一个人了 —— 人事部只能每来一桌就重新派一个。再往上,需要这个岗位的前台,也得每桌重新派。一个小小的 request 作用域依赖,会把整条链路都拖成「每个请求重新造一遍」。

比喻 ↔ 真实 对照

比喻Nest 写法造几个典型用途
制冰机@Injectable()(默认 Scope.DEFAULT)整个应用 1 个,开业时造绝大多数 Service、仓储、数据库连接池、配置
每桌一套餐具@Injectable({ scope: Scope.REQUEST })每个 HTTP 请求 1 个多租户:每个请求带着不同的租户 ID / 数据库连接
每人一把刀@Injectable({ scope: Scope.TRANSIENT })每个注入点 1 个带「主人名字」的 logger(每个类一个,打印时带上类名)
岗位被「传染」依赖了 REQUEST 作用域的 provider自己也变成每请求 1 个—— 这是代价,不是用途
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「单例 = 全店只有一台」——只在一家店里成立。Day 4 的 cluster、Day 5 提醒过的多副本(k8s replicas):每个进程都有自己的一整套容器,每个进程各一台制冰机。所以 InMemoryTasksRepository 在两个副本里是两份互不相通的数据,第一个副本建的任务,打到第二个副本上就查不到 —— 这正是 Week 4 要把数据搬进 PostgreSQL 的原因。
  2. 「每桌一套餐具 = 每桌一个服务员」——不是。request 作用域只是「每个请求造一套新对象」,不是每个请求一个线程。所有请求依然是同一个 event loop 在跑。反过来,单例是被所有同时进行的请求共用的:千万别把「当前请求的用户」这种数据存在单例的字段上,两个请求在 await 处交错时(Day 1),A 的数据会被 B 覆盖。
  3. 「传染了也没关系,反正自动的」——代价是实打实的。传染在代码里完全看不见(ReportService 一个字都没写 scope),但每个请求都要重新解析依赖图、new 一串对象、请求结束再交给 GC 回收。流量大时这是可测量的 CPU 和内存开销。默认用单例,只有确实需要「每个请求一份状态」时才用 request。
④ 真实术语: scope(作用域 / 生命周期,.NET 里叫 service lifetime):Scope.DEFAULT(singleton)、Scope.REQUEST、Scope.TRANSIENT;scope bubbling up / scope hierarchy:REQUEST 作用域沿依赖链向上「冒泡」,使用者也变成请求作用域(Nest 文档里的说法);transient 不会向上冒泡。请求作用域的对象不能用 app.get() 拿,要用 app.resolve()。另外,request 作用域的 provider 可以注入 REQUEST 拿到当前请求对象(多租户就靠这个),今天不展开。

✅ 总结与自测

今天带走的 4 句话

  1. DI = 前台只交用人申请单(构造函数参数),不自己招人;IoC = 招人的权力交给总部。好处是可替换(只改登记簿)和可测试(overrideProvider)。DI 是设计方式,容器只是自动化工具。
  2. IoC 容器 = 登记簿 + 开业时按依赖图从底层往上造、再把对象当参数递进去,默认记在花名册上(单例)。缺人在启动时就报错;循环依赖容器解不开,先改设计,forwardRef 是最后的补丁。
  3. token 是工牌号:类可以直接当 token;接口在运行时不存在,要配 Symbol / 字符串 token 并用 @Inject 写明。登记方式三种:useClass / useValue / useFactory + inject。
  4. 作用域 = 造几个:singleton 全应用 1 个(但只在一个进程里)、request 每请求 1 个、transient 每注入点 1 个;request 会沿依赖链向上传染,看不见但有代价。默认用单例,而且别在单例字段上存「当前请求」的数据。
