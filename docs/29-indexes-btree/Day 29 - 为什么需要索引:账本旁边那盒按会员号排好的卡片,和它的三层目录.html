🎫 接上回:数据多了以后还快吗

Week 4 结束时,nest-lab 的任务已经能存进 PostgreSQL 了。可是到现在为止,我们所有的表最多只有几十行。Day 22 的 EXPLAIN 里出现过 Index Scan 和 Seq Scan 两个词,当时说「4 行的时候没区别,400 万行的时候差几个数量级」;Day 24 说过「外键不会自动建索引」,Day 25 说过「JOIN 的逻辑结果和实际执行是两回事」。这些都欠着一个解释:数据库到底是怎么「找」的?

今天先造一张 100 万行的任务表,不建任何索引,看看「按 id 找一行」要多久;再建上索引,看看快了多少、为什么快;最后看一个反直觉的现象:建了索引,数据库也可能不用它。

🖥️ 前端翻译: 你在前端一定写过 tasks.find(t => t.id === 42):数组有多长,最坏就要比多少次,这叫 O(n)。数组一大,你会改成先建一个 Map:byId.get(42),一步到位。但你不会给每个字段都建一个 Map:每次数组变了,所有 Map 都要跟着更新,还要占内存。数据库的索引就是这个 Map 的「磁盘版」,今天你会看到它长什么样、为什么它不是哈希表而是一棵树,以及什么时候它帮不上忙。
💡 生活翻译: 中央账房的任务账已经记了一百万条,写满了八千多页。有人来问「第 500000 号任务是什么」,账房先生只能从第一页开始一页页翻。聪明的账房会在账本旁边放一个卡片盒:每张卡片只写「任务号 → 在第几页第几行」,卡片按任务号排好。查的时候先翻卡片盒,再直接翻到那一页。卡片太多,就再做一个目录:「1–3000 号在第一抽屉,3001–6000 号在第二抽屉……」。

📇 概念卡 #1:索引 —— 账本旁边那盒按会员号排好的卡片

① 一句话大白话: 表里的行是按写进来的顺序堆放的,没有按任何列排好。没有索引时,要找「id = 500000」只能把所有行都看一遍(全表扫描)。索引是另一份数据:它把某一列的值按顺序排好,每个值旁边记着「这一行在表里的位置」。查的时候先在索引里很快地找到位置,再直接去表里取那一行。

② 生活类比:账本和卡片盒

账本(表)是一页页写下来的,谁先来谁记在前面。卡片盒(索引)里每张卡片只写两样东西:任务号和「在第几页第几行」,卡片按任务号排好。找第 500000 号:在卡片盒里很快翻到那张卡片,看到「第 4166 页第 80 行」,直接翻过去。一个卡片盒只按一种东西排:按任务号排的卡片盒,帮不了「找标题叫『任务 777777』的」,那要另做一盒按标题排的卡片。

比喻 ↔ 真实 对照

比喻真实组件今天看到的
一页页的账本表 = heap(堆):由一个个 8 KB 的页(block)组成,行按写入顺序放进页里65 MB,8334 页,每页约 120 行

⑤ 动手验证 B:没有索引 vs 有索引。✍️ 预测:100 万行、没有任何索引,按 id 找一行要多少毫秒?建了索引以后呢?三个查询哪个快得最多?真实结果(npm run day29,每个查询跑 3 次,取 EXPLAIN ANALYZE 报告的 Execution Time;整个脚本跑了 3 遍,下面是 3 遍合起来的区间):

查询没有索引有索引量级
① WHERE id = 50000025.3 – 30.3 ms0.006 – 0.128 ms快 200–300 倍以上
② WHERE owner_id = 5000(50 行)28.8 – 37.9 ms0.029 – 0.661 ms快 40–55 倍以上
③ WHERE title = '任务 777777'29.7 – 41.6 ms0.006 – 0.113 ms快 300 倍左右

有索引时,每组 3 次里第一次明显更慢(如 0.128 / 0.010 / 0.014),后两次只有几微秒:第一次要把索引页读进内存,后面就命中缓存了(这正是 Day 30 的 BUFFERS 要看的东西)。没有索引时,三个查询都要把 100 万行全看一遍,所以耗时差不多,都在 30 ms 左右;有了索引,只看几个页。表越大,差距越大:全表扫描的耗时和行数成正比,索引查找只和树的层数有关(下一张卡)。建这三个索引分别用了约 0.3–0.6 秒(主键)、0.4–0.7 秒(owner_id)、1.0–1.3 秒(title),大小分别是 21 MB、7 MB、30 MB,而表本身是 65 MB:索引不是免费的。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「卡片盒做一次就好」——每次记账都要同步更新所有卡片盒。插入一行,每个索引都要插入一个条目;改一行(写新版本、ctid 变了),相关索引也要更新。三个索引加起来 58 MB,快赶上表本身了。索引越多,写入越慢、占的空间越大,这叫写放大,Day 32 实测。
  2. 「有卡片盒就什么都快」——卡片盒只对它排序的那一列(那几列)有用。按 owner_id 排的索引,对 WHERE created_at … 毫无帮助(下面 05-with-index.sql 里实测:仍然是全表扫描)。几列一起建的复合索引,也只有按特定顺序用才有效,Day 31 讲。
  3. 「卡片上记着行号,直接就能找到」——ctid 会变。行被更新、表被 VACUUM FULL 重写时,ctid 都会变。所以 ctid 只是数据库内部的「住址」,永远不要在应用里保存或使用它,应用要用主键。
④ 真实术语: index;heap / heap table;page / block(8 KB);ctid / TID(tuple identifier);sequential scan(full table scan);index scan;secondary index(PostgreSQL 的所有索引都是指向 heap 的「二级索引」);write amplification(Day 32)。

📇 概念卡 #2:B-tree —— 卡片盒的三层目录

① 一句话大白话: B-tree 是一棵又矮又胖的树:每个节点就是一个 8 KB 的页,能装几百个键。最下面一层(叶子页)装着所有的键和对应的 ctid,按顺序排好,并且一页连着一页;上面几层(中间页、根页)只是「目录」,告诉你该往哪一页去找。因为每页能分几百个叉,100 万个键只需要 3 层,查一个键只要读 3 个页。

② 生活类比:卡片盒的三层目录

一百万张卡片,放在 2700 多个抽屉里,每个抽屉装 360 多张,按任务号排好,抽屉和抽屉之间用绳子串起来(看完一个抽屉,顺着绳子就到下一个)。墙上有一张分区表,写着「1–10 万号在 A 柜,10–20 万号在 B 柜……」;每个柜子门上又贴着一张柜内目录:「这一柜的第 1 个抽屉从几号开始,第 2 个从几号开始……」。找第 500000 号:看墙上的分区表(根),去对应的柜子看柜门目录(中间层),拉开那个抽屉(叶子),三步。要找「1000 到 1100 号」:找到 1000 号所在的抽屉,然后顺着绳子往后翻就行。

  • 树高 3:根页(第 2 层)10 个条目 → 10 个中间页(第 1 层)→ 2700 多个叶子页(第 0 层)。查任意一个 id,只读 3 个索引页 + 1 个表页。数据再多 300 倍(3 亿行),也不过 4 层。这就是 B-tree 适合数据库的原因:层数随数据量对数增长,而且每一层正好是一次磁盘读取的单位(一页)。
  • 每页 367 个条目:每个条目是「条目头 8 字节(里面就是 ctid)+ bigint 键 8 字节」,再加页内的行指针 4 字节,共 20 字节;8192 字节去掉页头页尾约能放 407 个。实际是 367,因为 CREATE INDEX 建叶子页时默认只填 90%(fillfactor),留点空位给以后的插入,还剩 808 字节空闲。
  • 叶子里装的就是「键 → ctid」:第 2 条 01 00 … 是 id 1(小端序的 8 字节整数),指向 (0,1);第 3 条是 id 2,指向 (0,2)。第 1 条 6f 01 = 367,是这一页的上限键:比它大的键,去右边那一页找。
  • 不是超级用户时,观察脚本会改用估算(索引页数 2745、每页最多约 407 个键,估算树高 3),结果一致。

⑤ 动手验证 B:叶子页是连着的。真实结果(05-with-index.sql):

EXPLAIN SELECT * FROM tasks WHERE id BETWEEN 1000 AND 1100;

   Index Cond: ((id >= 1000) AND (id <= 1100))

   ->  Index Scan Backward using tasks_pkey on tasks  (cost=0.42..34317.43 rows=1000000 width=38)

-- 索引按 id 排,帮不了按 created_at 找
EXPLAIN SELECT * FROM tasks WHERE created_at >= '2025-06-01' AND created_at < '2025-06-02';
 Gather  (cost=1000.00..15745.40 rows=1614 width=38)
   Workers Planned: 2
   ->  Parallel Seq Scan on tasks  (cost=0.00..14584.00 rows=672 width=38)
         Filter: …

范围查询:找到 1000 所在的叶子页,顺着链表往后读,读到 1100 为止。ORDER BY id DESC LIMIT 10:从最右边的叶子页往左读 10 个就停,不用排序整张表(Index Scan Backward,注意 Limit 的总 cost 只有 0.77)。这正是 Day 19 / 27 的 keyset 分页能快的前提:ORDER BY … LIMIT 要有一个和排序方向对得上的索引,Day 31 专门讲。而 created_at 上没有索引,照样是全表扫描(Gather / Parallel Seq Scan 是「多个进程分头扫」,Day 30 讲)。

页分裂:给 Day 24 的数字补上原理。Day 24 实测过:20 万行逐条插入,UUID v4 主键索引 8.4 MB,UUID v7 只有 6.2 MB。现在可以解释了:叶子页满了以后,再往这一页插一个键,B-tree 会把它拆成两页、各装一半。按顺序插入时(自增 id、v7),新键永远落在最右边那一页,PostgreSQL 对这种情况有专门处理:拆分时左边留得很满,新开的右页继续往后写,所以最后几乎每页都是满的。随机插入时(v4),新键落在任意一页,哪一页满了就对半拆,拆出来的半空页之后只会被零星地填上,整体只有六七成满,于是索引更大、要读的页更多。今天的 tasks_pkey 是在数据全部写完后用 ALTER TABLE … ADD PRIMARY KEY 建的:建索引时会先把所有键排好序再一次性写成叶子页,根本不会分裂,所以每页整整齐齐都是 367 个。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「三层目录,所以就读 3 次磁盘」——大多数时候一次磁盘都不读。根页和中间页被访问得最频繁,几乎总在内存里(PostgreSQL 的 shared_buffers 和操作系统的页缓存);上面每组第一次慢、后两次快,就是缓存的效果。B-tree 的价值在于最坏情况也只读这么几页。哪些页是从缓存读的、哪些真的读了磁盘,Day 30 用 EXPLAIN (ANALYZE, BUFFERS) 看。
  2. 「卡片盒就是一个超大的 Map」——B-tree 不是哈希表。哈希只能回答「等于某个值」;B-tree 是有序的,所以还能回答「大于 / 小于 / 在某个范围 / 按顺序取前 10 个 / 以某个前缀开头」。PostgreSQL 也有 hash 索引,但只支持等值查找,很少用。前端的 Map 对应的其实是 hash,所以它帮不了 BETWEEN 和排序。
  3. 「拆开的抽屉以后会自己合并」——页分裂之后,空间不会自动变紧凑。大量删除也会留下空洞。索引膨胀以后要靠 REINDEX(或者 PostgreSQL 13 起的去重、14 起的自底向上删除这类内部优化来缓解);表和索引的清理机制(VACUUM)是 Week 6 的内容。
④ 真实术语: B-tree(PostgreSQL 实现的是 Lehman–Yao 风格的 B+tree:数据只在叶子,叶子之间有链表);root / internal (branch) / leaf page;fan-out(每页分几个叉);tree height;high key;sibling link;page split;fillfactor(B-tree 叶子默认 90);index bloat;pageinspect(bt_metap、bt_page_stats、bt_page_items)。

📇 概念卡 #3:EXPLAIN 与选择性 —— 账房先生先说打算怎么找,有时候宁可从头翻

① 一句话大白话: EXPLAIN 让数据库说出它打算怎么执行一条 SQL(执行计划),但不真的执行;EXPLAIN ANALYZE 会真的执行一遍,再报告实际花了多久。数据库(优化器)会估算每种做法的代价,选最便宜的。如果一个查询要返回表里很大一部分行,用索引要来回跳着取行,还不如从头扫一遍,所以建了索引不一定会用。一个条件能把行筛到多少,叫选择性。

② 生活类比:账房先生先报方案

你交给账房先生一张单子,他不马上动手,而是先说:「这张单子我打算先翻卡片盒,再去第 4166 页拿,估计要花 8 个工分。」这就是 EXPLAIN。如果你的单子是「把所有已经完成的任务都抄给我」,而 90% 的任务都完成了,他会说:「翻卡片盒再一张张跳着去找,还不如我从第一页翻到最后一页一起抄,反正几乎每页都要看。」他是按经验估算的,通常对,偶尔也会估错。

⑤ 动手验证 A:建索引前后的计划。✍️ 预测:没有索引时,WHERE id = 500000 的计划里会出现什么节点?cost 大约多少?建了主键以后呢?真实结果(02-no-index.sql / 05-with-index.sql):

 Gather  (cost=1000.00..14542.43 rows=1 width=38)
   Workers Planned: 2
   ->  Parallel Seq Scan on tasks  (cost=0.00..13542.33 rows=1 width=38)
         Filter: (id = 500000)

-- EXPLAIN ANALYZE:真的执行一遍
 Gather  (cost=1000.00..14542.43 rows=1 width=38) (actual time=24.671..29.524 rows=1 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on tasks  (cost=0.00..13542.33 rows=1 width=38) (actual time=17.892..21.838 rows=0 loops=3)
         Filter: (id = 500000)
         Rows Removed by Filter: 333333
 Planning Time: 0.022 ms
 Execution Time: 29.541 ms

-- 有了主键索引
 Index Scan using tasks_pkey on tasks  (cost=0.42..8.44 rows=1 width=38)
   Index Cond: (id = 500000)
-- EXPLAIN ANALYZE
 Index Scan using tasks_pkey on tasks  (cost=0.42..8.44 rows=1 width=38) (actual time=0.068..0.068 rows=1 loops=1)
   Index Cond: (id = 500000)
 Planning Time: 0.018 ms
 Execution Time: 0.075 ms

读法(今天只读这几样,其余 Day 30 细讲):

  • 节点名:Parallel Seq Scan 是「3 个进程(主进程 + 2 个 worker)各扫三分之一」,Gather 把它们的结果收起来;Rows Removed by Filter: 333333 说的是每个进程看了 33 万行、全部扔掉(loops=3)。有索引后变成一个 Index Scan,Index Cond 说明条件是在索引里用的,而不是逐行过滤。
  • cost:从 14542 降到 8.44。这两个数字只能互相比较,不是毫秒。0.42..8.44 前一个是「开始返回第一行之前的代价」,后一个是「全部做完的代价」。
  • rows / width:优化器估计会返回 1 行、每行约 38 字节。估得准不准,决定了它会不会选对计划。
  • actual time:29.5 ms → 0.075 ms。EXPLAIN ANALYZE 本身有一点额外开销,所以它的时间只用来对比,不要当成接口的真实耗时。

实际耗时呢?done = true 各跑 3 次、脚本跑 3 遍:优化器选的 Seq Scan 56–66 ms;强行走索引(bitmap)57–95 ms,大多更慢、偶尔持平;再把 bitmap 也关掉、逼它走普通 Index Scan,64–71 ms。差距没有 cost 显示的那么大,原因是这张 65 MB 的表在本机全在内存里,而 cost 模型默认「随机读一页比顺序读贵 4 倍」(random_page_cost = 4),这是按「数据要从磁盘读」来估的。数据不在内存、在云盘上时,这个差距会变得很真实。这也说明:优化器是按模型估算的,不是按真实耗时决定的,Day 30 看它什么时候会估错。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「账房先生的方案总是最快的」——优化器是在估算,会估错。它靠统计信息(上面的 {0.899, 0.101} 就是)估计每一步会出多少行,再用代价模型算代价。统计信息过期了(大批数据刚导入还没 ANALYZE)、数据分布很怪、代价参数和真实硬件不符时,它就会选错。Day 30 专门制造一次「估错」。
  2. 「cost 越小越快,cost 8 就是 8 毫秒」——cost 没有单位换算。它只用于同一条 SQL 不同计划之间的比较;不同 SQL 之间、不同机器之间比 cost 没有意义。真实耗时只能看 EXPLAIN ANALYZE 或者 Day 34 的 pg_stat_statements。
  3. 「给每一列都建个索引,总有一个会被用上」——不会被用的索引只有代价。done 这种只有两个值、而且分布是 90 / 10 的列,只有查少数那一边时才可能用上;更好的做法是只为少数那一边建「部分索引」(WHERE done = false),Day 32 讲。没用的索引可以从 pg_stat_user_indexes 里找出来,也是 Day 32。

面试高频:表本身是怎么存的?这是 PostgreSQL 和 SQL Server、MySQL 差别最大的地方之一:

PostgreSQLMySQL(InnoDB)SQL Server
表本身堆表:行按写入顺序放,不按任何列排序聚簇索引:表本身就是一棵按主键排序的 B+tree,行数据存在主键索引的叶子里默认主键建成聚簇索引(表按它排序存放);也可以建成没有聚簇索引的堆表
其他索引指向哪里指向 heap 里的 ctid二级索引的叶子里存的是主键值;找到主键后再去主键索引里查一遍(常说的「回表」)非聚簇索引里存的是聚簇键(堆表时是行定位符 RID)
主键选择的影响主键只是一个普通的唯一索引主键越长,所有二级索引越大;随机主键(UUID v4)会让整张表的数据页频繁分裂和 InnoDB 类似,聚簇键会被复制进每个非聚簇索引
能不能「按某列排好存」CLUSTER 命令可以按某个索引重排一次,但之后的写入不会保持这个顺序总是按主键排总是按聚簇键排

这张表解释了一个常见的面试题:「为什么 MySQL 推荐用自增主键?」——因为 InnoDB 的表就是主键索引,随机主键会让数据本身不停地页分裂,而不只是索引。在 PostgreSQL 里,Day 24 的 v4 vs v7 差别只体现在主键索引上,表本身不受影响。

"没有索引时,数据库只能全表扫描,耗时和表的行数成正比。索引是另一份按某列排好序的结构,每个条目指向表里那一行的位置,所以可以直接定位,不用看其他行。数据库用 B-tree,是因为它又矮又胖:每个节点就是一个磁盘页,能放几百个键,一百万行只要三层,查一个键只读三四个页,最坏情况也有保证;而且叶子是有序并且相互链接的,所以除了等值查找,还能做范围查询、排序和取前 N 个,这是哈希做不到的。建了索引不一定会用,因为优化器是基于代价的:如果条件筛出的行占比很大,比如百分之九十,用索引要大量随机回表,还不如顺序扫描;小表也是同样的道理。另外,统计信息过期会让它估错,条件写法和索引列不匹配也会用不上,比如对列做了函数运算,或者复合索引没用到最左边的列。索引也有代价:占空间,而且每次写入都要维护。我会用 EXPLAIN ANALYZE 确认实际计划和耗时。"

✅ 总结与自测

今天带走的 4 句话

  1. 表是按写入顺序堆放的(heap),行的地址是 ctid(第几页第几个);没有索引时只能全表扫描,100 万行约 25–40 ms,而且和行数成正比。
  2. 索引是另一份按某列排好序的数据,每个条目指向一个 ctid;有索引后同样的查询只要几微秒到零点几毫秒,快了几十到几百倍。代价是空间(三个索引 58 MB,表 65 MB)和每次写入的维护;主键和 UNIQUE 自动建索引,外键不会。
  3. B-tree 又矮又胖:根 → 中间 → 叶子,每页几百个键(实测 367),100 万行只有 3 层;叶子有序且相互链接,所以范围查询、排序、取前 N 个也快。顺序插入时页分裂几乎不浪费空间,随机插入会留下半空的页(Day 24 的 v4 vs v7)。
  4. 建了索引 ≠ 一定会用:优化器按统计信息和代价模型估算,要返回的行占比太大(done = true 占 90%)或表太小时,它宁可全表扫描。EXPLAIN 看计划不执行,EXPLAIN ANALYZE 真的执行;cost 不是毫秒,只用来比较同一条 SQL 的不同计划。
