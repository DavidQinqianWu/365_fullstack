🎫 接上回:「关着门办事」到底关得多严

Day 36 的隔离性只做了一个最小演示:A 没提交的修改,B 看不到;B 想改同一行时要排队,等 A 提交后在 A 的结果上再 +1,得到 71。可「看不到别人没提交的」只是隔离的最低要求。真实系统里还有很多更隐蔽的情况:

  • 同一个事务里读两次同一行,中间别人提交了修改,两次读到的不一样;
  • 两个请求都「先读出计数,在代码里 +1,再写回去」,结果只加了一次;
  • 两个请求都检查「这个用户的未完成任务还不到 3 个」,然后各自新建一个,最后变成 4 个。

最后两种就是 Week 4 review 时记下的「先查后改」问题(Day 40 修)。今天先把这些现象一个个复现出来,看 PostgreSQL 的三种隔离级别各拦得住哪些、拦不住哪些,拦下来之后应用该怎么办。

🖥️ 前端翻译: 两个浏览器标签页同时打开同一份文档。标签页 A 改了标题、点保存;标签页 B 改了正文、也点保存。B 保存的是它打开时拿到的那份完整文档,于是 A 改的标题被悄悄覆盖了,没有任何报错。这就是「丢失更新」。Google Docs 用协同编辑算法解决它;普通的表单通常用「版本号不对就提示『别人已经改过了,请刷新』」来解决(Day 40 的乐观锁)。数据库里的隔离级别,是另一种解决办法。

📇 概念卡 #1:快照与读到的异常 —— 每个伙计手里那张账本照片

① 一句话大白话: PostgreSQL 里,每次读数据都是读一份快照:某一刻已经提交的所有数据。Read Committed(默认)下,每条语句开始时拍一张新快照,所以同一个事务里两次读,中间别人提交了,第二次就会读到新的。这会造成不可重复读(同一行变了)和幻读(按条件数行,多了或少了)。Repeatable Read 和 Serializable 在事务的第一条语句时拍一张快照,一直用到事务结束,这两种现象都不会发生。脏读(读到别人没提交的)在 PostgreSQL 的任何级别下都不会发生。

② 生活类比:账本照片

账房不让伙计直接看正在被改的账本,而是给每个伙计发账本照片,照片上只有已经盖过章的内容。有两种发法:

  • 每看一页就重新拍一张(Read Committed):伙计第一次查 Alice 的余额是 100;过了一会儿别人盖章把它改成了 200,伙计再查,新照片上就是 200 了。数「1 号会员有几张没办完的单子」也一样,第二次数时多了一张别人刚登记的。
  • 开工时拍一张整本的照片,一直用到收工(Repeatable Read):不管外面怎么改,伙计手里的照片不变,两次查都是 100、两次数都是 2 张。

不管哪种发法,照片上都不会出现别人还没盖章的内容,所以没有「脏读」。

比喻真实概念实测

⑤ 动手验证 A:隔离级别怎么设。✍️ 预测:BEGIN ISOLATION LEVEL READ UNCOMMITTED 之后 SHOW transaction_isolation 显示什么?事务里已经执行过查询之后再 SET TRANSACTION 会怎样?真实结果(03-levels.sql):

 default_transaction_isolation:read committed
BEGIN ISOLATION LEVEL REPEATABLE READ;   → transaction_isolation:repeatable read
BEGIN; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;   → serializable
BEGIN; SELECT 1; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
ERROR:  SET TRANSACTION ISOLATION LEVEL must be called before any query
BEGIN ISOLATION LEVEL READ UNCOMMITTED;  → transaction_isolation:read uncommitted
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;   → default_transaction_isolation:repeatable read

隔离级别是每个事务自己选的:写在 BEGIN 里,或者在事务的第一条语句之前 SET TRANSACTION;也可以改一个会话、一个角色或一个数据库的默认值。READ UNCOMMITTED 这个名字可以设、也会原样显示出来,但下面的实验会看到它的行为和 READ COMMITTED 一模一样。

⑤ 动手验证 B:脏读、不可重复读、幻读。✍️ 预测:下面三个时间轴,在 Read Committed 和 Repeatable Read 下 T2 各读到什么?真实结果(npm run day37 第 2–4 幕):

── 脏读 · READ UNCOMMITTED ──
    T1 │ BEGIN                                                  → BEGIN
    T1 │ UPDATE accounts SET balance = 999 WHERE id = 1         → UPDATE
    T2 │ BEGIN ISOLATION LEVEL READ UNCOMMITTED                 → BEGIN
    T2 │ SELECT balance FROM accounts WHERE id = 1              → 100
    T1 │ ROLLBACK                                               → ROLLBACK
    判定:✅ 没发生:T2 读到 100

── 不可重复读 · READ COMMITTED ──                    ── 不可重复读 · REPEATABLE READ ──
    T2 │ BEGIN ISOLATION LEVEL READ COMMITTED                     T2 │ BEGIN ISOLATION LEVEL REPEATABLE READ
    T2 │ SELECT balance … → 100                                   T2 │ SELECT balance … → 100
    T1 │ UPDATE accounts SET balance = 200 …(自动提交)             T1 │ UPDATE accounts SET balance = 200 …
    T2 │ SELECT balance … → 200                                   T2 │ SELECT balance … → 100
    判定:⚠️ 发生了:第一次 100,第二次 200                       判定:✅ 没发生:两次都是 100

── 幻读 · READ COMMITTED ──                          ── 幻读 · REPEATABLE READ ──
    T2 │ SELECT count(*) … WHERE owner_id = 1 AND NOT done → 2    T2 │ … → 2
    T1 │ INSERT INTO tasks (owner_id, title) VALUES (1, '新任务')  T1 │ INSERT …
    T2 │ SELECT count(*) … → 3                                    T2 │ … → 2
    判定:⚠️ 发生了:第一次 2 行,第二次 3 行                      判定:✅ 没发生:两次都是 2 行
  • 脏读复现不出来:即使 T2 设成 READ UNCOMMITTED,读到的也是 100。PostgreSQL 的快照里根本没有「没提交的数据」,所以它把 RU 当成 RC 处理。这是 SQL 标准允许的:标准规定的是「每个级别至少要防住哪些异常」,数据库可以做得更严。
  • Read Committed 下,不可重复读和幻读都发生了:第二条 SELECT 拍了一张新快照,看到了 T1 刚提交的修改和新行。
  • Repeatable Read 下都没发生:T2 在第一条 SELECT 时拍了快照,之后一直用它。注意 PostgreSQL 的 RR 比 SQL 标准更强,标准允许 RR 出现幻读,PostgreSQL 的 RR 连幻读也防住了,因为它是用快照实现的,不是用锁。
  • RC 下读到新数据不一定是 bug。对「列表页刷新一下看到最新的」这种需求,RC 正合适。只有当一个事务里的多次读必须互相一致时(比如对账报表:先算总数、再算明细,两次必须对得上),才需要更高的级别。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「照片是开工那一刻拍的」——实际是在事务的第一条语句时拍的,不是 BEGIN 那一刻。BEGIN 之后隔了一会儿才执行第一条 SELECT,这段时间里别人提交的修改,这张快照能看到。
  2. 「照片不会变」只对读成立。RR 下 T2 想去改一行,而这一行在它拍照之后被别人改过并提交了,数据库不会让它在旧照片上改,而是直接报错(概念卡 #3)。读和写的规则是不一样的。
  3. 「每看一页重新拍」说的是每条语句,不是每一行。RC 下一条 SELECT 从头到尾用同一张快照,即使它要扫好几秒,结果也是一致的;变化只出现在两条语句之间。照片具体是怎么「拍」的(行版本、xmin / xmax),是 Day 38 的 MVCC。
④ 真实术语: snapshot;isolation level:READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE;BEGIN ISOLATION LEVEL …、SET TRANSACTION、default_transaction_isolation、transaction_isolation;dirty read、non-repeatable read、phantom read;snapshot isolation (SI)(PostgreSQL 的 RR 实际上就是 SI);MVCC(Day 38)。

📇 概念卡 #2:丢失更新与写偏斜 —— 各自抄下来、各自算、各自填回去

① 一句话大白话: 丢失更新:两个事务都「读出一个值 → 在应用里算出新值 → 写回去」,后写的那个是在旧值上算的,把先写的结果覆盖掉了。写偏斜(write skew):两个事务各自读了一组行,根据读到的结果各自写了不同的行,每一个单独看都没问题,合起来却违反了业务规则(「至少留一个人值班」「每人最多 3 个未完成任务」)。前者 Repeatable Read 能拦下,后者只有 Serializable 能拦下。

② 生活类比:各自抄下来、各自算、各自填回去

丢失更新:两个伙计都要给计数器加 1。他们各自走到账本前,抄下「现在是 0」,回到座位上算好「0 + 1 = 1」,再回来填上 1。先填的人填了 1,后填的人也填 1,于是加了两次、结果只是 1。如果伙计直接在账本上写「在原来的数上加 1」,第二个人就得等第一个人写完,再在 1 上加 1,得到 2。

写偏斜:医院规定「至少要有一位医生值班」。Alice 和 Bob 今晚都在值班,都想请假。Alice 看排班表:「值班的有 2 个人,我走了还有 Bob。」Bob 同时看排班表:「值班的有 2 个人,我走了还有 Alice。」两人各自改了自己那一行,谁也没碰对方那一行,改的时候也没有冲突,结果今晚没人值班。

比喻 ↔ 真实 对照

比喻真实概念实测
抄下来、回座位算、回来填读 → 应用里计算 → UPDATE … SET n = 算好的值RC:两次 +1,结果 1
直接在账本上「加 1」UPDATE … SET n = n + 1:读和写在同一条语句里RC:结果 2
各自看排班表、各自改自己那一行写偏斜:读的是同一组行,写的是不同的行RC、RR:没人值班了
「每人最多 3 张单子」,两人同时登记写偏斜的另一种:基于 count(*) 的检查 + 各自 INSERTRC、RR:变成 4 个

⑤ 动手验证 A:丢失更新。✍️ 预测:两个事务都读到 0、都写回 1,Read Committed 下最后是多少?Repeatable Read 下呢?换成 SET n = n + 1 呢?真实结果(第 5 幕、第 5½ 幕):

── 丢失更新 · READ COMMITTED ──
    T1 │ BEGIN ISOLATION LEVEL READ COMMITTED          → BEGIN
    T1 │ SELECT n FROM counters WHERE id = 1           → 0
    T2 │ BEGIN ISOLATION LEVEL READ COMMITTED          → BEGIN
    T2 │ SELECT n FROM counters WHERE id = 1           → 0
    T1 │ UPDATE counters SET n = 1 WHERE id = 1        → UPDATE
    T1 │ COMMIT                                        → COMMIT
    T2 │ UPDATE counters SET n = 1 WHERE id = 1        → UPDATE
    T2 │ COMMIT                                        → COMMIT
    最终:1   判定:⚠️ 发生了:两次 +1,结果只是 1
── 丢失更新 · REPEATABLE READ ──
    …(前六步相同)
    T2 │ UPDATE counters SET n = 1 WHERE id = 1        → ERROR 40001 could not serialize access due to concurrent update
    T2 │ COMMIT                                        → ROLLBACK
    最终:1   判定:🛑 被拦下:40001 could not serialize access due to concurrent update

── 原子自增 · READ COMMITTED ──
    T1 │ UPDATE counters SET n = n + 1 WHERE id = 1    → UPDATE
    T2 │ SELECT 1                                      → 1
    T2 │ (上一条在等 T1 结束)                           ← T2 的 UPDATE n = n + 1 卡住了
    T1 │ COMMIT                                        → COMMIT
    T2 │ UPDATE counters SET n = n + 1 WHERE id = 1    → UPDATE
    最终:2   判定:✅ 没丢:结果 2
── 原子自增 · REPEATABLE READ ──
    T2 │ UPDATE counters SET n = n + 1 WHERE id = 1    → ERROR 40001 could not serialize access due to concurrent update
    最终:1   判定:🛑 被拦下
  • Read Committed 下丢了一次,没有任何报错。这就是 nest-lab 的「先查后改」会遇到的问题。
  • Repeatable Read 下被拦下:T2 要改的这一行,在它拍快照之后被 T1 改过并提交了。在旧快照上改,等于覆盖 T1 的结果,所以 PostgreSQL 直接报 40001(serialization_failure),整个事务作废,要应用重试。
  • 原子自增在 Read Committed 下不会丢:SET n = n + 1 的读和写在同一条语句里。T2 等 T1 提交后,PostgreSQL 会重新读这一行的最新版本,在 1 上再加 1。这也是 Day 36 第 4 幕里 B 得到 71 的原因。
  • 反直觉的一点:原子自增在 Repeatable Read 下反而报错。RR 的规则是「不许在旧快照上改被别人改过的行」,不管你的 SQL 是不是原子的。所以把隔离级别调高不是免费的:原来不用重试的代码,也要开始处理 40001 了。

⑤ 动手验证 B:写偏斜。✍️ 预测:两个医生同时请假,Repeatable Read 能拦住吗?「每人最多 3 个未完成任务」呢?真实结果(第 6、7 幕):

── 写偏斜(值班医生)· REPEATABLE READ ──
    T1 │ BEGIN ISOLATION LEVEL REPEATABLE READ                       → BEGIN
    T1 │ SELECT count(*)::int FROM doctors WHERE on_call             → 2
    T2 │ BEGIN ISOLATION LEVEL REPEATABLE READ                       → BEGIN
    T2 │ SELECT count(*)::int FROM doctors WHERE on_call             → 2
    T1 │ UPDATE doctors SET on_call = false WHERE name = 'Alice'     → UPDATE
    T2 │ UPDATE doctors SET on_call = false WHERE name = 'Bob'       → UPDATE
    T1 │ COMMIT                                                      → COMMIT
    T2 │ COMMIT                                                      → COMMIT
    最终:0   判定:⚠️ 发生了:没人值班了

── 写偏斜(每人最多 3 个)· REPEATABLE READ ── 判定:⚠️ 发生了:未完成任务变成 4 个(上限 3)

Repeatable Read 拦不住:两个事务改的是不同的行(Alice 那行、Bob 那行;或者各自 INSERT 一行新的),没有任何一行被两个事务同时改,「在旧快照上改被别人改过的行」这条规则抓不到它们。冲突藏在读里:T1 读到的「还有 2 人值班」,被 T2 的写改变了;T2 读到的,也被 T1 的写改变了。

Day 24 说过,「每个用户最多 3 个未完成任务」这种跨行的规则,CHECK 约束表达不了(CHECK 只能看一行)。今天看到,在 RC 和 RR 下,应用里的「先 count 再 insert」也守不住它。能守住的办法有:Serializable(下一张卡)、显式加锁(Day 39 / 40)、或者把规则变成数据库能检查的形式(比如在用户表上维护一个计数列,配合 CHECK)。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「直接在账本上加 1 就不会丢」——只对「一条语句能算完」的情况成立。SET n = n + 1、SET stock = stock - 1 WHERE stock > 0 可以;但「先查出价格、调用外部的折扣服务、再算出总价写回去」这种逻辑,写不进一条 SQL,只能靠锁、版本号或更高的隔离级别。
  2. 「两人改的是不同的行,就不会冲突」——写偏斜恰恰就是这种情况。只盯着「写了哪些行」的检查(包括 RR 的检查,以及很多人手写的乐观锁)发现不了它;要看「读了什么、读到的东西有没有被别人改掉」。
  3. 「没报错就说明没出事」——RC 下丢失更新和写偏斜都是静默发生的。没有异常、没有日志,只有数据悄悄错了。这是并发 bug 难查的原因:测试时只有一个人在点,线上才偶尔出现。
④ 真实术语: lost update;read-modify-write cycle;atomic update(SET n = n + 1);RC 下更新时重新检查最新行版本(PostgreSQL 文档里叫 EvalPlanQual / re-check);write skew;SQLSTATE 40001 serialization_failure;cross-row invariant。

📇 概念卡 #3:三种隔离级别与重试 —— 更强的隔离,换来的是「请重来一次」

① 一句话大白话: PostgreSQL 实际上只有三种行为:Read Committed(每条语句一张快照,不报序列化错误,但丢失更新和写偏斜会静默发生)、Repeatable Read(整个事务一张快照,并发改同一行时报 40001)、Serializable(在 RR 的基础上,再追踪事务之间「谁读了谁写的东西」,发现可能出现写偏斜时也报 40001)。越往上,数据越不容易错,但应用越要准备好把整个事务从头重做。

② 生活类比:监工

Serializable 相当于账房请了一位监工。他不拦着大家同时干活,只是在旁边记下:谁看过排班表的哪部分、谁改了哪几行。等有人来盖章时,他检查一下:「你看过的东西,被另一个已经盖了章的人改过;而那个人看过的东西,又被你改了。你们俩不可能按任何先后顺序依次办完还得到这个结果。」于是让其中一个人作废重来。重来时,这个人重新看排班表,发现只剩自己一个了,就不请假了。

⑤ 动手验证 B:40001 之后怎么办。src/37-isolation-levels/with-retry.ts 的设计:

  1. 重试整个事务,不是最后一条语句。传进来的函数要从 BEGIN 做到 COMMIT,包括里面所有的读。失败的那次读到的东西已经过时了,必须重新读、重新算。
  2. 只重试可重试的错误:40001(序列化失败)和 40P01(死锁,Day 39)。约束违反、语法错误重试多少次都一样,直接抛出。
  3. 有上限、有退避:默认最多 5 次;每次等 [0, min(500, 10 × 2n−1)) 毫秒之间的随机时间(指数退避 + 全抖动),避免冲突的几个事务又在同一时刻撞在一起。
export async function withRetry<T>(runTransaction: (attempt: number) => Promise<T>, options: RetryOptions = {}): Promise<T> {
  …
  for (let attempt = 1; ; attempt++) {
    try {
      return await runTransaction(attempt);
    } catch (error) {
      if (attempt >= maxAttempts || !isRetryable(error)) throw error;
      const delayMs = backoffDelay(attempt, baseDelayMs, maxDelayMs, random);
      onRetry?.({ attempt, delayMs, error });
      await sleep(delayMs);
    }
  }
}

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「请了监工就万事大吉」——更高的隔离级别不是免费的。每个参与的事务都要能处理 40001 并从头重做;冲突多时,重试会叠加,延迟变长,极端情况下一直重试失败。监工本身(谓词锁)也占内存和 CPU。Serializable 适合「冲突不多、但一旦出错代价很大」的业务。
  2. 「监工看得见一切」——它只看得见数据库里的读和写。如果「值班人数」是从 Redis 缓存里读的,或者从另一个服务查来的,数据库不知道你读过它,SSI 就检测不到。另外,只有两边都用 Serializable 的事务之间才会被检测;一个用 SER、另一个用 RC,照样可能写偏斜。
  3. 「隔离级别是全库的开关」——它是每个事务自己选的。同一个数据库里可以有的事务用 RC、有的用 SER。好处是可以只给关键操作开 SER;坏处是很容易漏掉某一处,而漏掉的那一处恰好会破坏规则。
④ 真实术语: Serializable Snapshot Isolation (SSI);predicate lock(pg_locks 里的 SIReadLock);rw-dependency / rw-antidependency、pivot、dangerous structure;serialization failure;retry with exponential backoff and jitter;40P01 deadlock_detected(Day 39);max_pred_locks_per_transaction;SET TRANSACTION READ ONLY DEFERRABLE(只读的 SER 事务可以等一个「安全快照」,永远不会被取消)。

MySQL 的 RR 能防幻读吗?这是面试常问的问题,要分两种读来回答:

  • 快照读(普通 SELECT):读的是事务开始时的快照,看不到别人新插入的行。
  • 当前读(SELECT … FOR UPDATE、UPDATE、DELETE):读最新版本,靠 next-key lock 锁住范围,别人插不进来。
  • 但如果在同一个事务里先快照读、再当前读,两次可能看到不同的行数。所以说它「基本防住、但不是完全防住」。

✅ 总结与自测

今天带走的 4 句话

  1. 快照:Read Committed 每条语句一张,Repeatable Read / Serializable 整个事务一张(第一条语句时拍)。所以 RC 下会有不可重复读(100 → 200)和幻读(2 行 → 3 行),RR 下都没有;脏读在 PostgreSQL 的任何级别下都不会发生,READ UNCOMMITTED 就是 READ COMMITTED。
  2. 丢失更新:「读 → 应用里算 → 写回」在 RC 下静默地丢了一次(两次 +1,结果 1);SET n = n + 1 在 RC 下不会丢(2);RR 下两种写法都报 40001 could not serialize access due to concurrent update。
  3. 写偏斜:两个事务读同一组行、写不同的行,RC 和 RR 都拦不住(没人值班、4 个未完成任务);只有 Serializable 在提交时报 40001 could not serialize access due to read/write dependencies among transactions。
  4. 重试:40001 / 40P01 要把整个事务从头重做,带退避和上限;重做时重新读、重新做业务检查,规则才守得住(最终 n = 2、只有一个人请假成功)。更高的隔离级别不是免费的,它把「数据静默地错了」换成了「请重来一次」。
