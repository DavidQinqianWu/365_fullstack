📇 概念卡 #1:计划树与 BUFFERS —— 取货路线单从最里面往外读

① 一句话大白话: 执行计划是一棵节点树:缩进最深的节点最先产出数据,一层层往上交,最上面的节点给出最终结果。每个节点有两组数字:估算(cost、rows、width)和实际(actual time、rows、loops)。读计划最重要的一眼,是估算的 rows 和实际的 rows 差了多少。BUFFERS 告诉你每个节点碰了多少个 8 KB 的页,其中多少已经在 PostgreSQL 的缓存里(shared hit)、多少要去读(read)。

② 生活类比:取货路线单

路线单一层套一层,最里面的「先去哪个柜子」最先做。每一步旁边写着预计和实际:预计取几本、实际取了几本、这一步做了几趟(比如「对每个会员去 B 柜取一次」,会员有 2 个就是 2 趟)。还有一栏「这些账页是本来就摊在桌上的(hit),还是要去库房搬的(read)」。

比喻 ↔ 真实 对照

比喻真实组件怎么读
路线单一层套一层计划树:每个 -> 是一个子节点从缩进最深的往外读;同一层的两个子节点,上面的通常是「外层」,下面的是「内层」
预计要花几个工分cost=启动..总不是毫秒;「启动」= 吐出第一行之前的代价(Sort 的启动代价很高,因为要先排完)
预计 / 实际取几本rows=(估算)/ actual … rows=两者差 10 倍以上就值得怀疑
这一步做了几趟loops=actual time 和 rows 都是每一趟的平均值,总量要 × loops
桌上的 / 去库房搬的Buffers: shared hit=… read=…单位是页(8 KB);hit = 已在 shared_buffers,read = 从操作系统要(可能来自 OS 缓存,也可能真的读磁盘)
写路线单花的时间 / 跑完全程Planning Time / Execution Time最后两行;后者不含把结果传给客户端的时间

  • 按 id 查:第一次要从操作系统读 3 页,第二次全部命中缓存,只碰了 4 页(B-tree 三层 + 表里那一页),耗时从 0.158 ms 降到 0.036 ms。这就是 Day 29「每组 3 次里第一次明显更慢」的原因。
  • 全表扫描:第二次还在 read。这不是 bug:大表的顺序扫描用的是一个很小的「环形缓冲区」(只有几百 KB),扫过的页不会挤占共享缓存,免得一次报表查询把所有热数据都挤出去。所以大表的全表扫描每次都要向操作系统要页。
  • read 也很快:本机的这些页其实都在操作系统的页缓存里,所谓 read 只是从内核内存拷一份过来,6000 多页才多花几十毫秒。在生产环境里,数据比内存大很多、或者放在网络盘上时,read 才意味着真的磁盘 I/O,差距会是数量级的。BUFFERS 看不出这两种 read 的区别,这是它的局限。

  • Bitmap 介于 Index Scan 和 Seq Scan 之间:先在索引里把要去的页都标出来(位图),再按页号顺序去表里读,每页只读一次。4 万行分散在 8285 页里时,这比 Index Scan 一行一行跳着读省事。Recheck Cond 是「到了页里再核对一次条件」:位图在 work_mem 装不下时会变成 lossy(只记页号、不记是哪几行),于是那 7728 页里的每一行都要复查,扔掉了 88.8 万行,耗时从 27 ms 变成 76 ms。
  • Sort:work_mem(默认 4MB)是每个排序 / 哈希操作能用的内存,装不下就写临时文件分段排序再合并(external merge Disk: 48968kB)。
  • LIMIT:没有合适索引时,ORDER BY … LIMIT 10 仍要扫完 100 万行,但只维护「当前最小的 10 个」(top-N heapsort,26 kB);有一个顺序对得上的索引时,读到第 10 行就停(总 cost 只有 0.77)。这正是 keyset 分页要的东西。

一个反直觉的实测:排序 100 万行,脚本跑了 3 遍、每遍 3 次,work_mem = 4MB(溢出到磁盘)350–851 ms,256MB(全在内存 quicksort)652–784 ms,溢出版多数时候反而更快。原因有两个:临时文件写进了操作系统的页缓存,并没有真的写盘;分段排序时每段只有几 MB,能放进 CPU 缓存,而对 87 MB 的数据做 quicksort 会频繁地缓存未命中。结论不是「溢出更好」,而是调大 work_mem 不是万能的,要实测;而且 work_mem 是「每个排序 / 哈希操作」的额度,一个查询可能有好几个这样的操作,几百个连接同时用就是几百倍,所以不能随手全局调大。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「路线单上的工分就是要花的分钟数」——cost 和毫秒不是一回事。今天就有反例:不许 Hash Join 时,优化器换成的 Merge Join 估算代价 36366,比 Hash Join 的 26257 高,但实际更快(下一张卡的表格:126–170 ms 对 180–294 ms)。代价模型按「数据可能要从磁盘读」来估,本机数据都在内存里,估算就会偏。读计划时,cost 用来理解优化器为什么这么选,快慢要看 actual。
  2. 「每一步写的时间就是这一步花的时间」——actual time 是每趟的平均值,而且包含子节点。loops=3 时要乘 3;嵌套循环里 loops=500001 的内层节点,0.001 ms × 50 万次就是 500 ms(第 3 张卡)。一个节点的 actual time 包含了它下面所有子节点的时间,算「这一步自己花了多久」要减去子节点。
  3. 「量体温的时候不影响体温」——EXPLAIN ANALYZE 本身有开销。它要给每个节点、每一行计时。同一条「不许 Nested Loop」的查询,带计时的 EXPLAIN ANALYZE 报告 166 ms,用 TIMING OFF 跑只有 55–88 ms。所以脚本里比较耗时用的都是 EXPLAIN (ANALYZE, TIMING OFF),看计划结构时才打开计时。
④ 真实术语: plan tree / plan node;startup cost / total cost;estimated rows vs actual rows;loops;EXPLAIN (ANALYZE, BUFFERS);shared hit / shared read(还有 dirtied、written、temp read/written);shared_buffers 与 OS page cache;buffer ring(大表顺序扫描不污染缓存);Index Only Scan / Heap Fetches;Bitmap Index Scan / Bitmap Heap Scan、Recheck Cond、exact / lossy;Gather / parallel workers;Sort Method(quicksort / top-N heapsort / external merge);work_mem。

📇 概念卡 #2:JOIN 算法 —— 逐个去查、先做速查表、两本排好序并排翻

① 一句话大白话: Day 25 学的 JOIN 是「结果长什么样」,数据库实际有三种做法:Nested Loop(外层每一行,都去内层找一遍配对;内层有索引时很快,适合外层很小)、Hash Join(先把较小的一边做成哈希表,再扫一遍另一边逐行查表;适合大表的等值连接)、Merge Join(两边都按连接键排好序,并排往下走;适合两边本来就有序,比如都有索引、或者结果本来就要按这个键排序)。优化器按估算的行数和代价挑一种。

② 生活类比:三种对账方式

  • Nested Loop:手里拿着一张 2 个人的名单,对每个人去卡片盒里查他的订单。名单短、卡片盒好查时最快;名单有 1 万人时就要查 1 万次。
  • Hash Join:先把 1 万个会员抄成一张速查表(按会员号能一眼找到),然后把 100 万张订单从头翻一遍,每张订单在速查表里查一下是谁的。速查表太大、桌子放不下时,就把订单和会员按会员号尾数分成几堆,一堆一堆地对(分批)。
  • Merge Join:会员名册和订单本都已经按会员号排好了,左右手各拿一本,从头并排往下翻,号码对上就配一对。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「哪种对账方式最好,记住就行」——没有固定最好的算法,只有在这份数据上最合适的。同样是「用户 JOIN 任务」,换个 WHERE 条件(2 个用户 vs 全部用户)、加个 ORDER BY … LIMIT,优化器就换了算法,而且换得对。所以背「什么时候用 Hash Join」不如学会读计划里的 rows 和 loops。
  2. 「关掉某种方式,就能逼它走对的路」——enable_* 开关只是学习工具。它不是「禁止」,而是给那种算法加一个巨大的惩罚代价(实在没别的路时还会用)。在生产里用它「修」慢查询,等于给所有查询都换了规则;数据一变,昨天对的今天就错。真正的修法是让优化器有正确的信息(统计信息、索引、合适的参数),下一张卡就是一个例子。
  3. 「速查表多大都放得下」——Hash Join 和排序一样受 work_mem 限制。估错行数时,优化器可能以为速查表只有几十行,实际几百万行,就会分很多批、甚至写大量临时文件。看到 Batches 远大于 1、或者 temp read/written 很大,就要怀疑估算或内存。
④ 真实术语: Nested Loop Join(outer / inner,parameterized index scan:内层用外层的值作为索引条件);Hash Join(build side / probe side、buckets、batches、spill to disk);Merge Join(sort-merge join,Merge Cond);join order;planner method configuration(enable_hashjoin 等,仅用于调试);random_page_cost / effective_cache_size。

📇 概念卡 #3:统计信息 —— 账房对每个柜子的印象,过期了就派错路线

① 一句话大白话: 优化器不会在每次查询前去数表里有多少行,它靠一份统计信息:这张表大概有多少行多少页、每一列有多少种不同的值、最常见的几个值各占多少、其余的值大致怎么分布(直方图)。这份信息由 ANALYZE 抽样收集(平时由后台的 autovacuum 自动做)。数据变了很多而统计没更新时,优化器会把「50 万行」估成「1 行」,于是选出一条只适合 1 行的路线。

② 生活类比:账房对柜子的印象

账房先生不会每接一张单子都去数一遍柜子,他心里有个印象:「B 柜大概 1000 本,42 号会员只有 1 本。」所以接到「把 42 号的都拿来」时,他写的路线是「去卡片盒查一下就行,拿回来再排个序」。可是昨晚有人一次性往 B 柜塞了 50 万本 42 号的账,他不知道,于是照着「1 本」的路线去执行:一张张查卡片、拿回来再排序,累得半死。等他重新清点一遍(ANALYZE),印象更新了,就改成「直接把 B 柜从头搬一遍」。

读计划的顺序清单

  1. 先看最后两行:Execution Time 有多少?值得优化吗?
  2. 找到最「宽」的节点:actual time(× loops)最大的那个,减去它的子节点。
  3. 在那个节点上比较估算 rows 和实际 rows:差 10 倍以上,先怀疑统计信息(ANALYZE 一下再看)。
  4. 看 loops:内层节点循环了几万次以上?是不是嵌套循环选错了?
  5. 看 Buffers:读了多少页?是不是为了很少的结果读了整张表(该有索引)?
  6. 看 Rows Removed by Filter / by Index Recheck:扔掉的远多于留下的?
  7. 看内存:Sort Method: external merge、Batches > 1、lossy?

计划很长时,可以把文本粘到 explain.dalibo.com 或 explain.depesz.com 这类网站上看图形化的结果(它们会标出最耗时的节点);但不要依赖它们,上面的清单才是你自己的能力。⚠️ 生产环境的查询计划里可能有敏感的表名和常量,粘到公网之前想清楚。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「重新清点一遍就是全数一遍」——ANALYZE 是抽样。它很快(百万行也只读几万行),代价是统计本身就是近似的:n_distinct 估成 8155 而不是 9999,很少出现的值可能根本没被抽到。对分布特别不均匀的列,可以用 ALTER TABLE … ALTER COLUMN … SET STATISTICS 让它多抽一些。
  2. 「印象准了,路线就一定对」——统计准确也不等于计划最优。代价模型本身还有假设(随机读比顺序读贵 4 倍、各列独立……),第 2 张卡的 Merge Join 就是统计很准、模型和硬件不符的例子。统计信息是优化器最重要的输入,不是唯一的。
  3. 「账房会自己定期清点」——autovacuum 有触发阈值,会滞后。默认要等改动的行数超过表的约 10%(加一个常数)才会自动 ANALYZE。对一张 1 亿行的表,1000 万行变化之前它都不动;刚导入完的一小段时间里统计也是旧的。大批量写入之后手动 ANALYZE,是很便宜的保险。

✅ 总结与自测

今天带走的 4 句话

  1. 计划树从最里面往外读,每个节点有估算(cost、rows)和实际(actual time、rows、loops);actual 是每趟的平均值,要 × loops,而且包含子节点。读计划最重要的一眼是估算 rows 和实际 rows 差多少。cost 不是毫秒,而且可能和实际快慢相反(Merge Join 的例子)。
  2. BUFFERS 看碰了多少页:shared hit 是已在缓存,read 是向操作系统要(本机多半来自 OS 缓存,所以也快);大表顺序扫描用小环形缓冲区,不会把缓存挤满。work_mem 不够时排序溢出到磁盘、Hash 分批、Bitmap 变 lossy,但「调大 work_mem」也要实测。
  3. 三种 JOIN:Nested Loop(外层小、内层有索引:2 个用户 0.05–1 ms,换成 Hash 要 55–88 ms)、Hash Join(大表等值连接,先建哈希表)、Merge Join(两边有序,配 LIMIT 很早停);优化器按估算选,enable_* 开关只用于学习。
  4. 统计信息决定估算:过期时 50 万行被估成 1 行,选出嵌套循环 + 先排序的计划(458–560 ms);ANALYZE 之后 69–88 ms。批量导入后手动 ANALYZE;两列相关用 CREATE STATISTICS。EXPLAIN ANALYZE 会真的执行,写操作要包在事务里回滚。
