🎫 接上回:读不挡写,可写和写还得排队

Day 38 讲了 MVCC:每个事务看自己那份快照,读和写互不等待。但你也见过三次「等待」:

  • Day 36 第 4 幕,B 要改 A 正在改的同一行,只能等 A 提交;
  • Day 37 的原子自增,T2 的 UPDATE … SET n = n + 1 卡在那里,直到 T1 结束;
  • Day 34 在事务里 DROP INDEX,整张表被锁住。

这些都是锁。MVCC 解决的是读和写的冲突,写和写的冲突仍然要靠锁:同一行同一时刻只能有一个事务在改,改表结构的时候整张表都不能动。

今天把锁拆成三块讲:

  • 行锁:包括用它做一个任务队列;
  • 表锁:包括一个 ALTER TABLE 怎样让整个服务卡住;
  • 死锁、排查工具和咨询锁。

明天(Day 40)用这些工具修 nest-lab 的「先查后改」。

🖥️ 前端翻译: 你做过防重复点击:提交按钮点了以后先 disabled,请求回来再恢复,这就是一把最简单的锁。浏览器还有 Web Locks API:navigator.locks.request('sync', async () => { … }),同一个名字的锁,多个标签页里同一时刻只有一个能拿到。你可能也写出过「卡死」:两个 Promise 各自等着对方先 resolve,谁都不动。数据库里这三样都有,分别叫行锁、咨询锁和死锁。

📇 概念卡 #1:行锁与 SKIP LOCKED —— 压一块镇纸,看见镇纸就拿下一张

① 一句话大白话: 行锁保证同一行同一时刻只有一个事务在改它。UPDATE / DELETE 会自动加锁;SELECT … FOR UPDATE 让你在「读出来、在应用里算」之前就先锁住,别人想改就得等。锁一直拿到事务结束。等不了的话,NOWAIT 立刻报错,lock_timeout 等一会儿再报错,SKIP LOCKED 直接跳过被锁的行。最后这个正好拿来做任务队列:多个 worker 同时领任务,谁也不领重复的,谁也不用等谁。

② 生活类比:镇纸

伙计要改账本上的某一行,先在那一行上压一块镇纸:「我正在改,别动」。别的伙计照样可以看(MVCC 的照片),但要改这一行,就得站在旁边等镇纸拿走。镇纸要等这张作业单盖章或作废后才拿走,不是改完这一行就拿走。

镇纸有轻有重:最重的(FOR UPDATE)谁来都不行;普通改账压的那块(FOR NO KEY UPDATE)允许别人来核对「这个会员号还在不在」(外键检查)。

领活的伙计们从一叠工单里拿最上面那张。有了 SKIP LOCKED,他们看见上面压着镇纸就直接拿下一张,不排队;没有它,所有人都盯着同一张工单,前一个人办完,下一个人才能接着看。

  A:BEGIN; SELECT … WHERE id = 1 FOR UPDATE(A 的事务号 268568)
  B:普通 SELECT → balance = 100,2 ms(行锁不挡读);这一行的 xmax = 268568(= A 的事务号:行锁记在行头)
  B:UPDATE 同一行(lock_timeout 500ms)→ ERROR 55P03 canceling statement due to lock timeout,502 ms
  B:SELECT … FOR UPDATE NOWAIT → ERROR 55P03 could not obtain lock on row in relation "accounts",2 ms
  B:SELECT … FOR SHARE NOWAIT → ERROR 55P03 could not obtain lock on row in relation "accounts"(FOR SHARE 和 FOR UPDATE 冲突)
  B:INSERT 一笔引用 1 号账户的转账(外键检查要 FOR KEY SHARE)→ ERROR 55P03 canceling statement due to lock timeout,502 ms

  A:BEGIN; UPDATE accounts SET balance = … WHERE id = 1(普通 UPDATE 拿的是 FOR NO KEY UPDATE)
  B:同样的 INSERT → 成功,2 ms(FOR NO KEY UPDATE 不挡外键检查)
  B:SELECT … FOR NO KEY UPDATE NOWAIT → ERROR 55P03 could not obtain lock on row in relation "accounts"(两个写同一行仍然冲突)
  • 行锁记在哪:Day 38 说「xmax 有值不一定是删除」,这里就是一个例子。A 只是 FOR UPDATE,这一行的 xmax 就写上了 A 的事务号。PostgreSQL 不在内存里给每一行建锁记录,而是写在行头;多个事务同时拿共享锁时,xmax 里放的是一个「多事务号」(multixact)。所以锁住一百万行也不会耗尽内存,但会产生写入。
  • 四种模式:普通 UPDATE 拿的是 FOR NO KEY UPDATE(只要不改主键 / 唯一键),外键检查拿的是 FOR KEY SHARE,两者不冲突。所以「改账户余额」和「往这个账户上记一笔转账」可以同时进行。如果你显式写了 FOR UPDATE,就连外键检查也挡住了。只需要防止别人同时改时,用 FOR NO KEY UPDATE 比 FOR UPDATE 更友好。完整的冲突表在 02-row-locks.sql 的注释里(以官方文档「Explicit Locking」为准)。
  • NOWAIT 和 lock_timeout 都报 55P03(lock_not_available),区别只是等不等:前者立刻报,后者等满 500 ms(实测 502 ms)再报。

⑤ 动手验证 B:SKIP LOCKED 任务队列。每个 worker 的一次循环(03-skip-locked.sql):

BEGIN;
SELECT id FROM jobs WHERE status = 'pending' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;   -- 领一个
-- 处理(脚本里 sleep 5 ms)
UPDATE jobs SET status = 'done', worker = $2, times_done = times_done + 1 WHERE id = $1;    -- 标记完成
COMMIT;

✍️ 预测:4 个 worker 并发领 200 个任务(每个任务处理 5 ms)。有没有任务被处理两次?各 worker 分到多少?去掉 SKIP LOCKED 呢?真实结果(第 3 幕,3 遍):

    用时 376 – 384 ms;完成 200 个,其中恰好处理了 1 次的 200 个,最多被处理 1 次
    各 worker 分到:W1=50 W2=50 W3=50 W4=50                  (3 遍都是)
    领任务时花在等锁上的时间合计 2 – 5 ms

  FOR UPDATE(不加 SKIP LOCKED)
    用时 1458 – 1466 ms;完成 200 个,其中恰好处理了 1 次的 200 个,最多被处理 1 次
    各 worker 分到:W1=53 W2=45 W3=62 W4=40 / W1=44 W2=43 W3=51 W4=62 / W1=62 W2=39 W3=40 W4=59
    领任务时花在等锁上的时间合计 4350 – 4372 ms
    「等到锁却领了个空、其实队列里还有」0 次
  • SKIP LOCKED:4 个 worker 真正并行,200 × 5 ms ÷ 4 ≈ 250 ms 的活用了约 380 ms,每个任务恰好处理一次,几乎没有等锁。
  • 不加 SKIP LOCKED:结果同样正确(没有重复处理),但 4 个 worker 都去抢「id 最小的那个待处理任务」,一个在处理,另外三个排队,实际上变成了串行:用时约 1.46 秒,4 倍;四个 worker 等锁的时间加起来约 4.36 秒。
  • 一个可能的坑在这里没有出现:排队的 worker 等到锁时,那一行已经被标成 done。PostgreSQL 会重新检查 WHERE 条件,发现不满足就继续找下一行,所以不会「领了个空」(3 遍都是 0 次)。
  • 这就是很多「基于 PostgreSQL 的任务队列」的核心(比如 graphile-worker、pg-boss,只提名字,没有实测)。真正的队列还要处理任务失败重试、超时未完成的任务重新放回、死信等,Week 8 / 13 讲 Redis 和消息队列时再对比。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「压了镇纸,别人就看不到」——行锁不挡读。普通 SELECT 读的是快照(Day 38),2 ms 就返回。行锁只挡「也想改它的」和「也想锁它的」。
  2. 「改完就拿走镇纸」——锁一直拿到事务结束。A 锁住一行之后,如果又去调了一个 30 秒的外部接口,别人就被挡 30 秒(Day 36 说的「事务要短」又一次)。
  3. 「跳过镇纸」只适合队列。SKIP LOCKED 返回的是「此刻没被锁住的那部分行」,不是一个一致的结果。用它算报表或做业务判断(「还有没有库存」)会得到错误的答案。
④ 真实术语: row-level lock:FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE;pessimistic locking(Day 40);NOWAIT、SKIP LOCKED;lock_timeout、statement_timeout;SQLSTATE 55P03 lock_not_available、57014 query_canceled;multixact;job queue / work queue。

📇 概念卡 #2:表锁与锁队列 —— 整本收走重新装订,门口排起长队

① 一句话大白话: 每条语句都会在表上拿一把表锁:SELECT 拿最轻的 ACCESS SHARE,INSERT / UPDATE / DELETE 拿 ROW EXCLUSIVE,普通的 CREATE INDEX 拿 SHARE(挡写不挡读),ALTER TABLE、DROP、TRUNCATE、VACUUM FULL 拿最重的 ACCESS EXCLUSIVE(谁都挡)。锁按到达顺序排队:一个拿不到锁的 ALTER TABLE 排在门口时,它后面来的所有普通 SELECT 也只能排在它后面,整张表就像卡死了。线上做迁移一定要设 lock_timeout,拿不到锁就放弃、过一会儿重试。

② 生活类比:整本收走重新装订

平时大家都在翻同一本账,互不影响。装订师傅要给账本加一栏,得把整本账收走重新装订,装订期间谁都不能翻。可是现在有个伙计正拿着账本在看(一个没结束的读事务),师傅只好在门口等。这时又来了几个伙计要翻账,他们本来和正在看账的人完全不冲突,可按规矩他们得排在师傅后面。于是门口排起长队,账房看起来像停业了。

聪明的装订师傅会说:「我只等 200 毫秒,等不到就先走,过一会儿再来。」这样后面的人最多只被挡 200 毫秒。

⑤ 动手验证 A:常见语句拿的表锁。真实结果(04-ddl-lock-queue.sql,在一个事务里执行后查 pg_locks):

    表    |      锁模式      | 拿到了
----------+------------------+--------

⑤ 动手验证 B:锁队列。✍️ 预测:A 开着一个读过 big 的事务不结束;B 执行 ALTER TABLE big ADD COLUMN note text;C 执行一个普通的 SELECT count(*) FROM big(超时 1.5 秒)。C 会被挡住吗?真实结果(第 4 幕,3 遍一致):

  A:BEGIN; SELECT count(*) FROM big;(拿着 ACCESS SHARE,事务不结束)
  B:ALTER TABLE big ADD COLUMN note text;(要 ACCESS EXCLUSIVE → 排队)
  C:SELECT count(*) FROM big;(一个普通请求)
  此刻 pg_blocking_pids(谁挡住了谁):
    B-migration  在等 Lock:relation      被 A-reader(pid 15041)挡住     ALTER TABLE big ADD COLUMN note text
    C-request    在等 Lock:relation      被 B-migration(pid 15042)挡住  SELECT count(*) AS n FROM big
  C 的结果:ERROR 57014 canceling statement due to statement timeout,1501 ms(本来和 A 一点也不冲突)
  A:COMMIT → B 的 ALTER 完成,从开始排队算共 1707 – 1708 ms

  —— 线上的做法:迁移设 lock_timeout,拿不到锁就放弃、过一会儿重试 ——
  B 第 1 次:ERROR 55P03 canceling statement due to lock timeout → 等 100 ms 再试
  B 第 2 次:ERROR 55P03 canceling statement due to lock timeout → 等 100 ms 再试
  B 第 3 次:ERROR 55P03 canceling statement due to lock timeout → 等 100 ms 再试
  B 第 4 次:成功(1003 – 1004 ms)
  同一时间 C 的普通 SELECT:n = 100000,用了 156 – 159 ms(最多被挡 200 ms)
  • C 只要 ACCESS SHARE,和 A 完全兼容,却被挡住了:pg_blocking_pids 显示挡住 C 的是 B,不是 A。PostgreSQL 的锁是排队的,后来的请求不能「插队」绕过一个正在等待的冲突请求,否则 B 可能永远拿不到锁。
  • 这就是「线上执行一个 ALTER TABLE,整个服务卡住」的原因。ADD COLUMN 本身在 PostgreSQL 11 之后通常是瞬间完成的,只改表的定义、不重写数据,卡住的是等锁的那段时间。只要有一个长查询或者一个 idle in transaction 的连接(Day 38)拿着表锁,迁移就会在门口排队,所有请求跟着排队,连接池很快被占满(Day 27),然后报 500。
  • 修法:迁移脚本里 SET lock_timeout = '200ms'(或更短),拿不到就报 55P03、退出、重试。这样别的请求最多被挡 200 ms。同样道理,Day 34 的 schema.sql 整个重建在生产上不能用;建索引要用 CREATE INDEX CONCURRENTLY(不挡写),这些是 Week 9「零停机迁移」的内容。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「装订很快,不会影响别人」——慢的是排队,不是装订。ADD COLUMN 只要几毫秒,可它在等锁的这段时间里,后面所有请求都被挡住了。判断一个迁移危不危险,要看「它要什么锁」和「现在有没有长事务」,而不只是「它本身要跑多久」。
  2. 「设了 lock_timeout 就安全了」——失败了要有人重试。迁移工具或脚本要能在 55P03 后重试几次;重试也失败,就要找出是谁一直拿着锁(第三张卡的工具)。
  3. 「表锁只有 DDL 才有」——每条语句都拿表锁。只是普通读写的表锁彼此兼容,平时感觉不到。和 ACCESS EXCLUSIVE 一冲突,才发现连 SELECT 也在排队。
④ 真实术语: table-level lock:ACCESS SHARE / ROW SHARE / ROW EXCLUSIVE / SHARE UPDATE EXCLUSIVE / SHARE / SHARE ROW EXCLUSIVE / EXCLUSIVE / ACCESS EXCLUSIVE(8 种,今天只讲 4 种);lock queue;LOCK TABLE;pg_locks(locktype、mode、granted);lock_timeout;CREATE INDEX CONCURRENTLY(Week 9);zero-downtime migration。

📇 概念卡 #3:死锁、排查与咨询锁 —— 两块镇纸互相等,墙上一块值班牌

① 一句话大白话: 死锁:A 锁着 1 号等 2 号,B 锁着 2 号等 1 号,谁也等不到。PostgreSQL 在等待超过 deadlock_timeout(默认 1 秒)后检查谁在等谁,发现绕成了圈,就让其中一个事务报 40P01 deadlock detected 并回滚,另一个继续。避免的办法是所有人都按同一个顺序加锁。排查锁等待用 pg_blocking_pids() 配合 pg_stat_activity。咨询锁(advisory lock)不锁任何行或表,只锁一个数字,常用来保证「多个副本里同一件事同一时刻只有一个在做」。

② 生活类比:两块镇纸、一块值班牌

伙计甲在 1 号账上压了镇纸,接着要改 2 号;伙计乙在 2 号账上压了镇纸,接着要改 1 号。两个人都站着等对方的镇纸,永远等不到。账房掌柜每隔一会儿巡视一圈,发现这个圈,就让其中一个人作废他的作业单、把镇纸拿走,另一个人就能继续了。以后定一条规矩:要改几行账,一律按账号从小到大压镇纸,这样大家最多是排队,不会绕成圈。

墙上还挂着一块「今晚对账值班」的牌子,跟账本本身没关系。几家分店的伙计到点都来摘牌,谁先摘到谁对账,没摘到的就回去。前提是大家都遵守「先摘牌再对账」的约定。

  —— 修法:按固定顺序(id 从小到大)一次锁住要改的所有行 ——
  A:SELECT … WHERE id IN (1, 2) ORDER BY id FOR UPDATE → 拿到两行
  B:同样的语句 → 等 A(是排队,不是互相等)

  B:改完两行,COMMIT;最终余额 Alice=100 Bob=50(两笔转账都成功,没有死锁)
  • DETAIL 把圈写得清清楚楚:「进程 15048 在等事务 268988(进程 15049 的)」「进程 15049 在等事务 268987(进程 15048 的)」。两个进程等的都是对方的事务号(ShareLock on transaction):行锁的等待,实际上是「等那个事务结束」。具体是哪两条 SQL,要去服务器日志里看(HINT 说的就是这个)。
  • 报错之前正好等了约 1 秒,这就是 deadlock_timeout。检查等待图比较贵,所以只在等了这么久之后才查。它也是 log_lock_waits = on 时记录「等锁超过多久」的阈值。
  • 修法:要改多行,先用 ORDER BY id FOR UPDATE 按同一个顺序一次锁住,再改。B 只是排队等了 0.3 秒,两笔转账都成功了。其他办法:缩短事务(锁拿得越久越容易撞上)、一次少锁几行。
  • 死锁不是 bug,而是并发系统迟早会遇到的事。只要两段代码以不同顺序访问同一批数据,就有可能发生。所以除了尽量避免,还要把 40P01 当成可重试的错误:Day 37 的 withRetry 已经包含了它。

⑤ 动手验证 B:谁挡住了谁。线上卡住时第一件事就是跑这条查询(06-who-blocks.sql,复制到任何库都能用):

SELECT w.pid AS 等待者, now() - w.query_start AS 等了多久,
       w.wait_event_type || ':' || w.wait_event AS 在等什么, left(w.query, 60) AS 等待者的语句,
       pg_blocking_pids(w.pid) AS 被谁挡住,
       b.pid AS 挡路的, b.state AS 挡路者状态, now() - b.xact_start AS 挡路者的事务开了多久, left(b.query, 60) AS 挡路者最后一条语句
FROM pg_stat_activity w
JOIN LATERAL unnest(pg_blocking_pids(w.pid)) AS bp(pid) ON true
JOIN pg_stat_activity b ON b.pid = bp.pid
WHERE w.datname = current_database()
ORDER BY w.query_start;

第 4 幕里它的结果是:B(ALTER)被 A(idle in transaction 的读事务)挡住,C(SELECT)被 B 挡住。顺着「被谁挡住」一路往上找,找到那个自己没在等、却挡着别人的进程,它通常就是一个忘了提交的事务。处理办法:先联系它的主人;实在不行,SELECT pg_cancel_backend(pid) 取消它正在执行的语句,或 pg_terminate_backend(pid) 断开它的连接(Day 36 用过)。想在日志里留下证据,打开 log_lock_waits(点到为止)。

  • 典型用途:nest-lab 部署了 3 个副本(Day 4 / 5 的多进程、Phase 4 的多副本),每个副本里都有一个「每天凌晨发提醒邮件」的定时任务。每个副本到点先 pg_try_advisory_lock(某个固定数字),只有拿到的那个干活,其他直接跳过。不需要额外的 Redis 或 ZooKeeper,只要大家共用同一个数据库。
  • 事务级(pg_advisory_xact_lock)在事务结束时自动释放,不会忘;会话级(pg_advisory_lock / pg_try_advisory_lock)要手动 unlock 或者断开连接才释放。实测 COMMIT 之后它还在。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「定了顺序就再也不会死锁」——只能防住你自己写的、按顺序加锁的代码。外键检查、触发器、唯一索引冲突等待,都会在你看不见的地方拿锁。所以死锁要当成可重试的错误处理,而不是假设它不存在。
  2. 「值班牌数据库会帮你看着」——咨询锁只是一个约定。数据库不知道「数字 42 代表发邮件任务」,也不会拦住一个不先拿锁就直接干活的进程。所有相关的代码都得遵守约定,这个数字也要在团队里登记好,别撞号。
  3. 「拿到的牌子用完会自己挂回去」——会话级咨询锁在连接池里会泄漏。连接是借来还回去的(Day 27),如果拿了会话级锁却忘了 unlock,这个连接被还回池子时锁还在,下一个借到它的请求「意外地」拿着这把锁,而原来的代码以为自己已经放了。用 PgBouncer 的 transaction 模式时,同一个会话里的两条语句甚至可能跑在不同的服务器连接上,会话级锁就完全不可靠了(Day 41)。优先用事务级的。

✅ 总结与自测

今天带走的 4 句话

  1. 行锁:FOR UPDATE 不挡普通读(2 ms),挡写和别的锁,一直拿到事务结束,记在行头的 xmax 里。NOWAIT 立刻报、lock_timeout 等满再报,都是 55P03。普通 UPDATE 拿的 FOR NO KEY UPDATE 不挡外键检查,显式的 FOR UPDATE 会挡。
  2. SKIP LOCKED 队列:4 个 worker 领 200 个任务,每个恰好处理一次、各 50 个、用时约 380 ms;不加 SKIP LOCKED 结果也对,但变成串行,约 1460 ms,等锁合计约 4.4 秒。
  3. 表锁与锁队列:ALTER TABLE 要 ACCESS EXCLUSIVE,被一个没结束的读事务挡住后,后面的普通 SELECT 也排在它后面,实测 1.5 秒超时。迁移要设 lock_timeout 并重试:实测第 4 次成功,其间普通 SELECT 只被挡了约 157 ms。
  4. 死锁与咨询锁:相反顺序加锁约 1 秒后报 40P01 deadlock detected,DETAIL 写出谁在等谁;按 id 顺序一次锁住就只会排队。死锁要当可重试错误处理。pg_blocking_pids() 找出谁挡住了谁。咨询锁 3 个连接只有 1 个拿到,优先用事务级的,会话级的在连接池里会泄漏。
