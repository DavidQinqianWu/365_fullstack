📇 概念卡 #1:OpenAPI —— 全行业通用格式的「标准菜单册」

① 一句话大白话: OpenAPI 是一种用 JSON / YAML 描述 HTTP API 的标准格式:有哪些路径、每个路径支持哪些方法、要什么参数和请求体、会回哪些状态码和响应体。因为格式统一,一份文件可以同时喂给文档页面、前端类型生成器、mock 服务器和测试工具。

② 生活类比:连锁餐厅的标准菜单册

菜单册每一页是一道菜:菜名、价格、配料表、过敏提示;同一种配料(比如「秘制酱汁」)只在附录里写一次,各道菜引用它。格式是全行业统一的,所以点菜平板、外卖平台、营养师、品控都能直接读。菜单册有两种做法:先由总部设计好菜单,后厨照着做;或者后厨先有配方,从配方自动印出菜单。

code-first 还是 contract-first?两种都是正经做法,区别在于「谁是唯一的真相」:

contract-first(先写契约)code-first(从代码生成)
真相在哪手写的 openapi.yaml代码;OpenAPI 是产物
适合多团队并行(前端、后端、合作方先对齐契约,各自开发);对外的公开 API一个团队前后端节奏一致;框架装饰器 / 类型已经描述了大部分信息
风险实现偏离契约 → 需要契约测试或从契约生成服务端骨架文档只和装饰器一样准;容易「改代码不看文档 diff」

nest-lab 选 code-first:DTO 已经带着 class-validator 规则,再贴上文档标签就能印出菜单。为了补上它的风险,今天把生成的 openapi.json 提交进 git(PR 里能直接看到契约变化),并且加了「过期就变红」的检查(第 5 节)。

3.0 和 3.1 差在哪?OpenAPI 3.1(2021)和 JSON Schema 2020-12 完全对齐,3.0 只是「JSON Schema 的一个变体」。最常碰到的差别是 null:3.0 写 "type": "string", "nullable": true,3.1 写 "type": ["string", "null"]。@nestjs/swagger@12.1.0 生成的是 3.0.0,nest-lab 的 nextCursor 就是 "nullable": true(下面的真实输出里能看到)。工具一般两种都认,但如果你要拿 schema 直接给 JSON Schema 校验器(比如 Ajv)用,3.0 的 nullable 它不认识。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「菜单上写了,厨房就一定这样做」——文档描述的是「应该」,不保证实现。菜单册说「过敏原:无花生」,不等于厨师今天没换酱料。OpenAPI 里写着「失败时回 422 problem+json」,服务器完全可能回一个 500 HTML。code-first 让文档和装饰器一致,不是和真实行为一致。真实行为要靠契约测试保证:nest-lab 的 e2e(Day 15–19 写的那些)发真实请求、检查真实响应;今天又加了「schema 字段 = 映射函数真实输出」的测试。业界还有 Schemathesis 这类「按 OpenAPI 自动生成请求、检查响应是否符合文档」的工具,Week 11 讲测试体系时可以拿来对照。
  2. 「自动印出来的菜单一定对」——印刷机只能印配方卡上写着的东西。@ApiOkResponse({ type: TaskResponse }) 写成了 UserResponse,文档就会一本正经地错;一个字段忘了贴 @ApiProperty,文档里就少一个字段(第 4 节实测)。「自动生成」消灭的是「忘了同步」,消灭不了「写错」。
  3. 「菜单册就该摆在门口」——对外界来说,它也是一张完整的攻击面地图。每个路径、参数、哪里要钥匙,一目了然,还附带一个能直接发请求的页面。公开 API 当然可以公开文档;但内部服务、后台接口在生产环境默认不该开放。nest-lab 用配置 SWAGGER_ENABLED 控制,NODE_ENV=production 时默认关闭(第 5 节实测 404)。关掉文档不是安全措施本身(接口照样能被扫),鉴权才是,这是 Week 10 的事。
④ 真实术语: OpenAPI Specification (OAS) 3.0 / 3.1(Linux 基金会旗下 OpenAPI Initiative 维护;Swagger 2.0 是它的前身,「Swagger」现在主要指 SmartBear 的工具);Paths / Operation / Parameter / Request Body / Response;Components(schemas、securitySchemes);$ref;operationId(代码生成器拿它当函数名);tags(文档分组);design-first / API-first / code-first;contract testing。

读结果:

  • 11 个操作,没有 /tasks。tasks 控制器登记在 ['2', VERSION_NEUTRAL] 两个版本下,@nestjs/swagger 默认会把 /v2/tasks 和 /tasks 各登记一次(第一次生成时就是 8 个 path),同一个操作出现两次会让前端生成两套重复的函数。src/openapi.ts 里只保留 /v2/... 这一份,文档说明里写着「不带版本号的路径等同 v2」。
  • 没有 OPTIONS / HEAD / 「PATCH /v2/tasks」这类兜底路由:它们贴了 @ApiExcludeEndpoint()。405 是「这个方法不存在」,不该作为一道菜登记进菜单。
  • 🔑 = 写接口要求 demo-key。在 Swagger UI 右上角点 Authorize 填入 let-me-in,「Try it out」发出的请求就会带上 x-demo-key。
  • 每个操作都有 406(类级别的 @ApiProblemResponses(406),因为 Day 15 的内容协商中间件对所有路由生效);写接口都有 415 和 422。这些状态码不是 Nest 自动推断的,全部是我们按 Day 15–19 的真实行为声明的。

📇 概念卡 #2:@nestjs/swagger —— 印刷机只认贴了标签的配方

① 一句话大白话: @nestjs/swagger 在启动时扫描所有 Controller 和 DTO 上的装饰器元数据,拼出一份 OpenAPI。路由、路径参数、请求体类型它能从 @Get()、@Body() 推出来;DTO 有哪些字段、什么类型,它必须看到 @ApiProperty 这样的标签,因为 TypeScript 的类型在编译后就消失了。

② 生活类比:印刷机只认配方卡上的标签

印刷机看不懂厨师的手写配方,只认配方卡上贴的标准标签:「配料:面粉,必需」「辣度:可选」。厨房里有一个贴标签助手(CLI 插件),会在配方定稿时自动给每一行配料贴标签,省得厨师手贴。问题是:这个助手只在正式厨房上班,隔壁的试菜间他不来。

// src/app.setup.ts
export function configureApp(app: INestApplication): INestApplication {
  app.enableVersioning({ type: VersioningType.URI });
  // 必须在 enableVersioning 之后:生成文档时要知道版本前缀
  if (swaggerEnabled(app)) setupSwagger(app);
  return app;
}

实验:要不要开 CLI 插件?

官方文档推荐打开 CLI 插件(在 nest-cli.json 里加 "plugins": ["@nestjs/swagger"]),它会根据 TS 类型和 class-validator 装饰器自动生成字段的 schema,可以少写很多 @ApiProperty。✍️ 预测:nest-lab 是 ESM + vitest,打开插件之后,下面三种情况的 ReplaceTaskDto schema 各是什么样?① 不开插件、不写 @ApiProperty;② 开插件、nest build 后生成;③ 开插件、在 vitest 里生成。

三个发现:

  1. 不贴标签,菜单就是空白:6 个 DTO 的 schema 都是 "properties": {},列表接口的 query 参数一个都没有。前端拿到这份文档,生成出来的类型全是空对象。
  2. 插件在 nest build 下确实有效,连 class-validator 的 @MaxLength(100)、@IsEmail() 都翻译成了 maxLength、format: email。但 CreateTaskDto / UpdateTaskDto 仍然是空的:它们当时是用 @nestjs/mapped-types 的 PickType / PartialType 派生的,这个包只复制校验元数据,不复制文档元数据。修法:改从 @nestjs/swagger 导入同名函数,它两种元数据都复制(今天已经改了,并去掉了 @nestjs/mapped-types 这个直接依赖)。
  3. vitest 里插件不工作:插件是挂在 Nest CLI 编译流程上的,vitest 用自己的转换器编译 TS,根本不经过它。结果就是测试里生成的文档和 build 出来的文档不一样。对 nest-lab 这是硬伤:今天的 e2e 测试要比对「代码生成的文档 = 提交的 openapi.json」,两边不一致,这个测试就没法写。(社区有给 vitest 配 SWC 并接入插件的做法,但又多一层要维护的编译配置。)

结论:nest-lab 不开插件,每个字段显式写 @ApiProperty。代价是多写几行;换来的是 nest build、vitest、npm run openapi:generate 三处生成的文档完全一致(e2e 里的比对测试通过就是证明),而且每个字段的说明和例子都是自己写的,比插件推断的更有用:

// src/tasks/dto/replace-task.dto.ts(节选)
@ApiProperty({ description: '标题,首尾空格会被去掉,不能全是空白', maxLength: 100, example: '学 OpenAPI' })
@Transform(({ value }) => (typeof value === 'string' ? value.trim() : value))
@IsString()
@IsNotBlank()
@MaxLength(100)
title!: string;

// src/tasks/dto/create-task.dto.ts —— 从 @nestjs/swagger 导入,校验规则和文档说明一起「挑」过来
import { PickType } from '@nestjs/swagger';
export class CreateTaskDto extends PickType(ReplaceTaskDto, ['title', 'checklist'] as const) {}

注意 @ApiProperty({ maxLength: 100 }) 和 @MaxLength(100) 是两份:一份给菜单,一份给海关(Day 16 的 ValidationPipe)。它们可能不一致,这是显式写法要付的代价,插件能自动同步的恰好就是这部分。查询参数用的也是同一套写法:ListTasksQueryDto 的字段贴 @ApiPropertyOptional,@Query() 收的是 DTO,Nest 就会把每个字段展开成一个 query 参数。@ApiQuery 用在没有 DTO、单独 @Query('x') 取参数的场合。

响应文档和真实响应,怎么保证是同一份?

Day 18 的响应类型是 interface。interface 编译后不存在,印刷机看不到,所以今天把 TaskResponse、UserResponse、TaskPage 改成了 class,并且让同一个类同时承担两个角色:

// src/tasks/dto/task-response.ts
export class TaskResponse {                      // ② 菜单册的 schema
  @ApiProperty({ example: 1 }) id!: number;
  @ApiProperty({ example: '学 OpenAPI' }) title!: string;
  @ApiProperty({ example: false }) done!: boolean;
  @ApiProperty({ type: () => [ChecklistItemResponse] }) checklist!: ChecklistItemResponse[];
  @ApiProperty({ format: 'date-time', example: '2026-01-01T00:00:00.000Z' }) createdAt!: string;
}

export function toTaskResponse(task: Task): TaskResponse {   // ① 映射函数的返回类型
  return { id: task.id, title: task.title, done: task.done,
           checklist: task.checklist.map((i) => ({ text: i.text, done: i.done })), createdAt: task.createdAt };
}

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「标签贴了就算数」——@Api* 装饰器不改变任何运行时行为。@ApiProperty({ maxLength: 100 }) 不会拦截 101 个字的标题,拦截靠 @MaxLength(100);@ApiResponse({ status: 409 }) 不会让接口回 409。印刷机贴的标签和厨房的真实做法是两套东西,这正是第 3 节边界 1 的具体表现。
  2. 「插件是官方推荐,开就对了」——要看你的编译链。插件依赖 Nest CLI 的编译流程;如果测试、脚本、打包工具(vitest、esbuild、SWC)有任何一个不经过它,不同入口生成的文档就会不同。对用 Jest + ts-jest 也能配插件的 CommonJS 项目,开插件很合理;nest-lab 的选择是因为 ESM + vitest,并且我们要把文档当测试对象。
  3. 「class 就是 schema」——class 只描述字段,不描述「谁看到哪些字段」。UserResponse 的 internalNote 只有 admin 能看到,文档里只能标成可选并写说明;OpenAPI 没法表达「取决于请求头 x-demo-role」。同一个资源按角色返回不同字段时,文档总会比真实行为粗糙一些。

✅ 总结、Week 3 收口与自测

今天带走的 4 句话

  1. OpenAPI 是 HTTP API 的标准菜单册:paths + operations + components.schemas,一份文件同时驱动文档页面、前端类型 / SDK、mock 和测试。3.1 与 JSON Schema 完全对齐,@nestjs/swagger 输出的是 3.0(nullable: true)。
  2. code-first 的文档只和装饰器一样准:TS 类型运行时不存在,字段要贴 @ApiProperty;CLI 插件在 vitest 下不生效,nest-lab 选择显式标注,保证所有入口生成同一份文档。mapped types 要从 @nestjs/swagger 导入。
  3. 响应类既是映射函数的返回类型又是 schema:多字段、少字段由编译器拦,忘贴标签由 e2e 拦,所有变化出现在提交的 openapi.json diff 里;openapi:check 抓过期。
  4. 文档描述「应该」,不保证「真的」:真实行为靠 e2e / 契约测试;生成的前端类型只在编译时有效;文档页面生产环境默认关闭(SWAGGER_ENABLED)。
