🎫 接上回:一张表够用吗?

Day 22 我们建了一张孤零零的 tasks 表。可 nest-lab 里的东西不止任务:Day 18 有了用户(邮箱、显示名、角色、密码哈希),Day 16 每个任务带一个 checklist 数组。以后任务还会有负责人、标签。这些东西在数据库里该怎么放?

最省事的想法是:全塞进一张表。一行一个任务,负责人的邮箱和名字直接写在旁边,标签开三列 tag1 / tag2 / tag3,清单项用逗号拼成一个字符串。写的时候很爽,一条 INSERT 全搞定。今天的第一个实验就是看它什么时候开始出错。

💡 生活翻译: 餐厅刚开张时,老板只有一本大流水账:每来一单就记一行,「哪位会员、会员电话、点了什么、菜品标签、做菜步骤」全写在这一行里。生意大了以后问题来了:会员换了电话,要把他以前的几十行都改一遍;新会员办了卡但还没点过菜,流水账里没地方写他;一个老会员唯一的一单被退掉,划掉这一行,这个会员也从账上消失了。于是总店把账拆开:一本会员名册,一本订单本(只写会员编号),一本菜品标签本,再加一张「哪道菜贴了哪些标签」的对照表。
🖥️ 前端翻译: 你在 Redux 里一定见过这种建议:不要在 state 里存嵌套的 posts[].author{...},而是用 normalizr 或 Redux Toolkit 的 createEntityAdapter 存成 { ids: [...], entities: { 1: {...} } },每个作者只存一份,文章里只放 authorId。理由是:作者改了名字,只需要改一个地方。这就是数据库的范式化,同一个思想。今天你会看到它在数据库里的完整版本,以及它的反面:什么时候故意「不范式化」。

📇 概念卡 #1:实体与关系 —— 大流水账为什么会记乱

① 一句话大白话: 业务里每一种「有自己身份、需要单独记录的东西」(用户、任务、清单项、标签)叫一个实体,通常一个实体一张表。实体之间的联系叫关系,只有三种:一对一(1:1)、一对多(1:N)、多对多(N:M)。把几个实体硬塞进一张表,同一个事实就会被存好几份,于是出现三类异常:改不全、放不进、删多了。

② 生活类比:大流水账 vs 分开的账本

会员名册上每位会员一行;订单本上每单一行,只写「会员编号 7」,不再抄会员的名字电话;一道菜可以贴「辣」「招牌」好几个标签,一个「辣」标签也贴在好几道菜上,这种双向都是「多」的关系,既不能写在菜品那一行(要写几个?),也不能写在标签那一行,只能另外做一张对照表,每行写「第 3 道菜 — 辣」。

比喻真实组件day23 里

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「一本账就是一类东西」——表不等于 API 资源。Day 15 说过「资源不等于数据库表」,Day 18 的响应 DTO 把内部对象和对外字段分开,今天从数据库这头再看一次:TaskResponse 里的 checklist 数组,在数据库里是另一张表 checklist_items 的几行;同一行 users,普通用户和 admin 看到的字段不同;TaskPage 的 nextCursor 根本不是任何表里的列。建模按「数据的事实」拆,API 按「调用方要什么」拼,中间靠仓储和映射函数翻译(Day 27)。
  2. 「写了『见会员名册第 7 号』,账房就会帮你核对」——外键这一列,首先只是一个数字。今天的 REFERENCES 用来写明「这一列指向哪张表」。它确实会拦住一些事(你会在 05 里撞到一次),但它不懂业务:「一个人只能有一个邮箱」「标签名不能重复」「已完成的任务不能改标题」,数据库都不知道,要么靠约束写进去(Day 24),要么靠应用代码。
  3. 「对照表只是一张辅助的小纸条」——中间表是一张正经的表。它有自己的主键,可以有自己的列(比如「什么时候贴的标签、谁贴的」),也会和其他表一样变大、需要索引。ORM 里 task.tags 看起来像一个数组(第 6 节),但底下永远是这张表。
④ 真实术语: entity / attribute / relationship;cardinality(1:1、1:N、N:M);foreign key;junction table / join table / associative entity;ER diagram(crow's foot 鸦脚记法:|| 恰好一个、o{ 零到多个);update / insertion / deletion anomaly;atomic value;repeating group。

📇 概念卡 #2:范式 —— 整理账本的三条规矩

① 一句话大白话: 范式(normal form)是一组「拆表规矩」,目标是每个事实只存一份。它们都建立在函数依赖上:「知道 A 就能确定 B」,记作 A → B。1NF:一个格子里只放一个值,没有 tag1/tag2/tag3 这种重复列。2NF:如果主键由几列组成,其他列必须依赖整个主键,不能只依赖其中一部分。3NF:其他列必须直接依赖主键,不能「经过另一个非主键列」间接依赖。

② 生活类比:整理账本的三条规矩

  • 规矩一(1NF):一格只写一件事。不许在「标签」格里写「辣、招牌、新品」,也不许开「标签一、标签二、标签三」三栏;要几个标签就写几行。
  • 规矩二(2NF):每一栏都要跟着「整个编号」走。如果一行的编号是「订单号 + 标签」,那「菜名」这一栏只跟订单号有关、跟标签无关,就不该写在这里,否则一道菜贴了三个标签,菜名就抄了三遍。
  • 规矩三(3NF):不许转抄。订单上写了会员编号,就不要再写会员电话:电话是「通过会员」才确定的,不是通过订单确定的。要电话,拿编号去会员名册查。

比喻 ↔ 真实 对照

比喻真实概念day23 里的例子
「知道 A 就能确定 B」函数依赖 A → Btask_id → title;owner_email → owner_name
一格一事,没有重复栏1NF:原子值,没有重复组tag1/2/3 → 一个标签一行;checklist 字符串 → checklist_items 表
跟着整个编号走2NF:没有对主键一部分的依赖(部分依赖)tasks_1nf 主键是 (task_id, tag),但 title 只依赖 task_id → 拆出 tasks_2nf + task_tags_2nf
不许转抄3NF:没有经过非主键列的依赖(传递依赖)task_id → owner_email → owner_name → 拆出 users,任务里只留 owner_id
更严格的版本BCNF:每一个能「确定别人」的列组合都必须是候选键点到为止:绝大多数满足 3NF 的业务表也满足 BCNF

⑤ 动手验证:同一份数据,一级一级拆。每一步都用 INSERT … SELECT 从上一步的表搬数据(里面用到的 unnest、string_to_array、split_part 是 PostgreSQL 的数组 / 字符串函数,Day 26 再细讲),然后把宽表的毛病挨个再试一遍。

(← 的说明是我加的。)三类异常全部消失:换邮箱 UPDATE 1;Carol 没有任务也能注册;删掉任务 4,Bob 还在。两个 DELETE 1 分别是「先删任务 4 在 task_tags 里的对照行」和「再删任务 4」。为什么必须先删对照行?我单独试了直接删任务 4:

ERROR:  update or delete on table "tasks" violates foreign key constraint "task_tags_task_id_fkey" on table "task_tags"
DETAIL:  Key (id)=(4) is still referenced from table "task_tags".

外键不许「对照表里还写着第 4 号,第 4 号却没了」。这种情况能不能改成自动连带删除、该不该那样做,是 Day 24 ON DELETE 的主题。

拼回来(06-rebuild-view.sql)

拆开之后,「原来那张宽表的样子」要用 JOIN 拼回来。这里只用最基本的 JOIN … ON(内连接),各种 JOIN 的区别是 Day 25 的内容:

SELECT t.id, t.title, t.done, u.email AS owner_email, u.name AS owner_name
FROM tasks t
JOIN users u ON u.id = t.owner_id
ORDER BY t.id;

结算:同一个事实存了几份

步骤                「Alice 的邮箱」存了几份   「任务 1 的标题」存了几份
宽表 tasks_wide                3                         1
1NF tasks_1nf                5                         2
2NF tasks_2nf                3                         1
3NF users / tasks            1                         1

这张表就是今天的主线:只存一份,就不可能改不全。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「规矩越多越整齐,范式越高越好」——范式是减少冗余的方法,不是分数。3NF(加上偶尔 BCNF)是业务系统的常用目标,再往上的 4NF / 5NF 处理的是更少见的多值依赖,实际中很少专门去追。而且第一步 1NF 反而让冗余变多了(3 份变 5 份),说明这些规矩要一起用、按顺序用,只做一半可能更糟。范式也不排斥「故意冗余」,那是下一张卡的事。
  2. 「账拆开了,查起来一样快」——拆开的代价是读的时候要 JOIN。宽表上一条 SELECT 就能拿到的东西,3NF 下要连两三张表。4 行数据感觉不到,数据量大了 JOIN 的成本会显现,Week 5 用 EXPLAIN 会看到数据库具体怎么连、要花多少代价。范式化优化的是写的正确性,不一定是读的速度。
  3. 「拆对了就不会出错」——数据库不会自动知道你的业务规则。3NF 让「不一致」更难发生,但没有让它不可能:现在 users 里完全可以插两行一样的 alice@example.com,tags 里可以有两个 urgent,tasks.title 可以为空。哪些列必须唯一、不能为空、取值有范围,要用约束告诉数据库(Day 24)。范式回答「怎么拆」,约束回答「什么数据不许进来」。
④ 真实术语: functional dependency(A → B);candidate key / composite key(组合主键,如 (task_id, tag));partial dependency(2NF 消除);transitive dependency(3NF 消除);1NF / 2NF / 3NF / BCNF;normalization / decomposition;lossless join(拆开后能用 JOIN 无损地拼回来,06 就是在验证这一点)。

📇 概念卡 #3:反范式,以及「schema 设计是最难改的决定」

① 一句话大白话: 反范式(denormalization)是故意把某个事实多存一份,用来换读取速度或查询方便,比如在 users 上存一个 tasks_count。代价是:这份副本要有人负责维护,维护漏了就会和真相不一致。另外,表结构一旦上线就很难改:代码可以回滚,数据不能;表里已经有了几亿行,改一列可能要几个小时、要锁表、要双写迁移。所以建模值得多想一会儿。

② 生活类比:订单本上顺手抄一份会员名

前台每天要看「今天每位会员点了几单」,每次都去订单本上数太慢,于是在会员名册上加一栏「累计单数」,每来一单就 +1。查起来飞快,代价是:每个记账的人都要记得顺手 +1,退单要记得 −1;只要有一个新来的伙计忘了,名册上的数就不准了,而且没人会立刻发现。另一边,账本的栏目一旦印好、记了十年,哪天要把「电话」一栏拆成「区号」和「号码」,就得把十年的旧账一页页重抄。

比喻 ↔ 真实 对照

比喻真实做法什么时候值得 / 代价
名册上的「累计单数」计数缓存:users.tasks_count、tasks.checklist_done_count列表页频繁显示计数、读远多于写;代价:每次增删都要同步更新
订单上抄一份会员名冗余列:在 tasks 上存一份 owner_name几乎只读、源头很少改的数据;代价:源头一改要全部同步

失真不会报错,它就静静地待在那里,直到某个用户说「我明明有两个任务,怎么显示一个」。三种维护方式各有代价:应用代码最直观,但所有写入路径(包括别人写的脚本、后台任务)都要记得;触发器让数据库自己维护,但逻辑藏在数据库里,不好看见、不好测试;定期校正简单可靠,但中间有一段时间是错的。很多系统会组合使用:应用里实时维护,再加一个定期任务兜底。不管选哪种,都要把这份冗余登记下来(docs/er-diagram.md 末尾留了「有意的反范式」一节,目前是空的)。

为什么说「schema 设计是最难改的决定」

  • 数据比代码活得久。nest-lab 的代码可能三年后整个重写,换成另一种语言;数据库里的表和数据会被一路继承下去。今天随手起的列名、随手塞进字符串的 checklist,会被以后每一个读这张表的程序依赖。
  • 代码能回滚,数据不能。部署出错可以退回上一个版本;一次把 owner_name 拆出去的数据迁移跑到一半出错,要面对的是「一半的行已经改了」。
  • 线上改表有真实成本。给几亿行的表加一列、改一列的类型、建一个索引,可能锁表、可能跑几个小时;新旧代码同时在线时,两种结构要同时能用。Week 9 会专门学零停机迁移(expand → migrate → contract)。
  • 它和 Day 19 的 API 版本化是同一件事的两面。API 字段是对外契约,改名要发新版本;表结构是对所有读写这个库的程序的契约,改起来只会更难,因为没有 /v2 可以并行。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「抄一份是偷懒,是没设计好」——好的反范式是有意的、有记录的取舍。先范式化,确认某个读取真的慢、真的频繁,再有针对性地加冗余,并写清楚谁维护、怎么校正。「一开始就不拆」和「拆好以后有意加一个计数缓存」是两回事。
  2. 「放进 JSONB 就不用建模了」——JSONB 不是逃避建模的出口。它适合「只跟着这一行读写、不需要被单独查询或关联」的数据。如果你发现自己要查「所有清单里有牛奶的任务」、要统计「每个标签被用了几次」,那它就该是一张表。nest-lab 的 checklist 放 JSONB 还是放 checklist_items 表,Day 26 学完 JSONB 再做最终决定(ER 图目前画的是表)。
  3. 「最难改」不等于「不能改」。把表结构当成不可变的会让人不敢动,反而越堆越乱。正确的态度是:设计时多想一会儿,改动时有方法(迁移脚本、分步上线、数据回填、验证),这些是 Day 27(迁移脚本)和 Week 9 的内容。
④ 真实术语: denormalization;counter cache(计数缓存,Rails 里就叫这个名字);derived / redundant data;trigger;materialized view(PG 内置的「物化结果」);reconciliation job(定期校正任务);schema migration;expand / contract(Week 9);OLTP vs OLAP(业务库倾向范式化,分析库倾向宽表)。

🌍 跨语言对照 + 面试翻译练习

范式本身和语言无关:3NF 在 PostgreSQL、SQL Server、MySQL 里一模一样。不同的是 ORM 怎么把「关系」表达成代码。下表都是同一个模型:用户 1:N 任务,任务 N:M 标签。

命题Node.js / TS(Prisma)C# / EF CoreJava / JPA(Hibernate)Go
1:N schema 里 owner User @relation(fields: [ownerId], references: [id]),另一边 tasks Task[] 导航属性 User.Tasks / Task.Owner,配置 HasMany(u => u.Tasks).WithOne(t => t.Owner).HasForeignKey(t => t.OwnerId) @ManyToOne @JoinColumn(name = "owner_id") 在 Task 上,@OneToMany(mappedBy = "owner") 在 User 上 结构体字段 OwnerID int,关联数据自己查(GORM 也有 has many / belongs to)
N:M 两边各写 tags Tag[] / tasks Task[],Prisma 自动建一张隐式中间表(名字形如 _TagToTask);要在中间表上加列就改成显式模型 两边各一个集合导航属性,EF Core 5+ 自动建中间表(skip navigation);要加列就显式写中间实体 @ManyToMany + @JoinTable(name = "task_tags", joinColumns = …, inverseJoinColumns = …) 手写中间表和查询;GORM 用 gorm:"many2many:task_tags"
代码里看到的样子 task.tags 看起来是一个数组 / 集合。但底下仍然是 task_tags 中间表:往集合里加一个元素,ORM 会生成一条 INSERT INTO task_tags;读 task.tags,ORM 会生成一次 JOIN 或额外查询(这就是 Week 7 要讲的 N+1 问题的来源)。

🎤 面试翻译练习: 面试官问:"What is third normal form? When would you deliberately denormalize?"(或者:「什么是第三范式?什么时候你会故意反范式?」)你可以答:
"范式的目标是每个事实只存一份,避免更新、插入、删除三类异常。1NF 要求每个字段是原子值、没有重复的列组;2NF 要求非主键列依赖整个主键,不能只依赖组合主键的一部分;3NF 要求非主键列直接依赖主键,不能通过另一个非主键列传递依赖,比如任务表里存了负责人邮箱又存负责人姓名,姓名其实由邮箱决定,就应该把负责人拆成用户表,任务里只放 owner_id。多对多关系一定要有中间表。业务库我默认做到 3NF,然后在有证据的时候有针对性地反范式:比如列表页频繁显示的计数,用计数缓存;只读的报表用宽表或物化视图;不需要单独查询的附属数据可以放 JSONB。反范式的代价是要自己维护一致性,我会让应用在同一个事务里更新,再加一个定期校正任务兜底,并在设计文档里登记这份冗余。"

✅ 总结与自测

今天带走的 4 句话

  1. 把几个实体塞进一张表,同一个事实就会存好几份,于是有三类异常:改不全(更新异常)、放不进(插入异常)、删多了(删除异常)。
  2. 关系只有三种:1:1(常合并)、1:N(外键放在「多」的一方)、N:M(必须有中间表,ORM 里看起来像数组,底下仍是中间表)。表不等于 API 资源,建模按事实拆,API 按调用方需要拼。
  3. 范式建立在函数依赖上:1NF 一格一值、没有重复列组;2NF 不能只依赖组合主键的一部分;3NF 不能经过非主键列间接依赖。目标是每个事实只存一份;代价是读的时候要 JOIN;它不替你检查业务规则(那是 Day 24 的约束)。
  4. 反范式是有意、有记录的取舍(计数缓存、冗余列、报表宽表、JSONB),代价是要自己维护一致性;schema 是最难改的决定:数据比代码活得久,代码能回滚,数据不能。
