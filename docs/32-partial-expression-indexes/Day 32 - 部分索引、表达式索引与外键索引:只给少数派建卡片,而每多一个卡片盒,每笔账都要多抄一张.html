🖥️ 前端翻译: 你一定见过这种代码:为了列表页快,给每种筛选状态都建了一个缓存(useMemo、Redux 里的 selector 缓存、按 key 分的 SWR 缓存)。读的时候很爽;可是数据一改,就要让一堆缓存失效、重算。缓存越多,写越慢,还容易漏掉某一个。数据库的索引就是一种由数据库自己负责同步的缓存:它从不漏,但每一份都要在每次写入时付钱。

📇 概念卡 #1:部分索引与表达式索引 —— 只给少数派建卡片,卡片上写的是加工过的值

① 一句话大白话: 部分索引:建索引时加一个 WHERE,只给满足条件的行建条目(比如只收未完成的任务)。索引小很多,但只有当查询的条件让数据库看得出「要的行都在这个子集里」时,它才会被用。表达式索引:索引里存的不是列的原值,而是一个表达式的结果(比如 lower(email))。查询必须写同一个表达式才能用上;而且这个表达式必须是 IMMUTABLE 的,也就是同样的输入永远得到同样的输出,不受时区之类设置的影响。

② 生活类比:只给「还没完成」的单子建卡片盒,卡片上写的是小写会员号

账房发现:九成的单子早就完成了,没人再问;天天被问的是「还没完成的单子里最新的是哪些」。于是新建一个小卡片盒,只给没完成的单子建卡片。有人问「没完成的单子」,直接翻小盒子;有人问「完成了的单子」,小盒子里根本没有,只能去翻账本。

另一个卡片盒按邮箱排,但会员登记时大小写写得乱七八糟。账房干脆在卡片上统一抄成小写。问的人也得先把邮箱转成小写再来问;要是拿着原样的「User42@Example.com」来问,卡片盒里没有这种写法。还有一条规矩:卡片上抄的东西必须是谁抄都一样的。「这单是哪一天下的」就不行,北京的伙计和伦敦的伙计会抄出不同的日子,除非卡片上写明「按伦敦时间」。

⑤ 动手验证 A:部分索引能被哪些写法用上。✍️ 预测(先写再运行):只留部分索引 (created_at) WHERE done = false,下面四种 WHERE 各会不会用它?真实结果(02-partial.sql,只保留关键行):

          索引          |  大小   | 只收哪些行(WHERE)
------------------------+---------+-------------------
 tasks_done_created_idx | 30 MB   |

=== ④ WHERE done IS NOT TRUE(列是 NOT NULL,意思其实也一样)

  • 大小:部分索引只收 10 万个条目,2208 kB;完整的 (done, created_at) 收全部 100 万个,30 MB,差 14 倍。
  • 速度:这个查询两种索引都很快。各跑 3 次、脚本跑 3 遍:完整索引 0.009 – 0.100 ms,部分索引 0.007 – 0.130 ms,基本一样。部分索引的好处不在这个查询更快,而在于索引小(更容易整个留在内存里),以及 90% 的写入(插入已完成的任务)根本不用碰它。
  • 能不能用:数据库在做计划时做一个小小的逻辑证明:「查询的 WHERE 成立 ⇒ 索引的 WHERE 成立」。done = false 和 NOT done 能证明出来;done IS NOT TRUE 证明不出来,虽然因为列是 NOT NULL,它的意思其实一样(这个证明器不会去看列上的约束)。

⑤ 动手验证 B:参数化查询 done = $1。nest-lab 的 SQL 都是参数化的。✍️ 预测:WHERE done = $1 时,数据库做计划的那一刻还不知道 $1 是不是 false,它还能用部分索引吗?真实结果:

PREPARE open_latest(boolean) AS SELECT … WHERE done = $1 ORDER BY created_at DESC LIMIT 20;
 plan_cache_mode
-----------------
 auto
EXPLAIN EXECUTE open_latest(false);         -- 第 1 次,和执行 6 次之后都一样
   ->  Index Scan Backward using tasks_open_created_idx on tasks
    name     | 用通用计划的次数 | 用定制计划的次数
-------------+------------------+------------------
 open_latest |                0 |                8
SET plan_cache_mode = force_generic_plan;   -- 强制用通用计划
   ->  Sort
         ->  Seq Scan on tasks
               Filter: (done = $1)
EXPLAIN (GENERIC_PLAN) SELECT … WHERE done = $1 …   -- PostgreSQL 16 新增的写法,结果相同
         ->  Seq Scan on tasks
               Filter: (done = $1)

-- 观察脚本:用 nest-lab 的 pg 驱动发 EXPLAIN … WHERE done = $1,参数 [false]
  Limit
    ->  Index Scan Backward using b_part on tasks

结论要说准确:

  • 定制计划(custom plan):代入这一次的实际参数值再做计划,看得出 $1 = false,能用部分索引。通用计划(generic plan):不看参数值、做一份以后反复用的计划,它必须对 $1 = true 也正确,所以永远不能用部分索引。
  • 默认的 plan_cache_mode = auto:前 5 次执行用定制计划,之后比较通用计划的估算代价;这里通用计划要全表扫描,代价高得多,所以 8 次都还是定制计划。但这是代价比较的结果,不是保证:换一个部分索引优势不明显的查询,第 6 次以后可能就换成通用计划了。
  • nest-lab 用的 pg 驱动,在你不给查询起 name 时,每次都把 SQL 和参数一起发过去,数据库就带着实际值做计划(上面最后一段的实测)。给查询起了 name(或者用连接池 / ORM 的预编译缓存)时,才会进入「前 5 次定制、之后可能通用」的规则。
  • 稳妥的写法:要用部分索引的查询,把条件写成常量(WHERE done = false),而不是 done = $1。Day 34 给 nest-lab 加 done 的索引时要考虑这一点。

⑤ 动手验证 C:部分唯一索引。两个常见用法:「每个会员同时只能有一个正在计时的任务」,以及「软删除之后同一个邮箱可以重新注册」。✍️ 预测:下面的第 2 条和第 6 条 INSERT 会怎样?

CREATE UNIQUE INDEX timers_one_running_per_user ON timers (user_id) WHERE stopped_at IS NULL;
INSERT INTO timers (user_id, task_id) VALUES (1, 101);      -- INSERT 0 1
INSERT INTO timers (user_id, task_id) VALUES (1, 102);
ERROR:  duplicate key value violates unique constraint "timers_one_running_per_user"
DETAIL:  Key (user_id)=(1) already exists.
UPDATE timers SET stopped_at = now() WHERE user_id = 1 AND stopped_at IS NULL;
INSERT INTO timers (user_id, task_id) VALUES (1, 102);      -- INSERT 0 1:停掉之后就可以了

CREATE UNIQUE INDEX accounts_email_active_key ON accounts (lower(email)) WHERE deleted_at IS NULL;
INSERT … ('Alice@Example.com');                             -- INSERT 0 1
INSERT … ('alice@example.com');
ERROR:  duplicate key value violates unique constraint "accounts_email_active_key"
DETAIL:  Key (lower(email))=(alice@example.com) already exists.
UPDATE accounts SET deleted_at = now() WHERE lower(email) = 'alice@example.com';
INSERT … ('alice@example.com');                             -- INSERT 0 1:软删除之后可以重新注册
INSERT … ('ALICE@example.com') ON CONFLICT (lower(email)) WHERE deleted_at IS NULL DO NOTHING;   -- INSERT 0 0
 id |       email       | 已软删除
----+-------------------+----------
  1 | Alice@Example.com | t
  3 | alice@example.com | f

规则「只在某个子集里唯一」用普通的 UNIQUE 约束写不出来,用部分唯一索引一行就够了,而且它在数据库里兜底,应用代码的并发问题(两个请求同时检查「有没有正在计时的」)也挡得住。ON CONFLICT 要写出同样的表达式和 WHERE,数据库才找得到这个索引。顺便注意 id 跳过了 2:失败的 INSERT 已经从自增序列里取走了一个号,序列不会回滚(Day 24 讲过)。

  • timestamptz 存的是一个绝对时刻;「它是哪一天」取决于会话的 timezone 设置。同一个时刻,UTC 下是 6 月 1 日,上海是 6 月 2 日。如果允许按 created_at::date 建索引,改一下时区设置,索引里存的日子就全错了。所以 date(timestamptz)、两个参数的 date_trunc 都只是 STABLE(一条语句之内不变),不是 IMMUTABLE。
  • 修法是把时区写进表达式:created_at AT TIME ZONE 'UTC'(timezone(text, timestamptz),IMMUTABLE),或者 PostgreSQL 12 起的三参数 date_trunc('day', created_at, 'UTC')。查询必须写一模一样的表达式:各跑 3 次、脚本跑 3 遍,同一个表达式 0.099 – 0.331 ms,写成 created_at::date 66.0 – 102.3 ms。
  • ⑥ 是更常用的做法:不建表达式索引,用普通的 created_at 索引加一个范围条件,把「哪一天」换算成两个时刻(这一步在应用里按用户的时区算好)。一个普通索引能服务任意时区、任意范围的查询。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「小盒子里有的,账房就会去小盒子找」——要让数据库看得出来才行。数据库靠计划阶段的一个简单逻辑证明来判断,不会去理解你的意思:done IS NOT TRUE 和 done = false 在这张表上意思一样,它也用不上;通用计划里的 done = $1 永远用不上。写部分索引时,要同时约定好查询的写法。
  2. 「卡片上抄成小写,问的人自然会转小写」——表达式必须逐字一致。lower(email) 的索引帮不了 email ILIKE …、upper(email) = …,也帮不了 lower(trim(email))。ORM 生成的 SQL 更要用 EXPLAIN 确认。
  3. 「小盒子总比大盒子好」——部分索引只服务那一个子集。如果「已完成的任务」也经常要按时间查,你还得另建索引,两个加起来不一定比一个完整索引省。部分索引最适合「少数派、经常被问、条件固定」的子集:未完成的、未删除的、待处理的。
④ 真实术语: partial index(索引谓词 indpred);predicate implication(查询条件推出索引条件);custom plan / generic plan、plan_cache_mode、EXPLAIN (GENERIC_PLAN)(PostgreSQL 16 起);partial unique index;expression index / functional index;function volatility:IMMUTABLE / STABLE / VOLATILE;sargable(Day 31)。

📇 概念卡 #2:外键列的索引 —— 注销一个会员,要翻遍整本订单本

① 一句话大白话: 外键约束是双向的:往子表插一行时,要去父表确认「这个会员存在」(父表的主键有索引,很快);删除或修改父表的一行时,要去子表找「还有没有人引用它」(RESTRICT 就拒绝,CASCADE 就跟着删)。PostgreSQL 会给主键、唯一约束自动建索引,但不会给外键列建索引。外键列上没有索引,每删一个父行,子表就要全表扫描一次。

② 生活类比:注销会员时翻订单本

会员花名册按会员号排好,查「5000 号会员存在吗」一翻就到。可是注销一个会员时,规矩是「他的订单要一起作废」,订单本却是按下单顺序记的。账房只能从第一页翻到最后一页,找出这个会员的所有订单;哪怕这个会员一单都没下过,也得翻完整本才敢说「没有」。注销 10 个会员,就翻 10 遍。给订单本另做一个「按会员号排的卡片盒」,注销时一翻就知道他有哪些订单。

📇 概念卡 #3:索引的代价 —— 每记一笔账,所有卡片盒都要补一张卡

① 一句话大白话: 每个索引都是一份要同步维护的副本:每插入一行,每个索引都要插入一个条目;每次 UPDATE 写出新版本时,通常每个索引也都要插入一个新条目。这些改动都要先写进 WAL(预写日志)。表有几个索引,写入就慢几分、日志就多几分,这叫写放大。有一种例外叫 HOT 更新:改的列不在任何索引里,而且新版本能放进同一页,这时索引一个都不用动。最后,数据库会记下每个索引被用了几次,没人用的索引只是白付成本。

② 生活类比:记一笔账,补 N 张卡

账房每记一笔新账,伙计们要跑遍每一个卡片盒,各插一张新卡;每个卡片盒的每次改动还要先抄进「流水日记」(万一失火,靠它恢复;分店也靠它同步)。卡片盒从 1 个变成 6 个,记一笔账的工夫就变成好几倍。

改账时有一个省事的情况:改的那一栏(比如「完成了没有」)没有任何卡片盒抄过,而且同一页账上还有空位,可以把新写的那一行就写在旁边,并在旧的那一行上标一句「看旁边」。卡片盒上记的页码还对,所以一张卡都不用动。这就是 HOT。账本每页如果都写得满满的,新的那一行只能写到别的页去,卡片盒上的页码就全要改,所以有的账房会故意每页留一点空(fillfactor)。

月底盘点:哪个卡片盒一次都没人翻过?它每天照样在吃伙计的工夫。

③ ⚠️ 这个比喻在哪里会骗你:

  2. 「盘点时没人翻的盒子就可以扔」——idx_scan = 0 不一定等于没用。主键和唯一索引靠存在本身保证约束;低频的月报、年报、故障时才跑的运维查询、只在备库上跑的查询,在统计里可能是 0;统计还可能刚被重置过。先查清楚,再在低峰期删(DROP INDEX CONCURRENTLY),必要时保留建索引的语句以便恢复。
  3. 「每页留空就能一直 HOT」——HOT 有前提。改到任何一个索引里的列(包括 INCLUDE 列、部分索引的条件列、表达式索引用到的列)都不能 HOT;同一页的空位用完了也不行。fillfactor 是用空间换 HOT 的机会,不是开关。

✅ 总结与自测

今天带走的 4 句话

  1. 部分索引只收满足 WHERE 的行:WHERE done = false 的索引 2208 kB,完整的 30 MB,查询一样快。查询条件必须让数据库推得出索引条件:done = false、NOT done 可以;done IS NOT TRUE、通用计划里的 done = $1 不行(定制计划和 nest-lab 的不具名查询可以)。部分唯一索引能表达「只在子集里唯一」。
  2. 表达式索引要求查询写同一个表达式:lower(email) = … 0.003–0.083 ms,ILIKE 40.6–68.0 ms。表达式里只能用 IMMUTABLE 函数:created_at::date 依赖时区,会报错;把时区写死(AT TIME ZONE 'UTC'),或者干脆用普通索引加范围条件。
  3. PostgreSQL 不给外键列自动建索引:删除一个父行时,子表全表扫描,只体现在 Trigger for constraint 那一行(32–58 ms → 0.06–0.66 ms;10 个父行 401–500 ms → 0.14–3.9 ms)。复合索引只要以外键列打头也算数。nest-lab 的 checklist_items.task_id 已被主键覆盖。
  4. 每个索引都在每次写入时收费:20 万行 INSERT,0 → 6 个索引,约 0.2 秒 → 2 秒,WAL 18.7 MB → 122.7 MB。改的列不在任何索引里、页里有空位时才能 HOT(fillfactor 90 时 10000 / 10000,页满或者改到索引列、INCLUDE 列时都是 0)。用 pg_stat_user_indexes 找 idx_scan = 0 和重复的索引,但主键、唯一约束、低频查询要排除。
