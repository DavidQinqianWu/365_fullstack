📇 概念卡 #1:连接为什么贵、为什么不是越多越快 —— 账房里只有几张桌子

① 一句话大白话: PostgreSQL 每接一个连接,就专门开一个进程伺候它:要内存、要认证、要调度。连接数有硬上限(max_connections,默认 100),超了直接拒绝。而且干活的是 CPU,核心就那么几个:连接开得比核心多很多时,总吞吐不会再涨,每条查询只是排更久的队。

② 生活类比:账房里只有几张桌子

延续 Day 27 的比喻:连接 = 账房里的伙计,应用连接池 = 每家分店门口自己留着的几位伙计。

  • 账房只有 4 张桌子(4 个 CPU 核心)。伙计请得再多,同一时刻也只有 4 个人在写账,其他人站着等桌子。
  • 账房的花名册最多登记 100 个伙计(max_connections),其中 3 个名额留给掌柜(超级用户)。第 98 个来报到的伙计会被门卫挡回去。
  • 每家分店都觉得「我留 20 个伙计很合理」,6 家分店加起来就是 120 个,花名册不够。

③ 类比的边界 ⚠️

  • 站着等的伙计也要钱:每个空闲连接在 PostgreSQL 里仍然是一个进程,占内存;查询需要排序、哈希时,每个进程还能各自再用 work_mem(本机 4 MB),连接越多,最坏情况下的内存越大。
  • 不全是 CPU:查询在等磁盘、等锁(Day 39)、等网络时不占桌子,这时多几个连接确实能提高吞吐。所以公式只是起点:HikariCP 文档引用的 PostgreSQL 社区经验值是 核心数 × 2 + 有效磁盘数,本机约 9–10。
  • 超过上限是拒绝,不是排队:应用连接池满了会在应用里排队(Day 27 设了最多等 3 秒),但 PostgreSQL 的 max_connections 满了是直接报错。

📇 概念卡 #2:PgBouncer —— 总店门口的叫号台

① 一句话大白话: PgBouncer 是夹在应用和 PostgreSQL 中间的一个小程序。应用以为自己连的是数据库,其实连的是 PgBouncer;PgBouncer 自己只向 PostgreSQL 开少量连接(比如 20 个),把几百个应用连接轮流「接」到这 20 个上。transaction 模式下,一个事务结束,这个数据库连接就让给下一个人。

② 生活类比:总店门口的叫号台

6 家分店的伙计不再直接进账房,而是先到总店门口的叫号台取号。账房里始终只有 20 位总店伙计(default_pool_size)。几百位客人在门口排队(max_client_conn),叫到号的客人交给一位总店伙计办事。

  • transaction 模式:客人办完一张作业单(一个事务)就把伙计让出来,下一张单子可能换一位伙计。
  • session 模式:客人从进门到离开一直霸占同一位伙计,哪怕他坐着喝茶什么都不办。
  • statement 模式:每说一句话就换一位伙计,所以「一张作业单分好几步办」根本做不到。

③ 类比的边界 ⚠️

  • 叫号台不让账办得更快:PgBouncer 不加速任何查询。它只是让连接数可控,而且免掉了「每个应用连接都去 PostgreSQL 那边 fork 一个进程」的开销。账房还是那 4 张桌子。
  • 叫号台自己也是一个关口:它是一个单线程的程序(一个进程只用一个 CPU 核心;要用多核得开多个实例,比如 so_reuseport),也会挂、也要监控、也要高可用。连接多了排队时间会长(SHOW POOLS 的 cl_waiting、SHOW STATS 的等待时间)。
  • 数据库看到的「会话」不再等于应用的「连接」:transaction 模式下,应用的同一个连接,前后两个事务可能落在两个不同的后端进程上。凡是「记在会话上」的东西都会出问题,这是第 5 节的全部内容。
  • 和 HTTP/2 不一样:HTTP/2 是在一个连接里同时跑多个请求;PgBouncer 不会让一个服务端连接同时跑两个事务,它只是让多个客户端轮流用这些服务端连接。PostgreSQL 的协议本身也不支持一个连接上并发执行多个查询。

📇 概念卡 #3:transaction 模式的坑 —— 换了伙计,他不记得你喜欢红笔

① 一句话大白话: transaction 模式下,你的这个事务和下一个事务可能由两个不同的数据库进程处理。所以凡是「设在会话上、跨事务留着」的东西都靠不住:你设的 SET 下一次可能不见了,还可能出现在别人那里;会话级的咨询锁、临时表、具名预备语句也一样。办法只有一个:要么只在事务里设(SET LOCAL、pg_advisory_xact_lock),要么让 PgBouncer 替你记(max_prepared_statements)。

② 生活类比:「记住我喜欢用红笔」

客人对伙计说:「记住,我喜欢用红笔」(SET statement_timeout = '100ms')。这张作业单办完,伙计回到池子里。下一张作业单,叫号台给客人派了另一位伙计,他根本不知道红笔的事。更糟的是,原来那位伙计还记着「用红笔」,接下来他接待的陌生客人也被他用红笔记了账。

值班牌(Day 39 的咨询锁)也一样:客人让伙计挂上值班牌,作业单办完客人走了,牌子还挂在那位伙计身上。下一位客人分到这位伙计,问「我能挂值班牌吗?」,伙计说「能,我已经挂着了」。

③ 类比的边界 ⚠️

  • 不是一定串,而是可能串:能不能分到同一个服务端连接取决于当时谁闲着。测试里经常「碰巧没事」,上线后偶尔出问题。今天用只有 2 个服务端连接的 nest_lab_tiny,让现象每次都出现。
  • 事务内是安全的:一个事务从 BEGIN 到 COMMIT 一直在同一个服务端连接上。nest-lab 的 transaction()、悲观锁都靠这一点。
  • PgBouncer 会替你记一部分:client_encoding、TimeZone、application_name 等少数参数是「被跟踪的」,换服务端连接时 PgBouncer 自动补上。其他参数不跟踪。

⑤ 动手验证 A:SET 和咨询锁。✍️ 预测:A 执行 SET statement_timeout = '100ms',B 开一个事务查 statement_timeout,A 自己再查,各看到什么?A 用会话级咨询锁锁住 41,B 再 pg_try_advisory_lock(41) 得到什么?真实结果(第 5 幕,4 遍一致,只有 pid 不同):

  ① SET 不带 LOCAL

    B:BEGIN; 查 → pid 4185,statement_timeout = 100ms  ← A 设的值串到了 B 这里
    A:再查 → pid 4184,statement_timeout = 0  ← A 自己设的值「消失」了(换了一个服务端连接)
  修法:SET LOCAL,只在事务里生效
    C:BEGIN; SET LOCAL statement_timeout = '100ms' → pid 4187,100ms;SELECT pg_sleep(0.3) → ERROR 57014 canceling statement due to statement timeout;ROLLBACK
    D:BEGIN; 查 → pid 4187,statement_timeout = 0(同一个服务端连接,但设置已随事务结束撤销)
  ② 会话级咨询锁 pg_advisory_lock(Day 39 的「值班牌」)

    B:BEGIN; SELECT pg_try_advisory_lock(41) → true(pid 4189)  ← B「继承」了 A 的锁
    A:SELECT pg_advisory_unlock(41) → false(pid 4188),WARNING you don't own a lock of type ExclusiveLock
    B COMMIT 之后,直连 PostgreSQL 查 pg_locks:咨询锁 41 仍然被 pid 4189 持有
  修法:BEGIN; SELECT pg_advisory_xact_lock(41); … COMMIT → 事务中 pg_locks 里 1 个,COMMIT 后 0 个
  ③ 临时表(另一种会话级状态)
    A:CREATE TEMP TABLE scratch(在 pid 4192 上);B 开着事务时 A 再查 scratch → ERROR 42P01 relation "scratch" does not exist

咨询锁那段最危险:B 以为自己拿到了一把别人没有的锁,其实是「继承」了 A 的;A 想解锁却解不掉;锁最后挂在一个池子里的服务端连接上,没有任何客户端知道它的存在,直到这个连接被关掉。Day 39 说「会话级的在连接池里会泄漏」,这就是现场。

⑤ 动手验证 B:预备语句。✍️ 预测:pg 驱动执行一条具名查询 { name: 'add_one', text: … }。第一次会发 Parse(准备)+ Execute;驱动记住「这个连接上准备过了」,第二次只发 Bind + Execute。经过 transaction 模式的 PgBouncer,第二次会怎样?真实结果(第 6 幕,4 遍一致):

  max_prepared_statements = 0(1.22 的默认):
    A 第 1 次执行具名语句 add_one → ok(r = 2)
    B 开着事务占住那个连接;A 第 2 次执行 → ERROR 26000 prepared statement "add_one" does not exist
    新客户端 C 第 1 次执行同名语句(分到的服务端连接上已经有 A 留下的 add_one)→ ERROR 42P05 prepared statement "add_one" already exists
    不具名的参数化查询(nest-lab 的写法)→ ok(r = 2)
  max_prepared_statements = 100:
    以上四种全部 ok(r = 2)

开了 max_prepared_statements 之后,PgBouncer 自己记住每个客户端准备过哪些语句;换到别的服务端连接时,它替客户端补一次 Parse(在服务端用它自己起的名字,所以也不会和别人重名)。它只管协议层的预备语句,SQL 里的 PREPARE / EXECUTE 它不管。PgBouncer 1.24 起这个设置的默认值改成了 200。

nest-lab 只用不具名的参数化查询(Day 27),开不开都兼容。Day 32 也看到了它的另一面:具名预备语句执行几次之后可能换成「通用计划」(done = $1 用不上部分索引),不具名的每次都按真实参数做「定制计划」。

⏱️ 超时三件套:账房墙上的三条规矩

账房墙上贴着三条规矩:「一件事最多办多久」、「排队等镇纸最多等多久」、「拿着作业单发呆最多多久」。它们防的是三种不同的事故,都在把有限的连接从坏请求手里抢回来。

规矩设置防什么实测(第 7 幕)
一件事最多办多久statement_timeout一条失控的查询(漏了索引、被人拼了个超大的 IN)长时间占着连接和 CPU200ms:pg_sleep(1) 在 202 ms 时报 57014 canceling statement due to statement timeout
排队等镇纸最多等多久lock_timeout被长事务、DDL 锁队列(Day 39)挡住时无限排队300ms:306–307 ms 报 55P03 canceling statement due to lock timeout
拿着作业单发呆最多多久idle_in_transaction_session_timeout代码 BEGIN 之后去调了一个慢接口、或者忘了 COMMIT:锁一直拿着、VACUUM 被挡住(Day 38)、连接被占着(经过 PgBouncer 时连服务端连接也占着)500ms:发呆 800 ms 后,服务器直接断开连接:FATAL 25P03 terminating connection due to idle-in-transaction timeout

连接被断开之后,nest-lab 的连接池怎么恢复

  idle_in_transaction_session_timeout = 500ms:BEGIN 之后发呆 800 ms,再发 SELECT 1 →
      连接上收到的错误事件:FATAL 25P03 terminating connection due to idle-in-transaction timeout
      SELECT 1 本身:ERROR Client has encountered a connection error and is not queryable
      release(err) 之后:池里剩 0 个连接;下一个 pool.query 用的是 pid 4200(原来是 4199)→ 换了一个新连接,恢复正常
      release() 之后:  池里剩 0 个连接;下一个 pool.query 用的是 pid 4201(原来是 4200)→ 换了一个新连接,恢复正常

服务器发来的 FATAL 会作为连接上的 error 事件出现,不监听就会让 Node 进程崩溃(脚本里 pool.on('error')、client.on('error') 都监听了)。之后这个连接不能再查询,pg-pool 3.x 不管 release() 还是 release(err) 都会把它丢掉,下一个请求自动换新连接。Day 36 的 release(err) 照样有用:它管的是「看起来还活着、但状态不可信」的连接,那种 pg-pool 自己判断不了。

设在哪里:后面的覆盖前面的

    ALTER DATABASE … SET statement_timeout = '30s'               → 新连接看到 30000 ms(source = database)
    再 ALTER ROLE … IN DATABASE … SET statement_timeout = '5s'   → 新连接看到 5000 ms(source = database user)
    再加连接参数 options=-c statement_timeout=1s                  → 1000 ms(source = client)
    再在事务里 SET LOCAL statement_timeout = '200ms'               → 200 ms(source = session),COMMIT 后撤销
    经过 PgBouncer(新的服务端连接)                              → 5000 ms(source = database user):角色级设置对 PgBouncer 同样有效
    已恢复:pg_db_role_setting 里还剩 0 条设置

这几行是脚本临时设的,做完立刻 RESET,最后确认 pg_db_role_setting 为空。经过 PgBouncer 时,连接参数 options 过不去(第 7 节),会话级 SET 会串(第 5 节)。所以给应用定超时,最合适的地方是应用专用角色:ALTER ROLE … IN DATABASE … SET。

给 nest-lab 的建议(详见 nest-lab/docs/db-timeouts.md):statement_timeout = 5s、lock_timeout = 2s、idle_in_transaction_session_timeout = 15s,设在一个应用专用角色上。今天没有写进代码,也没有设在 nest_lab 角色上:这个角色同时用于 db:reset、灌 30 万行数据、各天的观察脚本(故意 pg_sleep),5 秒的限制会让它们失败。这也说明了为什么生产环境要把「应用角色」和「迁移角色」分开。

⚠️ 超时会让请求失败,应用要接得住:57014 / 55P03 目前在 nest-lab 里会变成 500;读请求可以重试一次,写请求要看幂等性(Day 15)。超时是保护数据库的最后一道闸,不是性能优化。

✅ 总结与自测

今天带走的 4 句话

  1. 连接贵,而且多了不快:一个连接一个进程(约 16 MB RSS,建一个 6–8 ms);池子复用比每次新建快 40 倍以上。4 核机器上 5 个并发连接就到吞吐顶了(约 850–930 条/秒),80 个时吞吐不变、p50 延迟涨到约 90 ms。
  2. 多副本要算总账:6 × 20 直连,24–25 个请求直接 53300 too many clients。PgBouncer transaction 模式下,同样 120 个客户端 600 条查询全部成功,PostgreSQL 里始终只有 20 个后端进程;session 模式几乎不省连接;statement 模式开不了事务。
  3. transaction 模式下会话状态不可靠:SET 会消失也会串,会话级咨询锁会被「继承」并泄漏,临时表找不到,具名预备语句报 26000 / 42P05。修法:SET LOCAL、pg_advisory_xact_lock、max_prepared_statements。连接参数 options 也过不去,nest-lab 因此加了 DB_STARTUP_SEARCH_PATH 和启动时的 schema 核对。
  4. 超时三件套:statement_timeout(57014)、lock_timeout(55P03)、idle_in_transaction_session_timeout(25P03,直接断开连接,池子自动换新的)。设在应用专用角色上,直连和经过 PgBouncer 都生效。
