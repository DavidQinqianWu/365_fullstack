任务

在 src/42-week6-review/request-lifecycle.md 里,用文字或 mermaid(推荐 sequenceDiagram)画出下面这个过程。Nest 管线可以简写成一两行,重点画「连接 → 事务 → 快照 / 行版本 → 行锁 → 写入 → 清理」。每一站标注两个编号:它是 Week 6 哪一天学的(Day 36–41),以及它建在 Week 1–5 的哪个机制上。

场景(主线)

# nest-lab:TASKS_STORAGE=postgres,DATABASE_URL 指向 PgBouncer(6432,transaction 模式),DB_STARTUP_SEARCH_PATH=false

要覆盖这些环节(顺序你自己排):

  • nest-lab 的连接池借连接、PgBouncer 给这次事务分配服务端连接;「读 → 判断 → 写」三步一共借了几次连接,会不会落在不同的服务端连接上
  • 真正发到 PostgreSQL 的 SQL 按顺序是哪几条,哪几条在同一个事务里。先别假设「乐观锁就是一条 UPDATE、不需要 BEGIN」。凭记忆想一想:nest-lab 的 repo.update 有没有包 transaction()?为什么?

为什么这张图值 25 分钟

前几周的图回答「请求经过哪些站」「数据怎么可靠地写进去」「同一条 SQL 为什么有时快有时慢」;今天这张图回答「两个人同时改,结果为什么还对;如果不对,错在哪一站」。面试里问「怎么防止丢失更新」,能从「两个请求在哪里相遇、行锁怎么排队、后到者用哪个版本重新判断、旧版本什么时候被清掉、长事务会把这一切卡住」一路讲下来的人,说明他真的在两个窗口里复现过,而不是只背过「加个 version」。

这张图在 MySQL 和 SQL Server 里大体一样:都有行锁、都有某种多版本(InnoDB 的 undo log、SQL Server 的 tempdb 版本存储),乐观锁的写法也一样。差别在细节:默认隔离级别、旧版本存在哪里、谁负责清理。你画的是「一个有 MVCC 和行锁的数据库怎么处理并发写」,不是「PostgreSQL 的实现细节」。
