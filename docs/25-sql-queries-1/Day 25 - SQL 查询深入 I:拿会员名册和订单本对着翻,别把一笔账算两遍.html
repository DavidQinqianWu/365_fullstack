🖥️ 前端翻译: 这些问题你在前端都手写过:users.map(u => ({ ...u, tasks: tasks.filter(t => t.ownerId === u.id) })) 就是一次 JOIN;tasks.reduce(…) 是聚合;lodash 的 groupBy 是 GROUP BY。区别在于:前端得先把所有用户和所有任务都拉到浏览器里,再在 JS 里两层循环配对;数据库是在数据旁边做,只把结果传给你,而且它会挑一种比两层循环快得多的方法去配对(Week 5 看它到底怎么做)。今天你会发现,SQL 里的坑和 JS 里的坑也是同一批:配对时漏了没有任务的人、求和时把同一笔账加了两遍、undefined 和 0 搞混。

📇 概念卡 #1:JOIN —— 拿名册和订单本按会员号对着翻

① 一句话大白话: JOIN 就是按一个条件,把两张表的行两两配对,每配上一对就拼成结果里的一行。INNER JOIN 只留配上的;LEFT JOIN 左边的每一行都留,配不上的右边补 NULL;CROSS JOIN 不要条件,每一行配每一行;自连接是同一张表和自己配。只想问「对面有没有」、不需要对面的行时,用 EXISTS / NOT EXISTS(半连接 / 反连接)。

② 生活类比:会员名册和订单本对着翻

左手拿会员名册,右手拿订单本,按「会员号」一条条对。INNER:只抄下两本里都有的配对,没下过单的会员不抄。LEFT:名册上的每个人都要列出来,没订单的就在订单那栏写「无」。CROSS:不管会员号,每个会员和每张订单都配一遍,3 个会员 5 张订单就是 15 行,大多毫无意义。自连接:员工名册里每个人旁边写着「经理是第几号」,拿同一本名册再翻一次,找到经理的名字。EXISTS:只问一句「这个会员有没有下过单」,不抄订单内容,有就打个勾。

比喻SQL今天的例子

应该有 4 个,NOT IN 一个都没查出来。x NOT IN (2, 4, NULL) 展开就是 x <> 2 AND x <> 4 AND x <> NULL,而 x <> NULL 永远是「不知道」;AND 上一个「不知道」,整个条件最好也只能是「不知道」,WHERE 把它当 false。所以子查询结果里只要混进一个 NULL,NOT IN 就返回空,而且不报任何错。规则:反连接一律用 NOT EXISTS。IN(正向的)没有这个问题,但为了统一,很多团队也习惯写 EXISTS。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「数据库就是像我这样一行行对着翻」——JOIN 的逻辑结果和实际怎么执行是两回事。「把两张表两两配对」是在描述结果应该是什么(SQL 是声明式的,Day 22)。数据库实际可能用嵌套循环、先建哈希表再查(hash join)、或者两边都排好序再合并(merge join),选哪种取决于数据量和索引。同一条 SQL 在 100 行和 100 万行上可能走完全不同的路。Week 5 用 EXPLAIN 看这些。
  2. 「对完的账按名册顺序排好了」——JOIN 的结果仍然没有顺序。上面所有输出看起来整整齐齐,是因为每条 SQL 都写了 ORDER BY(Day 22 的规矩)。换一种执行方式(比如哈希连接),不写 ORDER BY 的结果顺序可能完全不同。
  3. 「LEFT 就是左边全要,写在哪都一样」——条件放在 ON 还是 WHERE,结果不同。上面实测过:放进 WHERE 会把补出来的 NULL 行筛掉。INNER JOIN 时两种写法结果相同,所以很多人养成了随手写进 WHERE 的习惯,换成 LEFT JOIN 就出错。
④ 真实术语: inner join / left (outer) join / right (outer) join / full (outer) join / cross join;Cartesian product;self join;semi join(EXISTS / IN)与 anti join(NOT EXISTS);join predicate(ON 条件)vs filter predicate(WHERE 条件);nested loop / hash join / merge join(Week 5)。

📇 概念卡 #2:聚合与扇出 —— 分堆再数,别把一笔账算两遍

① 一句话大白话: GROUP BY 把行按某几列分成一堆一堆,聚合函数(count / sum / avg / min / max / string_agg)把每一堆算成一个值。WHERE 在分堆之前扔掉行,HAVING 在分堆之后扔掉整堆。扇出是最常见的聚合 bug:一对多 JOIN 会把「一」那边的行复制成好几行,这时再 SUM,同一笔数就被加了好几遍。

② 生活类比:按会员把订单分堆

月底统计,把订单按会员号分成一堆一堆,每堆数一数有几张、加一加金额。WHERE 是分堆之前先把作废的订单扔掉;HAVING 是分完以后,只留下「超过 1 张」的那几堆。扇出是这样发生的:你为了顺便统计标签,把订单本和标签对照表也对着翻了一遍,一张订单有 2 个标签,就被抄成了 2 行;接着按会员加金额,这张订单的金额就加了两次。账面上多出来的钱,一分都不存在。

--------------+--------+--------

160 = 30×2 + 20 + 40×2:「学 psql」和「买菜」各有两个标签,JOIN 之后各被复制成两行,求和时就加了两遍。这个 bug 不会报错,数字看起来也「挺像回事」,最容易混进报表。识别方法:看 JOIN 路径上有没有两个以上的「一对多」(用户 → 任务 → 标签),有的话,对「上游」的数求和就要小心。修法 1 最通用:每个子查询按 owner_id 先聚合,结果都是「一个用户一行」,再 JOIN 就不会扇出。修法 2 只适用于计数:count(DISTINCT t.id) 能把复制出来的同一个任务只数一次;但 sum(DISTINCT estimate_minutes) 不行,两个不同的任务时长恰好都是 30,就会被当成一个。另外注意错误版本里 Carol 的总时长是空的:sum 一个值都没有时结果是 NULL,修法 1 用 coalesce(…, 0) 把它显示成 0。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「分堆就是把订单摞起来,每堆都在」——没有行的堆根本不存在。INNER JOIN 后按用户分组,Carol 一行都没有,就不会有 Carol 这一堆,结果里也就没有 Carol。要让「0」出现,得先用 LEFT JOIN 把 Carol 留下来,再数 count(t.id):因为 LEFT JOIN 给她补了一行全是 NULL 的任务,count(*) 会把这一行数成 1,count(t.id) 不数 NULL,才是 0。
  2. 「数错了一眼就能看出来」——扇出的错误数字看起来很合理。160 分钟不像 9999 那样一看就假。唯一可靠的办法是:写完聚合查询,挑一个用户手算一遍,或者像上面那样把中间结果摊开看(去掉 GROUP BY,加上 WHERE 只看一个人)。这和前端写 reduce 时 console.log 一下中间数组是一个道理。
  3. 「WHERE 和 HAVING 都是过滤,随便写」——能写进 WHERE 的条件就别写进 HAVING。比如 HAVING u.id = 1 也能得到正确结果,但它是先把所有用户都分堆算完,再扔掉其他堆;写在 WHERE 里则是一开始就只拿 Alice 的行。结果一样,干的活差很多,数据量大时差别明显。
④ 真实术语: aggregate function;GROUP BY / HAVING;count(*) vs count(expr);aggregate FILTER clause(条件聚合);DISTINCT aggregate;functional dependency(按主键分组时其他列可以直接出现在 SELECT 里);fan-out / row multiplication(也叫 "chasm trap");pre-aggregation(先聚合再连接)。

📇 概念卡 #3:子查询、CTE 与 NULL —— 分步算账,「不知道」不是「零」

① 一句话大白话: 子查询是嵌在另一条 SQL 里的 SQL:可以返回一个值(标量子查询),一列值(给 IN 用),或一张临时的表(派生表,放在 FROM 里)。CTE(WITH 名字 AS (…))是给这些中间结果起名字、按顺序写出来,让复杂查询像几行代码一样分步可读;递归 CTE 能一层层往下找(组织架构、评论楼中楼)。NULL 表示「不知道」,和它比较的结果还是「不知道」,而 WHERE 只留下「确定为真」的行。

② 生活类比:分步算账,和账本上的「不知道」

复杂的月报,会计不会一口气写在一张纸上,而是先算一张「每位会员的消费汇总」草稿,给它起名叫「草稿 A」,再在草稿 A 上算完成率。CTE 就是这些有名字的草稿。递归像查族谱:先找到老祖宗,再找「父亲在上一轮名单里」的人,一轮轮往下,直到某一轮一个人都找不到为止。账本上还有一种格子写的是「不知道」:不是 0,也不是空字符串,就是「没人填」。问「这一格等于 30 吗?」,答案只能是「不知道」;问「这一格不等于 30 吗?」,答案还是「不知道」。

Carol 的完成率是空的:CTE 里写了 CASE WHEN 任务数 = 0 THEN NULL。一个任务都没有的人,完成率是「无从谈起」,不是 0%,这是一个业务决定,用 NULL 表达得很准确。递归 CTE 的结构永远是两段,用 UNION ALL 连起来:起点(没有经理的人)+ 递推(经理在上一轮结果里的人)。第 4 层之后再也找不到下属,递推得到 0 行,递归就停了。如果数据里有环(A 的经理是 B,B 的经理是 A),它会一直转下去,真实系统里要加层数上限或记录走过的路径来防止,这里只提一句。

子查询和 CTE 怎么选?能读懂是第一标准:一层子查询直接写;超过一层,或者同一个中间结果要用两次,就用 CTE。性能上,PostgreSQL 12 起会把只用一次的 CTE 内联进主查询一起优化,和子查询没区别;想强制先算出来存着,写 WITH x AS MATERIALIZED (…),反过来是 NOT MATERIALIZED。今天只点到,Week 5 看执行计划时再细看。

⑤ 动手验证 C:逻辑执行顺序。SQL 写的顺序是 SELECT … FROM … WHERE …,但逻辑上的执行顺序是:

FROM / JOIN  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  ORDER BY  →  LIMIT
(找表、配对)   (扔掉行)   (分堆)      (扔掉堆)    (算列、起别名) (排序)     (截取)
-- WHERE 里用 SELECT 起的别名
ERROR:  column "翻倍" does not exist

                                                             ^
HINT:  Perhaps you meant to reference the column "tasks.id".
-- ORDER BY 里用就可以
  title   | 翻倍
----------+------
 修自行车 |  120
 买菜     |   80

WHERE 执行时,SELECT 还没执行,别名「翻倍」还不存在;ORDER BY 在 SELECT 之后,所以认识它。(那条 HINT 是 PostgreSQL 在猜你想要哪一列,这次猜得不对,可以忽略。)同样的顺序解释了:为什么 WHERE count(*) > 1 不行(WHERE 时还没分堆)、为什么 HAVING 可以用聚合(它在 GROUP BY 之后)、为什么 Day 19 的 LIMIT 一定要配 ORDER BY(先排好序再截取,截的才是你想要的那几行)。这是逻辑顺序:数据库实际执行时会大量调整(比如把 WHERE 条件提前到读表时就用),但结果必须和按这个顺序执行的一样。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「草稿算完会先放在桌上,后面直接拿来用」——CTE 不一定被先算出来。PostgreSQL 12 起,只被引用一次的 CTE 默认会被内联,和直接写子查询没区别;它首先是让人读懂的工具。PostgreSQL 11 及更早的版本里,CTE 总是先完整算出来,常被当成「优化屏障」。看到老文章说「CTE 慢」,要先看它说的是哪个版本。
  2. 「『不知道』就是空着,当成 0 或空字符串处理就行」——NULL 不是 0,也不等于空字符串 ''。「预估 0 分钟」「预估没填」「标题是空字符串」是三件不同的事。sum / avg 跳过 NULL,但不跳过 0;把 NULL 用 COALESCE(x, 0) 变成 0 再求平均,平均值就从 37.5 变成了 30。哪种对,取决于业务含义,不取决于 SQL。
  3. 「查族谱总能查到头」——递归要有终点。递归 CTE 在「这一轮一行都没找到」时停止。数据里有环、或者递推条件写错(比如忘了 JOIN org o ON e.manager_id = o.id,变成每轮都配上所有人),它就停不下来,一直吃内存和 CPU。写递归 CTE 时,先在小数据上跑,并考虑加一个 WHERE 层级 < 20 之类的保险。

🌍 跨语言对照 + 面试翻译练习

SQL 本身是跨语言的;不同的是 ORM 怎么让你「不写 SQL 也能 JOIN 和聚合」。同一个问题:「每个用户的任务数,包括 0 个任务的用户」。

工具写法它生成的 SQL 大致是
Prisma(Node / TS)prisma.user.findMany({ include: { _count: { select: { tasks: true } } } });按列分组统计用 prisma.task.groupBy({ by: ['ownerId'], _count: true })一条带子查询计数的 SELECT(具体形式随版本变化)

✅ 总结与自测

今天带走的 4 句话

  1. JOIN 是按条件把两张表的行配对:INNER 只留配上的,LEFT 保留左边所有行(对右表的过滤写在 ON 里),CROSS 是笛卡尔积(旧式写法忘了条件也会变成它),自连接是同一张表起两个别名;只问有没有用 EXISTS,反连接用 NOT EXISTS,不用 NOT IN(子查询里一个 NULL 就让它返回空)。
  2. 聚合 = 分堆再算:count(*) 数行、count(列) 不数 NULL;SELECT 里没聚合的列要出现在 GROUP BY(按主键分组时放宽);WHERE 在分堆前、HAVING 在分堆后;FILTER 一行算出多个条件计数。
  3. 扇出:一对多 JOIN 之后再 SUM 会重复计算,数字还看起来很合理。修法:先按需要的粒度聚合再 JOIN;只数个数时可以 count(DISTINCT …)。写完聚合查询,挑一个人手算核对。
  4. NULL 是「不知道」:和它比较得到 unknown,WHERE 把 unknown 当 false,于是行会「消失」;用 IS NULL、IS DISTINCT FROM、COALESCE。逻辑执行顺序 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT 解释了别名和聚合能用在哪里。CTE 让复杂查询分步可读,递归 CTE 处理层级。
