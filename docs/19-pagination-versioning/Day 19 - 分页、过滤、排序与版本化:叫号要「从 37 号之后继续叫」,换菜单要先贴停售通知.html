📇 概念卡 #1:分页 —— 「跳过前 36 人」vs「从 37 号之后继续叫」

① 一句话大白话: 列表一次只给一页。offset 分页说「跳过前 N 条,给我接下来的 M 条」;cursor 分页说「从我上次看到的那一条之后,给我 M 条」。前者能跳页,但数据一变就会重复或漏掉;后者不重不漏,但不能跳页。

② 生活类比:排号叫号的两种叫法

offset:「请跳过前 10 位,第 11–20 位请进」。如果在这期间队伍前面有人插队,原来的第 10 位就变成了第 11 位,被叫了两次;如果前面有人离开,原来的第 11 位变成了第 10 位,两次都没被叫到。cursor:「41 号之后的 10 位请进」。不管前面有人插队还是离开,41 号之后是谁都不会变。代价是:你没法说「直接叫第 5 批」,只能一批接一批地叫。

比喻 ↔ 真实 对照

比喻真实组件nest-lab 里

今天的三个决定:

  • 集合响应是 { items, nextCursor }:nextCursor 为 null 表示到底了。它和 Day 18 的决定一致:这不是一个通用的 { data } 外壳,而是「一页任务」这个资源本身的表示。另一种做法是把下一页地址放进 RFC 8288 的 Link: <…>; rel="next" 响应头(GitHub 的 API 就这样做),body 仍然是纯数组;我们选 body,因为前端读起来最直接。
  • 不返回 total:「一共多少条」在数据库里是一个 COUNT(*),要扫描满足条件的所有行,大表上很贵;无限滚动根本用不到它。真的需要时,可以单独做一个接口,或者给一个估算值。
  • limit 超过 100 回 422,而不是悄悄截断成 100:截断会让调用方以为「一共就 100 条」,而且 bug 很难发现;明确报错能让他第一次调用就看到规则。
// src/tasks/tasks.service.ts —— cursor 分页的核心
listPage(query: ListTasksQueryDto): TaskListPage {
  const sort = parseSort(query.sort);                     // '-createdAt' → [{createdAt desc}, {id asc}]
  const filter = toFilter(query);
  const limit = query.limit ?? DEFAULT_LIMIT;
  const after = query.cursor ? decodeCursor(query.cursor, sort, filter) : undefined;
  const rows = this.repo.findPage({ filter, sort, limit: limit + 1, ...(after ? { after } : {}) });   // 多取 1 条
  const items = rows.slice(0, limit);
  const last = items.at(-1);
  const nextCursor = rows.length > limit && last
    ? encodeCursor(sort, filter, { values: sortTuple(last, sort), id: last.id })   // 取到了第 limit+1 条 → 还有下一页
    : null;
  return { items, nextCursor };
}
🖥️ 前端翻译: React Query 的 useInfiniteQuery 就是为 cursor 分页设计的:getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined,返回 undefined 时 hasNextPage 自动变成 false。今天的响应结构可以原样接上去。带页码的表格(「第 5 页 / 共 37 页」)才需要 offset 和 total,那是另一种 UI。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「拿着号码纸条,看到的就是领号那一刻的队伍」——cursor 只是位置书签,不是快照。书签之后的位置上如果新插进来一条(比如按标题排序时新建了一个「第 45 条任务(副本)」),你翻到那里时会看到它;如果某条任务的排序字段被修改了(标题改了),它可能「跳」到你已经翻过的位置,这一轮你就看不到它了。cursor 保证的是「按这个顺序,不重复、不因前面的增删而漏掉」,不是「冻结整个列表」。真正的快照要靠数据库的事务隔离(Week 7)。
  2. 「offset 重复 / 漏项是 bug,修一修就好」——这是方法本身的性质。「跳过前 10 条」的「前 10 条」每次都按当前数据重新数,数据变了结果就变,没法修。offset 仍然有它的位置:数据基本不变、需要跳到第 N 页的后台表格。另外它在数据库里越往后越慢:OFFSET 100000 意味着数据库要先找出并扔掉前 10 万行,Week 5 看 EXPLAIN 时会看到真实代价。
  3. 「小纸条上的内容是保密的」——不透明不等于加密。nextCursor 只是 base64url,任何人都能解开(第 3 节有原文)。「不透明」是一个约定:调用方不该解析、不该自己拼,服务器可以随时换内部格式。所以 cursor 里不能放任何敏感信息;被篡改时服务器要能识别(nest-lab 回 400 invalid-cursor)。cursor 还和「当时的排序与过滤条件」绑定:换了条件还拿旧 cursor,位置就没有意义了,也会被拒绝。
④ 真实术语: offset pagination(LIMIT … OFFSET …);keyset / cursor / seek pagination(WHERE (a, id) > ($1, $2) ORDER BY a, id LIMIT n,PostgreSQL 支持这种「行值比较」);tie-breaker(唯一的最后一个排序列);opaque cursor;RFC 8288 Web Linking(Link 头,rel="next");limit + 1 技巧(多取一条判断有没有下一页,省掉 COUNT(*))。

📇 概念卡 #2:过滤与排序 —— 只能按菜单上提供的方式挑

① 一句话大白话: 列表接口通过查询参数支持过滤(?done=false&q=关键字)和排序(?sort=-createdAt,title,- 表示倒序);能按哪些字段过滤、排序,由服务器列一张白名单,用 Day 16 的 DTO 校验,不合格回 Day 17 的 problem+json。

② 生活类比:按菜单提供的方式挑菜

菜单上写着「可选:辣度、价格排序、只看素菜」。客人可以说「只要不辣的,按价格从低到高」;但他不能说「按厨师的工资排序」,那不是对外提供的选项,厨房也不会告诉他。

// src/tasks/dto/list-tasks-query.dto.ts(节选)
export class ListTasksQueryDto {
  // ⚠️ 不能用 @Type(() => Boolean):Boolean('false') 是 true。只认 'true' / 'false' 两个字面值
  @IsOptional()
  @Transform(({ value }) => (value === 'true' ? true : value === 'false' ? false : value))
  @IsBoolean()
  done?: boolean;

  @IsOptional() @IsString() @MaxLength(100) q?: string;

  // 'createdAt,-title' → ['createdAt', '-title'],每一项都必须在白名单里
  @IsOptional()
  @Transform(({ value }) => (typeof value === 'string' ? value.split(',').map((s) => s.trim()) : value))
  @IsArray() @ArrayMaxSize(3)
  @IsIn(['id', '-id', 'createdAt', '-createdAt', 'title', '-title'], { each: true })
  sort?: string[];

  @IsOptional() @Type(() => Number) @IsInt() @Min(1) @Max(100) limit?: number;
  @IsOptional() @IsString() @MaxLength(500) cursor?: string;
}

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「白名单只是为了规矩好看」——到了数据库里它是安全边界。SQL 里的值可以用参数($1)安全传入,但列名和排序方向不能参数化,只能拼进 SQL 字符串。如果直接把 ?sort= 的内容拼进 ORDER BY,就是一个 SQL 注入口。白名单(把用户输入映射到你预先写好的列名)是唯一可靠的办法。Week 4 接 PostgreSQL 时会再强调一次。
  2. 「查询参数会按我声明的类型送来」——永远是字符串。?limit=20 送来的是 '20',要 @Type(() => Number) 转换;?done=false 送来的是 'false',而 @Type(() => Boolean) 等于 Boolean('false'),结果是 true(和 Day 12 的 z.coerce.boolean() 是同一个坑),所以要像上面那样只认两个字面值。
  3. 「错误里的 #/limit 指向请求体」——这里它指的是查询参数。Day 17 的 JSON Pointer 本来是为请求体设计的,nest-lab 对查询参数也沿用了 pointer;有些 API 会改用 "parameter": "limit" 这样的字段来区分。约定写进文档(Day 20)就行。
④ 真实术语: filtering / sorting parameters;allowlist(白名单,Day 18 也用过这个词);ORDER BY injection;stable sort(稳定排序:同值元素的相对顺序确定);常见的排序参数写法:sort=-createdAt(JSON:API 风格)、sort=createdAt:desc、orderBy=createdAt&order=desc,选一种保持一致。

📇 概念卡 #3:版本化与弃用 —— 新菜单上线,旧套餐先贴停售通知

① 一句话大白话: 接口要做破坏性变更时,不直接改,而是开一个新版本(/v2),旧版本(/v1)继续工作一段时间,并在响应头里告诉调用方「已弃用、哪天下线、去哪里迁移」。

② 生活类比:新旧菜单并行 + 停售通知

换新菜单那天,老顾客照样能点旧版套餐(v1 还在),桌上贴着一张卡:「旧版套餐自 11 月 4 日起不再推荐,2027 年 5 月 1 日停售,新套餐见第 2 页」(Deprecation / Sunset / Link)。厨房是同一个(同一个 TasksService),只是装盘方式不同(两个映射:v1 包 { data, timestamp },v2 直接给资源)。

方式例子优点缺点
URI(nest-lab 的选择)/v2/tasks一眼可见;curl、浏览器、日志、缓存都天然区分;最常见同一个资源有多个 URL;「版本」混进了资源标识

弃用三件套(@DeprecatedApi() 贴在 v1 上):Deprecation: @1793750400(RFC 9745,@ + Unix 秒数,这里是 2026-11-04)、Sunset: Sat, 01 May 2027 00:00:00 GMT(RFC 8594,计划下线时间)、Link: <迁移文档>; rel="deprecation", </v2/tasks>; rel="successor-version"。下线流程:贴出弃用头 → 文档、邮件通知 → 按版本统计调用量(日志、监控)→ 到 Sunset 日期后先返回 410 Gone 一段时间 → 删除 v1 的代码。

什么时候需要新版本?

变更兼容吗需要新版本吗
新增一个接口✅ 兼容不需要
响应里新增一个字段✅ 兼容(前提:调用方会忽略不认识的字段)不需要
请求里新增一个可选参数✅ 兼容不需要
请求里新增一个必填参数❌ 破坏性需要
删除 / 改名一个字段(包括 Day 18 去掉 data 包装)❌ 破坏性需要
改字段类型(id 从数字变字符串)❌ 破坏性需要
改状态码语义(校验失败从 400 改成 422,Day 16)❌ 破坏性需要(调用方可能写了 if (status === 400))
列表从「全部」改成「分页」(今天)❌ 破坏性需要 —— 所以今天的分页只在 v2 里
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「菜单版本越多,顾客越满意」——每个版本都是要维护的代码。v1 还在,就要为它跑测试、修安全漏洞、在每次改 Service 时确认它没被打坏。所以新版本要少开,旧版本要按计划下线;能用兼容变更解决的(加字段、加接口),就不要升版本。
  2. 「停售通知贴出去,到日子就自动停售」——Sunset 只是通知。它不会让任何东西自动下线,到期时还得有人真的去改代码、发布。而且 @Header() 只作用于成功响应:v1 返回 404 时,problem+json 错误响应上没有这些头。另外留意:POST /v2/tasks 返回的 Location 是 /tasks/31,不带版本前缀,它会落到「不带版本 = v2」上。
  3. 「不写版本号,自动给最新菜单,最方便」——方便的代价是顾客在不知情的情况下被换了菜单。nest-lab 让不带版本的 /tasks 指向 v2(VERSION_NEUTRAL),主要是为了 Day 8–18 的脚本和测试不用全改;但这意味着下次出 v3 时,所有「不写版本」的调用方会被悄悄升级,正是 Day 18 那种破坏性变更。对外的正式 API 更稳妥的做法是要求显式版本,或者像 GitHub 那样:不写版本时固定使用一个默认的旧版本,而不是最新版本。另一个坑:enableVersioning 只能在 app 实例上开,忘了调用会怎样,第 5 幕实测。
④ 真实术语: API versioning(URI / header / media type / query);Nest:app.enableVersioning({ type: VersioningType.URI | HEADER | MEDIA_TYPE | CUSTOM })、@Controller({ version })、@Version()(方法级)、VERSION_NEUTRAL、defaultVersion;Deprecation 头(RFC 9745,2025)、Sunset 头(RFC 8594)、Link 的 rel="deprecation" / rel="successor-version";410 Gone;breaking vs non-breaking change;Postel 法则(对接收的宽容:调用方应忽略不认识的字段,这是「加字段算兼容」的前提)。

"默认我用 cursor,也就是 keyset 分页:按排序键加一个唯一的 tie-breaker,比如 id,把上一页最后一条的位置编码成不透明的 cursor 返回,下一页用 WHERE (排序键, id) 大于这个位置来查。它在翻页过程中有新增或删除时不会重复也不会漏项,而且在数据库里性能不随页数变差。offset 实现简单、能跳页,但数据变化时会重复或漏项,深分页也越来越慢,所以只用在小而稳定的后台表格。limit 有默认值和上限,超过上限直接报错;排序和过滤字段都有白名单,这也是防 SQL 注入的必要条件;响应里不返回 total,因为 count 在大表上很贵。版本化方面,兼容变更比如新增字段、新增接口不需要新版本;删字段、改名、改类型、改状态码语义才需要。我倾向于 URI 版本,直观、好调试;旧版本保留一段时间,在响应头里加 Deprecation、Sunset 和指向迁移文档的 Link,按版本统计调用量,到期后先返回 410 再删除代码。"

✅ 总结与自测

今天带走的 4 句话

  1. 列表要分页:offset 简单能跳页,但数据变化时重复 / 漏项(方法本身的性质),深分页慢;cursor(keyset)不重不漏、性能稳定,但不能跳页。cursor 是位置书签不是快照,不透明不等于加密,排序键最后要有唯一的 tie-breaker。
  2. nest-lab 的约定:集合响应 { items, nextCursor },不给 total;limit 默认 20、最大 100,超过回 422;cursor 坏了或条件变了回 400 invalid-cursor。
  3. 过滤与排序走白名单:查询参数永远是字符串,用 DTO 转换和校验;排序字段白名单在 SQL 里是防注入的必要条件。
  4. 破坏性变更开新版本:URI 版本 /v2,旧版 /v1 贴 Deprecation / Sunset / Link,按计划下线;加字段、加接口不需要新版本。enableVersioning 必须在每个创建 app 的地方生效,用 createApp() / configureApp() 统一入口加测试保证。
