🎫 接上回:「账本照片」到底是怎么拍出来的

Day 37 用「账本照片」解释了隔离级别:Read Committed 每条语句拍一张,Repeatable Read 整个事务一张。可是数据库不可能真的给每个事务复制一份数据。它的做法叫 MVCC(多版本并发控制):同一行同时存在好几个版本,每个事务按自己的「照片名单」挑出该看的那个版本。

Week 5 有几件事一直没解释,今天都有答案:

  • Day 29 看到 UPDATE 之后 ctid 变了;
  • Day 31 的 Heap Fetches 要等 VACUUM 之后才归零;
  • Day 32 的 HOT 更新「留下了旧行」;
  • Day 36 的 pg_current_xact_id() 是个越来越大的数。

最后还有一个线上最常见的事故:一个忘了提交的事务,让整个库的清理工作停下来,表越来越大。

🖥️ 前端翻译: React 里你从不直接改 state:setTasks(tasks.map(t => t.id === id ? { ...t, done: true } : t)) 生成一个新对象,旧对象原封不动。正在渲染的组件还拿着旧对象,不受影响;等没人再引用旧对象了,垃圾回收器才把它回收。git 也一样:改文件就产生新的提交,旧版本一直留在历史里。PostgreSQL 的 MVCC 就是这个思路:UPDATE 写一个新版本,旧版本留着给还在用它的事务看,等没人需要了,由 VACUUM 回收。

📇 概念卡 #1:行版本与快照 —— 账本从不涂改

① 一句话大白话: PostgreSQL 的 UPDATE 不改原地的行,而是写一个新版本,并在旧版本上记下「从第几号事务起作废」;DELETE 也只是做这个标记。每个版本带着两个事务号:xmin(谁写下了它)和 xmax(谁让它作废)。快照是一张名单:「拍照那一刻,哪些事务已经结束、哪些还在进行」。一个版本对某张快照可见,当且仅当写下它的事务在快照里已经提交,而且让它作废的事务在快照里还不算数。所以读和写各看各的版本,读不阻塞写,写不阻塞读。

② 生活类比:账本从不涂改

账房立了一条规矩:账本上写过的字永远不涂改。要改 Alice 的余额,就在后面另起一行写新余额,并在旧的那一行旁边注明「自第 231454 号作业单起作废」;要删一笔账,也只是在那一行旁边写上作废标记。

每个伙计手里都有一张名单(快照),是他拍照那一刻抄下的:「这些号的作业单已经盖章了,这些号还在办,比这个号大的还没开始」。伙计查账时,一行行地对照名单:「写这一行的作业单在我名单上盖章了吗?作废它的那张呢?」于是同一页账本,两个伙计可能看到不同的行。谁也不用等谁。

  • 页上有 5 个版本,用户能看到的只有 2 行。被删除的 id=3、被替换的 id=1 旧版本,都是死元组。
  • 回滚也会产生死元组:回滚的那个 UPDATE 已经写下了新版本(lp 5),回滚只是让它永远不可见,并没有把它擦掉。所以 PostgreSQL 的回滚很快(只要把事务标成 aborted),但留下的垃圾同样要清理。
  • HOT(Day 32):id=1 改的列不在任何索引里,新版本又放在同一页,于是索引不用动。VACUUM 后 lp 1 变成「重定向」(lp_flags = 2),索引里仍然指向 lp 1,顺着它跳到 lp 4。这种页内的清理在平时的查询中也会顺手做(page pruning),不一定要等 VACUUM。

  • 快照 231504:231504: 的意思是:「231504 以前的事务都结束了;231504 及以后的事务,拍照时还没开始;中间没有进行中的事务」。B 的事务号正好是 231504,所以对 A 来说「B 不存在」:B 写的新版本看不见,B 打在旧版本上的作废标记也不算数。A 看到旧版本 v = 11。
  • 可见性规则:一个版本可见 ⇔ xmin 已提交、且在快照之前(不在 xip_list 里、小于快照的 xmax),并且 xmax 为 0,或者 xmax 的事务对这张快照不可见(回滚了、还在进行中、或者在快照之后)。
  • B 的 UPDATE 用了 4.1–4.7 ms(3 遍),A 读 B 正在改的行用了 0.6–0.7 ms:读和写互不等待。但「写不阻塞写」不成立:Day 36、37 里,两个事务改同一行时,后来的那个要等前一个结束。
  • 只读的事务不分配事务号(第一次写才分配),这让只读查询非常便宜。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「读不阻塞写」不等于「写不阻塞写」。两个事务改同一行,后来的必须等前一个结束(Day 36 第 4 幕 B 等 A),因为新版本只能接在最新版本的后面。MVCC 解决的是读和写之间的冲突。
  2. 「作废标记」不一定生效。xmax 有值,可能是删除、更新、回滚了的更新,甚至只是行锁(Day 39 的 SELECT … FOR UPDATE 也会写 xmax)。真正判断要看那个事务的状态。
  3. 「从不涂改」有代价。账本只会越写越长:每次更新都多一行,旧行不会自己消失。下一张卡就是清理它们的人。
④ 真实术语: MVCC(multi-version concurrency control);tuple / row version;系统列 xmin / xmax / ctid(还有 cmin / cmax);snapshot:pg_current_snapshot()、pg_snapshot_xmin/xmax/xip、pg_visible_in_snapshot();pg_current_xact_id_if_assigned()、pg_xact_status();commit log (CLOG / pg_xact);hint bits;pageinspect:get_raw_page、heap_page_items、lp_flags(normal / redirect / dead / unused);HOT chain、page pruning。

📇 概念卡 #2:死元组与 VACUUM —— 清洁工、誊抄新册子

① 一句话大白话: 作废的版本(死元组)不会自己消失,要等「没有任何快照还需要它」之后,由 VACUUM 回收。普通 VACUUM 把空间标成「可以再用」,留给这张表以后写入,文件一般不会变小,也不挡读写。VACUUM FULL 把整张表誊抄成一个新文件,空间还给操作系统,但期间整张表被锁住,谁都不能读写。平时靠 autovacuum 在后台按阈值自动清理:默认死元组超过 50 + 20% × 行数 才动手,大表要按表调小。

② 生活类比:清洁工、誊抄新册子

账本只往后写,作废的行越来越多。账房请了一位清洁工:把「没有任何伙计的照片还会用到」的作废行擦掉,腾出格子,以后新记的账可以写在这些空格子里。账本的页数不会因此变少,只是里面空格子多了,以后不用再加页。

如果账本已经被作废行撑得太厚,还可以誊抄:把有效的行一行行抄到一本新册子上,扔掉旧册子。新册子薄了很多,但誊抄的时候,谁都不能翻这本账。

清洁工不是一直站在旁边,而是每隔一段时间(默认 1 分钟)巡视一遍,看哪本账的作废行超过了「该打扫的线」才动手。

  • 触发线 = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples。20 万行的表要 40050 个死元组;1 亿行的表要 2000 万个,对大表来说太晚了。常见做法是给大表单独设 ALTER TABLE big SET (autovacuum_vacuum_scale_factor = 0.01),或者把 scale factor 设成 0、只用一个固定的阈值。
  • autovacuum 不是实时的:launcher 每 autovacuum_naptime(默认 60 秒)检查一次每个库,所以从超线到被清理,等了 26 秒到一分多钟不等。
  • 只插入不更新的表,PostgreSQL 13 起也会按 autovacuum_vacuum_insert_threshold 定期 VACUUM(为了更新 visibility map 和冻结),不然 Index Only Scan 会一直回表。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「打扫完账本就变薄了」——普通 VACUUM 腾出的空间只给这张表自己用,文件一般不缩(只有表末尾整页都空了才会截掉)。监控上看到 VACUUM 之后磁盘没降,不代表它没工作。
  2. 「清洁工一直在旁边」——autovacuum 不是实时的,而且同时只有 autovacuum_max_workers(默认 3)个在干活。大批量 UPDATE / DELETE 之后,最好手动 VACUUM (ANALYZE) 一次,而不是等它。
  3. 「誊抄一下就好了」——VACUUM FULL 锁住整张表,还需要和表一样大的额外磁盘空间(新旧文件同时存在)。它是事故后的补救,不是日常维护。日常靠的是让普通 VACUUM 跟得上。
④ 真实术语: dead tuple、table bloat / index bloat;VACUUM、VACUUM (VERBOSE, ANALYZE)、VACUUM FULL(重写表,ACCESS EXCLUSIVE);free space map (FSM)、visibility map (VM);autovacuum:launcher / worker、autovacuum_naptime、autovacuum_vacuum_threshold、autovacuum_vacuum_scale_factor、autovacuum_vacuum_insert_threshold、autovacuum_max_workers、按表的 storage parameter;pg_stat_user_tables:n_dead_tup、last_autovacuum、autovacuum_count;pg_stat_force_next_flush()。

📇 概念卡 #3:长事务与冻结 —— 拿着旧照片不走的伙计

① 一句话大白话: VACUUM 只能清理「所有还活着的快照都不需要」的死元组。只要有一个事务拿着一张很旧的快照不走(Repeatable Read 的事务、写过数据还没提交的事务,常见的是 idle in transaction 的连接),它开始之后产生的所有死元组,全库的 VACUUM 都清不掉,表就一直膨胀。另一个问题是事务号只有 32 位,会转圈;VACUUM 要定期把足够老的行版本「冻结」,否则转一圈之后它们会被误判成「来自未来」。

② 生活类比:拿着旧照片不走的伙计

清洁工擦作废行之前,要先问一圈:「还有谁手里的照片比这一行作废得早?」只要有一个伙计拿着一张早上 9 点拍的照片坐在角落里不走,9 点以后作废的所有行都不能擦。也许他还要用到这些行。哪怕他早就去喝茶了、根本不会再看照片,清洁工也不敢擦。一天下来,账本越来越厚。

不过,如果这个伙计用的是「每看一页重新拍」的方式(Read Committed),而且只看过、没写过,他每看完一页就把照片扔了,手里其实没有照片,就挡不住清洁工。

  • 事务号是 32 位的(约 42 亿个),用完了从头再来;比较「谁新谁旧」靠的是「前后各约 21 亿」的窗口。一个行版本如果 20 多亿个事务都没被处理,它的 xmin 就会被误判为「在未来」,这一行突然对所有人不可见。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「只要有人挂着事务就会挡」——要看他手里有没有快照或事务号。RC 下只读过的空闲事务没挡;RR 事务、写过的事务、正在执行的长查询会挡。但不管挡不挡,idle in transaction 都占着一个连接(Day 27 的池子),还可能锁着行(Day 39),都应该消灭。

PostgreSQL 这种「旧版本留在表里」的设计,好处是回滚极快、读旧版本不用回溯日志、不需要一个单独的 undo 区域;代价是需要 VACUUM、频繁更新的表容易膨胀、每次非 HOT 的更新都要改所有索引(Day 32 的写放大)。没有哪种设计绝对更好,这是 PostgreSQL 运维比 MySQL 多一块「VACUUM 调优」的原因。

ORM 层面:UPDATE tasks SET … 不带 WHERE、或者 ORM 的「批量更新全部记录」(EF Core 的 ExecuteUpdate、Prisma 的 updateMany({})、JPA 的批量 JPQL),在 PostgreSQL 里等于把整张表复制一遍,今天实测 20 万行表一次就多出 16 MB。批量修数据时:分批做,每批之间让 autovacuum 有机会跟上;或者做完手动 VACUUM (ANALYZE)。

✅ 总结与自测

今天带走的 4 句话

  1. MVCC:UPDATE 写新版本(新 ctid、新 xmin),旧版本记上 xmax;DELETE 只记 xmax;回滚的更新也会留下一个永远不可见的版本。xmax 有值不等于被删了,要看那个事务的状态。
  2. 快照 = 「哪些事务已结束、哪些还在进行」的名单。版本可见 ⇔ xmin 在快照里已提交,且 xmax 为 0 或不算数。所以读写互不等待(B 改并提交用了 4 ms,A 读正在被改的行用了 0.6 ms),但写同一行仍要排队。
  3. VACUUM:20 万行全表更新 3 遍,16 MB → 64 MB;VACUUM 后死元组归零、Heap Fetches 归零,文件仍 64 MB,再更新也不再变大;VACUUM FULL 回到 16 MB,但要锁整张表。autovacuum 默认死元组超过 50 + 20% × 行数 才来,而且每 60 秒才巡视一次。
  4. 长事务:一个持有旧快照(RR)或事务号(写过)的空闲事务,会让全库的死元组 not yet removable;RC 下只读过的空闲事务不会。用 pg_stat_activity 找、用 idle_in_transaction_session_timeout 兜底。冻结防的是 32 位事务号回卷,同样靠 VACUUM。
