🍳 接上回:开分店太贵了,有没有便宜点的帮手?

Day 4 我们学会了"开分店"(fork 子进程):CPU 硬菜外包出去,总店服务员照常巡场。但 Day 4 习题 2 最后一道思考题已经埋了个钩子:开一家分店要新起一个完整的 Node(新 V8、几十 MB 内存、几百毫秒)。如果硬菜只要做几毫秒,却一天要做几百万次,每次都开一家分店,开店的钱比菜钱还贵。

💡 生活翻译: 你不会为了切一盘黄瓜,专门去隔壁街租个门面开分店。你会在自己店里请一个帮厨:不用新门面、不用新执照,上岗快、成本低,切完黄瓜接着切土豆。今天的主角 worker_threads 就是这个帮厨。

📇 概念卡 #1:worker_threads —— 自带小灶的帮厨

① 一句话大白话: 在同一家店里多请一个能独立做菜的人,专门做费时间的硬菜,让服务员腾出手继续招呼客人。

② 生活类比:自带小灶的帮厨

这个帮厨和服务员在同一个店面(同一个进程,PID 相同),但他有自己的一口小灶、自己的砧板、自己的待办清单,不碰服务员的锅。两人之间隔着一个传菜口:服务员把单子从传菜口递进去,帮厨做好再从传菜口递出来。

import { Worker, isMainThread, parentPort } from "node:worker_threads";

if (isMainThread) {
  // 服务员:请一个帮厨(同一个文件,换个身份运行)
  const w = new Worker(new URL(import.meta.url));
  w.postMessage(40);                              // 从传菜口递单
  w.on("message", (r) => console.log("fib =", r)); // 从传菜口接菜
} else {
  // 帮厨:在自己的小灶上做硬菜
  parentPort!.on("message", (n) => parentPort!.postMessage(fib(n)));
}

比喻 ↔ 真实 对照

比喻真实组件
同一个店面同一个 OS 进程(process.pid 相同)
帮厨这个人一个 OS 线程(threadId 不同,主线程是 0)
帮厨自己的小灶 / 砧板独立的 V8 isolate:自己的 JS 堆、自己的全局变量
帮厨自己的待办清单帮厨自己的 event loop(他里面也能 setTimeout、await)
传菜口消息通道:postMessage / on("message")(parentPort 是帮厨那一侧的传菜口)
上岗时手里拿的交接单workerData:创建 Worker 时一次性带进去的数据
③ ⚠️ 这个比喻在哪里会骗你:
  1. "同一家店的员工应该共用厨房"——在 Node 里不成立。Java、C# 的线程默认共享所有对象(真的共用一个厨房,所以要处处加锁)。Node 的帮厨自带小灶,服务员的变量他看不见,只能靠传菜口递消息。只有一种例外:专门划出来的"共享白板"(概念卡 #2)。
  2. "帮厨是独立的人,他出事不关我事"——只对了一半。帮厨抛了没 catch 的异常,只要服务员这边监听了 worker.on("error"),就只有这一个帮厨下岗;但如果服务员没监听 error,这个异常会被转抛到主线程,把整家店带崩。而像底层 C++ 崩溃、整个进程内存耗尽这种"店面着火",帮厨和服务员会一起完蛋。论隔离,帮厨不如分店。
  3. "请帮厨很便宜"——是相对的。每个帮厨都是一个完整的 V8 isolate,也要几十 MB 内存、上百毫秒才能上岗。比开分店便宜,但绝不是免费(习题 1 你会亲手量出来)。
④ 真实术语: worker_threads 是 Node 的多线程 API:每个 Worker 运行在独立的 OS 线程上,拥有独立的 V8 isolate 和 event loop,线程之间默认不共享 JS 对象,通过消息传递(message passing)通信。它和 libuv 线程池的区别:libuv 线程池跑的是 Node 内部的 C++ 系统活,你没法往里塞 JS;worker_threads 跑的是你自己写的 JS。

⑤ 动手验证:习题 1 里,你先猜"帮厨算 fib(40) 时服务员的心跳停不停"、"请帮厨和开分店的上岗成本差多少",再运行看答案。

📇 概念卡 #2:给帮厨递东西的三种方式 —— 复印 / 整箱交出去 / 共用白板

① 一句话大白话: 东西要从服务员手里到帮厨手里,只有三种办法:给他一份复印件、把原件整箱交给他、或者两人在同一块白板上写字。

② 生活类比 + 比喻 ↔ 真实

方式餐厅里真实 API代价
复印(默认) 菜谱复印一份递进去,原件还在服务员手里,两人各改各的 w.postMessage(obj),底层是 structured clone(结构化克隆) 东西越大,复印越慢
整箱交出去 把一整箱食材直接推过传菜口,服务员手里就没了 w.postMessage(buf, [buf]):第二个参数是 transferList 几乎零成本,但原件作废(变成 0 字节的空壳)
共用白板 墙上挂一块两人都能写的白板,不用递来递去 SharedArrayBuffer + Atomics 不用拷贝,但必须守写字规矩,否则会记乱账 
// 复印:原件还在
w.postMessage(bigBuffer);
// 整箱交出去:原件变空壳
w.postMessage(bigBuffer, [bigBuffer]);
console.log(bigBuffer.byteLength); // 猜猜是多少?(习题 2 揭晓)

// 共用白板
const shared = new SharedArrayBuffer(4);
const counter = new Int32Array(shared);
new Worker(file, { workerData: { shared } }); // 白板的"位置"告诉帮厨,不复印
Atomics.add(counter, 0, 1);                    // 守规矩地 +1
③ ⚠️ 这个比喻在哪里会骗你:
  1. "什么都能复印"——不能。函数、class 实例上的方法、数据库连接、socket 这类"活物"复印不了,会报 DataCloneError,或者丢掉原型只剩一个普通对象。能复印的只有纯数据:对象、数组、Map、Date、Buffer 等。
  2. "什么都能整箱交出去"——也不能。只有 ArrayBuffer、MessagePort 这类特殊的"箱子"支持 transfer,普通对象只能复印。
  3. "白板上写个数字只是一步"——这是最危险的错觉。counter[0]++ 看起来是一步,实际是"读出来 → 加 1 → 写回去"三步。两个帮厨同时读到 100,各自加 1 写回 101,两笔账只记了一笔。这就是竞态条件(race condition)。现实中白板上的笔迹是看得见的,内存里的"同时写"却悄无声息。
④ 真实术语: structured clone:postMessage 默认使用的深拷贝算法;transferable:可以转移所有权的对象,转移后原对象被 detach(byteLength 变成 0);SharedArrayBuffer:多个线程映射到同一块内存;Atomics:对共享内存做原子操作(读改写一气呵成,中间不会被别人插队)。
默认选择:日常一律复印(简单,不会出错);大块二进制(图片、音视频、大数组)用 transfer;只有高性能场景(多个线程频繁更新同一批数字)才值得用共享内存 + Atomics。

⑤ 动手验证:习题 2 里递一个 200MB 的箱子,比较复印和整箱交出去的耗时;再让 4 个帮厨在同一块白板上各记 100 万笔账,看最后会不会丢账。

📇 概念卡 #3:线程池 —— 别每道菜现招一个帮厨

① 一句话大白话: 提前请好固定几个帮厨,菜来了先排队,哪个帮厨空了就接下一道。

② 生活类比:帮厨班组 + 排队单

如果每来一道硬菜就现招一个帮厨,招人的时间比做菜还长,做完还要辞退。聪明的店长会开店时就请好一个固定的帮厨班组,门口挂一张排队单:菜来了写到单子上,谁空了谁接。帮厨做完一道不走人,回到待命区等下一道。

class MiniPool {
  idle: Worker[] = [];   // 待命区
  queue: Job[] = [];     // 排队单

  run(n) {               // 来了一道菜
    this.queue.push(n);
    this.dispatch();
  }
  dispatch() {           // 有空闲帮厨 + 有菜排队 → 派单
    while (this.idle.length && this.queue.length) { ... }
  }
}

习题 3 里有完整的 60 行实现,你会亲手看到 8 道菜由 4 个帮厨轮流接走。

比喻 ↔ 真实 对照

比喻真实组件
帮厨班组线程池(thread pool):预先创建、反复复用的固定数量线程
排队单任务队列(task queue)
灶台数量CPU 核数(os.availableParallelism())
帮厨做完回待命区线程复用:不销毁、不重建,省掉每次的启动成本
③ ⚠️ 这个比喻在哪里会骗你:
  1. "帮厨越多,出菜越快"——错。真正的瓶颈是灶台(CPU 核)。4 个灶台请 32 个帮厨,同一时刻还是只有 4 个人在炒,其余的人在抢灶台(OS 来回切换线程,即上下文切换),反而更慢。CPU 密集任务的池大小 ≈ 核数。习题 3 可以试试池大小 32。
  2. "有了帮厨,什么活都交给他更快"——错。帮厨只对"算"(CPU 密集)有用。查数据库、调 HTTP 这种"等"(I/O 密集),服务员本来就不站着等(Day 1 的黄金法则),交给帮厨等于多雇一个人陪你一起等外卖。
④ 真实术语: thread pool(线程池)+ task queue(任务队列);CPU-bound(CPU 密集:图片压缩、密码哈希、大报表、解析巨型 JSON)vs I/O-bound(I/O 密集:DB、HTTP、文件);context switch(上下文切换)。生产上不要自己手写池,Node 生态用 piscina,它还帮你处理了帮厨崩溃重招、队列上限、单任务超时、取消等问题。

⑤ 动手验证:习题 3 里对比"服务员一个人串行做 8 道 fib(38)"和"4 人帮厨班组",先猜能快几倍、会不会正好快 4 倍。

🧭 四种帮手怎么选:一张决策表

你遇到的情况选谁为什么
查数据库、调 HTTP、读写文件(I/O 等待)什么都不用加,直接 async/await服务员本来就不站着等,libuv 和操作系统已经在后台干活
CPU 重活,频繁、单次时间短(哈希、压缩、解析)worker_threads 线程池(piscina)上岗成本低、复用、可以传大块二进制
要跑别的程序(ffmpeg、git、Python 脚本),或者要强隔离child_process帮厨只会做 JS;分店着火不烧总店
同一个 HTTP 服务想吃满多核cluster / 多副本(生产:k8s replicas)每个副本仍是简单的单线程 event loop,状态外迁
📇 Week 1 并发模型收官: Day 1 的"服务员不站着等"解决的是 I/O 等待;Day 4 的分店和 Day 5 的帮厨解决的是 CPU 计算。先判断瓶颈是"等"还是"算",再选工具:这是所有语言里做并发设计的第一步。

✅ 总结与自测

今天带走的 4 句话

  1. worker_threads = 同一家店里自带小灶的帮厨:同一进程、不同线程,各有独立的 V8 isolate 和 event loop,默认不共享变量,靠消息传递沟通;比开分店便宜,但不是免费,隔离也不如分店。
  2. 递东西三种方式:默认复印(structured clone);大块二进制整箱交出去(transfer,原件变空壳);高性能场景共用白板(SharedArrayBuffer),但必须用 Atomics 守规矩,否则 ++ 会丢账。
  3. 线程池:提前请好固定的帮厨班组 + 排队单,池大小 ≈ 核数;灶台才是瓶颈,人多了只会抢灶台。
  4. 先判断瓶颈是"等"还是"算":等(I/O)直接 async;算(CPU)用线程池;要隔离或跑外部程序用子进程;吃满多核跑服务用多副本。
