📇 概念卡 #1:Problem Details —— 标准投诉回执单的五个栏目

① 一句话大白话: RFC 9457 规定了 HTTP API 报错时响应体长什么样:Content-Type: application/problem+json,固定五个字段(type / title / status / detail / instance),需要的话再加自己的扩展字段。

② 生活类比:标准投诉回执单

HTTP/1.1 404 Not Found
Content-Type: application/problem+json; charset=utf-8
x-request-id: 1aa9c79f-7496-4591-b27f-46175848b9e8

{
  "type": "https://nest-lab.example/problems/not-found",   ← 投诉类别编号(查得到说明)
  "title": "资源不存在",                                     ← 类别名称(同类永远一样)
  "status": 404,                                             ← 状态章
  "detail": "没有 id 为 999 的任务",                          ← 这次具体发生了什么
  "instance": "/tasks/999",                                  ← 在哪张桌子上发生的
  "requestId": "1aa9c79f-7496-4591-b27f-46175848b9e8"        ← 本店加的栏目:桌号牌
}

比喻 ↔ 真实 对照

回执单栏目字段规则
投诉类别编号type一个 URI,标识「哪一类错误」;调用方用它做程序判断。不写时默认是 about:blank,意思是「除了状态码本身,没有更多语义」
类别名称title简短的人类可读标题,同一个 type 永远相同;about:blank 时应该就是状态码的标准短语(如 Payload Too Large)
状态章status和响应行的状态码一致(只是方便阅读,以响应行为准)
这次发生了什么detail这一次的具体说明,给人看的;帮助客户端解决问题,而不是调试信息
在哪张桌子instance这一次出错的 URI(nest-lab 用请求路径)
本店加的栏目扩展字段任意名字,但不能和标准字段重名;nest-lab 加了 requestId 和校验错误的 errors
🖥️ 前端翻译: 有了统一格式,前端的 axios 拦截器只需要写一次:if (res.headers['content-type']?.startsWith('application/problem+json')) 就弹 problem.title / problem.detail;遇到 422 把 errors 映射到表单(卡 #3);遇到某个特定 type(比如 …/conflict/task-completed)再做特殊处理,比如弹出「重新打开任务」按钮。不用再为每个接口写不同的解析,也不用去解析 detail 里的中文。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「有了标准回执单,该盖什么章也就定了」——RFC 9457 只规定格式,不规定状态码。用 400 还是 422、404 还是 403,仍然是 Day 15 / 16 的决定;problem+json 只是保证不管你选了什么,错误体长得都一样。它也不能替代状态码:代理、缓存、监控仍然只看响应行。
  2. 「类别名称写详细点更友好」——title 不能塞具体细节。如果写成「任务 999 不存在」,同一类错误就有无数种 title,监控面板没法按类别统计、告警规则也没法写。具体信息放 detail(或扩展字段);程序判断看 type,不要去解析 detail 里的文字。
  3. 「回执单格式统一了,成功的小票也该一样」——那是两套东西。problem+json 只用于错误;成功响应现在是 Day 10 的 { data, timestamp } 包装。两者都用会让客户端先看状态码、再决定按哪种格式解析。要不要保留成功包装,是 Day 18 要讨论的事(很多团队的答案是「不包装,直接返回资源」)。
④ 真实术语: RFC 9457 Problem Details for HTTP APIs(2023,取代 2016 年的 RFC 7807,字段完全兼容,主要新增了多个问题的表达方式、类型注册表,并澄清了 about:blank);媒体类型 application/problem+json(还有 application/problem+xml);extension members(扩展字段)。

📇 概念卡 #2:错误类型目录 —— 投诉类别编号表

① 一句话大白话: 给系统里每一类错误起一个稳定的名字(type URI),登记在一张公开的目录里,写清「什么时候出现、调用方该怎么做」;业务代码抛错时指明类别,投诉台照着目录填回执单。

② 生活类比:投诉类别编号表

总部发给每家分店一本投诉类别编号表:「A-404 菜品不存在」「C-409-1 菜已上桌不能改口味」「Z-500 后厨故障」…… 每个编号下面写着处理建议。服务员填回执单时只写编号和这次的情况,不自己发明类别。顾客(调用方)拿到编号,翻表就知道该怎么办。

type URI 怎么起名?RFC 9457 说它是一个 URI,可以是绝对的(https://…)也可以是相对的(/problems/not-found,相对于请求地址解析)。nest-lab 用绝对 URI + example 域名占位:.example 是 RFC 2606 保留的域名,永远不会有人注册,避免碰巧指向别人的网站;真正上线时换成自己的文档站,让每个 URI 都能打开 docs/problems.md 对应的那一段。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「编号表随时可以改版」——type 一旦发布就是对外契约。调用方会写 if (problem.type.endsWith('/conflict/task-completed')),你把它改名成 …/task-already-done,他们的代码就悄悄失效了,而且不会报错。规则:只增不改;语义变了就新建一个 type,旧的保留。title 同理(有人拿它做统计)。
  2. 「编号必须能打开」——不必,但最好能。type 首先是一个标识符,客户端不应该在出错时去请求这个 URL(它可能根本不存在,比如今天的 nest-lab.example)。但如果它能打开、并且指向一页说明,接入方遇到陌生错误时就能自助查到原因,这正是 RFC 推荐的做法。
  3. 「投诉台要把后厨发生的事如实告诉顾客」——对外要克制。500 的 detail 永远是一句固定的通用说明,不能把数据库地址、SQL、调用栈带出去(观察脚本里那个 bug 的原话带着 password=hunter2,响应里一个字都没有)。真实原因只写进带 requestId 的服务端日志 —— 但请注意,今天的日志里也出现了那个密码(见下方日志节选)。日志同样不该保存密钥,这需要「脱敏」(redaction),Week 15 可观测性和 Week 20 安全周会处理。
④ 真实术语: problem type(问题类型)与 type URI;about:blank;IANA 的 HTTP Problem Types 注册表(RFC 9457 新增,用来登记通用的 type);error catalog(错误目录);对外信息最小化(OWASP:不要在错误信息里暴露实现细节)。

📇 概念卡 #3:字段级 errors 与补发桌号牌

① 一句话大白话: 校验错误要告诉前端「哪个字段、什么问题」,用 JSON Pointer 指明位置;另外,有些错误发生在发桌号牌之前,投诉台要能当场补发一张,保证每张回执单都有桌号。

② 生活类比:在单子上圈出错的格子 + 补发桌号牌

报关单(Day 16)被退回时,海关不再只说「你填错了三处」,而是在单子上把每个错的格子圈出来:「第 2 张子表格的第 1 栏:不能为空」。顾客照着圈改就行。另一件事:有的顾客一进门就把单子扔在地上(JSON 语法错误),门口的接单员(body parser)当场就拒收了,这时他还没走到发牌员那里,手上没有桌号牌。投诉台发现回执单上桌号是空的,就按同样的规则补发一张(客户带了 x-request-id 就沿用,没带就新发),写在回执单上、也贴到顾客身上(响应头)。

// src/common/problems/validation-exception.factory.ts —— 错误树压平成 JSON Pointer 列表
export function flattenValidationErrors(errors: ValidationError[], parent = ''): ProblemFieldError[] {
  return errors.flatMap((e) => {
    const pointer = `${parent}/${escapePointer(e.property)}`;           // checklist → 1 → text
    const own = Object.values(e.constraints ?? {}).map((detail) => ({ pointer: `#${pointer}`, detail }));
    return [...own, ...flattenValidationErrors(e.children ?? [], pointer)];
  });
}
// validation.options.ts:exceptionFactory: validationExceptionFactory

// src/common/all-exceptions.filter.ts —— 没有桌号牌时兜底补发
if (!this.context.requestId) {
  const requestId = resolveRequestId(req);                // 和发牌 middleware 同一个函数、同一套规则
  if (!res.headersSent) res.setHeader(REQUEST_ID_HEADER, requestId);
  requestContext.run({ requestId, startedAt: performance.now() }, () => this.respond(exception, req, res));
  return;
}

为什么 Day 16 时 requestId 是 null?Express 里中间件按注册顺序执行:Nest 在 app.init() 时先挂上 body parser,然后才挂各模块 configure() 里的 middleware(发牌员就在那里)。JSON 一坏,body parser 直接把错误交给错误处理,发牌员根本没机会运行。修法有三种:

修法做法为什么没选 / 为什么选
A. 发牌提前在 main.ts 里用 app.use() 发牌(它比 body parser 更早)e2e 测试和观察脚本不走 main.ts,会再次出现 Day 10 / 13 踩过的「测试里没有这个切面」的坑
B. 推迟 body parserNestFactory.create(AppModule, { bodyParser: false }),在 configure() 里发牌之后再挂 json()每个创建 app 的地方(main、每个 e2e、每个脚本)都要记得传 bodyParser: false,漏一个就退回原样
C. 投诉台兜底(nest-lab 的选择)filter 发现没有桌号就补发只改一个文件,所有创建 app 的方式都生效;规则和发牌员共用 resolveRequestId(),不会两套逻辑跑偏
🖥️ 前端翻译: react-hook-form 有 setError(name, { message })。拿到 422 之后,把 pointer 换成表单字段名就能标红:problem.errors.forEach(e => setError(e.pointer.slice(2).replaceAll('/', '.'), { message: e.detail })),#/checklist/1/text 正好变成 checklist.1.text,也就是 useFieldArray 里第 2 项的 text 输入框。没有字段级明细时,前端只能弹一个笼统的「提交失败」。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「圈出来的格子就是表单上的输入框」——pointer 指向的是请求体里的位置。它和前端表单的字段名常常一致,但不保证:前端可能把「开始日期 + 结束日期」两个输入框合成一个 range 字段发给后端。映射规则要前后端约定好。#/id 这种「多余字段」错误在表单上也找不到对应的输入框,只能整体提示。
  2. 「补发了桌号牌,这个请求就和其他请求一样完整了」——只补了投诉台之后的部分。JSON 语法错误的请求没经过发牌员,也没经过登记员,所以日志里没有「进门 / 出门」两行,只有投诉台那一行(带着补发的桌号)。补发能保证「回执单上有桌号、响应头里有桌号、投诉台的日志带桌号」,但前面那几站确实没发生过。
  3. 「errors 是标准字段」——它是本项目选的扩展。RFC 9457 附录里的示例用的就是 errors + pointer + detail,但没有强制。ASP.NET Core 的 ValidationProblemDetails 用的是字典 "errors": {"Title": ["…"]},Spring 默认没有字段明细。接入别家 API 时要看它的文档,别假设所有 problem+json 的扩展都一样。
④ 真实术语: JSON Pointer(RFC 6901,# 开头的是 URI fragment 形式);ValidationPipe 的 exceptionFactory;class-validator 的 ValidationError 树(property / constraints / children);Express 中间件的注册顺序 = 执行顺序;Nest 的 bodyParser: false 选项和 app.useBodyParser()。

✅ 总结与自测

今天带走的 4 句话

  1. 所有错误都用同一张回执单:RFC 9457 problem+json,Content-Type: application/problem+json,type / title / status / detail / instance + 扩展字段(requestId、errors)。它只规定格式,不规定状态码。
  2. type 是对外契约:维护一份公开的错误目录,只增不改;title 同类固定,具体信息放 detail;程序判断看 type,不解析 detail;没登记的状态码用 about:blank。
  3. 校验错误按字段给出:exceptionFactory 把错误树压平成 errors: [{ pointer: '#/checklist/1/text', detail }],前端能直接映射到输入框。
  4. 对外克制,对内详尽;每张回执单都有桌号:500 只给通用说明,真实原因进日志(日志本身也要脱敏);body parser 跑在发牌员之前,所以 filter 兜底补发 requestId。
