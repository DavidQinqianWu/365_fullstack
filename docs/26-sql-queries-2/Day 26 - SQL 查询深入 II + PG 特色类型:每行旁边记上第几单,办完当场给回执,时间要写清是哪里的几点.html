📇 概念卡 #1:窗口函数 —— 每一行旁边记上「这是他的第几单」

① 一句话大白话: 窗口函数和聚合一样是「对一组行做统计」,区别在于它不把行压扁:每一行都还在,只是旁边多了一列结果。OVER (PARTITION BY 分组 ORDER BY 排序) 定义「对哪一组、按什么顺序」看。常用的有:编号排名 row_number / rank / dense_rank,看前后行 lag / lead,以及把 sum / avg 变成累计和、移动平均。

② 生活类比:在账本每一行旁边用铅笔记一笔

Day 25 的 GROUP BY 像月底统计:按会员把订单分堆,每堆写一张汇总单,原来的订单就看不到了。窗口函数像在原来的账本上,每一行旁边用铅笔写上「这是 Alice 的第 3 单」「到这一单为止 Alice 累计花了 90 分钟」「比她上一单晚了 18.5 小时」。一行都不撕,所以你还能拿着这些铅笔字去挑「每个人的最后一单」。

(后两种只保留了结果行。)三种写法对 Alice 和 Bob 的结果完全一致;LATERAL 那种是从 users 出发再 LEFT JOIN,所以 Carol 也在,只是没有最新任务。怎么选:要可移植、要 Top-N,用 row_number;在 PostgreSQL 里只要每组一行,DISTINCT ON 最短;要从「组」那张表出发、每组只取几行(而且有合适的索引时),LATERAL 往往最快,原因 Week 5 看执行计划时就明白了。注意三种写法的排序里都加了 id DESC:两个任务创建时间相同时,也要有确定的答案(和 Day 19 的 tie-breaker 是同一个道理)。

-- 窗口函数写在 WHERE 里
ERROR:  window functions are not allowed in WHERE

最后那个报错和 Day 25 的「WHERE 里不能用别名、不能用聚合」是同一个原因:窗口函数在逻辑执行顺序的 SELECT 这一步才计算,WHERE 早就执行完了。所以「每组最新」的写法 ① 要套一层子查询,先算出 rn,再在外层 WHERE rn = 1。这条规则也说明了为什么窗口函数「能看到」WHERE 过滤后剩下的所有行:上面 lag 那条加了 WHERE owner_id = 1,窗口里就只有 Alice 的四行。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「记完铅笔字,账本就变成每人一行了」——窗口函数从不减少行数。想要「每组一行」,还得自己再过滤(WHERE rn = 1)或用 DISTINCT ON。新手常写出「窗口函数算出了每个用户的总数,但每个用户出现了好几次」的结果,然后再加一个 DISTINCT 去补救。那种时候,其实该用的是 GROUP BY。
  2. 「第几单是固定的」——row_number 只在排序能分出先后时才确定。两个任务预估都是 30 分钟,哪个排第 3、哪个排第 4,这次和下次可能不一样。用它做分页或「取第一个」时,排序键最后一定要加一个唯一的列(id)。
  3. 「铅笔字不要钱」——窗口函数通常需要先排序。PARTITION BY + ORDER BY 意味着数据库要把行按这个顺序排好,数据量大时这是一笔真实的开销,能不能利用索引避免排序是 Week 5 的内容。
④ 真实术语: window function;OVER / PARTITION BY / ORDER BY;window frame(ROWS / RANGE BETWEEN … PRECEDING AND … FOLLOWING);WINDOW 子句(给窗口定义起名,多处复用);ranking functions(row_number / rank / dense_rank / ntile);offset functions(lag / lead / first_value / last_value);greatest-n-per-group(每组 Top-N,经典问题名);DISTINCT ON;LATERAL join。

📇 概念卡 #2:UPSERT 与 RETURNING —— 一个动作办完,当场给回执

① 一句话大白话: INSERT … ON CONFLICT 在插入时如果撞上某个唯一约束,不报错,而是按你的吩咐处理:DO NOTHING(算了)或 DO UPDATE SET …(改成更新),这种「有就更新、没有就插入」的操作俗称 UPSERT。判断和插入是数据库在一个动作里完成的,所以并发下也是安全的。RETURNING 让 INSERT / UPDATE / DELETE 直接把写入后的行返回给你,不用再查一次。

② 生活类比:一个动作办完,当场给回执

以前办事要两步:前台先翻名册看有没有这个人(查),再决定是开卡还是改电话(写)。两个前台同时办同一个人,就会各开一张卡(Day 24 实测过)。现在账房有了一个新窗口:「按邮箱办理:有这个人就更新最后来访时间,没有就开卡」,账房自己一次办完,中间不留空档。办完以后,账房当场递出一张回执,上面写着卡号、开卡时间、现在的状态,前台不用再跑一趟去查。

  • Dave 的 id 是 7,不是 4。前面插入 Alice 的三次尝试(DO NOTHING、报错的那次、DO UPDATE)都先从序列拿了号,然后才发现冲突。这就是 Day 24 说的「主键有空洞」:UPSERT 用得很多的表(比如每次登录都 upsert),id 会跳得很快,这也是默认用 bigint 的理由之一。
  • DO UPDATE 的回执也是 INSERT 0 1:不管实际是插入还是更新,psql 都显示 INSERT。想知道到底是哪一种,可以 RETURNING (xmax = 0) AS inserted,这是一个依赖 PostgreSQL 内部实现的常见技巧,今天不展开。

-- 「先试着插,插不进去就再查一次」写成一条语句
WITH ins AS (
  INSERT INTO tags (name) VALUES ('urgent') ON CONFLICT (name) DO NOTHING RETURNING id
)
SELECT id FROM ins
UNION ALL
SELECT id FROM tags WHERE name = 'urgent' AND NOT EXISTS (SELECT 1 FROM ins);
 id
----
  3

DO NOTHING 时,已存在的那一行不会出现在 RETURNING 里,这是写「get or create」时最常见的坑:代码以为一定能拿到 id,结果拿到空数组。上面的 CTE 写法是一种常见解法(插进去了就用插入的 id,没插进去就去查)。另一种写法是 DO UPDATE SET name = EXCLUDED.name RETURNING id,用一次「假更新」换来一定有回执,代价是每次都真的写了一行。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「账房会判断这个人是不是来过」——UPSERT 只认唯一约束。「同一个人」的定义完全取决于你建了哪个唯一约束:如果邮箱唯一约束是区分大小写的,Alice@… 和 alice@… 就是两个人(Day 24 用 lower(email) 唯一索引解决,这时冲突目标要写成 ON CONFLICT ((lower(email))))。没有唯一约束,UPSERT 根本写不出来。
  2. 「有就更新、没有就插入,所以永远只是一行」——DO UPDATE 会覆盖别人刚写的值。两个请求同时 upsert 同一个用户的不同字段,后到的会按自己的 SET 覆盖。SET 里只写你真正想改的列,别写 SET email = EXCLUDED.email, display_name = EXCLUDED.display_name, … 一把全覆盖。更复杂的并发更新(丢失更新)是 Week 6 的内容。
  3. 「回执上一定有我要的东西」——DO NOTHING 的回执里没有已存在的那一行。上面实测过。另外,RETURNING 返回的是数据库里的真实值(包括触发器、默认值改过的),这正是它比「应用自己记着刚才插入了什么」更可靠的地方,但前提是你真的读了它。
④ 真实术语: UPSERT;INSERT … ON CONFLICT (conflict_target) DO NOTHING | DO UPDATE SET …;EXCLUDED 伪表;conflict target / arbiter index;RETURNING;get-or-create;atomic operation;MERGE(SQL 标准,PostgreSQL 15 起;17 起 MERGE 也支持 RETURNING)。

📇 概念卡 #3:JSONB、数组与时间 —— 便条、一格多值、写清是哪里的几点

① 一句话大白话: PostgreSQL 有几种「一般数据库没有或不常用」的类型。JSONB:一个格子里放一整段 JSON,能按里面的字段查询,但数据库不检查里面的类型和引用。数组(text[]):一个格子里放一串值。timestamptz:一个绝对时刻,读出来时按会话时区显示;timestamp(不带时区):只是一串「墙上的数字」,不知道是哪里的几点。后端的时间一律用 timestamptz。

② 生活类比:订单背面的便条,和写清楚是哪里的几点

订单正面是印好栏目的表格,每一栏账房都会检查;背面允许附一张便条,写什么都行:「客人从小程序下的单」「要求不放葱」。便条很方便,但账房不会检查便条上写的会员号是不是真的存在,也没法按「不放葱」去统计。数组像在一格里写「辣、招牌、新品」,省了一张对照表,但哪天「招牌」改名成「主厨推荐」,就得把每一张订单都翻出来改。记时间时,上海分店写「17:00」,柏林分店也写「17:00」,如果不写清楚是哪里的 17 点,总部根本对不上账;timestamptz 的做法是统一换算成世界时记下来,谁来看就按谁的当地时间念给他听。

  • timestamptz 记住的是「哪一刻」:上海的 17:00 在柏林显示为 10:00+01、在 UTC 显示为 09:00+00,都是同一刻。timestamp 只记住了「17:00」这几个数字,不管谁来读都是 17:00;上海和柏林各自写入的「17:00」实际相差 7 小时,timestamp 却认为它们完全相同(相差 0)。用户分布在不同时区的系统,用 timestamp 迟早会排错序、算错时长。
  • 夏令时:柏林在 2026-03-29 凌晨把时钟从 2 点拨到 3 点,这一天只有 23 小时。+ interval '1 day' 是「日历上的明天同一时刻」(还是 12:00),+ interval '24 hours' 是「过 24 个小时」(墙上变成了 13:00)。哪个对取决于业务:「明天同一时间提醒我」要 1 day,「24 小时后过期」要 24 hours。注意这种计算结果取决于会话时区,应用里要么固定会话时区为 UTC,要么在计算时显式写 AT TIME ZONE。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「便条也是订单的一部分,账房会核对」——JSONB 里的东西数据库不校验类型、不能加外键、不能加唯一约束。它适合结构多变、只跟着这一行读写的附属数据(第三方回调原文、客户端信息、实验性的配置)。需要外键、唯一、频繁按字段过滤和聚合的核心数据,放进 JSONB 就是在逃避建模(Day 23 卡片 #3 的边界)。按 JSONB 字段查询在大表上要靠 GIN 索引,Week 5 讲。
  2. 「timestamptz 把时区也存下来了」——它并不存时区。它存的是一个绝对时刻(内部就是相对于 UTC 的一个数),写入时按会话时区(或你写的偏移)换算成这个时刻,读出时再按当前会话时区换算回来显示。原来是「上海时间」这个信息是丢掉了的。如果业务需要知道「用户当时在哪个时区」(比如按用户当地日期统计),要另外存一列时区名(如 'Asia/Shanghai')。
  3. 「一格多值和对照表只是写法不同」——数组省掉的是 JOIN,丢掉的是约束和独立性。数组里的元素没有外键、不能单独有属性(比如「这个标签是谁贴的」)、改名要改每一行。Day 23 的规则仍然适用:元素是一个独立的实体,就用中间表。

✅ 总结与自测

今天带走的 4 句话

  1. 窗口函数不折叠行,只在每行旁边多一列组内统计:row_number / rank / dense_rank(并列时不同)、lag / lead、累计和 / 移动平均。每组最新:row_number() = 1(可移植、能 Top-N)、DISTINCT ON(PG 最短)、LATERAL(从组出发、可保留空组),排序最后加唯一列。它在 SELECT 阶段才算,不能写在 WHERE 里。
  2. UPSERT 靠唯一约束原子地判断「是否已存在」:DO NOTHING / DO UPDATE SET … = EXCLUDED.…;并发注册时第二个请求不报错、事务照常提交;冲突也会消耗序列号;DO NOTHING 的 RETURNING 不返回已存在的行。
  3. RETURNING 当场给回执:INSERT 拿 id 和默认值(201 + Location)、UPDATE 拿更新后的行、返回 0 行就是 404。一次往返,不需要先查。
  4. JSONB 是便条,不是表:方便、能查,但不校验、不能加外键;nest-lab 的 checklist 用子表,读时用 json_agg 拼形状。标签用中间表不用数组。时间一律 timestamptz:存绝对时刻(不存时区),按会话时区显示,应用输出 ISO 8601 UTC;夏令时下 1 day ≠ 24 hours。
