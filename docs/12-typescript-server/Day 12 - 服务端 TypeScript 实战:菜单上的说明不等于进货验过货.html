🧾 接上回:钥匙写死在代码里

Day 11 的全局保安认的钥匙是 'let-me-in',直接写在代码里。这会带来三个问题:换钥匙要改代码重新发布;开发环境和生产环境用的是同一把钥匙;钥匙跟着代码进了 git,谁能看代码谁就能开门。

正确做法是把这类「每个环境不一样」的东西放进环境变量(process.env)。但环境变量有个大坑:它来自外部世界(部署平台、.env 文件、你的终端),TypeScript 管不着。

💡 生活翻译: 菜单上写着「本店牛排均为 200 克」,这是说明(类型)。说明写得再清楚,也不能保证供应商今天送来的肉真的是 200 克,所以后厨收货时要上秤验货(运行时校验)。连锁店开门前还有一张开店检查单:煤气、电、营业执照逐项核对,有一项不合格就不开门,而不是营业到一半才发现没有煤气。今天就是给 nest-lab 加上「验货」和「开店检查单」。

📇 概念卡 #1:类型 ≠ 校验 —— 菜单说明 vs 进货验货

① 一句话大白话: TypeScript 的类型只在写代码时存在,编译后全部消失;从外面进来的数据(请求体、环境变量、第三方接口的响应)在运行时什么都可能是,必须真的检查一遍才能当成你以为的类型用。

② 生活类比:菜单说明 vs 进货验货

菜单(类型)是写给店里自己人看的约定:「牛排 200 克」。店里的厨师互相传菜时,大家都照菜单办事,所以店内靠菜单就够了。但供应商不看你的菜单,他送来什么就是什么。所以在收货口(系统边界)要上秤:合格才入库,入库以后店里就可以放心按菜单来。as Task 相当于收货员看都不看就在单子上签了「200 克」。

比喻 ↔ 真实 对照

比喻真实组件
菜单上的说明TS 类型(type Task = {...}),编译后被擦掉
看都不看就签字as Task / any:让编译器闭嘴,不做任何检查
「来路不明,先别动」unknown:不检查就不能用(比 any 安全)
上秤验货运行时校验:手写类型守卫 x is Task,或 zod 的 schema.parse()
收货口系统边界:HTTP 请求体、process.env、第三方 API 响应、读文件、读消息队列
「验货标准」和「菜单」用同一张纸印zod:const schema = z.object({...}) 负责验货,type T = z.infer<typeof schema> 自动生成菜单
🖥️ 前端翻译: 你在前端多半已经这么干过:react-hook-form + zodResolver(schema) 校验表单,同一个 schema 用 z.infer 得到表单值的类型。后端是一样的套路,只是「不可信的输入」从「用户在表单里打的字」变成了「任何人发来的 HTTP 请求和部署平台注入的环境变量」。fetch(...).then(r => r.json() as User) 这种写法在前端也一样危险,只是后端出事的代价更大。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「菜单写清楚了,后厨就不会出错」——编译期检查只管你自己写的代码。编译器能保证「你的代码之间」类型一致,但它看不见运行时从网络、磁盘、环境变量进来的东西。JSON.parse 返回 any,process.env.X 是 string | undefined,这两处一不小心就把「外部世界」直接放进了你的类型系统。
  2. 「每道菜上桌前都再称一次」——没必要,也有成本。zod 校验是真实的运行时代码,要遍历对象、生成错误信息。正确做法是只在收货口验一次(请求进来、配置加载、外部响应回来),验过之后的数据在店内用类型传递就行。不要在热路径上对内部数据反复 parse。
  3. 「自己写的验货规则一定对」——手写类型守卫也是你在对编译器打包票。function isTask(x): x is Task 里少检查一个字段,编译器照样相信你。所以字段多了就用 zod 这种从 schema 生成校验和类型的库,让「验什么」和「类型是什么」只写一遍,不会两头对不上。
④ 真实术语: type erasure(类型擦除):TS 编译成 JS 时删掉所有类型;type assertion(as):断言,不是转换;unknown vs any:any 关掉检查,unknown 要求先收窄再用;type guard / narrowing(类型守卫 / 收窄);discriminated union(可辨识联合):用一个公共字段(如 ok: true | false)区分几种形状,判断后 TS 自动收窄;schema validation:zod 的 parse(失败抛错)/ safeParse(返回 { success, data | error },本身就是一个 discriminated union)。
口诀:Parse, don't validate —— 在边界把 unknown 解析成有类型的值,之后就只和有类型的值打交道。

📇 概念卡 #2:类型安全的 env 配置 —— 开店检查单

① 一句话大白话: 启动时把所有环境变量按一张清单逐项检查,该转数字的转数字、该有的必须有;有一项不合格就直接拒绝启动,并说清楚哪一项错了。检查通过后,代码里读到的配置都有正确的类型。

② 生活类比:开店检查单

开门前,店长拿着检查单逐项核对:「煤气:有;电:有;营业执照:有,未过期;今天的门禁钥匙:已更换」。任何一项不过,今天就不开门,而且检查单上会写明是哪一项不过。这比营业到晚上八点、客人点了一份需要明火的菜,才发现煤气没开要好得多。

// src/config/env.schema.ts —— 一份定义两用
export const envSchema = z
  .object({
    NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
    PORT: z.coerce.number().int().min(0).max(65535).default(3000),   // '3000' → 3000
    DEMO_KEY: z.string().min(8, '至少 8 个字符').default('let-me-in'),
    LOG_REQUESTS: z.stringbool().default(true),                       // 'false' → false
  })
  .superRefine((env, ctx) => {                                       // 按 NODE_ENV 分支的规则
    if (env.NODE_ENV === 'production' && env.DEMO_KEY === 'let-me-in') {
      ctx.addIssue({ code: 'custom', path: ['DEMO_KEY'], message: '生产环境必须设置自己的 DEMO_KEY,不能用默认值' });
    }
  });
export type Env = z.infer<typeof envSchema>;   // { NODE_ENV: 'development' | 'test' | 'production'; PORT: number; ... }

// src/app.module.ts
ConfigModule.forRoot({ isGlobal: true, validate: validateEnv })   // validateEnv 里调用 envSchema.safeParse

// src/common/demo-key.guard.ts —— 类型安全地读
constructor(private readonly reflector: Reflector, config: ConfigService<Env, true>) {
  this.demoKey = config.get('DEMO_KEY', { infer: true });   // string;key 拼错是编译错误
}

🖥️ 前端翻译: Vite 的 import.meta.env.VITE_API_URL、Next.js 的 process.env.NEXT_PUBLIC_API_URL 也全是字符串,而且是构建时被直接替换进 JS 包里的。所以带 NEXT_PUBLIC_ 前缀的变量所有访问网站的人都能看到,密钥绝对不能加这个前缀。服务端的 env 是运行时读的,不会进浏览器,但一样要校验。前端圈的 t3-env(@t3-oss/env-nextjs)做的就是今天这件事:用 zod 校验 env,分开声明 server / client 变量。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「检查单上写的是数字,进来的就是数字」——process.env 里永远是字符串(或者没有)。所以一定要显式转换。最常见的坑是布尔值:z.coerce.boolean() 等于 Boolean(x),'false' 会变成 true(非空字符串都是真)。要用 z.stringbool()(zod 4),它只认 true/false/1/0/yes/no/on/off 这些写法。
  2. 「检查单通过了,今天就一定没问题」——它只检查「格式」,不检查「真假」。DEMO_KEY 长度够 8 个字符就算过,至于它是不是团队约定的那把钥匙、DATABASE_URL 指向的数据库能不能连上,检查单都不知道。连通性要靠启动后的健康检查(Week 14 的 readiness probe)。另外检查单只在开门时核对一次,进程运行中改环境变量不会生效,要重启。
  3. 「默认值越多越省事」——默认值是双刃剑。开发时不用配任何东西就能跑,很方便;但生产环境忘了配,就会悄悄用上开发默认值(比如演示钥匙)。所以今天加了一条按 NODE_ENV 分支的规则:生产环境用默认钥匙就拒绝启动。真正的密钥(数据库密码、JWT 密钥)根本不该有默认值。
④ 真实术语: fail fast(快速失败);12-Factor App 的第三条「配置存在环境里」(Config in the environment),代码和配置分离;@nestjs/config:ConfigModule.forRoot(validate 函数,或者 Nest 12 也支持直接传 validationSchema: envSchema,因为 zod 实现了 Standard Schema 接口)、ConfigService<Env, true>(第二个泛型 true 表示「已校验」,get 不再返回 undefined);优先级:进程里已有的环境变量高于 .env 文件,这也是测试能在 vitest.config.ts 里用 test.env 固定配置、不受本机 .env 影响的原因。
另一种常见写法是按领域拆配置:registerAs('db', () => ({...})) + @Inject(dbConfig.KEY) cfg: ConfigType<typeof dbConfig>,Week 4 接 PostgreSQL 时会用到。

  • 失败时一条路由都没注册(没有 Mapped {...}),进程直接以 1 退出。部署平台(Week 14 的 Docker / K8s)看到退出码非 0,就知道新版本起不来,不会把流量切过去。
  • 错误一次列全:第 2 幕-C 三个问题一起报出来,不用改一个、重启一次、再发现下一个。
  • LOG_REQUESTS=false 真的生效了:第 3 幕的请求日志里没有 → ① Middleware 进门,因为 configureApp 读到的是布尔值 false,不是字符串 'false'。

📇 概念卡 #3:DI token 的类型安全 —— 工牌号上印岗位

① 一句话大白话: Day 9 的 CLOCK = Symbol('CLOCK') 只是一个编号,它不知道自己该配一个 Clock;给 token 带上类型,登记时编译器就能检查「配进去的东西对不对」。

② 生活类比:工牌号上印岗位

人事部的登记簿上,工牌号 CLOCK 只是一串编号。有人把一个「报时会说『大概下午吧』的人」登记到这个编号下,人事部照收不误,直到后厨要用准确时间算出餐时长时才出事。改进办法:工牌上直接印岗位要求「CLOCK · 必须能报出精确时间(Date)」。登记的时候人事部对照一下,不符合的当场退回。

// src/common/typed-token.ts
declare const tokenType: unique symbol;
export type TypedToken<T> = symbol & { readonly [tokenType]?: T };   // 运行时就是 symbol,编译期多一个类型标记
export const createToken = <T>(description: string) => Symbol(description) as TypedToken<T>;
export const valueProvider = <T>(provide: TypedToken<T>, useValue: T) => ({ provide, useValue });
export const classProvider = <T>(provide: TypedToken<T>, useClass: Type<T>) => ({ provide, useClass });

// src/common/clock.ts
export const CLOCK = createToken<Clock>('CLOCK');

// src/tasks/tasks.module.ts
providers: [
  classProvider(TASKS_REPOSITORY, InMemoryTasksRepository),   // 类必须实现 TasksRepository
  valueProvider(CLOCK, systemClock),                           // 值必须是 Clock
]

比喻 ↔ 真实 对照

比喻真实组件
只有编号的工牌普通 Symbol('CLOCK'):{ provide: CLOCK, useValue: 任何东西 } 都能编译
印了岗位要求的工牌TypedToken<Clock>:运行时还是 Symbol,编译期带着 Clock 这个类型
登记时当场核对valueProvider(CLOCK, x) / classProvider(TOKEN, Cls):泛型参数要求 x 是 Clock、Cls 能 new 出 T
按检查单读配置ConfigService<Env, true>:key 和返回类型都来自 Env(卡 #2)
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「工牌上印了岗位,领人的那一头也会核对」——不会,只管登记那一头。@Inject(CLOCK) private readonly clock: Clock 这一行,TS 的参数装饰器拿不到参数的类型,你写成 clock: string 编译器也不会拦。两头都要安全,就靠约定(token 和类型放在同一个文件里导出)+ 测试。
  2. 「工牌上印的字,运行时也能读到」——读不到。那个类型标记只存在于编译期,运行时 CLOCK 就是一个普通的 Symbol(CLOCK)(习题 1 的 ex2 打印出来给你看),Nest 容器完全不知道它带过类型。
  3. 「类型对了,行为就对了」——类型只管形状。测试里的假时钟永远返回 2026-01-01,类型完全正确,这正是我们想要的;但如果生产环境不小心也登记了它,类型检查同样会放行。「登记了哪个实现」仍然要靠代码审查和测试。
④ 真实术语: branded / phantom type(品牌类型 / 幽灵类型):只在编译期存在、用来区分「看起来一样的值」的类型标记;InjectionToken(Nest 的 token 类型:类、字符串、Symbol 都行);Type<T>(能 new 出 T 的类)。Angular 的 new InjectionToken<Clock>('CLOCK') 是官方内置的同款思路;Nest 没有内置,所以今天自己写了 15 行。另一个现成的类型安全写法是卡 #2 末尾提到的 registerAs + ConfigType<typeof xxx>。

✅ 总结与自测

今天带走的 4 句话

  1. 类型是菜单说明,校验是进货验货:TS 类型编译后消失,外部输入(env、请求体、第三方响应)运行时都是 unknown;as 只是让编译器闭嘴。在边界验一次,之后靠类型传递。
  2. zod 一份定义两用:schema 负责运行时校验和转换,z.infer 负责编译期类型,不会两头对不上。
  3. env 配置 = 开店检查单:process.env 里永远是字符串,用 z.coerce.number() / z.stringbool() 转换(别用 z.coerce.boolean());启动时校验,不合格就拒绝启动(fail fast),错误一次列全;生产环境不许用演示默认值;.env.example 提交,.env 不提交。
  4. 带类型的 token 让登记那一头可检查:valueProvider(CLOCK, x) 配错会编译报错;但 @Inject 那一头的参数类型仍然没人检查,运行时 token 也还是普通 Symbol。
