⚠️ 为什么 ② 在修之前的内存版上「通过」了

修之前,内存仓储的 findById 交出去的是数组里那个对象本身。插进来的请求用 Object.assign 改了它,改标题的请求手里的「快照」也跟着变成了已完成,于是 409。测试通过,原因却是错的:PG 版读到的是真正的快照,结果相反。今天把内存仓储改成一律交出复印件(structuredClone),两边的行为一致了。

那内存版到底会不会有竞态?✍️ 预测:Node 是单线程的,内存仓储里没有任何延迟,两个请求同一时刻发出,修之前会违规吗?npm run day40 第 6 幕:

  修之前:违规 20 / 20
  乐观锁:违规 0 / 20
  悲观锁:违规 0 / 20

单线程保证的是同步代码中间不会被打断。await repo.findById() 之后函数就暂停了,另一个请求的代码在这时跑完它的读;两个请求都拿着「未完成」继续往下走。插队发生在 await 和 await 之间。所以内存版 update 里「检查版本 + 写」这几行中间没有 await,天然是原子的;而 Service 里「读 → 判断 → 写」跨了两个 await,不是。

先查后删呢?

remove() 没有这个问题:PG 版先 findById(为了返回被删的那条),但真正决定结果的是 DELETE 的 rowCount,0 行就是 404。用例 ③(两个 DELETE 同时到达)修之前就通过:一个 204、一个 404。删除没有「基于读到的内容做判断」,所以不需要版本号。

📇 概念卡 #1:乐观锁 —— 看账页右上角的版本号

① 一句话大白话: 读的时候不加锁,但记下「我读到的是第几版」。写的时候说:「只有它还是第 3 版,才写,并把它变成第 4 版。」如果已经不是第 3 版,说明在我读和写之间有人改过,这次什么都不写,告诉我「被抢先了」。由我决定是重新读一遍再来,还是告诉用户。

② 生活类比:账页右上角的版本号

账本每一页的右上角写着一个数字。伙计抄走一页去算账时,顺便记下这个数字(比如 3)。算完回来写账之前,先看一眼右上角:

  • 还是 3:写上去,把 3 划掉改成 4。
  • 已经是 4:有人在你算账的时候改过这一页了。你手里的那份抄件过时了,不能照着它写。重新抄一遍再算。

谁都不用等谁,也不用在账页上压东西。只有真撞上的时候,后到的那个人白算一遍。

③ 类比的边界 ⚠️

  • 「看一眼」和「写上去」必须是同一个动作。如果先 SELECT version 看一眼、再 UPDATE,中间又能被插队,等于没做。真实写法把检查放进 UPDATE 自己的 WHERE 里:UPDATE … SET …, version = version + 1 WHERE id = $1 AND version = $2。数据库保证这一条语句的检查和写入之间不会被插队(两个事务同时 UPDATE 同一行,后一个会等前一个提交,再用最新的行重新检查 WHERE,Day 37、39),所以 Read Committed 就够,不需要提高隔离级别。
  • 版本号不是时间。它只能说明「变没变」,不能说明「谁先谁后、变了什么」。想合并两份修改,要自己去比较内容。
  • 改了什么都要 +1。nest-lab 的清单项在子表 checklist_items 里;只改清单的时候,tasks 这一行也要 UPDATE 一下把版本号 +1,不然别人察觉不到「清单被改过」。
  • 0 行有两种意思:版本对不上,或者这一行已经被删了。nest-lab 在 0 行时再查一次 id 在不在,在就是 409,不在就是 404。

④ 真实术语

乐观并发控制(optimistic concurrency control,OCC),口语叫乐观锁。「乐观」是假设冲突很少,所以先不锁,冲突了再处理。虽然叫「锁」,但它不持有任何锁:这也是它能跨请求使用的原因(第 6 节)。

在 nest-lab 里的写法

仓储(pg-tasks.repository.ts,节选):

const sets = ['version = version + 1'];          // 改了什么都 +1
if (changes.title !== undefined) sets.push(`title = $${params.push(changes.title)}`);
if (changes.done !== undefined) sets.push(`done = $${params.push(changes.done)}`);
const versionCheck = expectedVersion === undefined ? '' : ` AND version = $${params.push(expectedVersion)}`;
const { rowCount } = await client.query(`UPDATE tasks SET ${sets.join(', ')} WHERE id = $1${versionCheck}`, params);
// rowCount 0 → 再查一次:SELECT 1 FROM tasks WHERE id = $1 → 在:stale(409),不在:not-found(404)

Service(tasks.service.ts,节选):

return await withRetry(async () => {
  const current = await this.findOne(id);                                    // 404 在这里
  if (input.version !== undefined && input.version !== current.version) throw stale; // 客户端基于的版本已过时
  assertCanChange(current, input);                                           // 业务规则:409 task-completed
  const result = await this.repo.update(id, changes, current.version);       // 带着「我读到的版本」写
  if (result.status === 'updated') return result.task;
  if (result.status === 'not-found') throw new NotFoundException(…);
  if (input.version !== undefined) throw stale;   // 客户端给了 version:交给客户端决定
  throw new LostRace();                            // 没给:服务器替它整轮重做
}, { isRetryable: (e) => e instanceof LostRace, maxAttempts: 3, baseDelayMs: 5, maxDelayMs: 50 });

重做的是整轮:重新读、重新判断业务规则、再写。这正是用例 ② 需要的:改标题的请求被抢先之后重读,发现任务已经完成,于是 409 task-completed,不会把标题写进一个已完成的任务。

API 怎么变:version 放在请求体里,可选

请求行为
PUT / PATCH 带 "version": 3当前不是第 3 版 → 409 conflict/stale-version,什么都不写。写的时候才发现被抢先,也是 409
PUT / PATCH 不带 version和以前一样能用;服务器保证自己这一轮「读 → 判断 → 写」不被插队(被抢先就重做,最多 3 轮)
所有任务响应(v1、v2)新增 version 字段
PATCH 只给 version422:「至少要给 title、done、checklist 中的一个」
"version": 0 或不是整数422(@IsInt @Min(1))

兼容性(按 Day 19 的规则判断):响应新增字段、请求新增可选字段、新增一个 problem type,都是非破坏性变更,老客户端不用改。如果把 version 设成必填,所有老客户端的 PUT / PATCH 都会变成 422,那就是破坏性变更,要走版本化。

还有一个变化要说清楚:每次写入成功 version 都 +1,包括内容完全相同的 PUT。test/rest.e2e-spec.ts 里「PUT 重复发结果不变(幂等)」的用例因此改成「除了 version 都相同,version 每次 +1」。幂等说的是对资源状态的效果:标题、完成状态、清单都没变;版本号像 updated_at 一样记录的是「被写过几次」。反过来,带着同一个 version 把 PUT 重放两次,第二次是 409,这让「重放」变得可以察觉。

openapi.json 重新生成后的差异:TaskResponse 多了必填的 version(integer);ReplaceTaskDto、UpdateTaskDto 多了可选的 version(integer,minimum 1);PUT / PATCH 的描述和 409 的说明更新了。没有删除或改名任何东西。

为什么今天不用 HTTP 标准的 ETag / If-Match / 412?它们做的是同一件事(条件请求),但要同时处理响应头、弱 ETag、If-None-Match 的缓存语义,Week 12 讲 HTTP 缓存时一起做。到时候 ETag 的值可以就从 version 算出来。

📇 概念卡 #2:悲观锁 —— 先压上镇纸再看

① 一句话大白话: 在读之前先把这一行锁住(SELECT … FOR NO KEY UPDATE),再读、判断、写,事务提交时才放开。别人想改这一行,只能排队;排到的时候,读到的已经是前一个人改完的最新状态。冲突的请求不会失败,只是等。

② 生活类比:Day 39 的镇纸

伙计要按某一行算账,先在那一行压上镇纸,再抄、再算、再写,写完盖章才拿开。第二个伙计来改同一行,看见镇纸就站在旁边等。等到镇纸拿开,他看到的是第一个伙计写完之后的账,不会照着旧账算。

③ 类比的边界 ⚠️

  • 镇纸只能在一张作业单(一个事务)里压着。事务一结束锁就放了。HTTP 请求结束时事务早就提交了,所以悲观锁不能跨请求:不能「GET 的时候锁住,PUT 的时候再放开」(第 6 节)。
  • 压着镇纸的时候别出门。锁持有期间做的任何慢事情(调外部 API、等用户、发邮件)都会让排队的人一起等,还占着一个数据库连接。第 3 幕里读和写之间加了 20 ms 延迟,悲观锁在锁里也等了这 20 ms。
  • 不加锁的读不排队。普通 SELECT 不受行锁影响(Day 39),读到的是旧值。悲观锁只对「也来加锁」的人有效,所以所有「读 → 判断 → 写」的代码路径都要用同一种加锁方式,漏一处就漏了。
  • 锁多行可能死锁。今天只锁一行;要锁多行时按固定顺序(Day 39 第 5 幕)。

④ 真实术语

悲观并发控制(pessimistic concurrency control),口语叫悲观锁:假设冲突经常发生,先锁再做。PostgreSQL 里就是 Day 39 的行锁。为什么用 FOR NO KEY UPDATE 而不是 FOR UPDATE:我们不改主键;FOR UPDATE 会挡住「往 checklist_items 插一行引用这个任务」时外键检查要拿的 FOR KEY SHARE,FOR NO KEY UPDATE 不挡(Day 39 的兼容表)。普通 UPDATE 自己拿的也是 FOR NO KEY UPDATE。

在 nest-lab 里的写法

async updateLocked(id, decide) {
  return this.transaction(async (client) => {
    const { rowCount } = await client.query('SELECT 1 FROM tasks WHERE id = $1 FOR NO KEY UPDATE', [id]);
    if (!rowCount) return undefined;
    const current = (await this.findById(id, client))!;  // 锁已经在手:读到的就是最新的
    const changes = decide(current);                     // 抛异常 → transaction() 回滚,锁释放
    await this.writeChanges(client, id, changes);        // 和乐观锁共用,同样 version + 1
    return this.findById(id, client);
  });
}

锁和读分成两条 SQL,因为 SELECT_TASKS 里用 json_agg 拼清单;只锁 tasks 这一行就够了。decide 是同步函数:在它里面不能 await 别的东西,这也是在提醒你「压着镇纸的时候别出门」。

它没有接到 HTTP 上:主线是乐观锁(第 6 节解释原因)。updateLocked 由观察脚本和 test/concurrency.e2e-spec.ts 里的两个用例使用(10 个并发「读计数 → +1 → 写」一个不丢;decide 抛异常时不写、版本不变)。

⚠️ 关于事务边界:今天的写法有个限制

updateLocked 的事务开在仓储里,Service 只能通过 decide 回调把判断塞进去。如果一个业务操作要锁两张表、调用两个仓储,今天的结构就做不到「同一个事务」。Week 7 会讲事务传播:让 Service 开事务、把同一个连接自动交给它调用的所有仓储。用的还是 Day 13 请求 ID 贯穿日志的那个工具 AsyncLocalStorage:那次放进「请求上下文」的是请求 ID,到时候放进去的是「当前事务的连接」(常见做法是 nestjs-cls 和它的 @Transactional();Spring 的 @Transactional 和传播行为 REQUIRED / REQUIRES_NEW 是同一个概念)。今天不引入,先把问题记下来。

⑤ 动手验证。✍️ 预测:A 用 FOR NO KEY UPDATE 锁住任务 3。B 普通 SELECT 会等吗?B 用 NOWAIT 呢?B 不加 NOWAIT 地去锁,A 300 ms 后把 done 改成 true 并提交,B 读到什么?真实结果(第 2 幕,3 遍一致,等待时间 302–305 ms):

  A:BEGIN; SELECT … FOR NO KEY UPDATE → done = false, version = 1(压上镇纸)
  B:普通 SELECT(不加锁)→ 立刻返回 done = false, version = 1(行锁不挡读,读到的是 A 提交前的值)
  B:SELECT … FOR NO KEY UPDATE NOWAIT → ERROR 55P03 could not obtain lock on row in relation "tasks"
  B:BEGIN; SELECT … FOR NO KEY UPDATE → 卡住,在等 A
  A:(300 ms 后)UPDATE … SET done = true, version = version + 1; COMMIT
  B:这时才返回(等了 304 ms),读到 done = true, version = 2 —— 是 A 提交之后的最新值

最后一行是关键:B 排到的时候,读到的不是它开始等时的旧快照,而是 A 提交后的值(Read Committed 下,加锁的读在拿到锁之后读最新提交的版本)。所以 B 的判断基于最新状态。

📇 概念卡 #3:怎么选 —— 客人要想 5 分钟的时候

① 一句话大白话: 如果「读」和「写」在同一个请求里,两种都行:冲突少用乐观锁,冲突多、重做代价大用悲观锁。如果「读」和「写」是两个请求(用户打开编辑页、想一会儿、再保存),只能用乐观锁:锁不能跨请求压着,只有版本号能跟着页面走一趟再带回来。

② 生活类比:客人要想 5 分钟

客人拿着账页的复印件回座位想了 5 分钟,再回柜台说「照这个改」。你不可能让镇纸在账页上压 5 分钟,所有人都得等着;客人也可能根本不回来了。能做的只有:复印件右上角印着版本号,客人回来时对一下。对不上,就告诉他「这页在您想的时候被别人改过了,请看看新的」。

③ 类比的边界 ⚠️

  • 服务器内部的重试救不了跨请求的丢失更新。客户端没带 version 的 PUT,服务器看到的是两个各自合法、先后到达的请求,它没法知道 A 是照着 5 分钟前的页面改的。第 4 幕实测见下面。
  • 409 之后不能原样重试。原样重发等于覆盖别人的修改。要重新 GET 最新内容,让用户确认或合并,再带着新的 version 提交(docs/problems.md 里这样写了)。
  • 乐观锁不是 React Query 的「乐观更新」。乐观更新说的是界面:不等服务器回应就先显示成功,失败了回滚;它不防止覆盖。两者可以一起用:乐观更新先改界面,请求里带上 version,收到 409 时回滚并提示「已被他人修改」。
  • Google Docs 不是乐观锁。它不拒绝后到的修改,而是把两个人的编辑操作实时合并(操作变换 / CRDT 一类的技术,未展开、未实测)。乐观锁只负责「发现冲突」,不负责「合并」。

④ 真实数据:三种写法放在同一组场景里

怎么选

情况选为什么
读和写跨请求(编辑页、表单、离线编辑)乐观锁(只能它)锁不能跨请求;version 跟着客户端走
同一个请求里,冲突少(大多数 CRUD)乐观锁无冲突时没有额外代价,不持锁、不占连接等待
同一个请求里,同一行冲突很多(库存、余额、计数器、抢座)悲观锁,或者干脆用一条原子 SQL乐观锁会大量重做(第 5 幕重做约 9 倍);如果逻辑能写成 SET n = n + 1、SET stock = stock - 1 WHERE stock > 0,一条语句最好(Day 37)
重做的代价很大(调了外部 API、发了消息)悲观锁乐观锁失败要重做整轮
规则涉及多行或「不存在的行」(「至少留一个人值班」、「同一时段不能重复预订」)Serializable + withRetry,或约束 / 咨询锁版本号和行锁都只管「这一行」;写偏斜(Day 37)要 SSI 来发现,发现后报 40001,整轮重做

nest-lab 选乐观锁作主线:任务编辑是典型的跨请求场景(用户在页面上改完再保存),冲突少;同一个请求内部的竞态也顺带解决了(被抢先就整轮重做)。悲观锁的实现留在仓储里,作为对比和以后的备选。

用到的 withRetry 就是 Day 37 写的那个,今天搬进了 nest-lab。它本来是给 40001 / 40P01 用的,今天换了一个 isRetryable,用来重试「写的时候版本变了」。两种情况的道理一样:失败那一轮读到的东西已经过时,必须从头重做,而不是只重试最后一步。

✅ 总结与自测

今天带走的 4 句话

  1. 先查后改有两种翻车:丢失更新(后写的把先写的盖掉,没有报错)和绕过业务规则(基于过时的状态判断通过)。插队发生在 await 和 await 之间,单线程的 Node、内存仓储一样会发生(修之前 20 / 20 次违规)。
  2. 乐观锁:UPDATE … SET …, version = version + 1 WHERE id = $1 AND version = $2,0 行就是被抢先(再查一次区分 404 / 409)。客户端带了 version 就 409 stale-version,没带就整轮重做。Read Committed 就够,因为后到的 UPDATE 会用最新的行重新检查 WHERE。
  3. 悲观锁:事务里先 SELECT … FOR NO KEY UPDATE 再读、判断、写,别人排队,排到时读到最新值(实测等了约 300 ms,读到 version 2)。锁只活在一个事务里,持锁时别做慢事。
  4. 怎么选:跨请求只能乐观锁;同一行冲突多用悲观锁或一条原子 SQL(50 并发同一行:乐观锁重做 414–463 次、451–683 ms,悲观锁 134–316 ms;无冲突时三者都在 20–38 ms);多行规则用 Serializable + withRetry。
