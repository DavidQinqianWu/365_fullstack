📋 接上回:每道菜谱都写一遍「洗手」?

Day 9 我们让总部人事部(IoC 容器)负责招人和接线,前台、后厨只管自己的活。今天来了新要求:老板想知道每个接口花了多少时间、想让每个成功响应都长成同一种格式、想给新建任务加一道门禁、想让所有报错都用同一种格式答复客人。

不用新工具,最直接的写法是在每个 handler 里复制粘贴:

@Get(':id')
findOne(@Param('id') idText: string) {
  const start = performance.now();                          // 计时(每个方法都抄一遍)
  try {
    const id = Number(idText);
    if (!Number.isInteger(id)) throw new BadRequestException(); // 参数转换(每个带 id 的方法都抄)
    const data = this.tasksService.findOne(id);
    return { data, timestamp: new Date().toISOString() };    // 包装(每个方法都抄)
  } finally {
    console.log(`findOne 用时 ${performance.now() - start} ms`);
  }
}
@Post()
create(@Body() body, @Headers('x-demo-key') key: string) {
  if (key !== 'let-me-in') throw new ForbiddenException();   // 门禁(每个要保护的方法都抄)
  const start = performance.now();                           // 计时,又抄一遍……
  /* …… */
}

真正的业务只有一行 this.tasksService.findOne(id),其余全是「每个接口都要、但不属于任何一个接口」的东西。接口一多,有人忘抄、有人抄错,计时格式五花八门。

💡 生活翻译: 连锁店里,每道菜都要「洗手、计时、出餐打包、出事走投诉流程」。如果把这些写进每一道菜谱,一百道菜就要写一百遍,改个打包规则要改一百处。聪明的总部会把它们写成店规(标准作业流程 SOP),贴在门口、出餐口、投诉台,由固定岗位在固定时间执行。菜谱里只写菜怎么做。这就是今天的 AOP(Aspect-Oriented Programming,面向切面编程)。

📇 概念卡 #1:横切关注点与 AOP —— 店规不写进菜谱

① 一句话大白话: 把「每个接口都要做、但跟业务无关」的事(日志、计时、鉴权、错误处理)从业务代码里抽出来写一次,再声明「对哪些接口、在什么时候」自动套上去。

② 生活类比:店规 = 三句话

每一条店规都能拆成三句话:做什么(掐表记录出餐时间)、什么时候做(上菜前开始、上菜后结束)、对哪些菜(全店 / 只有热菜部 / 只有这一道招牌菜)。菜谱完全不用改,厨师甚至不知道有人在掐表。

比喻 ↔ 真实 对照

比喻AOP 术语nest-lab 里
一条店规(整件事)aspect(切面):一个横切关注点的完整实现TimingInterceptor、DemoKeyGuard……
「做什么 + 什么时候做」advice(通知):before(之前)/ after returning(正常返回后)/ after throwing(抛异常后)/ after(无论成败)/ around(包住全程)guard ≈ before;interceptor = around;filter ≈ after throwing
「对哪些菜」pointcut(切点):选中哪些方法挂在哪里:全局 / Controller / 方法 / 参数
每一次「做一道菜」join point(连接点):切面可以插进去的执行点Nest 里就是「一次 handler 调用」
把店规落实到流程里weaving(织入)Nest 启动时把切面和 handler 组装成管线
菜谱业务代码 / 核心关注点TasksService、Controller 方法体
🖥️ 前端翻译: 你早就用过 AOP:axios 拦截器(axios.interceptors.request.use 给每个请求加 token、response.use 统一处理 401)就是 before / after advice;React 高阶组件 withAuth(Page) 是 around advice:一个函数包住另一个组件;Error Boundary 是 after throwing。Next.js 的 middleware.ts 则对应今天的 ① 号站:它在路由匹配之前跑,不知道最后会渲染哪个页面组件。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「店规是另外的人在执行,厨师不受影响」——错。切面代码还是同一个服务员(event loop)在同一次请求里执行的,只是你没在业务方法里看见它。每个请求都多跑了这些代码:切面里写一个慢操作(同步读文件、算哈希),所有被它套住的接口一起变慢。
  2. 「店规对店里发生的一切都生效」——不是。Nest 的切面只套在「经过 Nest 管线的那次 handler 调用」上。你在 TasksService 里直接调用另一个 Service 的方法,不会经过任何 interceptor / guard。Spring AOP 用代理对象能切到 Service 方法级,但也有「类内部自己调自己不生效」的坑。
  3. 「切点 = 一条规则表达式」——在 Nest 里不是。Spring 能写 execution(* com.shop..*Service.*(..)) 这种表达式,按名字批量选方法;Nest 的切点就是「你把它挂在哪」(全局 / 类 / 方法 / 参数)。想让切面按「标签」决定做不做(比如「标了 @Public() 的接口不查钥匙」),要靠 Day 11 的自定义装饰器 + 元数据。
④ 真实术语: cross-cutting concern(横切关注点):日志、计时、鉴权、缓存、事务、异常处理、限流 —— 「横着」切过所有业务模块;separation of concerns(关注点分离):业务代码只关心业务。AOP 的本质很朴素:高阶函数,一个函数接收「原来的 handler」,返回一个「包了一层的新 handler」。Nest 把这件事做成了固定的五种站,按固定顺序织入。

📇 概念卡 #2:管线五件套 —— 登记员、保安、领班、核单员、投诉台

① 一句话大白话: Nest 把「什么时候做」固定成五种站,每种站拿到的信息不同、能做的事不同,你按需求选对站,挂到对的范围上。

② 生活类比:五个岗位各管一段

  • 门口登记员(middleware):人一进门就登记。他只看得到客人本身,不知道客人订的是哪个包间。
  • 保安(guard):手里有订座表,知道客人要去哪个包间(哪个 handler),只做一个决定:进,还是不进。
  • 领班(interceptor):从上菜前一直跟到上菜后,一个人包住全程:开始掐表、菜出来后打包装盘、记下用时。他甚至可以换掉菜(改返回值)或者嫌太慢直接撤单(超时)。
  • 核单员(pipe):把单子上手写的「三」改成数字 3;看不懂的单子直接退回(400)。他只管单子上的某一栏(某一个参数)。
  • 投诉处理台(exception filter):不管哪一站出事,都由这里给客人一个格式统一的答复。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「领班有两个,一个在上菜前,一个在上菜后」——是同一个人、同一个函数。Day 8 图上画成 ②-2 和 ⑤-1 两站,是为了看清时间顺序;代码里只有一个 intercept():next.handle() 之前的代码是去程,.pipe(tap(...)) 里的是回程,两边共享同一个 start 变量。
  2. 「谁先注册谁先执行」——只对同一种站成立。不同种类的顺序是 Nest 写死的:middleware → guard → interceptor → pipe → handler,就算你在代码里先写 @UseInterceptors 再写 @UseGuards,guard 也永远先跑。只有同一种的多个之间,才按「全局 → Controller → 方法」和数组顺序排(今天 Timing 是全局、Wrap 是 Controller 级,所以 Timing 在外层)。
  3. 「登记员也看得到订座表」——看不到。middleware 跑的时候还没有 ExecutionContext,它不知道请求会去哪个 handler,甚至请求可能根本没有匹配的路由(Day 8 的 GET /nope 也经过了 ①)。要按「去哪个接口」做决定,就用 guard / interceptor。

绑定范围:app.useGlobalXxx(new X())(全局,但在 DI 容器之外,不能注入依赖)/ { provide: APP_INTERCEPTOR, useClass: X }(全局,在容器之内,可以注入,接 Day 9)/ @UseXxx() 挂在类或方法上 / pipe 还能挂在单个参数上。今天的 WrapResponseInterceptor 挂在 Controller 上,所以它由 TasksModule 的容器创建,能注入 CLOCK。

核心代码只有这几行(src/common/timing.interceptor.ts):

intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
  const where = `${context.getClass().name}.${context.getHandler().name}`;  // 知道要去哪
  const start = performance.now();                                          // 去程
  return next.handle().pipe(                                                // 调用 handler(还没执行,是个 Observable)
    tap({
      next: () => stop('正常返回'),                                         // 回程:成功
      error: (err) => stop(`抛出了 ${err.constructor.name}`),               // 回程:失败,错误继续往外抛
    }),
  );
}

📇 概念卡 #3:异常短路 —— 哪一站出事,就从哪一站直奔投诉台

① 一句话大白话: 管线上任何一站抛异常,后面的站全部跳过,直接交给 exception filter 写错误响应;所以「请求停在哪一站」决定了哪些切面做了事、哪些没做。

② 生活类比:出事就走投诉通道

保安拦下了客人,客人就不会见到领班和前台;核单员看不懂单子,后厨就不会开火;后厨发现没这道菜,领班的「打包装盘」就不做了(没有菜可打包),但他还是会在本子上记一笔「这单用了多久、结果是退单」。最后,所有出事的客人都被送到同一个投诉处理台,拿到一张格式统一的说明。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「出了事,领班总会记一笔」——只有在他包住的范围里出事才会。Guard 在 interceptor 之前,情况 2 被拦下时领班还没上岗,所以 403 响应没有 X-Response-Time。想让「所有响应」都带这个头(包括被拦的),要放到更外层的 middleware 里(习题 3 的思考题)。
  2. 「投诉处理台是流水线的最后一站」——它是旁路。正常请求(情况 1)根本不经过 filter;出事时,从出事那一站直接跳过去。所以包装 interceptor 的 map 只会包装成功的返回值:成功体是 { data, timestamp },错误体是 filter 写的 { statusCode, error, message, path },两种长得不一样。这不是 bug,而是要你有意识地设计:Week 3 会把错误体升级成 Day 6 手写过的 problem+json(RFC 9457),并决定成功体要不要包装(很多团队选择不包,直接用 HTTP 状态码 + 原始资源)。
  3. 「投诉台接住了,问题就解决了」——它只是给客人一个体面的答复。@Catch() 不写参数会接住所有异常,包括代码 bug 抛的普通 Error:今天的 filter 会回 500 + "Internal server error",故意不把内部报错信息给客户端(防止泄露实现细节),但 bug 本身还在,必须有日志 / 告警让你知道(Week 15 可观测性)。
④ 真实术语: short-circuit(短路):一站失败,后续不再执行;HttpException 家族:ForbiddenException(guard 返回 false 时 Nest 自动抛)、BadRequestException(pipe 失败)、NotFoundException(你自己抛);@Catch(HttpException) 只接 HTTP 异常,@Catch() 接全部;RxJS 错误通道:handler 抛的异常会变成 Observable 的 error 通知,所以 interceptor 用 tap({ error }) 能看见它、用 catchError 能把它换成别的,但 map 不会执行。

「请求管线 + 几种固定的拦截点」是所有企业级后端框架的共同结构,只是每家切的站数和名字不同:

Nest 的站C# / ASP.NET CoreJava / Spring BootGo(net/http / Gin)
① Middleware Middleware(app.Use(...),await next() 前后各做事) Servlet Filter(chain.doFilter()) func(next http.Handler) http.Handler;Gin 的 c.Next()
②-1 Guard Authorization filter / [Authorize] + 授权策略 Spring Security 过滤器链;HandlerInterceptor.preHandle() 返回 false 鉴权 middleware 里 c.AbortWithStatus(403)
②-2 / ⑤-1 Interceptor Action filter(OnActionExecuting / OnActionExecuted,或 IAsyncActionFilter 包住 next());Result filter 改结果 Spring AOP:@Aspect + @Around("execution(...)")(pjp.proceed() 就是 next.handle())、@Before、@AfterReturning;改响应体用 ResponseBodyAdvice 还是 middleware 包 handler;没有「知道去哪个 handler」的专门站
②-3 Pipe Model binding + 验证([FromRoute] int id 转不了自动 400) 参数解析 + @Valid(Bean Validation) 手动 strconv.Atoi(c.Param("id"))
⑤-2 Exception Filter Exception filter;更常用 UseExceptionHandler middleware + ProblemDetails @ControllerAdvice + @ExceptionHandler(Spring 6 内置 ProblemDetail) recover() middleware + 自己写错误响应
绑定范围 全局 options.Filters.Add(...) / Controller 或 Action 上的 Attribute 切点表达式按包名、方法名、注解批量选 挂在 router / 路由分组 / 单个路由上

📌 两个值得记的差异:Spring AOP 的切点是表达式,能切到任意 Bean 的方法(包括 Service),Nest 只切 HTTP handler;Go 没有框架管线,一切都是「函数包函数」,而这恰好就是 AOP 最本质的样子(习题 1 你手写的 weave)。

🎤 面试翻译练习: 面试官问:"What's the difference between middleware, guards, interceptors and pipes in NestJS?"(或者 .NET 面试:「Middleware 和 Filter 有什么区别?」)你可以答:
"它们都是处理横切关注点的 AOP 工具,区别在执行时机和能拿到的信息。Middleware 最早执行,只有原始的请求和响应,不知道请求会路由到哪个 handler,适合日志、CORS 这类通用处理。Guard 拿得到 ExecutionContext,知道目标 handler,只决定放行还是拒绝,用于鉴权。Interceptor 用 Observable 包住 handler,前后都能做事,可以计时、改返回值、做缓存或超时。Pipe 针对单个参数做转换和校验。任何一步抛异常都会短路,交给 exception filter 统一生成错误响应。顺序是框架固定的:middleware、guard、interceptor、pipe、handler。这和 ASP.NET Core 的 middleware 加 authorization、action、exception filter,以及 Spring 的 Filter、HandlerInterceptor、@Around 切面、@ControllerAdvice 是一一对应的。"

✅ 总结与自测

今天带走的 4 句话

  1. 横切关注点 = 每个接口都要、但不属于任何接口的事(日志、计时、鉴权、错误处理);AOP 把它们写一次,用「做什么(advice)+ 对哪些(pointcut)」自动套上去。本质就是函数包函数。
  2. Nest 管线五件套,顺序固定:middleware(只有 req/res)→ guard(知道去哪,只决定进不进)→ interceptor(包住全程,能改返回值)→ pipe(管单个参数)→ handler;出事走 exception filter。
  3. interceptor 的「前」「后」是同一个函数,外层先进后出;同种站之间按「全局 → Controller → 方法」排,不同种站之间的顺序由框架写死。
  4. 异常会短路:从出事那一站直接跳到 filter,后面的站全跳过;所以 guard 拦下的请求没有计时头,包装只包成功体。全局切面要在 e2e 里也挂上(configureApp)。
