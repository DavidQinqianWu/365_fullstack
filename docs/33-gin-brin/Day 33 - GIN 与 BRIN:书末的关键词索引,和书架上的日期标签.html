🎫 接上回:nest-lab 的搜索框,B-tree 帮不上

Day 29–32 的卡片盒都是 B-tree:按某个值从小到大排好,所以能做等值、范围、排序、最左前缀。nest-lab 的 ?q=(Day 19 / 27)生成的却是这样的 SQL:

WHERE t.title ILIKE '%' || 关键字 || '%' ESCAPE '\'

Day 30 的习题里你应该已经看到了:不管有没有索引,计划都是 Seq Scan。原因很简单:卡片是按标题开头排的,「标题中间有 urgent」的卡片散落在整盒的各个位置,没有一个「从这里开始、到那里结束」的范围。今天学两种结构完全不同的索引:

  • GIN:一行里拆出很多「关键词」,每个关键词记下它出现在哪些行。用来做子串搜索、全文搜索、JSONB 和数组的「包含」查询。
  • BRIN:不记每一行,只给每一段连续的数据页记一个「最小值到最大值」。用来对付按时间追加的超大表,索引只有几十 KB。
🖥️ 前端翻译: 你做过前端搜索框:items.filter(x => x.title.toLowerCase().includes(q)),每次都把全部数据扫一遍,数据一多就卡。浏览器的 Ctrl+F 也是从头扫到尾。Algolia、Elasticsearch 快,是因为它们提前建好了一张「词 → 出现在哪些文档」的表(倒排索引),搜的时候直接查表。GIN 就是 PostgreSQL 里的这张表。

扩展(extension)是 PostgreSQL 的插件:pg_trgm 提供三元组,btree_gin 让普通的标量列也能放进 GIN 索引。它们随 PostgreSQL 一起安装在磁盘上,但要在每个数据库里 CREATE EXTENSION 一次才能用。谁能建?

  • pg_trgm 和 btree_gin 都是受信任的扩展(trusted,PostgreSQL 13 起有这个概念):对数据库有 CREATE 权限的用户就能建,不需要超级用户。本机的 nest_lab 是 nest_lab 库的 owner、不是超级用户,01-setup.sql 里直接 CREATE EXTENSION 成功了(pg_extension.extowner 显示为 nest_lab)。
  • 用 Docker 的官方镜像时,POSTGRES_USER 指定的用户本身就是超级用户,什么扩展都能直接建。
  • 如果你的用户既不是 owner 也没有 CREATE 权限,或者要装的是不受信任的扩展,就用超级用户在这个库里建一次:sudo -u postgres psql -d nest_lab -c 'CREATE EXTENSION pg_trgm'。托管数据库(RDS、Cloud SQL 等)通常有一张允许的扩展清单。

📇 概念卡 #1:GIN 与 pg_trgm —— 书末的关键词索引,关键词是每 3 个字一组

① 一句话大白话: GIN(Generalized Inverted Index,通用倒排索引)反过来记:不是「这一行的值是什么」,而是「这个关键词出现在哪些行」。一行可以拆出很多关键词。pg_trgm 把文本拆成「每 3 个字符一组」的三元组;查 '%urgent%' 时,先把 urgent 也拆成三元组,找出「这几组都出现过」的行,再逐行复查一遍。这样「中间有某个子串」也能走索引了,而且天然不分大小写。

② 生活类比:书末的关键词索引

技术书最后几页的「索引」:每个关键词后面列着页码,「事务 …… 12, 87, 203」。想找讲事务的地方,不用从第一页翻起。账房给账本也做了一份这样的索引,只是他偷懒,不判断什么算「词」,而是把每个标题每 3 个字切一刀:「urgent」切成 urg、rge、gen、ent,再加上表示开头结尾的几组。有人问「标题里有 urgent 的单子」,账房把 urgent 也这样切开,在索引里找出这几组都出现过的单子号,然后翻到这些单子逐张核对一遍(几组都出现过,不一定就是连在一起的 urgent)。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「书末索引能找到页码,就能按顺序翻」——倒排索引不能排序,也不能做范围查询。GIN 只回答「哪些行包含它」,给出的是一堆行位置,没有顺序;ORDER BY、LIMIT 和 keyset 分页还要靠 B-tree 或者排序。所以 GIN 只有 Bitmap Index Scan,没有普通的 Index Scan。
  2. 「什么词都能查」——少于 3 个字符的查询帮不上忙。'%加急%'、'%ab%' 抽不出三元组;很常见的词(命中 5% 的行)也只是快一点。用三元组时要给搜索框设一个最短长度,或者接受这些情况下的全表扫描。
  3. 「卡片小,书末索引也小」——GIN 很大,写起来也慢。trigram GIN 40 MB,比 title 列本身(26 MB)还大,因为每个标题拆成十几组,每组都要进索引。写入代价见下一张卡的实验 C。
④ 真实术语: GIN(generalized inverted index)、posting list / posting tree、operator class(gin_trgm_ops);trigram、show_trgm、similarity / word_similarity、% / <%、pg_trgm.similarity_threshold;recheck;GiST(一句话:也能做 trigram,还能按「相似度距离」做最近邻排序 ORDER BY title <-> 'x' LIMIT 10,但通常查得比 GIN 慢、建得和写得比 GIN 快);trusted extension;btree_gin。

📇 概念卡 #2:全文搜索与 JSONB / 数组 —— 关键词换成「词」和「键值」

① 一句话大白话: 同一个 GIN,换一种「拆关键词」的方法就是另一种功能。全文搜索按语言切成词,再把每个词还原成词根(running → run,invoices → invoic),扔掉 the 这种没意义的词,所以搜 deploying 能找到 Deploy。代价是它不懂中文,一整串汉字会被当成一个词。JSONB / 数组的 GIN 把每个元素、每个键和值当成关键词,回答「包含……的行有哪些」。

② 生活类比:按「词」编的索引,和按「标签」编的索引

书末的索引如果是认真编的,就不会按 3 个字乱切,而是按词编:「部署(deploy, deploying, deployed)…… 12, 87」,同一个词的各种变形归到一条。但编索引的人得懂这门语言,英文有现成的规则(哪里是词的边界、怎么去掉 -ing / -s);中文的词之间没有空格,他不知道「修复发票导出」该从哪里切开,只好整串当一个词记下来。

另一种索引是贴标签:每张单子贴着几个标签(backend、security),或者一张小卡写着「来源:api,优先级:high」。按标签编的索引回答「贴了 security 的有哪些单子」「来源是 api 且优先级是 high 的有哪些」。

📇 概念卡 #3:BRIN —— 书架上贴一张「这架的日期从 X 到 Y」

① 一句话大白话: BRIN(Block Range Index,块范围索引)不记每一行,只给每一段连续的数据页(默认 128 页一段)记一个「这一段里的最小值到最大值」。查某一天时,先排除范围不沾边的段,只把可能有的那几段读出来、逐行检查。数据如果是按时间顺序追加的,每一段的范围都很窄,一下子就能跳过绝大部分数据,而索引本身只有几十 KB。数据顺序一乱,每段的范围都很宽,它就什么也跳不过了。

② 生活类比:书架上的日期标签

账房的旧账本按日子一本本往后放,放满一个书架就换下一个。他不给每一页做卡片,只在每个书架上贴一张标签:「这一架:2025-05-28 到 2025-06-03」。问「6 月 1 日的单子」,看一眼标签就知道只可能在这一架,别的几百架都不用碰;到了这一架,还得一本本翻、一行行找(标签只说「大概在这里」)。可要是有人把账本打乱了放,每一架上都混着各个日子,每张标签都写着「2024-01-01 到 2025-11-27」,标签就没用了。

  2. 「贴一次标签就一直准」——顺序是会被破坏的。按时间追加的表,只要中间夹着大量 UPDATE、DELETE 后的空位复用,或者补录了一批旧数据,相关段的范围就变宽了。新插入的页也要等 VACUUM(或 autosummarize)才会补上摘要。上线 BRIN 后要定期看 correlation 和计划里的 Rows Removed by Index Recheck。
  3. 「小索引总是更好」——小表上 BRIN 没有意义。100 万行的表上 B-tree 也只有 21 MB,而且查得更快。BRIN 的价值在 B-tree 大到放不进内存、维护成本太高的表上。

  5. 常见词(命中很多行)加上排序和 keyset 分页时,GIN + 排序不一定比「按排序索引扫、边扫边过滤」快,Day 34 要对比两种计划。

BRIN 这类块级摘要BRIN无列存储索引的段元数据(segment elimination)有类似的思路

ORM 里怎么声明 GIN:

  • Prisma:@@index([tags], type: Gin)(PostgreSQL 上可选 Gin、Gist、Brin、SpGist);trigram 要指定操作符类,写法是 @@index([title(ops: raw("gin_trgm_ops"))], type: Gin);扩展用 postgresqlExtensions 预览功能,或者在迁移 SQL 里手写 CREATE EXTENSION。
  • EF Core(Npgsql):HasIndex(t => t.Title).HasMethod("gin").HasOperators("gin_trgm_ops");全文搜索用 HasIndex(…).HasMethod("GIN").IsTsVectorExpressionIndex("english")。
  • JPA / Hibernate:标准 @Index 不能指定索引方法,写在 Flyway / Liquibase 的 SQL 里。Go:迁移文件里手写 SQL。

什么时候该用专门的搜索引擎(Elasticsearch / OpenSearch / Meilisearch / Algolia):需要相关度调优、同义词、拼写纠错、按拼音或中文分词、分面统计(「每个标签各有多少结果」)、高亮、千万级以上的文档和高并发搜索,或者要搜的数据来自多个系统。代价是多了一个要运维的系统,还要解决「数据库改了以后搜索引擎什么时候同步」的问题(Week 13 的消息队列 / CDC)。nest-lab 这种规模,PostgreSQL 的 trigram 和全文搜索足够了。

"B-tree 按值的开头排序,前缀查询 LIKE 'abc%' 能变成一个范围,所以能用(在 PostgreSQL 里还要求索引按字节排序,也就是 C 排序规则或 text_pattern_ops);'%abc%' 匹配的行散在整个索引里,没有一个连续的范围,只能全表扫描。优化办法要看需求:要找子串,在 PostgreSQL 里用 pg_trgm 建 trigram 的 GIN 索引,它把文本拆成三个字符一组,查询时先找出包含这些组的行再复查,我实测少见的词从 500 毫秒降到几毫秒,但少于三个字符的词帮不上,常见词的提升也有限;要按词搜,用全文搜索,它会分词和还原词根,但默认不支持中文;规模更大、要相关度和分词时,上 Elasticsearch 这类搜索引擎。倒排索引就是反过来记:不是『这一行有什么』,而是『每个词出现在哪些行』,一行可以对应很多词。GIN 就是 PostgreSQL 的倒排索引,也用于 JSONB 和数组的包含查询;它的代价是写入慢、体积大,而且不能用来排序。"

✅ 总结与自测

今天带走的 4 句话

  1. B-tree 只能帮 LIKE 做前缀,而且要求索引按字节排序(PostgreSQL 16 只认 C / POSIX:本机的 C.UTF-8 和 Docker 的 en_US.utf8 都要 text_pattern_ops 或 COLLATE "C");'%abc%' 和 ILIKE 它都帮不上。
  2. GIN 是倒排索引,pg_trgm 把文本拆成三元组:ILIKE '%urgent%' 从 450–650 ms 到 1.7–7.4 ms,中文 3 个字符以上也能用;但少于 3 个字符('%加急%')抽不出三元组,常见词的帮助有限,索引(40 MB)比列本身还大,写入慢 10 倍以上(关掉 fastupdate 时 100 倍、WAL 1 GB)。nest-lab 的参数化 SQL 不用改就能用上它。
  3. 全文搜索找「词」,trigram 找子串:english 配置会还原词根(exports → export),但 PostgreSQL 默认不分中文词。JSONB / 数组的 GIN 做包含查询,jsonb_path_ops 小一半但不支持 ?。
  4. BRIN 只记每一段数据页的 min / max:24 kB 对 B-tree 的 21 MB,按时间顺序的表上查一天只慢一倍;数据一打乱(correlation 0.0022)就一段也排除不了,比全表扫描还慢。
