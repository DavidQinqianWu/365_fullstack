核心代码只有三段,先扫一眼,下面三张卡片逐行拆:

// src/tasks/tasks.module.ts —— 部门编制表
@Module({
  controllers: [TasksController],   // 这个部门的前台
  providers: [TasksService],         // 这个部门的后厨
})
export class TasksModule {}

// src/tasks/tasks.controller.ts —— 前台:只管「哪张单子交给谁」
@Controller('tasks')
export class TasksController {
  constructor(private readonly tasksService: TasksService) {}   // 只声明「我需要后厨」,不自己 new

  @Get()          findAll()                        { return this.tasksService.findAll(); }
  @Get(':id')     findOne(@Param('id') id: string) { return this.tasksService.findOne(Number(id)); }
  @Post()         create(@Body() body: { title: string }) { return this.tasksService.create(body.title); }
}

// src/tasks/tasks.service.ts —— 后厨:只管「菜怎么做」,不知道 HTTP 的存在
@Injectable()
export class TasksService {
  private readonly tasks: Task[] = [ /* 两条初始任务 */ ];
  findOne(id: number): Task {
    const task = this.tasks.find((t) => t.id === id);
    if (!task) throw new NotFoundException(`没有 id 为 ${id} 的任务`);   // 抛异常,不写 res.writeHead(404)
    return task;
  }
  // findAll / create 略
}

(为了排版,上面把 Controller 的方法压成了一行,真实文件里有注释和观察用的 console.log。)

📇 概念卡 #1:框架与三件套 —— 连锁店的编制表、前台、后厨

① 一句话大白话: 框架 = 别人替你写好的那 80% 杂活 + 一套「代码该放哪」的规矩;你只写跟自己业务有关的那 20%,框架来调用你。

② 生活类比:连锁餐厅的加盟体系

加盟一家连锁店,总部不会让你自己琢磨怎么排班、怎么接单。总部发给你一张编制表,上面按部门写好:「任务部门:前台 1 名(TasksController),后厨 1 名(TasksService)」。开业那天(NestFactory.create(AppModule)),总部照着总部编制表(AppModule)顺藤摸瓜,把每个部门的人招齐、把「前台找哪个后厨」接好线,然后开门营业。

  • 前台(Controller):接单,看清「哪桌、点什么」,把单子递给后厨,再把菜端出去。不做菜。
  • 后厨(Provider / Service):只管做菜,从来不见客人,不知道客人是从门口进来的、还是外卖平台下的单。
  • 部门编制表(Module):写清这个部门有谁。没写进编制表的人,开业时不会被招进来。

🖥️ 前端翻译: 如果你写过 Angular:Nest 的设计几乎是照着它抄的,@Module ≈ @NgModule,@Injectable 一字不差。如果你主要写 Next.js:Controller ≈ app/api/tasks/route.ts 里的 GET / POST 函数,Service ≈ 你抽到 lib/ 里的业务函数;区别是 Next.js 靠文件放在哪决定路由,Nest 靠装饰器标签决定路由(下一张卡),而且 Service 不用你 import 了自己调,由 Nest 送到 Controller 手里。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「前台和后厨是两个人,可以同时干活」——错。Controller 和 Service 只是两段代码,不是两个线程。真正跑它们的,还是 Day 1 那个唯一的服务员(event loop 主线程):他先站到前台岗位执行 Controller,再走进后厨执行 Service。如果你在 Service 里写一个同步死循环或者算 fib(45),整家店照样卡死,Day 1 和 Day 5 的规矩一条都没变。
  2. 「Provider = 后厨厨师」只说对了一半。Provider 指任何交给 Nest 管理、可以被送到别人手里的东西:业务 Service、数据库连接、配置对象、日志器都是 Provider。「后厨」只是最常见的那一种。
  3. 「部门之间有墙」——没有物理的墙。所有 Module 都在同一个进程、同一块内存里,Module 只是逻辑上的分组和可见性规则(一个部门的后厨默认不借给别的部门,要 exports 才行,Day 9 讲)。它不是微服务,也不是 Day 4 的分店。
④ 真实术语: framework vs library:库(library)是你调用它(JSON.parse、lodash);框架(framework)是它调用你(你写 findAll(),但从来不自己调用它,请求来了 Nest 调)。这种「控制权反过来」叫 Inversion of Control(控制反转),俗称好莱坞原则:「别打给我们,我们会打给你」——明天 Day 9 的主角,今天只记住这个名字。
Module:组织代码的单元;Controller:处理 HTTP 请求的类;Provider:被 Nest 管理、可被注入的类或值;Service:放业务逻辑的 Provider(只是命名惯例,不是特殊语法)。
分层的意义:Controller 只认 HTTP,Service 只认业务。所以你能脱离 HTTP 直接 new TasksService() 做单元测试,将来把内存数组换成 PostgreSQL 时 Controller 一行不用改。

📇 概念卡 #2:装饰器 —— 贴在员工身上的岗位便利贴

① 一句话大白话: 装饰器就是贴在类、方法、参数上的便利贴。贴的时候几乎什么都不做;开店时总部挨个读便利贴,照着上面写的把店组装起来。

② 生活类比:岗位便利贴 + 开业排班

新员工入职,总部给他身上贴几张便利贴:

  • 胸口(类上):@Controller('tasks') —— 「我是前台,负责 /tasks 这一片」
  • 左手(方法上):@Get(':id') —— 「GET /tasks/某个号 的单子归这只手」
  • 手里的小本(参数上):@Param('id') —— 「接单时把单子上的桌号抄给我」
  • 后厨工牌:@Injectable() —— 「此人归总部统一调配,谁需要就派过去」

开业那天,总部的排班员(Nest 的 RoutesResolver / RouterExplorer)拿着编制表挨个看人身上的便利贴,排出一张路由表:「GET /tasks → 前台的 findAll 手;GET /tasks/:id → findOne 手……」。你在启动日志里能看到这张表被一行行排出来。

比喻 ↔ 真实 对照

便利贴真实发生的事(nest-lab 里亲眼看得到)
@Controller('tasks')在 TasksController 这个类上记一条元数据:path = "tasks"
@Get(':id')在 findOne 方法上记两条:path = ":id"、method = 0(0 是 GET 的枚举值)
@Param('id') / @Body()在方法上记「第 0 个参数要路径里的 id / 要请求体」
@Injectable() / @Module({...})标记「这个类归 Nest 管」/ 记下部门编制
(没贴,但 tsc 自动写的)design:paramtypes = [TasksService]:构造函数要什么类型 —— Day 9 自动注入就靠它
开业排班员NestFactory.create 里读元数据、注册路由的代码(启动日志 Mapped {/tasks/:id, GET} route)
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「贴了便利贴,事情就成了」——错。装饰器只负责贴,真正干活的是读便利贴的人。如果 TasksController 没写进任何 Module 的 controllers,标签照样贴在类上,但总部开业时根本不看他 —— 路由一条都不会注册,请求全是 404(习题 2 亲手撕一次)。
  2. 「每来一个客人,便利贴就被执行一次」——错。装饰器函数在类定义的那一刻(文件被 import 时)只跑一次;请求来了以后查的是已经排好的路由表,不会再读一遍便利贴。所以装饰器不会让请求变慢。
  3. 现实里便利贴看得见,代码里的标签看不见。它们存在 reflect-metadata 维护的一张隐形表里,要用 Reflect.getMetadata(...) 才能读出来。而且 Nest 用的是 TypeScript 的旧版实验装饰器(nest-lab/tsconfig.json 里的 experimentalDecorators + emitDecoratorMetadata),和 JS 标准(TC39)装饰器不是同一套;design:paramtypes 只有 tsc 会生成,用 tsx / esbuild 直接跑 Nest 源码,构造函数注入会拿到 undefined。这就是观察脚本先 nest build 再读 dist/ 的原因。
④ 真实术语: decorator(装饰器):一个在类 / 方法 / 参数定义时被调用的函数;metadata(元数据):「关于代码的数据」,这里指贴在类和方法上的标签;reflect-metadata:提供 Reflect.defineMetadata / getMetadata 的库;reflection(反射):程序在运行时查看自己的结构。
更重要的是一种思维:声明式(declarative)vs 命令式(imperative)。Day 6 你是命令式地写「如果方法是 GET 且路径匹配这个正则,就调用这个函数」;今天是声明式地说「这个方法负责 GET /tasks/:id」,怎么匹配交给框架。C# 的 Attribute([HttpGet])、Java 的 Annotation(@GetMapping)是同一个思路,而且它们比 TS 更早就这么干了。

📇 概念卡 #3:一个请求在 Nest 里的一生 —— 连锁店的标准接待流程

① 一句话大白话: 请求进门后不是直接到你的方法,而是走一条固定顺序的流水线,每一站都可以插手;今天你只写了中间两站(前台和后厨),其余的站要么空着,要么用的是总部的默认版。

② 生活类比:连锁店的标准接待流程

连锁店接待每位客人都走同一套流程:门口登记员记下谁进来了 → 保安查会员卡,没卡不让进 → 领班掐表开始计时 → 核单员检查单子格式、把「三」改写成「3」 → 前台接单 → 后厨做菜 → 领班把菜装盘、记下用了多久 → 端出门。任何一站出了事(没这道菜、厨房着火),都直接转到投诉处理台,由它给客人一个体面的、格式统一的答复,而不是让后厨冲出来对客人吼。

⑥端出门响应写完,res 这条可写流(Day 3)触发 'finish'登记员打印「出门」
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「流水线上每一站都站着人」——不是。没注册 Guard / Interceptor / Pipe 时,这几站根本不存在,请求直接跳过,没有任何开销。今天的观察输出里只有 ①③④⑥,就是这个原因。
  2. 「一个客人走完整条流水线,下一个客人才能进门」——错。真实系统里只有一个服务员(event loop),但他在任何一个 await 处都可以放下这位客人去接待下一位(Day 1–2)。几个请求的流水线是交错进行的:A 还在后厨等数据库,B 可能已经走到前台了。
  3. 「投诉处理台是流水线的最后一站」——不是。Exception Filter 是一条旁路:哪一站 throw,就从哪一站直接跳过去,后面的站一概跳过。另外,如果根本没有匹配的路由(GET /nope),请求连前台都到不了,Nest 直接回 404 —— 格式和你自己抛的 NotFoundException 一模一样,因为走的是同一套异常处理。
④ 真实术语: request lifecycle(请求生命周期):Nest 官方文档里固定的顺序是 Middleware → Guard → Interceptor(前)→ Pipe → Controller → Service → Interceptor(后)→ Exception Filter(出错时)→ 响应。这条管线就是 Day 10 要讲的 AOP(面向切面) 在 Nest 里的落地形式,今天只需要记住站的顺序。
HttpException:Nest 里「带 HTTP 状态码的异常」的基类,NotFoundException(404)、BadRequestException(400)、ForbiddenException(403)都是它的子类。思维转变:业务代码只管 throw,状态码和响应格式交给统一的那一站,不再像 Day 6 那样每个分支自己 sendProblem(res, 404, ...)。

✅ 总结与自测

今天带走的 4 句话

  1. 框架 = 替你写好的杂活 + 代码该放哪的规矩,而且是它调用你。Nest 跑在 Express 上,Express 跑在 node:http 上,Day 6 你做的每件杂活 Nest 都在替你做,只是换成了默认值。
  2. 三件套 = 编制表(Module)+ 前台(Controller,只认 HTTP)+ 后厨(Provider/Service,只认业务)。它们都是同一个服务员(event loop)在跑的代码,不是三个线程。
  3. 装饰器 = 便利贴,只负责贴;读便利贴的是启动时的 Nest。标签存在 reflect-metadata 的隐形表里;没被 Module 登记的类,贴了也白贴。
  4. 请求的一生 = Middleware → Guard → Interceptor → Pipe → Controller → Service → Interceptor → (出错时 Exception Filter)→ 响应。今天写了 ①③④,用了内置的 Filter;业务代码只管 throw,状态码交给统一的那一站。
