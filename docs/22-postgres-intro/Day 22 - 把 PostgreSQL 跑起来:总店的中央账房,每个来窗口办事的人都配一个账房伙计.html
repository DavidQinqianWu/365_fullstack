🎫 接上回:任务存在内存里,重启就没了

Week 3 结束时,nest-lab 已经是一个契约完整的 REST API,但它的数据还放在 Day 9 写的 InMemoryTasksRepository 里,也就是 Node 进程里的一个数组。Day 21 的遗留清单第 7 条写着:重启丢数据。你可以现在就验证:npm run start:dev,POST 一条任务,改一行代码让它热重启,再 GET,那条任务就没了。

问题不只是重启。Day 4 讲 cluster 的时候,我们开了好几个工作进程,每个进程有自己的内存。如果 nest-lab 开 4 个副本,就有 4 个互不相通的数组:用户在副本 1 建的任务,下一个请求被分到副本 2,就找不到了。还有并发(两个请求同时改同一条)、崩溃(写到一半断电)、数据量(5 亿条放不进内存)这些问题。

🖥️ 前端翻译: 前端也有「存起来」的地方:localStorage、IndexedDB。它们解决的是「这一个用户、这一个浏览器」刷新后数据还在。后端的问题完全不同:数据属于所有用户,要被很多个服务进程同时读写,还要在任何一个进程崩溃、重启、扩容时都不丢、不乱。所以后端不把数据放在自己的内存里,而是交给一个专门的、独立运行的程序:数据库服务器。
💡 生活翻译: 连锁餐厅每家分店的服务员,以前都在自己的小本子上记账(内存数组)。本子丢了账就没了,分店之间也对不上账。后来总店建了一个中央账房:所有账都记在这里,账房有防火柜、有流水底稿,停电了也能对回来。各分店不再自己记账,而是到账房的窗口去办事。

📇 概念卡 #1:客户端-服务器 —— 中央账房和每人一个账房伙计

① 一句话大白话: PostgreSQL 是一个一直在运行的服务器程序,数据由它保管。psql、nest-lab、DBeaver 这类图形工具,全都只是客户端:通过网络(或本机 socket)连上去,发 SQL,收结果。PostgreSQL 给每一个连接单独开一个操作系统进程来服务它。

② 生活类比:中央账房的窗口

账都在总店的中央账房里。分店经理、会计、老板,谁要查账改账,都得到窗口来;窗口本身不存账,账在后面的柜子里。账房有一位总管,一直守在门口;每来一个办事的人,总管就专门派一个账房伙计陪着他,直到他办完离开,伙计才下班。所以窗口前站了三个人,后面就有三个伙计在忙。

比喻 ↔ 真实 对照

比喻真实组件今天看到的
中央账房数据库服务器(PostgreSQL server,一个长期运行的程序)本机的 PostgreSQL 16.15;你电脑上是 Docker 容器里的 postgres:16
来窗口办事的人客户端:psql、nest-lab(Day 27 起)、GUI 工具、另一个服务day22-A / B / C 三个 psql
窗口监听的地址和端口(默认 5432)+ 连接参数(用户、密码、库名)postgresql://nest_lab:***@localhost:5432/nest_lab

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「伙计随叫随到,来多少人派多少个」——伙计是很贵的。每个后端进程都是一个真正的操作系统进程,有自己的内存;服务器还有连接上限,本机实测 SHOW max_connections 是 100(默认值)。nest-lab 如果每个请求都新开一个连接、用完就断,光「派伙计、遣散伙计」就很慢,高并发时还会把上限打满。解法是连接池:先请好固定几个伙计,请求轮流用。这是 Day 27 接回 nest-lab 时的第一件事,Week 6 还会讲 PgBouncer。(对比 Day 4:Node 的 cluster 是「多进程,每个进程处理很多请求」;PostgreSQL 是「每个连接一个进程」。MySQL 则是每个连接一个线程。)
  2. 「窗口就是账房」——psql 只是一个客户端。关掉 psql,数据一点没少;换 GUI 工具、换 nest-lab 连进去,看到的是同一份数据。反过来,服务器没起来时,psql 什么也做不了(第 0 幕的报错)。很多新手以为「装了 psql 就装了数据库」,其实客户端和服务器可以装在不同的机器上,Docker 方式下服务器就在容器里。
  3. 「账房就是一个更大的柜子」——数据库不是更大的内存数组。它要同时解决:持久化(写进磁盘,重启还在)、并发(100 个连接同时读写不乱)、崩溃恢复(写到一半断电,重启后能恢复到一致状态,靠的是 WAL 预写日志,Week 6 / Week 9 讲)。下面的实验里,我把 PostgreSQL 整个重启了一次,数据还在。内存数组一样都做不到。
④ 真实术语: client-server architecture;connection string / URI(postgresql://user:password@host:port/dbname);process-per-connection;postmaster 与 backend process;pg_stat_activity(当前所有连接的系统视图);pg_backend_pid();max_connections;connection pooling;durability(持久性,ACID 的 D,Week 6)。

📇 概念卡 #2:层级与 psql —— 账房、分账房、柜子、账本,和窗口口令

① 一句话大白话: 一个 PostgreSQL 服务器(集群)里可以有好几个数据库;每个数据库里分成若干 schema(命名空间,默认叫 public);schema 里放表;表由列(栏目,每列有固定类型)和行(一条条记录)组成。psql 里有两种输入:SQL(发给服务器执行,分号结束)和元命令(反斜杠开头,psql 自己处理,比如列出有哪些表)。

② 生活类比:账房里的分账房、柜子和账本

中央账房(集群)里隔出几间分账房(数据库):餐厅业务一间,集团人事一间,互不相通。每间分账房里有几个柜子(schema),默认只有一个叫「公共柜」(public)。柜子里一本本分类账(表):任务账、用户账。每本账先印好栏目(列:编号、标题、完成没有、登记时间),然后一行记一条。你在窗口说话有两种:对账房伙计说「请把任务账上编号 2 那条念给我听」(SQL,伙计去柜子里办);或者对窗口说「把这间房里有哪些账本列一下」「换到隔壁分账房」(元命令,窗口自己的功能)。

比喻 ↔ 真实 对照

比喻真实组件psql 里怎么看
中央账房集群(cluster):一个服务器实例和它管的一整份数据目录\conninfo
分账房数据库(database):一个连接只能连一个库\l 列出,\c 库名 切换
柜子schema:库里的命名空间,默认 public\dn
分类账表(table)\dt 列出,\d 表名 看结构
栏目 / 一条记录列(column,有类型)/ 行(row)SELECT …;行太宽用 \x 竖着看
谁能进哪间房角色(role)与权限\du;今天只点到,Week 21 细讲
对伙计说的事 / 对窗口说的口令SQL(; 结束,发给服务器)/ psql 元命令(\ 开头,客户端自己处理)\? 看全部元命令,\q 退出

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「分账房之间开个门就能互相查」——PostgreSQL 的数据库之间是隔开的。一条 SQL 不能直接查另一个库的表;\c 其实是断开当前连接、重新连一个(下面实测:pid 变了)。要在一个库里分隔不同模块,用 schema,而不是开很多库。这一点和 MySQL 不同:MySQL 里 database 和 schema 是同一个东西,可以 库名.表名 跨库查询。
  2. 「schema 就是表结构」——这个词在中文语境里有两个意思。口语里「改 schema」常指「改表结构」(Day 23 的概念卡「schema 设计是最难改的决定」用的就是这个意思);PostgreSQL 里的 schema 对象则是「柜子」这个命名空间。看上下文分辨。

📇 概念卡 #3:第一张表与 CRUD —— 记账的四个动作,和那次忘了圈范围

① 一句话大白话: 先用 CREATE TABLE 定好表有哪些列、每列什么类型,再用四个语句操作数据:INSERT(新增)、SELECT(查)、UPDATE(改)、DELETE(删)。改和删用 WHERE 圈出「哪几行」,不写 WHERE 就是整张表。SQL 只描述「要什么」,数据库自己决定「怎么找」。

② 生活类比:记账的四个动作

新开一本账,先印栏目。之后只有四个动作:添一行、翻查、涂改、划掉。涂改和划掉之前,要先用笔把「哪几行」圈出来;如果没圈就直接说「把完成栏都改成『是』」,伙计会老老实实把整本账都改掉。你也不用告诉伙计怎么翻账,只要说「我要编号 2 那条」,他自己知道该翻目录还是从头翻。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「账本是一页页按顺序记的」——表里的行没有顺序。关系模型里表是「行的集合」,集合没有先后。不写 ORDER BY 时,返回顺序只是数据库这一次碰巧怎么读的。下面的实验里,连续两次不带 ORDER BY 的 SELECT,只因为中间改了一行,顺序就变了。nest-lab 的 cursor 分页(Day 19)依赖稳定的顺序,所以 Day 27 的 SQL 里 ORDER BY 必须明确写出来。
  2. 「划掉的行还在纸上,能看出来」——DELETE 是立即、永久生效的,没有回收站。psql 默认自动提交(autocommit):每条语句执行完就落定。只有在 BEGIN 开启的事务里,ROLLBACK 才能撤销。下面两个实验:有 BEGIN 时救回来了;没有 BEGIN 时,ROLLBACK 只换来一句警告。(很多系统用「软删除」,加一列 deleted_at 只做标记,那是应用层的设计,不是数据库自带的;Day 23 讨论建模时会遇到。)
  3. 「只要说要什么,怎么找不用我管」——声明式不等于不用关心性能。同样是「找一条」,按 id 找走了索引(Index Scan),按 title 找只能从头扫(Seq Scan)。4 行的时候没区别,400 万行的时候差几个数量级。你不用写「怎么找」,但要知道数据库能不能找得快,这是 Week 5 的全部内容。

✅ 总结与自测

今天带走的 4 句话

  1. 数据不放在服务的内存里:重启会丢、多副本对不上、并发和崩溃都没人管。数据库是一个独立的服务器,负责持久化、并发和崩溃恢复;psql、nest-lab、GUI 工具都只是它的客户端。
  2. PostgreSQL 每个连接一个后端进程,由主进程 postmaster fork 出来,连接断开就退出;pg_stat_activity 能看到所有连接。连接是贵的资源(默认上限 100),所以 Day 27 要用连接池。
  3. 层级是集群 → 数据库 → schema(默认 public)→ 表 → 行 / 列;一个连接只连一个库,\c 是换连接。psql 里 SQL 要分号、发给服务器,元命令用反斜杠、psql 自己处理;看提示符就知道它在等什么。
  4. CRUD = INSERT / SELECT / UPDATE / DELETE,回执里的行数是你的报警器,也是 Day 27 的 404 依据;不写 WHERE 就是整张表,没有 BEGIN 就没有反悔;不写 ORDER BY 就没有顺序;SQL 说「要什么」,数据库决定「怎么找」。
