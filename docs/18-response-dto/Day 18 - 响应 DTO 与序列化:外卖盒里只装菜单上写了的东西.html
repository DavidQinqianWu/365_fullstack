🥡 接上回:进口报了关,出口还没人管

Day 16 给每个请求配了「进口报关单」(输入 DTO):客户端不能填 id、createdAt。但「出口」一直是这样写的:

@Get(':id')
findOne(@Param('id') id: number) {
  return this.tasksService.findOne(id);   // 内部对象原样出门
}

任务现在的内部字段刚好都能给人看,所以一直没出事。可一旦内部模型多了一个敏感字段,问题就来了。今天给 nest-lab 加一个 users 模块,内部的 User 长这样:

export interface User {
  id: number;
  email: string;
  displayName: string;
  role: 'user' | 'admin';
  passwordHash: string;   // ❌ 绝对不能出门(scrypt 哈希,真正的密码存储 Week 10 / 20 再讲)
  internalNote: string;   // ⚠️ 只给管理员看的内部备注
  createdAt: Date;
}

如果照老习惯 return user,passwordHash 和 internalNote 就会原样出现在响应里。更隐蔽的是:半年后有人往 User 里加了一个 resetToken(能重置密码的令牌),没人改 Controller,它也会自动出门。另一个问题是响应结构被内部结构绑死:后端把 displayName 改名成 nickname,所有前端页面立刻崩掉。

💡 生活翻译: 后厨里有半成品、内部配料单、员工写的备注(「这位客人上次投诉过」)。外卖打包时,只能装菜单上写了的东西;配料单和备注留在店里。VIP 客人的外卖盒里可以多一张会员卡,但普通客人的盒子里没有。出餐口站着一位打包检查员:盒子封口之前,照着清单检查一遍。

📇 概念卡 #1:响应 DTO —— 出餐口的打包检查

① 一句话大白话: Controller 不直接返回内部对象,而是返回一份专门的「出口报关单」(响应 DTO):只列出允许给外面看的字段,以及它们对外的格式。

② 生活类比:出餐口的打包检查

后厨的盘子(内部对象)上什么都有;外卖盒(响应体)里只放菜单上写了的东西。打包员按清单装盒,检查员封口前再核对一遍。菜单(响应 DTO)印出去以后,顾客就按它点餐,所以菜单上的菜名不能说改就改。

比喻 ↔ 真实 对照

比喻真实组件nest-lab 里
后厨盘子里的全部东西内部模型 / EntityUser、Task
外卖盒HTTP 响应体JSON
菜单上写了的东西响应 DTOUserResponse、TaskResponse
按清单装盒序列化(把内部对象变成对外的表示)toUserResponse()、toTaskResponse()
VIP 盒子多一张会员卡同一资源的不同视图admin 视图多 internalNote、email 不打码
装盒前的加工(切块、去骨)格式化Date → ISO 字符串、email 打码
🖥️ 前端翻译: 前端常有的想法是「接口返回什么,我就渲染什么;页面上没显示 passwordHash,就不算泄露」。可是浏览器 DevTools 的 Network 面板里,整个 JSON 一览无余,任何用户都能看到。页面不渲染不等于不泄露,必须在后端出门之前就拿掉。GraphQL 让客户端「只查需要的字段」,但那只是省流量;服务端照样要对每个字段做权限控制,否则客户端多写一个字段名就查到了。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「检查员会看是谁来取外卖」——不会,他只管盒子里装什么。序列化决定「出门的样子」,不决定「谁有资格拿」。今天 admin 视图靠请求头 x-demo-role 判断,而这个头谁都能伪造:任何人带上 x-demo-role: admin 就能看到 internalNote。「谁能看」是 guard / 认证的事(Day 11、Week 10 的 JWT),序列化只能在「已经确认身份」之后选择视图。
  2. 「外卖盒检查过了,就不会泄露」——响应体只是其中一个出口。日志、错误详情、消息队列、缓存、导出文件,都可能把内部对象原样带出去。Day 17 的观察脚本里,数据库密码就出现在了日志里。今天的 UsersService.create 只记 email,不记整个 dto(里面有明文密码),也不记 passwordHash。
  3. 「菜单换个菜名无所谓」——响应 DTO 是对外契约。字段只能增加,不能悄悄删除或改名:前端、移动端、第三方集成都按它解析。确实要改,就走版本化(Day 19),或者新旧字段并存一段时间、先标记弃用。所以响应 DTO 和内部模型要分开:内部改名不该波及外部。
④ 真实术语: response DTO / view model(响应 DTO / 视图模型);serialization(序列化:内部对象 → 对外表示);excessive data exposure(过度数据暴露,OWASP API Security Top 10 的 API3:2023 Broken Object Property Level Authorization 的一半,另一半是 Day 16 的批量赋值);projection(投影:只取需要的字段)。

📇 概念卡 #2:黑名单 vs 白名单 —— 「禁带清单」和「装箱清单」

① 一句话大白话: Nest 自带的做法是在类的属性上贴 class-transformer 的装饰器,由 ClassSerializerInterceptor 在出门前统一转换。贴法有两种:黑名单(默认都出门,@Exclude 的不出)和白名单(默认都不出门,@Expose 的才出)。应该用白名单。

② 生活类比:「禁带清单」和「装箱清单」

黑名单是贴在出餐口的「禁止装盒:配料单」。后厨哪天新添了一样不该带走的东西(比如一张写着顾客地址的便签),禁带清单上没有,检查员就照装不误。白名单是一张「装箱清单:米饭、主菜、汤、筷子」,清单上没写的一律不装,后厨新添什么都不会被误装。

// src/serialization-demo/user-entities.ts
// ① 黑名单:默认全部出门
export class UserBlacklistEntity {
  @Exclude() passwordHash!: string;          // 只点名拦这一个
  internalNote!: string;                       // 忘了拦 → 出门
  constructor(user: User) { Object.assign(this, user); }
}

// ② 白名单:配合 strategy: 'excludeAll',只有 @Expose 的出门
export class UserWhitelistEntity {
  @Expose() id!: number;
  @Expose()
  @Transform(({ value, options }) => (options.groups?.includes('admin') ? value : maskEmail(String(value))))
  email!: string;                               // @Transform:出门前格式化(非 admin 打码)
  passwordHash!: string;                        // 没有 @Expose → 不出门
  @Expose({ groups: ['admin'] }) internalNote!: string;   // groups:只有 admin 视图才出门
  @Expose() @Transform(({ value }) => (value instanceof Date ? value.toISOString() : value)) createdAt!: Date;
  // …
}

// Controller
@UseInterceptors(ClassSerializerInterceptor)
@SerializeOptions({ strategy: 'excludeAll', groups: ['admin'] })
@Get('whitelist-admin')
whitelistAdmin() { return new UserWhitelistEntity(this.users.findOne(1)); }   // 必须 new 出 class 实例

比喻 ↔ 真实 对照

比喻真实组件
出餐口的检查员ClassSerializerInterceptor(Day 10 的 interceptor 回程:map 里调用 instanceToPlain)
禁带清单@Exclude()(默认 exposeAll 策略)
装箱清单@Expose() + @SerializeOptions({ strategy: 'excludeAll' })
装盒前的加工@Transform()(在序列化方向上执行)
VIP 盒子的会员卡@Expose({ groups: ['admin'] }) + 序列化时带 groups
检查员按哪张清单查返回值的 class:装饰器的元数据挂在类上(Day 11)
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「检查员会检查所有出门的盒子」——他只认得 class 实例。装饰器贴在类上,如果你返回的是普通对象(比如手滑写了 { ...entity },或者直接返回仓储查出来的普通对象),检查员找不到任何清单。结果是两个方向的失败:黑名单版全部出门(passwordHash 泄露),白名单版什么都不出门(返回 {})。修法是 @SerializeOptions({ type: UserWhitelistEntity }),告诉检查员「把普通对象当成这个类来查」(第 4 幕实测)。
  2. 「禁带清单写全就安全」——写全的只是今天的字段。黑名单的安全取决于每个新增字段都被人记得加上 @Exclude;忘一次就泄露一次,而且没有任何报错(第 2 幕的 resetToken)。白名单把默认值反过来:忘了加 @Expose,后果只是「前端少了一个字段」,发现后补上就行。和 Day 11 的「默认上锁」是同一个思路:出错时宁可少给,不可多给。
  3. 「VIP 会员卡的规则写在清单上,一目了然」——规则分散在一堆装饰器里。groups 是字符串,拼错一个('admim')不会报错,只会静默失效(Day 11 拼错元数据 key 的老问题);@Transform 里还要从 options.groups 判断视图。规则一多,就要在类、装饰器、Controller 的 @SerializeOptions 三处来回看。
④ 真实术语: ClassSerializerInterceptor、@SerializeOptions()(strategy、groups、type);class-transformer 的 instanceToPlain、@Exclude / @Expose / @Transform、strategy: 'excludeAll' | 'exposeAll'、excludeExtraneousValues(plainToInstance 方向上的白名单开关);allowlist vs denylist(白名单 / 黑名单,安全领域通用原则:默认拒绝)。

⑤ 动手验证:✍️ 预测(先写再运行):① 内部模型新增一个敏感字段 resetToken,四种方式各自会不会泄露?② 白名单的 groups 和显式映射,对普通访客和管理员分别给出什么?③ 黑名单和白名单都返回普通对象 { ...实例 } 时,各出门几个字段?

黑名单 class 实例           → 字段数 6,❌ 带出了 internalNote
黑名单 但返回了 {...实例}   → 字段数 7,❌ 带出了 passwordHash, internalNote
白名单 class 实例           → 字段数 5

第 2 幕是今天最重要的一张表:黑名单和直接返回,都在新字段出现的那一刻就泄露了,而且没有人改过一行 Controller。第 4 幕的 { ...实例 } 在真实代码里很常见,比如 return { ...task, extra: 1 },一个展开运算符就让检查员失明。

📇 概念卡 #3:显式映射 + 去掉包装 —— nest-lab 的两个决定

① 一句话大白话: 写一个普通函数 toUserResponse(user, viewer),一个字段一个字段地拼出响应对象;没写进去的字段不可能出门。另外,成功响应不再包一层 { data, timestamp },资源本身就是响应体。

② 生活类比:打包员照着装箱单亲手装盒

与其请一位检查员对着各种贴纸检查(装饰器),不如让打包员拿着装箱单,一样一样亲手放进盒子:米饭、主菜、汤。VIP 就多放一张会员卡(一个 if)。盒子也不再套一层「外包装袋」写着「这是您的外卖 + 打包时间」:顾客拿到的就是饭盒本身,打包时间印在小票上(响应头)。

// src/users/dto/user-response.ts —— 主线做法
export interface UserResponse {
  id: number; email: string; displayName: string; role: UserRole; createdAt: string;
  internalNote?: string;            // 只有 admin 视图有
}

export function toUserResponse(user: User, viewer: Viewer): UserResponse {
  const base: UserResponse = {
    id: user.id,
    email: viewer === 'admin' ? user.email : maskEmail(user.email),
    displayName: user.displayName,
    role: user.role,
    createdAt: user.createdAt.toISOString(),
  };
  return viewer === 'admin' ? { ...base, internalNote: user.internalNote } : base;   // 视图差异就是一个 if
}

// Controller:永远只返回映射后的结果
@Public() @Get(':id')
findOne(@Param('id', TracedParseIntPipe) id: number, @Headers('x-demo-role') role?: string): UserResponse {
  return toUserResponse(this.users.findOne(id), viewerOf(role));
}

比喻 ↔ 真实 对照:两种做法怎么选

维度显式映射函数(主线)ClassSerializerInterceptor 白名单(对照)
默认安全吗✅ 天然白名单:没写的字段不会出现✅ 要记得开 excludeAll(默认是黑名单)
依赖 class 实例吗不依赖,输入是什么都行依赖:返回普通对象就失效(第 4 幕)
视图差异普通的 if,类型检查得到groups 字符串,拼错静默失效
能不能单测纯函数,直接测(user-response.spec.ts)要走 interceptor 或手动 instanceToPlain
样板代码多:每个字段写一行少:贴装饰器
和 swagger(Day 20)需要给响应类型写一个带 @ApiProperty 的类(只用来写文档)同一个类既管序列化也管文档

决定 1:主线用显式映射,ClassSerializerInterceptor 保留在 src/serialization-demo/ 做对照。理由:它天然是白名单,不依赖「返回值必须是 class 实例」这个容易被一个展开运算符打破的前提;视图差异是普通代码,读一个函数就知道出门的完整样子;纯函数好测。代价是样板代码多一点,以及 Day 20 要为文档另写响应类。这也和 .NET 的「返回 record DTO + 手动映射 / Mapster」、Java 的 MapStruct 是同一个思路。

决定 2:去掉 { data, timestamp } 包装,资源本身就是响应体。理由:

  • HTTP 已经有放元信息的地方:状态码说成功还是失败,响应头里已经有 Date(服务器时间)、X-Response-Time、x-request-id、Location,不需要在 body 里再包一层 timestamp。
  • 成功和失败本来就分得开:Day 17 起错误是 application/problem+json,成功是 application/json,再加上状态码,客户端不需要靠「有没有 data 字段」判断。
  • 调用方和文档都更简单:const task = await res.json() 直接用;Day 20 的 OpenAPI 里响应 schema 就是 TaskResponse,不用为每个接口再套一层泛型外壳。
  • 集合响应留到 Day 19:分页时响应会变成类似 { items: [...], nextCursor: "…" } 的结构,那是「一页任务」这个资源本身的表示,有明确的语义,不是一个通用的外壳。

代价:这是一次破坏性变更,所有调用方都要从 .data 改成直接读(今天 nest-lab 里改了 3 个测试文件和 2 个脚本)。nest-lab 目前没有外部调用方,所以可以直接改;真实 API 要走版本化或提前通知。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「写了返回类型 TaskResponse,编译器就会拦住多出来的字段」——拦不住。TypeScript 是结构类型:一个对象只要包含目标类型要求的字段就算合格,多出来的字段(非字面量时)不报错。我实测了一下:把带着 deletedAt、ownerToken 的任务直接当成 TaskResponse 返回,tsc 一声不吭;User 当成 UserResponse 返回时报错了,但报错的原因是 createdAt 一个是 Date、一个是 string,纯属碰巧。所以映射函数必须新建一个对象字面量,不能 return task。
  2. 「有了映射函数,就不会漏」——新接口可能忘了调用它。某天有人新写了一个 GET /users/me,顺手 return this.users.findOne(id),前面的一切都白费。兜底靠测试:users.e2e-spec.ts 对每个用户接口、每种视图都断言「响应文本里不出现 password」。
  3. 「去掉外包装袋只是换个样子」——它会打断所有已经按旧格式写好的客户端。今天所有 .body.data 都要改。真实项目里,这类变化要和 Day 19 的版本化一起规划,而不是某天悄悄上线。
④ 真实术语: mapper / mapping function(映射函数,手写或用 AutoMapper、MapStruct 这类工具生成);structural typing(结构类型)与 excess property check(多余属性检查,只对对象字面量生效);envelope(响应外壳:{ data, meta } 这类包装,JSON:API 等规范会用;nest-lab 选择不用);breaking change(破坏性变更)。

🎤 面试翻译练习: 面试官问:"How do you make sure sensitive fields like password hashes never leak through your API?"(或者 .NET 面试:「为什么不直接返回 EF 实体?」)你可以答:
"我不直接返回内部模型或数据库实体,而是为每个资源定义响应 DTO,用映射函数一个字段一个字段地构造响应,这天然是白名单:内部模型以后新增的字段,包括敏感字段,不会自动出现在响应里。如果用 Nest 的 ClassSerializerInterceptor,我会选默认排除、显式 @Expose 的白名单策略,而不是 @Exclude 黑名单,因为黑名单在新字段出现时会悄悄泄露;同时要注意它只对类实例生效,返回普通对象时装饰器不起作用。同一个资源对不同角色返回不同字段时,用 groups 或者在映射函数里按角色分支,但前提是角色来自已经认证过的身份。另外,响应 DTO 是对外契约,字段只增不减,改名要走版本化;测试里我会断言响应文本中绝不出现 passwordHash 这类字段,日志里也同样不记录它们。这和 ASP.NET Core 返回专门的 DTO 加 Mapster、Spring 的 MapStruct 或 @JsonView 是一个思路。"

✅ 总结与自测

今天带走的 4 句话

  1. 进口要报关,出口也要:Controller 不直接返回内部对象,而是返回响应 DTO;响应 DTO 是对外契约,字段只增不减,改名走版本化。
  2. 用白名单,不用黑名单:黑名单在新字段出现时会自动泄露;白名单出错时只是少给一个字段。ClassSerializerInterceptor 只认 class 实例,返回普通对象时黑名单全漏、白名单全空。
  3. nest-lab 主线是显式映射函数:天然白名单、不依赖 class 实例、视图差异就是一个 if、纯函数好测;TypeScript 的结构类型拦不住多余字段,所以映射函数必须新建对象。
  4. 成功响应不再包装:资源本身就是响应体,元信息在状态码和响应头里;错误是 problem+json;集合的结构由 Day 19 的分页决定。序列化只管出门的样子,不管谁能看;日志等其他出口同样要防泄露。
