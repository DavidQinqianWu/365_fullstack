📇 概念卡 #1:DTO —— 接口的进出口报关单

① 一句话大白话: DTO(Data Transfer Object)是一个只描述「这个接口收什么 / 发什么」的类,每个字段旁边写着规则;它和店里内部用的数据模型(Task)是两样东西。

② 生活类比:报关单 vs 仓库台账

仓库内部有一本台账(Task):货号(id)、入库时间(createdAt)都是仓库自己填的。报关单(CreateTaskDto)只让外面的人填他们该填的栏目:品名、清单。如果有人在报关单上自己写了个货号,海关不会照抄进台账,而是把单子退回去。而且不同业务用不同的单子:新货入境(POST)、整批换货(PUT)、补一张更正单(PATCH),栏目要求都不一样,但很多栏的格式规则是共用的。

// src/tasks/dto/replace-task.dto.ts —— PUT 的完整报关单
export class ReplaceTaskDto {
  @Transform(({ value }) => (typeof value === 'string' ? value.trim() : value))
  @IsString() @IsNotBlank() @MaxLength(100)
  title!: string;

  @IsBoolean()
  done!: boolean;

  @IsOptional() @IsArray() @ArrayMaxSize(20)
  @ValidateNested({ each: true }) @Type(() => ChecklistItemDto)
  checklist?: ChecklistItemDto[];
}

// POST:从完整报关单里「挑」两栏(连同规则一起挑过来)
export class CreateTaskDto extends PickType(ReplaceTaskDto, ['title', 'checklist'] as const) {}
// PATCH:同一套规则,每栏都变成可选(呼应 Day 15:PUT 整体替换,PATCH 部分更新)
export class UpdateTaskDto extends PartialType(ReplaceTaskDto) {}

为什么 DTO 和 Task 要分开?① 字段不同:id、createdAt 由服务器管理,客户端不能写;② 演化速度不同:数据库加一列内部字段,不应该自动出现在接口里;接口要兼容老客户端,也不能跟着表结构随便改;③ 安全:如果直接把请求体「合并」进内部对象,客户端多传一个 isAdmin: true 就可能把自己升成管理员 —— 这就是批量赋值漏洞(2012 年 GitHub 就因为 Rails 的这个问题被人往 Rails 官方仓库推了代码)。

(Day 20 接 swagger 时,PickType / PartialType 要改成从 @nestjs/swagger 导入同名工具,这样文档也能跟着继承;用法完全一样。)

🖥️ 前端翻译: 你在前端用 react-hook-form + zodResolver 校验过表单,常有人问:「前端已经校验了,后端为什么还要校验?」因为前端校验是体验,后端校验是安全:任何人都可以绕过你的页面,直接 curl 你的接口(今天的观察脚本就是这么干的)。前端校验让用户少等一次网络往返,后端校验保证进入系统的数据一定合格。两边规则最好同源 —— 如果后端用 zod,前后端甚至可以共享同一个 schema(卡 #3)。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「过了海关,这批货就一定能卖」——报关单只管格式,不管业务。「标题非空、≤100 字」是格式;「已完成的任务不能改标题」(Day 15 的 409)是业务规则,要看资源当前的状态,DTO 根本不知道。观察脚本 J:PATCH /tasks/1 {title} 格式完全合法,照样被 Service 以 409 拒绝。同理,「标题不能重复」这种规则也属于 Service(甚至数据库唯一约束,Week 4)。
  2. 「报关单上没印的栏目,海关一律退回」——只有贴了装饰器的字段才算「印在单子上」。whitelist 认的是「有没有校验装饰器」,不是「类里有没有声明这个属性」。你在 DTO 里写了 note?: string 却忘了贴 @IsOptional() @IsString(),开了 whitelist 时它会被悄悄丢掉,前端发了也白发,还没有任何报错(第 3 幕亲眼看)。
  3. 「有了报关单,台账就安全了」——还要看 Service 往台账里写什么。DTO 挡住了客户端传的 done,但真正决定「新任务一律 done: false」的是 Service 里那一行 done: false。如果 Service 写成 this.repo.insert({ ...dto, ...其他 }) 这种「整包合并」,哪天 DTO 加了个字段,它就会直接流进台账。Service 只写自己明确列出的字段,是 DTO 之外的第二道保险。
④ 真实术语: DTO(Data Transfer Object):跨边界传数据的对象,只有数据和规则,没有业务行为;Entity / domain model(领域模型):系统内部的数据与规则;mass assignment / over-posting(批量赋值,OWASP API Security Top 10 里的 Broken Object Property Level Authorization);mapped types:PickType / OmitType / PartialType / IntersectionType(TypeScript 的 Pick / Omit / Partial,但连运行时的校验装饰器一起继承)。

📇 概念卡 #2:ValidationPipe —— 海关的三道工序

① 一句话大白话: 全局 ValidationPipe 对每个带类型的参数做三件事:先把普通 JSON 变成 DTO 类的实例(transform),再按装饰器逐栏检查(validate),最后按白名单处理多余字段(whitelist);任何一步不过就抛异常,Controller 根本不会执行。

② 生活类比:海关的三道工序

  1. 誊写(class-transformer):报关员把手写单据誊到标准表格上,「叁拾」写成「30」,首尾多余的空格划掉;子表格也一张张誊好(@Type(() => ChecklistItemDto))。
  2. 逐栏核对(class-validator):对着每一栏的格式要求检查,子表格也要进去查(@ValidateNested)。一张单子上的问题一次全列出来,不会改一个退一次。
  3. 划掉没印的栏目(whitelist):表格上没印的栏目,要么默默划掉,要么(forbidNonWhitelisted)整张退回。
// src/common/validation/validation.options.ts
export const validationPipeOptions: ValidationPipeOptions = {
  whitelist: true,              // 只保留有装饰器的字段
  forbidNonWhitelisted: true,   // 多余字段不是丢掉,而是报错
  transform: true,              // 普通对象 → DTO 实例;路径 / 查询参数按声明类型转换
  errorHttpStatusCode: HttpStatus.UNPROCESSABLE_ENTITY,   // 422(卡 #3)
};
// src/app.module.ts —— Day 13 的 DI 版注册
{ provide: APP_PIPE, useFactory: () => new ValidationPipe(validationPipeOptions) }

// src/common/validation/is-not-blank.validator.ts —— 自定义校验器:名字 + validate 函数 + 默认错误信息
registerDecorator({
  name: 'isNotBlank', target: target.constructor, propertyName,
  validator: {
    validate: (value) => typeof value === 'string' && value.trim().length > 0,
    defaultMessage: (args) => `${args?.property} 不能为空或全是空白`,
  },
});

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「单子递上来,海关就会查」——只有它认得是哪种表格时才查。ValidationPipe 靠 design:paramtypes 知道参数是哪个类。如果 Controller 里写成 import type { CreateTaskDto },编译后类型被擦掉,参数类型变成 Object,校验被整个跳过,而且没有任何报错(习题 2 亲手试)。同理,transform: false 时校验照做,但你拿到的是普通对象,不是 DTO 实例(第 2 幕)。
  2. 「誊写也算检查」——transform 只转换,不报错。开了 transform 后,路径参数 '42' 会变成数字 42,但 'abc' 会变成 NaN,不会报错(第 2 幕)。所以 :id 上的 ParseIntPipe 还得留着(观察脚本 K 的 400 就是它拦下的)。这也是为什么 Day 10 的观察脚本现在显示 'NaN' 不是整数:全局 pipe 先跑,把 'abc' 誊成了 NaN,参数级的 pipe 后跑。
  3. 「子表格自然会被一起查」——要两个装饰器配合。@ValidateNested() 告诉 class-validator「进去查」,@Type(() => ChecklistItemDto) 告诉 class-transformer「每一项要变成这个类」。少了 @Type,数组里每一项还是普通对象,上面没有任何规则,于是里面那层什么都不查。另外,class-validator 默认把一个字段的所有错误都列出来:A 的 POST {} 一次报了三条 title 错误,有点吵;Day 17 的 problem+json 会把它们按字段归组。
④ 真实术语: ValidationPipe 选项:whitelist、forbidNonWhitelisted、transform(以及 transformOptions.enableImplicitConversion,按 TS 类型隐式转换,今天没开)、errorHttpStatusCode、stopAtFirstError、exceptionFactory(自定义错误格式,Day 17 会用);class-transformer:plainToInstance、@Type、@Transform、@Exclude / @Expose(Day 18 出口用);class-validator:registerDecorator、@ValidateNested、@ValidateIf。

第 3 幕的 note 是本卡边界 2 的现场:它其实「声明」在 DTO 里,只是没贴装饰器,于是被当成多余字段。whitelist vs forbidNonWhitelisted 选哪个?nest-lab 选报错:① 客户端拼错字段名(titel)会立刻发现,而不是「发了没生效」查半天;② 有人试探性地传 id、isAdmin 时能在日志里看到 422。代价:客户端如果习惯「把 GET 拿到的整条记录改一改再 PUT 回来」,会因为带着 id、createdAt 被拒绝,必须只发可写字段(习题 3 讨论)。如果你的 API 要对大量老客户端保持宽容,选「静默丢弃」也是合理的。

📇 概念卡 #3:400 还是 422,class-validator 还是 zod —— 两个要拍板的决定

① 一句话大白话: 校验失败回什么状态码、规则用哪种库写,都没有唯一正确答案;要的是选一个、说清理由、在整个 API 里保持一致,并用测试把它钉住。

② 生活类比:两种海关风格

A 海关:每张表格的每一栏旁边贴一张规则小标签(class-validator:装饰器贴在类的属性上),表格本身就是一个「类」,能被其他部门(swagger、Nest 的各种工具)直接认出来。B 海关:先写一本规则手册,表格是从手册自动印出来的(zod:先写 schema,类型用 z.infer 推导),手册可以复印给前端用。

// class-validator(主线):规则贴在字段旁边,类本身就是类型
export class CreateTaskDto extends PickType(ReplaceTaskDto, ['title', 'checklist'] as const) {}
@Post() create(@Body() dto: CreateTaskDto) { ... }

// zod(对照):规则是数据,类型从规则推导
const notBlank = z.string().trim().min(1, '不能为空或全是空白').max(100);
export const createTaskSchema = replaceTaskSchema.pick({ title: true, checklist: true }).strict();
export type CreateTaskInput = z.infer<typeof createTaskSchema>;
@Post() create(@Body(new ZodValidationPipe(createTaskSchema)) dto: CreateTaskInput) { ... }

比喻 ↔ 真实 对照:两个决定

维度class-validator + class-transformerzod
类型从哪来类本身就是类型;规则和类型写在一起,但可能对不上(写了 title!: string 却贴 @IsNumber(),编译器不管)z.infer 从 schema 推导,不可能对不上(Day 12 的「一份定义两用」)
写法噪音装饰器多,一个字段四五行链式调用,紧凑
和 Nest 生态集成原生:ValidationPipe、@nestjs/swagger 直接读 DTO 类生成 OpenAPI(Day 20)、ClassSerializerInterceptor(Day 18)要自己写 pipe(今天 19 行),swagger 要额外的桥接库
性能(第 5 幕实测)每次约 24 µs每次约 1.3 µs
生态Nest 官方文档主推,和 .NET DataAnnotations、Java Bean Validation 写法几乎一样(迁移友好)前端、tRPC、Next.js 生态的主流,前后端能共享 schema

决定 1:校验失败回 422。Day 15 时我们说「先跟 Nest 生态用 400」,今天正式拍板改成 errorHttpStatusCode: 422。理由:nest-lab 里 400 和 422 分工明确 ——400 = 请求本身坏了(JSON 语法错由 body parser 回 400;路径参数不是整数由 ParseIntPipe 回 400),422 = JSON 没问题,但内容不符合规则。客户端看到 422 就知道「把表单错误标红给用户看」,看到 400 就知道「是我的代码拼请求拼错了」。GitHub 的 REST API 也用 422 表示校验失败。代价:Nest / Spring / ASP.NET Core 的默认都是 400,接入方可能要多看一眼文档 —— 所以 Day 20 的 OpenAPI 文档里要写清楚。

决定 2:主线用 class-validator,zod 版保留为对照。理由:Week 3 后面三天(Day 18 序列化、Day 20 swagger)都建立在「DTO 是一个类」之上,Nest 生态集成最顺;写法也和 .NET / Java 一一对应。zod 的类型推导和性能确实更好,如果哪天 nest-lab 要和前端共享 schema(比如做 tRPC),换过去只需要把 pipe 和 DTO 一起换掉。src/tasks/dto/task-dto.spec.ts 用同一批输入测两种写法,保证它们「过 / 不过」的结论一致。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「B 海关快 18 倍,当然选 B」——要看这点时间在整单里占多少。24 µs 和 1.3 µs 差了一个数量级,但一个 HTTP 请求从进门到出门通常是毫秒级(Day 13 的日志里一个最简单的请求也要 1–2 ms),校验占不到 2%。只有批量导入、高频内部消息这种「每秒几十万次校验」的热路径,才值得为此换库。第 5 幕的数字只看数量级,不要当成精确基准。
  2. 「两种写法规则一样,结果就一样」——默认行为不一样。第 4 幕里,zod 的 .trim() 是规则的一部分;class-validator 要自己加 @Transform(今天补上之前,class-validator 版保留了首尾空格)。zod 对未知字段默认是丢掉,要 .strict() 才报错;错误信息的措辞、条数也不同(缺 title 时 class-validator 报 3 条,zod 报 1 条)。「等价」不能靠眼睛看,要靠测试钉住。
  3. 「422 能盖住所有输入问题」——不能。JSON 语法错的请求根本走不到 ValidationPipe:body parser 先拒绝,回 400。而且这类请求的错误体里 requestId 是 null(我在 curl 实测时发现的:body parser 跑在 Day 13 的发牌 middleware 之前,那时还没有桌号牌)。这个问题 Day 17 统一错误格式时一起处理。
④ 真实术语: 400 Bad Request vs 422 Unprocessable Content(RFC 9110 §15.5.21,旧名 Unprocessable Entity,Nest 里叫 UnprocessableEntityException);schema-first(zod:先写 schema,类型由它推导)vs class-first / decorator-based(class-validator:类是核心,规则贴在属性上);Standard Schema(zod、valibot、arktype 共同实现的接口,Day 12 的 @nestjs/config 就是靠它直接吃 zod schema)。

⑤ 动手验证:✍️ 预测(先写再运行):同一批 5 个输入,两种写法的结论会不会有不一致的?哪一种错误信息更多?20000 次校验,两者大概差几倍?

【合法】输入 {"title":"  学 zod  ","checklist":[{"text":"a","done":false}]}

✅ 总结与自测

今天带走的 4 句话

  1. DTO 是接口的报关单,和内部模型分开:字段不同(id、createdAt 由服务器管)、演化速度不同、防批量赋值。PUT 用完整 DTO,POST 用 PickType,PATCH 用 PartialType。
  2. 全局 ValidationPipe 三道工序:誊写(transform)→ 核对(validate)→ 划掉没印的栏目(whitelist);嵌套要 @ValidateNested + @Type;import type 会让校验整个失效;transform 不报错,'abc' 会变成 NaN。
  3. DTO 只管格式,业务规则留在 Service:状态冲突仍是 409;Service 只写自己明确列出的字段。
  4. 两个决定:校验失败回 422(JSON 语法错和路径参数错是 400);主线 class-validator(Nest 生态、swagger、迁移友好),zod 版保留对照(类型推导、性能更好),用测试保证两者结论一致。
