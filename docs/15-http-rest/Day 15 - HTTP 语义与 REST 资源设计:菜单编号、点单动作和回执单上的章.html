📇 概念卡 #1:资源与 URI —— 菜单编号体系

① 一句话大白话: URI 用来指认一样东西(名词),「对它做什么」交给 HTTP 方法(动词)去说;同一类东西放在一个集合下,单个东西用编号定位。

② 生活类比:菜单编号体系

菜单上不会写「点红烧肉」「退红烧肉」「加辣红烧肉」三个条目,而是只有一个编号 「热菜 · 12 号:红烧肉」,点、退、改都对着这个编号说。热菜是一个分类(集合),12 号是分类里的一道菜(单个),「12 号的配菜」是挂在这道菜下面的子项。

比喻真实设计例子
菜单分类集合资源,用复数名词/tasks
分类里的一道菜单个资源,集合 + 标识/tasks/1
这道菜的配菜子资源:只在父资源下面有意义的东西/tasks/1/comments、/tasks/1/comments/7
点、退、改HTTP 方法(下一张卡)POST /tasks、DELETE /tasks/1、PATCH /tasks/1
「只看辣的」查询参数:过滤、排序、分页(Day 19)/tasks?done=false
❌ 动词塞进 URI                     ✅ 名词 + 方法
POST /createTask                   POST   /tasks
GET  /getTask?id=1                 GET    /tasks/1
POST /tasks/1/complete             PATCH  /tasks/1        {"done": true}
POST /deleteTask/1                 DELETE /tasks/1
🖥️ 前端翻译: 你在 Next.js App Router 里写过 app/api/tasks/route.ts(导出 GET / POST)和 app/api/tasks/[id]/route.ts(导出 GET / PUT / PATCH / DELETE):文件路径就是资源,导出的函数名就是方法。这本身就是 REST 的思路。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「菜单编得漂亮,点单就一定顺」——REST 不是标准,而是一种风格。没有哪个工具会因为你写了 /getTask 而报错。它是一组约束(Roy Fielding 2000 年的博士论文):客户端-服务器、无状态(每个请求自带全部信息,服务器不靠「上一个请求」记住你)、可缓存、分层、统一接口。其中最高一级的 HATEOAS(响应里带上「下一步能去哪」的链接)现实中很少有人完整实现;大多数「REST API」其实是「资源 + 方法 + 状态码都用对了的 HTTP API」,这就够用了。
  2. 「一切都能说成『改某个字段』」——真正的命令硬塞进 PATCH 会藏住语义。「把任务标记为完成」确实就是改 done,用 PATCH 很自然;但「归档并通知所有关注者」「重新发送邀请邮件」「退款」是有副作用的动作,硬写成 PATCH {"archived": true} 反而让人看不出会发邮件。常见的两种做法:Google API 风格的 POST /tasks/1:archive,或者把动作建模成资源 POST /tasks/1/archive-requests。取舍:前者直白,后者能记录每一次动作(谁、什么时候、结果如何)。
  3. 「一个编号对应后厨一个冰柜」——资源不等于数据库表。资源是你对外承诺的模型:一个资源可以由几张表拼出来,一张表也可以拆成几个资源。URI 一旦发布就很难改(客户端都写死了),所以要按「调用方怎么理解」设计,而不是按表结构。
④ 真实术语: resource(资源)、collection / item(集合 / 单个)、sub-resource(子资源)、URI(统一资源标识符);REST 约束:client-server、stateless、cacheable、layered system、uniform interface、HATEOAS;常用的成熟度说法是 Richardson 成熟度模型(0 级:一个 URI 全靠 POST;1 级:资源;2 级:资源 + 方法 + 状态码;3 级:HATEOAS)—— 今天的 nest-lab 在 2 级。

📇 概念卡 #2:方法语义 —— 「再来一份」和「换成这份」不是一回事

① 一句话大白话: 每个 HTTP 方法都带着一份承诺:会不会改东西(安全)、重复发几次结果是否和发一次一样(幂等)。客户端、浏览器、代理、重试逻辑都靠这份承诺做决定,所以服务器必须兑现它。

② 生活类比:五种点单动作

点单动作方法安全(不改东西)幂等(说 N 次 = 说 1 次)nest-lab 里
「看看菜单 / 看看我那道菜做到哪了」GET(以及 HEAD、OPTIONS)✅✅200
「再来一份」POST❌❌ 说两次就上两份201 + Location
「把 12 号换成这份:红烧肉,不要辣,大份」PUT(整体替换)❌✅ 说两次还是这一份200
「12 号不要香菜」(其他照旧)PATCH(部分更新)❌⚠️ 看你怎么写(下面讲)200
「撤掉 12 号」DELETE❌✅ 撤两次,桌上还是没有这道菜204

PUT vs PATCH 的关键在于:PUT 发过去的是这个资源完整的新样子,服务器照着替换;PATCH 发过去的是一张修改单,只动提到的字段。所以 PUT 漏了字段,要么被当成「这个字段不要了 / 恢复默认」,要么(nest-lab 的做法)直接拒绝:

// src/tasks/task-input.ts(Day 16 换成 DTO)
export function parseReplace(body: unknown): ReplaceTaskInput {   // PUT:客户端能改的字段一个都不能少
  const obj = asObject(body);
  return { title: checkTitle(obj.title), done: checkDone(obj.done) };
}
export function parsePatch(body: unknown): PatchTaskInput {       // PATCH:给了哪个改哪个
  const obj = asObject(body);
  const patch: PatchTaskInput = {};
  if ('title' in obj) patch.title = checkTitle(obj.title);
  if ('done' in obj) patch.done = checkDone(obj.done);
  if (Object.keys(patch).length === 0) throw new BadRequestException('至少要给 title 或 done 中的一个');
  return patch;
}

比喻 ↔ 真实 对照

比喻真实概念
只是看看,不动后厨safe(安全方法):GET / HEAD / OPTIONS,不应该改变服务器状态;浏览器预取、爬虫、缓存都假设它安全
说几遍都是那一份idempotent(幂等):请求执行 1 次和 N 次,服务器状态相同;GET / PUT / DELETE 都是
「再来一份」说两遍上两份POST 不幂等 → 网络超时后客户端不敢自动重试,用户双击按钮会建出两条
服务员记下「这张单我已经处理过」Idempotency-Key 请求头:客户端给每次「下单」一个唯一键,服务器记住处理过的键,重复的直接返回上次的结果(支付接口的标配;本课程后面实现)
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「方法写成 PUT,它就自动幂等了」——语义是约定,服务器不会替你强制。你完全可以写一个 GET /tasks/1/delete 去删数据,或者让 PUT 每次都往数组里追加一条,框架一个字都不会说。后果是:爬虫顺着链接把数据删光、网关自动重试 PUT 时建出重复数据。幂等是你的实现兑现出来的。
  2. 「幂等 = 每次的响应都一样」——不对,说的是服务器状态。观察脚本里 DELETE /tasks/3 第一次 204、第二次 404:响应不同,但「任务 3 不存在」这个状态是一样的,所以 DELETE 仍然幂等。同理,PUT 两次响应里的 timestamp 不同,也不影响幂等。
  3. 「PATCH 天生不幂等」/「PATCH 天生幂等」——都不对,取决于修改单怎么写。nest-lab 的 PATCH 是「把 done 设成 true」这种设置值的写法(JSON Merge Patch 风格),发多少次结果都一样,是幂等的;但如果修改单写的是「{"op": "increment", "field": "views"}」这种相对操作,每发一次就加一次,就不幂等。规范只保证 GET / PUT / DELETE 幂等,PATCH 不作保证,所以客户端不会自动重试它。
④ 真实术语: RFC 9110(HTTP Semantics,2022 年取代旧的 RFC 7231)定义了方法的 safe / idempotent / cacheable 属性;PATCH 在 RFC 5789;PATCH 的两种常见格式:JSON Merge Patch(RFC 7396,application/merge-patch+json,今天的写法)和 JSON Patch(RFC 6902,[{"op":"replace","path":"/title","value":"x"}]);Idempotency-Key(IETF 草案,Stripe 等支付 API 广泛使用)。

📇 概念卡 #3:状态码与内容协商 —— 回执单上的章

① 一句话大白话: 状态码是给程序看的结论:成功还是失败、是谁的错、该不该重试、新东西在哪。内容协商是双方先说好「你给我什么格式、我回你什么格式」,说不拢就用 406 / 415 明确拒绝。

② 生活类比:回执单上的章

每张回执单盖一个章:「已上菜」「已下单,桌号在这」「已撤,无需取餐」「单子写得看不懂」「没有这道菜」「这里不能这么点(只能堂食)」「和你桌上现在的状态冲突(菜已经上了,不能再改口味)」。顾客不用读回执上的小字,看章就知道下一步怎么做。另外,本店只有中文菜单:你说「我只看英文菜单」(Accept),店员回一个「抱歉,没有」的章(406);你递过来一张英文单子(Content-Type),店员也回一个「看不懂这种单子」的章(415)。

看不懂你递的单子415 Unsupported Media Type请求体的 Content-Type 服务器不支持Content-Type: text/plain

400 还是 422?两派都有。RFC 9110 的意思是:400 = 请求坏了(语法错、缺必填、类型不对);422 = 格式和语法都对,但内容没法处理(语义错误)。Rails、Laravel、FastAPI 校验失败默认回 422;Nest(明天的 ValidationPipe)、Spring、ASP.NET Core 默认回 400。选一种,在整个 API 里保持一致比选哪种更重要。nest-lab 跟随 Nest 生态用 400(ValidationPipe 的 errorHttpStatusCode 可以改成 422,明天会看到)。

405 是怎么补上的:Express / Nest 只认「路径 + 方法」的组合,组合找不到就一律 404。nest-lab 的做法是在 Controller 最后写两个 @All() 兜底路由(Day 8 讲过:路由按声明顺序匹配,前面的具体方法都没匹配上才轮到它们),设置 Allow 头再抛 MethodNotAllowedException;OPTIONS 请求则直接回 204 + Allow。取舍:改动小、看得懂,但每个 Controller 都要手写一份 Allow 列表,新增方法时要记得同步(Spring、ASP.NET Core 和 Go 1.22 的路由器会自动做这件事)。

🖥️ 前端翻译: 你一定见过这种接口:永远回 200,失败时 body 里写 {"code": 500, "msg": "系统错误"}。前端每个请求都要 if (res.data.code !== 0)。它的问题是:fetch 的 res.ok、axios 对非 2xx 的自动 reject、浏览器和 CDN 的缓存、网关的重试与熔断、监控面板上的错误率,全都只看状态码,这些工具因此全部失效。状态码说清「结论」,body 里再放给人看的细节(Day 17 的 problem+json 会规范 body 的格式)。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「章盖错了,店员会发现」——状态码选错不会报错。改动之前,text/plain 的请求得到的是 500,程序照样跑,只是监控会说「服务器坏了」,客户端可能还会重试。状态码错了没人提醒你,只能靠规范、code review 和测试(今天的 rest.e2e-spec.ts 把每个码都钉住了)。
  2. 「章盖得越细越好」——不要发明新码,有时还要故意模糊。用标准里已有的码,别自造 499、别拿 418 I'm a teapot 开玩笑。另一方面,出于安全,有时会故意不说实话:对「无权查看的资源」回 404 而不是 403,避免告诉攻击者「这个 ID 存在」(GitHub 对私有仓库就是这么做的)。
  3. 「顾客说只看英文菜单,就一定只能给英文」——Accept 是偏好,不是命令。Accept 可以带权重(application/xml, */*;q=0.1 意思是「最想要 XML,实在不行什么都行」),这时服务器回 JSON 完全合规(观察脚本第 4 幕有这一条)。只有当客户端列出的所有类型都给不了时,才回 406。很多 API 甚至选择忽略 Accept、永远回 JSON,这也常见,只是不够严谨。Content-Type 则不一样:它描述的是请求体本身是什么,服务器读不懂就该 415。
④ 真实术语: 状态码五个家族(Day 6):1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误;content negotiation(内容协商):proactive(服务器根据 Accept、Accept-Language、Accept-Encoding 挑选表示)、quality value(q=0.1);Content-Type(请求体 / 响应体的媒体类型)vs Accept(客户端想要的响应类型);ETag + If-Match / If-None-Match(条件请求:412 和 304,后面讲)。Express 里现成的两个工具:req.accepts(type)、req.is(type)。

内容协商的核心只有几行(src/common/content-negotiation.middleware.ts):

if (!req.accepts('application/json')) throw new NotAcceptableException(...);              // 406
const hasBody = Number(req.headers['content-length'] ?? 0) > 0 || req.headers['transfer-encoding'] !== undefined;
if (METHODS_WITH_BODY.has(req.method) && hasBody && !req.is('application/json'))
  throw new UnsupportedMediaTypeException(...);                                            // 415

(写 hasBody 是一次真实的踩坑:最初直接用 req.is() === false 判断,结果 fetch 发来的「没有请求体的 POST」带着 Content-Length: 0,被 Express 当成「有请求体但类型不对」,误判成了 415。现在没有请求体的写请求交给 handler,回 400「请求体必须是一个 JSON 对象」。)

HTTP 语义是协议层的规矩,和框架无关;区别只在于各家框架默认替你做了多少:

🎤 面试翻译练习: 面试官问:"What's the difference between PUT and PATCH? Why isn't POST idempotent, and how would you deal with duplicate submissions?"(或者中文:「PUT 和 PATCH 的区别?POST 为什么不幂等?」)你可以答:
"PUT 是整体替换:请求体是资源完整的新表示,服务器照着替换,所以缺字段要么被视为删除或重置,要么直接拒绝;它是幂等的,同样的 PUT 发多次,服务器状态和发一次一样,客户端可以放心重试。PATCH 是部分更新,只带要改的字段;它是否幂等取决于修改单的写法,设置值的写法是幂等的,像自增这种相对操作就不是。POST 的语义是让服务器在集合下创建一个新资源,ID 由服务器分配,所以发两次就会建两条,网络超时后不能盲目重试。处理重复提交,常见做法是让客户端带一个 Idempotency-Key 请求头,服务器记录已经处理过的键,重复的请求直接返回第一次的结果;前端也会在提交时禁用按钮。另外创建成功应该返回 201 并在 Location 头里给出新资源的地址,删除成功常用 204。"

✅ 总结与自测

今天带走的 4 句话

  1. URI 是名词,方法是动词:集合用复数(/tasks),单个用编号(/tasks/1),从属关系用子资源;真正有副作用的命令可以用 POST /tasks/1:archive 或动作子资源,别硬塞进 PATCH。REST 是风格不是标准。
  2. 方法带着承诺:GET 安全且幂等;PUT、DELETE 幂等(说的是服务器状态,不是响应);POST 不幂等,重复提交要靠 Idempotency-Key;PATCH 是否幂等看修改单写法。承诺要靠你的实现兑现。
  3. PUT 整体替换,PATCH 部分更新:PUT 要完整表示,缺字段 nest-lab 直接 400;PATCH 只改给了的字段。
  4. 状态码是给程序看的结论:201 + Location、204、400 / 422(选一种保持一致)、404、405 + Allow、409、406、415。Nest / Express 默认不管 405 / 406 / 415,今天手动补上;选错状态码不会报错,要靠测试钉住。
