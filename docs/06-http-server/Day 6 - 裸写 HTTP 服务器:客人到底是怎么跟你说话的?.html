🚪 接上回:后厨调教好了,前门还没看过

Day 5 我们给店里请了帮厨,Week 1 的「后厨扩容」到此齐了:服务员不站着等(Day 1)、按固定路线巡场(Day 2)、大菜走传送带(Day 3)、开分店(Day 4)、请帮厨(Day 5)。但有一件最基本的事我们一直没看:客人走到门口,到底是怎么跟你说话的?

💡 生活翻译: 客人不会进门跟你闲聊,他递一张点菜单。点菜单的格式全世界统一:第一行写「我要什么」,接着几行写「我是谁、我能吃什么、附件多重」,空一行,下面是附件。你也回一张回执单,格式几乎一样,只是第一行写「成了 / 没成 / 走错门了」。这套格式就叫 HTTP。

你天天写 fetch,看到的是浏览器 DevTools 整理好的表格。今天把表格拆掉,看原文。这不是为了以后手写服务器(你 99% 的时间会用 NestJS),而是为了在这些时候能看穿框架:

  • 接口返回 200,但前端 res.json() 报错 → 回执单上的 Content-Type 写错了
  • 中文接口偶尔被截断、客户端报 Parse Error → Content-Length 按字符数算了(今天习题 3 亲手复现)
  • 上传大文件服务器内存爆了 → 把请求体当字符串一次读完了(Day 3 的背压问题)

📇 概念卡 #1:HTTP 报文 —— 一张有固定格式的点菜单

① 一句话大白话: 浏览器和服务器之间传的,就是几行按固定格式写的字,没有魔法。

② 生活类比:点菜单的四个栏目

一张点菜单固定分四栏,顺序不能乱:第一行写点什么、抬头栏写备注(一行一条)、一道横线表示备注写完了、横线下面贴附件(可以没有)。下面是习题 1 里 fetch 发 POST 时,服务器真实收到的字节(\r\n 已显形,来自本机实测):

POST /tasks?from=fetch HTTP/1.1\r\n          ← 第一行:请求行(方法 路径 协议版本)
host: localhost:34285\r\n                     ← 抬头栏:请求头,一行一条「名字: 值」
connection: keep-alive\r\n
content-type: text/plain;charset=UTF-8\r\n
accept: */*\r\n
accept-language: *\r\n
sec-fetch-mode: cors\r\n
user-agent: node\r\n
accept-encoding: gzip, deflate\r\n
content-length: 20\r\n                        ← 附件有 20 个字节
\r\n                                          ← 横线:一个空行,头写完了
{"title":"学 HTTP"}                           ← 附件:请求体(body)

注意两个细节:你只写了 method 和 body,fetch 自己补了 9 行头;{"title":"学 HTTP"} 只有 18 个字符,却写着 content-length: 20——「学」在 UTF-8 里占 3 个字节。HTTP 只认字节,不认字符,这个伏笔在概念卡 #3 收。

比喻 ↔ 真实 对照

比喻真实组件例子
第一行「我要什么」请求行(request line):方法 + 路径(含 query)+ 协议版本GET /tasks/1?x=2 HTTP/1.1
「点菜 / 加菜 / 换菜 / 退菜」这个动作方法(method)GET 看、POST 新建、PUT 整个替换、PATCH 改几个字段、DELETE 删
抬头备注栏请求头(headers),名字不区分大小写Host、Content-Type、Authorization
那道横线一个空行 \r\n\r\n服务器靠它知道「头结束了」
附件请求体(body),长度由 Content-Length 说明JSON、表单、文件字节
递单的那个窗口一条 TCP 连接(node:net 那一层)HTTP 只是在这条管子上约定「怎么写字」
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「点菜单是一整张纸递进来的」——不是。TCP 是一条字节流(Day 3 的传送带),没有「一张」的概念:一个大请求可能分好几个 data 块到达,keep-alive 时两张单子也可能挤在一块里。所以服务器才必须靠「空行」找头的结尾、靠 Content-Length 找体的结尾——没有这两个记号,根本分不清一张单子在哪结束。
  2. 「HTTP 永远是人能读的文字」——只对 HTTP/1.1 成立。HTTP/2、HTTP/3 在线路上是二进制帧,加了 HTTPS 还是加密的,你抓包看不到明文。但语义完全一样:还是方法、路径、头、体、状态码。今天学的是「内容」,换的只是「信封」。
  3. 「格式写错一点没关系,对方会将就」——别指望。行尾标准是 \r\n,有些客户端对 \n 宽容,有些不;宽容的解析器还曾被利用来做请求走私攻击。自己手写报文时一律 \r\n。
④ 真实术语: HTTP message(报文)= start line(请求行 / 状态行)+ header fields + 空行 + message body。HTTP 是跑在 TCP 之上的应用层协议,客户端发 request、服务器回 response,一问一答。node:net 给你原始 TCP 字节;node:http 帮你把字节解析成对象。

⑤ 动手验证:习题 1 用 node:net(绕开 http 库)起一个裸 TCP 服务器,把客人的原话原样打印出来,然后手写一张回执单回去。先猜:你不写任何 header,fetch 会自己带几行?你只手打两行字(请求行 + Host),服务器会理你吗?

📇 概念卡 #2:回执单与状态码 —— 五个家族、401 vs 403、幂等

① 一句话大白话: 服务器回的单子第一行有个三位数,只看第一位就知道是「成了」「换地方」「你错了」还是「我错了」。

② 生活类比:回执单第一行盖的章

回执单和点菜单长得几乎一样,只有第一行不同:HTTP/1.1 200 OK。这个三位数像是盖在回执单上的章,五种颜色的章对应五个家族:

家族餐厅里的章常见成员(今天习题 2 会亲眼看到带 ★ 的)
1xx「稍等,还没完」101 换协议(升级成 WebSocket,Week 26 见)
2xx「成了」★200 OK · ★201 Created(新菜已下单,单号在 Location 里)· ★204 No Content(办成了,但没东西给你)
3xx「不在这儿,去那边」301 永久搬家 · 302 临时去那边 · 304 你手上那份还新鲜(缓存)
4xx「客人的错」★400 话都没说清(JSON 不合法)· 401 · 403 · ★404 没这道菜 · 409 冲突 · ★422 话说清了但内容不合理 · 429 点太快了
5xx「店家的错」500 后厨炸了 · 502 上游供应商出问题 · 503 忙不过来 · 504 上游太慢

4xx 和 5xx 的分界决定了要不要半夜爬起来修:用户填错表单你回 500,监控会天天报警,而那根本不是你的锅。反过来,「什么都回 200、错误写在 body 里 {"success": false}」也是坏习惯——缓存、CDN、监控、重试逻辑都只看状态码。错误的 body 怎么写有个国际标准叫 problem+json(RFC 9457),习题 2 已经在用,Week 3 设计 API 时细讲。

401 vs 403:门口保安的两句话

餐厅里真实含义
401 Unauthorized「你是谁?先出示会员卡」没认证 / 凭证无效(其实应该叫 Unauthenticated,历史命名错误)
403 Forbidden「会员卡看过了,是你本人。但这是员工通道,你不能进」认证了,但没授权

幂等:同一张单子递十次,后厨最后是什么样

幂等(idempotent)= 同一个请求做 1 次和做 10 次,服务器最终的状态一样。习题 2 的真实输出正好是一组对照:

③ POST /tasks     → 201 Created   Location: /tasks/3
④ POST /tasks     → 201 Created   Location: /tasks/4   ← 同样的单子,多出第二个任务:不幂等
⑦ DELETE /tasks/1 → 204 No Content
⑧ DELETE /tasks/1 → 404 Not Found                      ← 状态码变了,但「1 号已不存在」这个状态没变:幂等

为什么这件事重要?网络会抽风:客户端发了请求没收到回执,它分不清是「店家没收到单子」还是「做了但回执丢了」。幂等的请求可以放心重试,不幂等的重试可能下两次单、扣两次钱。GET / PUT / DELETE 按约定是幂等的,POST 不是;支付这类 POST 要靠「幂等键」(Week 5 落地)。

比喻 ↔ 真实 对照

比喻真实组件
回执单第一行状态行(status line):HTTP/1.1 201 Created
章的颜色状态码第一位数字(status class)
新菜的单号201 时的 Location 响应头
回执单背面的说明响应体;错误时推荐 application/problem+json
同一张单子递十次客户端重试;是否安全取决于方法是否幂等
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「章是协议盖的,盖错了会被拦下」——不会。状态码就是你代码里写的一个数字,没有任何东西阻止你给错误回 200、给成功回 500。正确性全靠你自觉,这也是为什么团队要统一规范。
  2. 「幂等 = 每次回执单一样」——错。幂等说的是服务器状态,不是响应:⑦⑧ 的两次 DELETE 一个 204 一个 404,照样是幂等的。另外「GET/DELETE 是幂等的」只是约定,你要是在 GET 里写了「访问次数 +1 并扣积分」,框架不会拦你,重试就会出事。
  3. 「状态码名字照字面理解」——小心。401 叫 Unauthorized 其实是「没认证」;422 在 Node 里打印成 Unprocessable Entity(习题 2 实测),新标准 RFC 9110 已改名 Unprocessable Content,是同一个码。
④ 真实术语: status code 五类:1xx Informational、2xx Successful、3xx Redirection、4xx Client Error、5xx Server Error。Authentication(认证,你是谁)→ 401;Authorization(授权,你能干什么)→ 403。Idempotent methods:GET、HEAD、PUT、DELETE(还有 OPTIONS);safe methods(只读不改):GET、HEAD。

⑤ 动手验证:习题 2 会按顺序发 9 个请求,先在文件顶部给每个请求写下你猜的状态码,再运行对答案。重点看 ③④ 和 ⑦⑧ 这两组。

📇 概念卡 #3:node:http —— 前台帮你拆单,但菜还是在传送带上走

① 一句话大白话: node:http 替你把点菜单拆成对象、把回执单拼成字节;但单子的附件和你上的菜,依然是一点一点流过去的。

② 生活类比:前台拆单 + 两条传送带

习题 1 里你用 node:net 亲手拆过单:收到一坨字节,自己找空行、自己切行。node:http 就像店门口的前台:把点菜单的第一行和抬头栏抄成一张整齐的表格(req.method、req.url、req.headers)递给服务员;回执单的格式、空行、\r\n 也由前台替你写对。

但附件和菜不经过前台抄写:客人的附件(请求体)放在一条进店传送带上一段段送进来,这就是 req;你上的菜放在一条出店传送带上一盘盘送出去,这就是 res。不是比喻——req 就是 Day 3 的 Readable,res 就是 Day 3 的 Writable。

import http from "node:http";
import fs from "node:fs";

http.createServer((req, res) => {
  req.method;                    // "GET"          ← 前台抄好的请求行
  req.url;                       // "/tasks?done=1" ← 只有路径 + query,没有域名
  req.headers["content-type"];   // 头名字一律转小写

  // res 是 Writable:先写头,再写体
  res.writeHead(200, { "Content-Length": fs.statSync("big.bin").size });
  fs.createReadStream("big.bin").pipe(res);   // Day 3 的 pipe,自带背压
}).listen(3100);

上菜的两种报数方式 + 吃完别急着走

餐厅里真实 header什么时候用
「这桌一共 3 盘,上完就齐了」Content-Length: 12(字节数)开始发之前就知道总大小:JSON、静态文件
「做好一盘上一盘,最后喊一声『上齐了』」Transfer-Encoding: chunked开始发时还不知道总大小:AI 逐字回答、查数据库边查边吐。你不写 Content-Length,Node 自动切成 chunked(习题 3 实测)
客人吃完不走,接着点下一单Connection: keep-aliveHTTP/1.1 默认:一条 TCP 连接连续跑多个请求,省掉每次重新建连接

回收概念卡 #1 的伏笔:Content-Length 要的是字节数。"你好,HTTP!" 的 .length 是 8,UTF-8 字节数是 12。习题 3 用 8 当 Content-Length,客户端实测只收到 "你好,H",剩下的 4 个字节 TTP! 被当成「下一张回执单」去解析,于是报 Parse Error: Expected HTTP/。和习题 1 Part C 是同一个病:报的数和实际发的不一致,对方要么截断,要么把多出来的字节当成下一张单子。永远用 Buffer.byteLength(str),或者干脆让框架替你算。

比喻 ↔ 真实 对照

比喻真实组件
前台抄好的表格http.IncomingMessage 上的 method / url / headers(底层解析器是 C 写的 llhttp)
进店传送带(附件)req:Readable 流,for await (const chunk of req) 或 pipeline(req, file)
出店传送带(上菜)res:http.ServerResponse,Writable 流,write() / end() / pipe(res)
先报「一共几盘」Content-Length
一盘一盘上,最后喊上齐Transfer-Encoding: chunked(每块前面写长度,最后一个长度为 0 的块表示结束)
同一桌客人接着点keep-alive:同一条 TCP 连接复用
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「前台是另一个员工,他忙他的,服务员忙服务员的」——不是。node:http 没有另开线程,拆单就发生在服务员自己的主线程上,你的 handler 也在这儿跑。handler 里做 2 秒 CPU 计算,所有客人一起等(Day 1 的老规矩,该交给 Day 5 的帮厨)。
  2. 「客人吃完不走,就能同时点好几单」——HTTP/1.1 里不行。一条 keep-alive 连接上同一时刻只跑一个请求,前一个没回完后一个只能排队(队头阻塞),所以浏览器会对同一个域名开好几条连接;HTTP/2 才能在一条连接上并行。而且「不走」也有期限:Node 默认空闲 5 秒就关(响应头里能看到 keep-alive: timeout=5)。
  3. 「传送带自带红灯,不会撑爆」——只有你接对了才会。pipe / pipeline 会处理背压;你要是写 req.on("data", c => body += c) 把附件全攒进内存,或者 res.end(fs.readFileSync(大文件)),传送带就形同虚设。习题 3 会量出差距。
④ 真实术语: http.createServer(handler):每个请求调用一次 handler(req, res);req 是 IncomingMessage(Readable),res 是 ServerResponse(Writable)。Content-Length(定长,字节数)vs chunked transfer encoding(分块,长度未知时用);persistent connection / keep-alive(连接复用)。框架做的事 = 在这之上加路由、body 解析、序列化、错误映射。

⑤ 动手验证:习题 3 四个小实验:中文 Content-Length 用错会怎样、不写 Content-Length 头里多了什么、keep-alive 时服务器看到几条连接、发 100MB 时流式和一次性的内存差多少。每个都先猜再跑。

🧩 这在 NestJS 里对应什么

从 Day 8 起我们用 NestJS 写同一个任务清单接口(进 nest-lab/),今天先看一眼对照。Nest 默认跑在 Express 上,Express 的 req / res 就是 node:http 的那两个对象加了些方法——你今天看到的点菜单、回执单、两条传送带,一样不少,只是有人替你填。

// 示意代码(今天不用建 Nest 项目)
import { Controller, Get, Post, Delete, Param, Body, Query, Res,
         HttpCode, NotFoundException, ParseIntPipe } from "@nestjs/common";
import type { Response } from "express";
import { createReadStream } from "node:fs";

@Controller("tasks")                                  // 路径前缀 /tasks
export class TasksController {
  constructor(private readonly tasks: TasksService) {}

  @Get()                                              // GET /tasks
  list(@Query("done") done?: string) {
    return this.tasks.list(done);                     // 直接 return 对象 → 自动 200 + JSON + Content-Length
  }

  @Get("export")                                      // 想自己掌管出店传送带时
  export(@Res() res: Response) {
    createReadStream("tasks.csv").pipe(res);          // @Res() 拿到的就是底层的流(更推荐用 StreamableFile)
  }

  @Get(":id")                                         // GET /tasks/:id
  get(@Param("id", ParseIntPipe) id: number) {        // /tasks/abc → 自动 400
    const task = this.tasks.find(id);
    if (!task) throw new NotFoundException(`没有 id 为 ${id} 的任务`);   // 抛异常 → 自动 404
    return task;
  }

  @Post()                                             // POST 默认就回 201
  create(@Body() dto: CreateTaskDto) {                // body 自动读完 + JSON.parse
    return this.tasks.create(dto);
  }

  @Delete(":id")
  @HttpCode(204)                                      // 改默认状态码
  remove(@Param("id", ParseIntPipe) id: number) {
    this.tasks.remove(id);
  }
}
今天在习题 2 里手写的Nest 里谁替你做
正则切 /tasks/:id、判断 req.method@Controller("tasks") + @Get(":id") / @Post() / @Delete()
Number(idText) + 判断是不是整数@Param("id", ParseIntPipe)(Pipe,Week 2 细讲)
for await (const c of req) 读 body + JSON.parse + 1MB 上限@Body()(底层是 Express 的 body parser,默认也有大小上限)
writeHead + JSON.stringify + Buffer.byteLengthhandler 直接 return 对象
手写 201 / 204POST 默认 201;其他默认 200,用 @HttpCode() 改
sendProblem(res, 404, ...)throw new NotFoundException(),由内置的异常过滤器(Exception Filter)翻译成 404
fs.createReadStream().pipe(res)@Res() 拿底层 res(之后 Nest 就不再替你发响应),或返回 StreamableFile

⚠️ 一个小差别先记着:Nest 默认的错误体是 {"statusCode":404,"message":"...","error":"Not Found"},不是 problem+json。想统一成 RFC 9457 格式,要自己写一个异常过滤器——这正是 Week 3 要做的事。

✅ 总结与自测

今天带走的 4 句话

  1. HTTP 报文 = 有固定格式的点菜单:请求行 + 头 + 空行 + 体;回执单只把第一行换成状态行。TCP 上只有字节流,服务器靠「空行」找头的结尾、靠 Content-Length(或 chunked)找体的结尾。
  2. 状态码看第一位:2 成了、3 去别处、4 客人的错、5 店家的错;401 不知道你是谁,403 知道你是谁但不让进。
  3. 幂等看服务器状态,不看回执单:DELETE 两次是 204 + 404,照样幂等;POST 两次多一条数据,不幂等,所以不能盲目重试。
  4. node:http 帮你拆单拼单,但 req / res 就是 Day 3 的流:大东西用 pipe;Content-Length 写字节数;不知道总长就让 Node 用 chunked;Nest 只是在这之上加了路由、body 解析、序列化和错误映射。
