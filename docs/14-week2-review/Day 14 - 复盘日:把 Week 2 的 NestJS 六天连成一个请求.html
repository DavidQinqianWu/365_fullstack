🗺️ 第一件事:画出「一个 POST /tasks 请求在 nest-lab 里的一生」(约 25 min)

Week 1 复盘时你画的是「一个 HTTP 请求在 Node 服务器里的一生」。今天把同一张图往上盖一层:同一个请求,进了 NestJS 以后又经过了哪些站。六天学的东西,串成一条线。

任务

在 src/14-week2-review/request-lifecycle.md 里,用文字或 mermaid 画出下面这个过程。每一站标注两个编号:它是 Week 2 哪一天学的(Day 8–13),以及它建在 Week 1 的哪个机制之上(Day 1–6)。

场景

curl -i -X POST localhost:3000/tasks \
  -H 'content-type: application/json' \
  -H 'x-demo-key: let-me-in' \
  -H 'x-request-id: review-1' \
  -d '{"title":"复盘 Week 2"}'

要覆盖这些环节(顺序你自己排):

  • TCP 连接进来、报文被解析成 req 和 res
  • 请求 ID 从哪里来、存在哪、怎么回写到响应头
  • 「进门 / 出门」两行日志是谁打的,为什么它们都带着 review-1
  • 全局保安怎么判断这个接口要不要钥匙,钥匙的值从哪来
  • 计时从哪里开始、在哪里结束、计时头在哪里写
  • 请求体怎么变成 body 参数,@RequestId() 参数从哪拿值
  • Controller 怎么拿到 Service,Service 怎么拿到仓储和时钟(谁 new 的?)
  • 返回值怎么变成 { data, timestamp },状态码为什么是 201
  • 如果中途抛了异常,从哪一站跳到哪一站,错误体长什么样

再写三条支线:换成 DELETE /tasks/1(钥匙 + x-demo-role: admin)多经过哪几站;GET /tasks/999 从哪一站开始短路;开店时、第一个请求到来之前已经发生了哪些事。

为什么这张图值 25 分钟

面试官问「你用过 NestJS 吗」,背 API 的人说「我写过 Controller 和 Service」;能把这张图从 TCP 画到响应头的人,会被追问到 Spring 和 ASP.NET Core——而你能接得住。

这张图在 Spring Boot 和 ASP.NET Core 里结构几乎一样:Filter / Middleware → 鉴权 → 拦截器 / Action Filter → 参数绑定与校验 → Controller → Service → 异常处理。你画的是「企业级后端框架」,不是「NestJS」。

4.2 自测 12 题(闭卷,约 20 min,写在 src/14-week2-review/self-test.md)

基础题(每题 1 分)

  1. Module、Controller、Provider 各管什么?为什么 Controller 不直接操作数据?
  2. 为什么 TasksService 的构造函数要写 @Inject(TASKS_REPOSITORY),而 TasksController 注入 TasksService 时不用写?
  3. Nest 默认的 Provider 作用域是什么?REQUEST 作用域的「传染」是什么意思?
  4. 按执行顺序写出 Nest 请求管线的五种站(出错时走哪一站)。
  5. @Public() 这张标签是什么时候贴上去的?谁在什么时候读它?
  6. 为什么不能用 z.coerce.boolean() 解析环境变量 LOG_REQUESTS=false?

理解题(每题 2 分)

  1. 没带钥匙的 POST /tasks 被拦下后,响应里为什么没有 X-Response-Time?错误体为什么没有被包装成 { data, timestamp }?
  2. 类上贴 @Roles(['staff'])、方法上贴 @Roles(['admin']):getAllAndOverride 和 getAllAndMerge 各读出什么?为什么拼错 SetMetadata 的 key 不报错,而拼错 config.get('DEMO_KEI', { infer: true }) 会编译报错?
  3. 为什么单例 Service 的字段存 requestId 会串号,而 AsyncLocalStorage 不会?举出两个拿不到 ALS 值的地方。
  4. app.useGlobalInterceptors(new X()) 和 { provide: APP_INTERCEPTOR, useClass: X } 有什么区别?为什么这个区别在写 e2e 测试时特别要紧?

综合题(每题 5 分)

  1. 场景题:新同事给 nest-lab 加了导出功能,上线后出了三件怪事:① 他新建了 ExportController,为了让导出接口公开,在类上贴了 @Public(),又在同一个类里顺手加了 DELETE /export/cache,结果任何人不带钥匙都能清缓存;② 他在 TasksController 的末尾加了 GET /tasks/stats,调用却返回 400 Validation failed (numeric string is expected);③ 有人反馈日志里同一个请求的 requestId 对不上,有几行是别的请求的 ID,还有几行干脆没有 ID。请定位每个现象最可能的原因,并给出修法。
  2. 场景题:Week 4 要把内存仓储换成 PostgreSQL。列出哪些文件需要改、哪些文件完全不用改,并解释为什么不用改。再说明:单元测试和 e2e 测试分别怎么保证「换仓储」没有改坏业务逻辑?数据库地址这个配置应该怎么接入,才能做到 fail fast?

Week 3 预告(Day 15–21):API 设计 + DTO 与验证

以 roadmap 的 Week 3 为准,大致包括(每天的具体拆分以当天讲义为准):

  • HTTP 语义深入:方法、状态码、幂等性、内容协商(接 Day 6:Day 6 你对 DELETE /tasks 回了 405,Day 8 发现 Nest 默认回的是 404)
  • REST 约束、版本化、分页:资源怎么命名、/v1 放哪、游标分页 vs 偏移分页
  • 统一错误格式 RFC 9457 / 7807 problem+json:把 Day 10 和 Day 13 的 AllExceptionsFilter 升级成标准格式(requestId 怎么放进去?)
  • DTO 与验证专题:DTO 是接口的「进出口报关单」,和数据库 Entity 分开的原因;class-validator + class-transformer + 全局 ValidationPipe(whitelist、transform、嵌套与数组校验、自定义校验器);和 Day 12 的 zod 方案对比取舍。Day 8 留下的那个坑「POST {} 被收下还回了 201」终于要补上了
  • 响应 DTO:ClassSerializerInterceptor + @Exclude(),防止把密码哈希这类字段返回给前端
  • OpenAPI:@nestjs/swagger 从 DTO 自动生成文档(会用到 Day 13 留给 configureApp 的那个位置)
  • 实战:在 nest-lab/ 里实现完整的任务管理 REST API,设计文档按语言无关的方式写;对照 ASP.NET Core DataAnnotations / FluentValidation、Spring Bean Validation(@Valid)
