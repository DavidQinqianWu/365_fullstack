🚀 先跑起来:开启 pg_stat_statements、灌数据、加负载

① 开启 pg_stat_statements(一次性,要超级用户)

它是 PostgreSQL 自带的扩展,但必须在服务器启动时就加载(它要在每条语句执行时记账),所以分三步:

# 本机安装(本课程环境就是这么做的):改 /etc/postgresql/16/main/postgresql.conf 第 752 行
#   原来:#shared_preload_libraries = ''
#   改成: shared_preload_libraries = 'pg_stat_statements'
sudo service postgresql restart              # 改这个参数必须重启,reload 不够

# 在 nest_lab 库里建扩展:它不是「受信任的扩展」(Day 33),普通用户建不了
sudo -u postgres psql -d nest_lab -c 'CREATE EXTENSION IF NOT EXISTS pg_stat_statements WITH SCHEMA public'
# 可选:让 nest_lab 用户自己能清零统计(默认只有超级用户能)
sudo -u postgres psql -d nest_lab -c 'GRANT EXECUTE ON FUNCTION public.pg_stat_statements_reset(oid, oid, bigint) TO nest_lab'

Docker:nest-lab/compose.yaml 今天加了一行 command: ['postgres', '-c', 'shared_preload_libraries=pg_stat_statements'],docker compose up -d 重建容器后,用 POSTGRES_USER(它是超级用户)执行一次 CREATE EXTENSION。本课程环境没有 Docker,这个写法没有实测。它是数据库实例的配置,不是应用的表结构,所以不写进 schema.sql。

📇 概念卡 #1:pg_stat_statements —— 账房的「每日工作量统计表」

① 一句话大白话: pg_stat_statements 给数据库执行过的每一种 SQL 记账:执行了几次、一共花了多少时间、平均多久、最慢多久、返回多少行、碰了多少缓存页和磁盘页。参数不同、形状相同的 SQL 合成一行(字面值都换成 $1)。按总耗时排序,排在最上面的就是最值得先优化的。

② 生活类比:每日工作量统计表

账房想让大家干活快一点,不是去问「哪件事最难」,而是让每个伙计在一张表上记账:「查会员的单子」今天做了 260 次,一共花了 14 分钟;「按日期找最新的单子」做了 135 次,一共花了 15 个钟头。一看就知道该先改哪件事。表上记的是事情的种类,不分具体是哪个会员:查 5000 号和查 42 号会员,记在同一行。表只记伙计在账房里干活的时间,客人在门口排队、跑腿送货的时间不在上面。表是从上次清零开始累计的。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「表上的时间就是客人等的时间」——它只记数据库内部的执行时间。网络往返、连接池排队、Nest 的校验和 JSON 序列化都不在里面。优化后「按 id 排的第一页」在数据库里只要 0.1 ms,HTTP 的 p50 却是 8–10 ms。用户感受到的慢,要从应用层的指标(Week 19 的 APM / OpenTelemetry)往下找,pg_stat_statements 只负责数据库这一段。
  2. 「一行就是一种请求」——规范化会把差别很大的调用合成一行。同一行里,?q=12345 要 75 ms,?q=invoice 只要 0.4 ms。看 min / max / stddev,差得大就说明这一行里混着不同的情况。反过来,同一个请求换了 SQL 写法(比如今天修 keyset 后)会变成新的一行。
  3. 「表上排第一的就是生产上最慢的」——这是本机、这份数据、这个负载比例下的结果。生产的数据量、缓存命中率、请求比例都不一样。今天的结论(以及 docs/query-tuning.md)要拿到生产规模的数据上复验。
④ 真实术语: pg_stat_statements、shared_preload_libraries(改了要重启)、query normalization / queryid(compute_query_id)、calls / total_exec_time / mean_exec_time / stddev_exec_time / rows / shared_blks_hit / shared_blks_read、pg_stat_statements_reset()、pg_stat_statements.max;相关的还有 log_min_duration_statement(慢查询日志)和 auto_explain(把慢查询的计划写进日志)。

📇 概念卡 #2:先测量,后优化 —— 一次优化,一次回退,一次修复

① 一句话大白话: 优化是一个循环:测量(找到最费时的那一条)→ 解释(EXPLAIN 看它为什么慢)→ 改一处 → 用同样的方法再测(确认真的变快了,而且别处没变慢)。每一步都留下证据,改了什么、为什么、代价是什么都写下来。不测量的优化是猜;只测一次的优化可能是巧合。

② 生活类比:先查表,改一件事,再查表

账房查完统计表,发现「按日期找最新的单子」最费时,于是给它做了一个按日期排的卡片盒。第二天再查表,这件事果然快了;可「找标题里有 invoice 的单子」却变慢了。翻了半天才发现,伙计做决定前会先「估一下大概有多少张」,而他估的时候只随手翻了几页样本,有时估成 30 张,有时估成 2 万张。估成 30 张时,他就选了「把卡片全拿出来再排」的办法。于是账房让伙计估的时候多翻一些样本。改完再查一次表,确认这回真的好了。

第 3 圈:?q= 加 trigram GIN,出现了一次回退。第一次建好 GIN 后,负载下大部分搜索快了,但常见词 q=invoice 的 HTTP p50 反而从约 20 ms 变成了 77–123 ms(3 遍里有 2 遍)。EXPLAIN 解释了原因:优化器要在两种计划里选,

  • 「按主键顺序扫、边扫边过滤、凑够 21 条就停」:命中多的词很快,invoice 只要扫 388 行,0.34 ms。
  • 「用 GIN 找出全部匹配行、再排序」:命中少的词很快,命中多的词要取出 1.5 万行再排,强制走这个计划时 23.7 ms(单次)。

短关键词的决定:接受,不改 DTO。

  • 1–2 个字符抽不出三元组(Day 33)。可以给 q 加 @MinLength(3),但这会让以前合法的请求变成 422,是破坏性的契约变更(openapi.json 和客户端都要跟着改),而中文里 2 个字的词(「登录」「加急」)是完全合理的搜索。
  • 实测:统计目标调高后,命中 0.1% 的短词 7–12 ms,负载下 p50 21–23 ms,可以接受。
  • 最坏的情况是「命中很少或没有结果的短词」,要扫完整张表,70–100 ms。负载脚本里没有模拟这种请求。
  • 要不要为它做点什么(pg_bigm 二元组、中文分词、v3 接口加最短长度),先得有数据。但 pg_stat_statements 把所有关键词合成了一行,拆不出「短词占多少」,需要在应用层按 q 的长度和结果数打指标。这是 Week 19 可观测性要解决的事。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「改一件事,只影响那一件事」——一处优化可能让别处变慢。加 GIN 让常见词的计划变差;调高统计目标让常见词稳定了,却让「少见词 + 按时间排序」(?q=urgent&sort=-createdAt)从 GIN 的 2.6 ms 变成了倒着扫时间索引的 20.0 ms(单次):优化器假设匹配的行均匀分布,估计扫 2 万行就够,实际扫了 4 万多行。这是成本模型的局限。权衡下来保留了这个设置,并写进了报告。所以每改一处,都要把整套负载重新跑一遍,不能只看改的那一条。
  2. 「测一次就知道」——测量本身有抖动,而且会被计划选择放大。同一份数据上,?q=urgent 在优化前有一遍是 9 ms、另两遍是 75 ms,就是因为 ANALYZE 抽样不同选了不同的计划。只测一次,很可能把「这次抽样运气好」当成「优化有效」。所以这门课的每个数字都跑 3 遍、写区间。
  3. 「本机测好了就行」——本机数据小、全在缓存里、负载和应用跑在同一台机器上。吞吐的绝对值(600 多个/秒)没有参考意义,只看相对变化。上线后用生产的 pg_stat_statements 复验,是优化循环的最后一步。
④ 真实术语: measure → explain → change → re-measure;baseline(基线);regression(回退);row estimate / selectivity;default_statistics_target 与列级 SET STATISTICS;plan instability / plan flip;cost model;load test(p50 / p95、吞吐);observer effect(测量本身会影响结果)。

📇 概念卡 #3:一个查询一个索引,还是少数索引服务多数查询

① 一句话大白话: 最省事的想法是「每条慢查询配一个专门的索引」,但每个索引都在每次写入时收费(Day 32)。更好的做法是找出能同时服务好几条查询的少数几个索引:一个索引既能正着读也能倒着读,能用最左前缀,能「按顺序扫、边扫边过滤」;对剩下那些已经足够快的查询,就不建。每个建或不建的决定,都要写下证据和代价。

② 生活类比:少做几个卡片盒,每个都多管几件事

账房本来打算做六个卡片盒:按日期正着排的、倒着排的、只收未完成单子的、按标题排的……每多一个盒子,每记一笔账就要多抄一张卡。后来他发现:按日期排的那一盒,从前往后翻、从后往前翻都行;问「最新的未完成单子」,从后往前翻、看到已完成的跳过,翻不了几张就凑够了。最后只留了三个盒子,另外三个不做,并且在墙上贴了一张纸,写清每个盒子管哪些事、哪些盒子为什么没做。

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「盒子越少越好」——少不是目标,够用且代价可接受才是。今天的负载是读多写少;如果系统主要是批量导入(写多读少),连这三个索引都可能太多,要在导入时先删索引、导完再建(Day 33:先插数据后建 GIN 快得多)。索引是取舍,不是越少越好,也不是越多越好(回扣 Day 32)。
  2. 「我建了索引,账房就会用」——优化器按估算选计划,可能不用你想让它用的那个。今天的常见词就不走 GIN,而少见词 + 排序在调高统计目标后也不走 GIN。建了索引,要用 EXPLAIN 确认它在哪些查询里真的被用了,上线后再看 pg_stat_user_indexes.idx_scan。
  3. 「墙上那张纸写一次就行」——数据和请求会变。未完成任务的比例、标题的写法、哪种排序最常用,都会随着产品变化。今天不建的 done 索引,明年可能就该建了;今天建的 title 索引,可能一直没人用。报告要和 pg_stat_statements 一起定期复看。

✅ 总结与自测

今天带走的 4 句话

  1. 先测量:pg_stat_statements 要 shared_preload_libraries + 重启 + 超级用户 CREATE EXTENSION;按总耗时(次数 × 平均)排序找优化对象。它只统计数据库内部的时间,而且会把参数不同的同一种 SQL 合成一行。
  2. 逐条改、逐条复测:(created_at, id) 让 -createdAt 第一页从 41–62 ms 到 0.06–0.46 ms;keysetCondition 补一个冗余范围条件,深分页从 28–38 ms 到 0.06–0.20 ms;trigram GIN 让很少或没有结果的搜索从 70–100 ms 到 1 ms 以内;负载下吞吐从 84–91 个/秒到 619–686 个/秒。
  3. 优化会回退:加 GIN 后,常见词因为行数估算不稳(ANALYZE 抽样,估算差将近 1000 倍)选错了计划;把 title 的统计目标调到 1000 修好了,但「少见词 + 按时间排序」因此变慢。每改一处都要整套重测,并把权衡写下来。
  4. 少数索引服务多数查询:最后只建了 3 个(写入因此慢 5–8 倍,多占 53 MB)。done 不建,因为按时间扫几十行就够;created_at 用升序,因为按时间追加时降序索引大 70%。offset 翻到第 10001 页要 18–28 ms,keyset 不到 0.1 ms。
