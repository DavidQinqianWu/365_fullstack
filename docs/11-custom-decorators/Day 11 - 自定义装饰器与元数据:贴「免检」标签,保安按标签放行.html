🏷️ 接上回:保安只会「挂上就查」

Day 10 的 DemoKeyGuard 挂在哪个接口上,哪个接口就要钥匙。这个做法有两个隐患:

  • 默认不设防:以后新写一个 PATCH /tasks/:id,忘了挂 @UseGuards,它就裸奔上线了,没有任何报错提醒你。
  • 规则写死:「只有管理员能删」「这几个接口谁都能看」—— 这些都是每个接口不同的规则,保安却只有一种行为。

更安全的做法是反过来:保安守在全店每个门口(全局),默认谁都要钥匙;只有贴了「免检」标签的门才放行。这样忘贴标签的后果是「多拦了一个人」(403,安全的失败),而不是「放进了一个不该进的人」。

💡 生活翻译: Day 8 我们说过,装饰器是贴在员工身上的便利贴,开店时总部读便利贴排路由。今天我们自己印便利贴:「免检」「仅限管理员」;再自己写读便利贴的人:保安上岗时看一眼这道门上贴了什么,再决定查不查。Day 8 提过的那句话 ——「只贴不读等于白贴」—— 今天把「读」的那一侧亲手写出来。

📇 概念卡 #1:元数据装饰器 + Reflector —— 贴标签的人和读标签的人

① 一句话大白话: 在方法或类上贴一张写着「数据」的标签(@Public()、@Roles(['admin']));切面(guard / interceptor)运行时用 Reflector 把标签读出来,按标签决定怎么做。

② 生活类比:门上的贴纸 + 会看贴纸的保安

开业前,装修队按图纸在各个门上贴好贴纸:大堂门贴「免检」,仓库门贴「仅限管理员」。装修队贴完就走了,贴纸本身不会拦任何人。开业后,保安每放一个人进门之前,先抬头看一眼这道门上的贴纸:「免检」→ 直接放;「仅限管理员」→ 查工牌。如果某道门上贴了一张保安看不懂的贴纸(写错了字),保安就当没看见,按默认规则办事。

比喻 ↔ 真实 对照

比喻真实组件nest-lab 里
贴纸metadata:挂在类 / 方法上的键值数据isPublic = true、Roles = ['admin']
印贴纸的模具(经典款)SetMetadata(key, value):返回一个装饰器Public = () => SetMetadata(IS_PUBLIC_KEY, true)
印贴纸的模具(防错款)Reflector.createDecorator<T>():装饰器对象本身就是 key,值有类型Roles = Reflector.createDecorator<string[]>()
装修队贴贴纸装饰器在类定义时执行,把数据写进元数据表import 文件的那一刻
保安抬头看贴纸Reflector(一个可注入的 Provider)DemoKeyGuard、RolesGuard 的构造函数里注入
「先看这道门,没有再看整栋楼的规定」getAllAndOverride(key, [handler, class]):第一个有值的胜出方法上的 ['admin'] 盖过类上的 ['staff']
「门上的和楼里的规定都算」getAllAndMerge(key, [handler, class]):数组拼起来、对象合并['admin', 'staff']
只看这道门get(key, target)reflector.get(Roles, TasksController.prototype.remove)
🖥️ 前端翻译: Angular 的 @Component({ selector, template }) 就是元数据装饰器:组件类本身不知道自己是组件,框架读标签才知道。React 圈也有同款套路,只是不用装饰器:老版 Next.js 常写 Page.requireAuth = true(给组件挂 static 属性),再在 _app.tsx 里读 Component.requireAuth 决定要不要跳登录页 —— 「页面贴标签,外层布局读标签」,和今天的「handler 贴标签,guard 读标签」一模一样。App Router 里 export const dynamic = 'force-dynamic' 也是一种给框架读的元数据。
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「贴了『仅限管理员』,就只有管理员能进」——错,要有保安读它才算数。标签是数据,不是代码,本身不拦任何人。实验部门里 DecoratorDemoController 类上贴了 @Roles(['staff']),但 open 方法没挂 RolesGuard,于是这张标签对 open 毫无作用(J1、J2 都是 200)。这就是 Day 8 说的「只贴不读等于白贴」。
  2. 「贴纸写错字,保安会提出来」——不会,保安当没看见。手写字符串 key 拼错了('isPubilc'),TypeScript 不报错、启动不报错、请求也不报错,只是静默失效(实验 G:想免检的接口照样 403)。防法:key 用导出的常量(IS_PUBLIC_KEY),或者直接用 Reflector.createDecorator,它连 key 都不需要,拼错装饰器名字就是编译错误。
  3. 「就近原则是贴纸自带的规矩」——不是,是保安自己选的读法。同样两张贴纸(类上 staff、方法上 admin),用 getAllAndOverride 读出 ['admin'],用 getAllAndMerge 读出 ['admin','staff'],结论完全不同。「方法覆盖类」还是「两者都算」,是你写 guard 时做的设计决定,要和团队约定清楚。
④ 真实术语: metadata decorator(元数据装饰器);SetMetadata;Reflector 的 get / getAllAndOverride / getAllAndMerge;Reflector.createDecorator(Nest 10.2 起提供,类型安全、无需 key,今天的 @Roles 用它;@Public() 保留经典写法,因为官方文档和大量现有代码都这么写,两种你都要认得)。
declarative security(声明式安全):在接口上声明需要什么权限,由统一的切面去执行,而不是在每个方法里写 if (role !== 'admin') throw ...。

📇 概念卡 #2:参数装饰器 —— 前台的自动填表员

① 一句话大白话: 参数装饰器是一个「每个请求都执行一次」的小函数,从请求里取出某样东西,直接当成 handler 的参数值递进去。@Param()、@Body() 是 Nest 自带的,今天自己写一个 @RequestId()。

② 生活类比:自动填表员

前台接单时要填一张表:「桌号」「点了什么」「流水号」。Nest 自带的填表员会填「桌号」(@Param)和「点了什么」(@Body)。今天新雇一个填表员专门填「流水号」:单子上已经印了流水号就照抄(方便后厨、收银对账),没印就当场编一个新的。每来一张单子,他就填一次。

比喻 ↔ 真实 对照

比喻真实组件
填表员这个岗位createParamDecorator((data, ctx) => 值) 创建的装饰器
填表员的工作手册工厂函数:拿到 ExecutionContext(Day 10)→ 取出 req → 返回值
表上那一栏handler 的那个参数:create(@Body() body, @RequestId() requestId: string)
单子上印好的流水号请求头 x-request-id(网关 / 上游服务常会带)
当场编一个randomUUID()
给填表员的额外说明data 参数:@RequestId('xxx') 里的 'xxx'(今天没用到)
③ ⚠️ 这个比喻在哪里会骗你:
  1. 「装饰器都只在开业时执行一次」——参数装饰器例外。元数据装饰器(@Public())在类定义时执行一次,之后只是被读;参数装饰器的工厂函数在每个请求都会执行(实验 J1、J2:两次请求拿到两个不同的 UUID)。所以工厂函数里不要做慢操作,它和 Day 10 的切面一样,算在每个请求的成本里。
  2. 「填表员会检查流水号对不对」——不会,他只负责取值。参数装饰器不做校验;要校验 / 转换,再挂一个 pipe(Day 10)。例如自带的 @Param('id', ParseIntPipe) 就是「取值 + 核单」两步。
  3. 「单子上印的就是真的」——客户端说什么都可以。x-request-id 用来串日志没问题;但今天的 x-demo-role 也是从请求头读的,任何人都能伪造自己是 admin。这只是演示。Week 10 的 @CurrentUser() 会用同样的写法,但值来自验过签名的 JWT,而不是客户端随手写的头。
④ 真实术语: param decorator:createParamDecorator;request ID / correlation ID(请求 ID / 关联 ID):一个请求从网关到各个服务都带着同一个 ID,出问题时用它把所有日志串起来(Week 15 可观测性会用到);常见的自定义参数装饰器还有 @CurrentUser()、@ClientIp()、@Tenant()。

📇 概念卡 #3:组合装饰器与「默认上锁」—— 一张套餐贴纸

① 一句话大白话: applyDecorators 把几张贴纸和几个切面打包成一个装饰器(@AdminOnly());再配上「全局保安默认拦、@Public() 例外」,就得到 Nest 里最常见的鉴权写法。

② 生活类比:套餐贴纸 + 默认上锁

仓库、财务室、监控室都要「贴『仅限管理员』+ 门口加一个查工牌的保安」。与其每道门都贴两样,不如印一张套餐贴纸「管理员区」,背面写清楚「= 仅限管理员贴纸 + 工牌保安」。同时,总部规定所有门默认上锁(要钥匙),只有贴了「免检」的门才敞开。

// src/common/decorators/admin-only.decorator.ts
export function AdminOnly() {
  return applyDecorators(Roles(['admin']), UseGuards(RolesGuard));
}

// src/tasks/tasks.controller.ts
@Public() @Get()        findAll() { ... }      // 免检
@Public() @Get(':id')   findOne(...) { ... }   // 免检
@Post()                 create(...) { ... }    // 没贴 = 要钥匙
@AdminOnly() @Delete(':id') remove(...) { ... } // 要钥匙 + 要 admin

③ ⚠️ 这个比喻在哪里会骗你:
  1. 「套餐贴纸是一种新能力」——它只是打包。@AdminOnly() 展开后和你手写 @Roles(['admin']) @UseGuards(RolesGuard) 完全等价,第 2 幕读到的 remove 上就是 Roles=["admin"]。好处是「改一处、全站生效」(以后加 swagger 的 @ApiBearerAuth() 也只改这里);坏处是读代码的人要点进去才知道它到底贴了什么。
  2. 「默认上锁了,就万无一失」——只锁住了第一道门。全局保安只管「有没有钥匙」。角色检查(RolesGuard)仍然是挂上才有:如果哪天新写了一个删除接口却忘了贴 @AdminOnly(),拿着钥匙的普通用户照样能删。真实项目会把角色也做成全局 guard(没有 @Roles 就不限制),并配上测试兜底。
  3. 「哪个保安写在前面,哪个先查」——顺序看范围,不看你写的位置。全局 guard 永远先于 Controller / 方法级的 guard(实验 D:先过钥匙,才轮到角色)。所以「不带钥匙的 admin」会被第一道保安拦下,根本见不到查角色的那位(e2e 里专门有这个用例)。
④ 真实术语: applyDecorators(composite / composed decorator,Java 里叫 meta-annotation);APP_GUARD;secure by default / default deny(默认拒绝):先全部拦住,再显式开放,忘了的代价是 403 而不是数据泄露;RBAC(Role-Based Access Control,基于角色的访问控制)—— Week 10 会把今天的请求头换成 JWT 里的角色声明。

「给方法贴注解,框架 / 切面运行时用反射读注解」是 .NET 和 Java 的看家本领,它们比 TypeScript 早用了二十年:

命题NestJS(教具)C# / ASP.NET CoreJava / Spring BootGo
定义一种标签 SetMetadata(key, v) / Reflector.createDecorator<T>() 继承 Attribute 的类 + [AttributeUsage] @interface Roles + @Retention(RUNTIME)(否则运行时读不到)+ @Target 没有注解(struct tag 只用于序列化)

📌 一个关键差异:Java 注解要写 @Retention(RUNTIME) 才能在运行时被反射读到;C# 的 Attribute 默认就保留在程序集里;TypeScript 的类型和接口在运行时全部消失,只有装饰器主动写进去的元数据才留得下来 —— 这也是 Day 9 里接口要配 token 的同一个原因。Go 干脆不走这条路:没有注解、没有反射式的框架魔法,一切都在注册路由时显式写出来。

🎤 面试翻译练习: 面试官问:"How would you implement role-based authorization in NestJS? How does a guard know which roles an endpoint requires?"(或者 .NET 面试:「[Authorize(Roles=...)] 背后是怎么工作的?」)你可以答:
"我会用元数据装饰器加 guard。在接口上用自定义装饰器声明需要的角色,比如 @Roles('admin'),它在类定义时把角色作为元数据挂到方法上。guard 通过 ExecutionContext 拿到目标 handler 和 controller,用 Reflector 读出元数据,通常是方法级覆盖类级,再和当前用户的角色比较,不满足就返回 false,得到 403。为了默认安全,我会把鉴权 guard 注册成全局的,公开接口用 @Public() 显式放行,这样忘了标注的接口是被拒绝而不是被暴露。常用的组合可以用 applyDecorators 打包,比如 @AdminOnly()。这和 ASP.NET Core 的 [Authorize] / [AllowAnonymous]、Spring 的 @PreAuthorize 加 permitAll 是同一个思路:声明式安全,用注解描述规则,由统一的切面执行。"

✅ 总结与自测

今天带走的 4 句话

  1. 元数据装饰器只「贴」,切面用 Reflector「读」:标签是数据不是代码,贴了没人读就毫无作用;拼错 key 会静默失效,用常量或 Reflector.createDecorator 防住。
  2. 读法决定结论:get 只看一处,getAllAndOverride 就近覆盖(方法优先),getAllAndMerge 合并;这是你的设计决定。
  3. 两种装饰器的执行时机不同:元数据装饰器在类定义时执行一次;参数装饰器(createParamDecorator)每个请求执行一次,负责「取值」,校验交给 pipe。
  4. AOP 闭环 = 全局切面 + 按标签开关:APP_GUARD 默认拦(secure by default),@Public() 例外,@AdminOnly() 用 applyDecorators 打包。这就是 [Authorize] / [AllowAnonymous]、@PreAuthorize 在 Nest 里的样子。
