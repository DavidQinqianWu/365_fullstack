# 环境变量与 .env：让同一份代码跑在不同环境

> 2026-10-09 · DevOps · 约 11 分钟 · 来源：每日全栈15min 自动生成

## 摘要

同一份代码要同时跑在开发机、测试服务器和生产环境，差异全靠环境变量管理。本文讲解 .env 文件的分层加载、代码中如何读取、以及为什么绝不能把密钥提交进仓库。这是每个全栈工程师上线第一个项目前必须养成的习惯。

## 要点

- 环境变量把「代码」与「环境差异配置」分离，是同构部署的前提
- .env 存本地默认值，.env.production 等文件按环境覆盖
- 代码里用 process.env.X 读取，缺关键变量时应快速失败
- .env 必须加入 .gitignore，密钥只存在于部署平台的环境配置里
- 给 .env 配一份不含密钥的 .env.example 供团队参考

## 示例

.env 的常用组织方式与读取方式，以及必须做的两件事。

```bash
# .env（本地开发用，已加入 .gitignore）
PORT=3000
DATABASE_URL=postgres://localhost:5432/myapp
API_SECRET=本地随便填一个

# .env.example（提交到仓库，供同事参考需要哪些变量）
PORT=
DATABASE_URL=
API_SECRET=

# 启动时加载（Node 20+ 原生支持，或借助 dotenv）
# node --env-file=.env server.js

# 代码中读取，并在缺失时尽早暴露问题
# const url = process.env.DATABASE_URL;
# if (!url) throw new Error('DATABASE_URL 未配置');
```

## 踩坑提醒

把含真实密钥的 .env 提交进 Git 后，即使后来删除并忽略，密钥仍完整留在提交历史里，必须视为已泄露并立即轮换。
