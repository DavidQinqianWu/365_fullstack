# 幂等性（Idempotency）：让重试变得安全的后端设计

> 2026-10-04 · 后端 · 约 11 分钟 · 来源：每日全栈15min 自动生成

## 摘要

网络会超时，客户端一定会重试，而重试可能把一笔订单扣两次款。幂等性保证同一个请求执行一次和执行多次效果相同。用 Idempotency-Key 头配合去重存储，是支付、下单等写接口的标准做法，也是后端工程师必须掌握的基础防御手段。

## 要点

- GET/PUT/DELETE 天然幂等，POST 每次调用都会创建新资源，不幂等
- 幂等键通常用 UUID，客户端为同一次业务操作生成一次、重试时原样重发
- 服务端把「幂等键 + 用户 + 接口」作唯一键，首次执行并记录结果
- 重试命中已有记录时直接返回首次的结果，不再执行副作用
- 结果记录要设过期时间（如 24h），并考虑并发请求加锁防重复执行

## 示例

Express 中间件：用幂等键防止重复提交产生副作用：

```javascript
const store = new Map(); // 生产环境应换成 Redis 并设 TTL

app.post('/api/payments', (req, res) => {
  const key = req.header('Idempotency-Key');
  if (!key) return res.status(400).json({ error: 'missing key' });

  const idemKey = `${req.user.id}:${key}`;
  if (store.has(idemKey)) {
    return res.status(store.get(idemKey).status).json(store.get(idemKey).body);
  }
  // 并发下需加锁，确保同一 key 只有一个请求真正执行
  const result = processPayment(req.body);       // 副作用只发生一次
  store.set(idemKey, { status: 201, body: result });
  res.status(201).json(result);
});
```

## 踩坑提醒

只在数据库加唯一约束就以为万事大吉：约束能防重复写入，但重试的第二次请求会拿到 500 而非首次的结果，客户端无法判断业务是否成功。幂等设计要「防重放」也要「返回首次结果」。
