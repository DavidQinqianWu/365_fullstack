## 1. 用"总店 / 分店 / 服务员"的比喻讲清:进程和线程的区别是什么?为什么 Node 要靠"多开分店"而不是"多招服务员"来利用多核?

- **进程 = 一家分店**:有自己独立的厨房、仓库、账本(独立内存空间),一家着火不会烧到另一家;代价是开店贵(每个 Node 进程几十 MB 起步),分店之间只能打对讲机(IPC,传的是拷贝)。
- **线程 = 同一家店里的服务员**:共用一个厨房和仓库(共享内存),沟通便宜,但会抢同一口锅(竞态,要加锁),一个人把厨房点着,整家店一起完蛋。
- Node 的 JS 代码只有**一个主服务员**(单线程 event loop),JS 层面没法"多招几个服务员一起处理请求";想吃到多核,最直接的办法就是多开几家一模一样的分店(cluster / 多进程 / 多副本)。
- (Day 5 预告:Node 其实也能招服务员 —— `worker_threads`,但它更像"各自带一个独立小厨房的帮厨",默认也不共享内存。)

## 2. child_process 四兄弟 exec / execFile / spawn / fork 各适合什么场景?为什么"输出可能很大"时必须选 spawn?

| 兄弟 | 外号 | 适合 |
|---|---|---|
| `exec` | 外卖窗口(走 shell,攒全单) | 输出很小、想用管道/通配符的一次性小命令,如 `git rev-parse HEAD` |
| `execFile` | 不走 shell 的外卖窗口 | 输出小、参数里有用户输入 —— 不经过 shell,避开注入 |
| `spawn` | 传送带(stream,来一块给一块) | 输出大或时间长:日志、ffmpeg 转码、大文件处理 |
| `fork` | 开一家 Node 分店 + 对讲机 | 子进程也是 Node,并且要双向传消息(IPC):CPU 重活外包 |

- 输出大必须选 spawn:exec/execFile 把输出**全部攒进内存**,超过 `maxBuffer`(默认 1MB)就直接杀掉子进程(ex1 实测 6MB 当场报错);spawn 是流,内存只占"传送带上那几块",和输出总量无关。

## 3. cluster 共享同一个端口的魔法是怎么回事?店长(primary)为什么只管看店、不接客?

- **魔法**:真正 `listen` 端口、持有那个监听 socket 的只有 primary。worker 调 `listen(3456)` 时,并不自己去占端口,而是请店长代办;新连接进来后,店长按 round-robin 把连接的句柄递给某个 worker(Linux 默认;Windows 上是 worker 直接共享句柄)。所以不报 `EADDRINUSE`。
- **店长不接客**:店长是整家连锁店唯一的"大门 + 管理员"。它要是也去炒菜,一道 CPU 硬菜就会让它卡住,卡住期间新连接没人分发、分店倒闭没人重开;它要是崩了,所有分店跟着一起关门。所以店长越简单越好,只做 fork、分发、盯梢、重开。

## 🧠 思考题参考答案

### ex1(exec vs spawn)

1. **调大 maxBuffer 能"修"吗?** 只是把炸弹引线加长。输出照样全部攒在内存里,今天 6MB 调到 10MB 能过,明天日志 2GB 就会把主进程内存撑爆,而且炸得更晚、更难查。根治办法是换成流(spawn),内存与输出大小脱钩。
2. **不走 shell 对安全意味着什么?** 参数数组原样交给程序,`;`、`&&`、`$( )` 都只是普通字符,不会被当成命令执行。exec 是字符串拼接后交给 shell 解析,文件名 `a.txt; rm -rf ~` 会被拆成两条命令,第二条真的把家目录删掉:这就是**命令注入**(Week 20 安全周会再复现一次)。原则:有用户输入就别用 exec。
3. **小命令用哪个?** 输出就几行时 exec 完全合理:回调一次拿到完整字符串,代码最短;还能直接用 shell 的管道和通配符。前提是命令里**没有用户输入**。

### ex2(fork + IPC)

1. **为什么不共享内存?** 进程的定义就是"独立内存空间",这正是隔离和稳定的来源。两家分店没有共用的仓库,只能打对讲机,消息会被序列化**拷贝**过去。真要共享内存(SharedArrayBuffer)就得面对竞态和加锁,那是线程的世界,也是 Day 5 的话题。
2. **谁崩了会怎样?** 子进程卡死或崩溃:主进程**照常营业**,只会收到 `exit` / `error` 事件(或者一直等不到回话),所以生产上要给子任务设**超时**,超时就 kill 掉重试。主进程崩了:IPC 通道断开,子进程收到 `disconnect`,默认不一定自动退出,可能变成没人管的"孤儿",所以子进程要监听 `disconnect` 后自行退出。
3. **几毫秒的活,一天几百万次,每次 fork 划算吗?** 不划算。每次 fork 都要新起一个 V8(几十 MB、几十毫秒),开店成本远大于炒菜成本。正确做法是**池化**:预先开好固定数量的帮手反复用(进程池,或者更轻的 **worker_threads 线程池,如 piscina**)。这正是 Day 5 的内容。

### ex3(cluster)

1. **为什么不报 EADDRINUSE?谁持有 socket?** primary 持有唯一的监听 socket,worker 的 listen 只是"登记接单",见默写 Q3。
2. **primary 为什么不接单?** 见默写 Q3:店长一卡,分发和重开全停;店长一崩,全店关门。
3. **cluster 重开 vs PM2 / systemd / k8s?** 是同一个思想("进程死了就拉起来")在不同层级的实现:cluster 管同一台机器、同一个进程树里的 worker;PM2 / systemd 管整个进程(包括 primary 自己);k8s 管容器,还能跨机器调度、做健康检查。**生产上优先用外层(k8s / systemd)**:它们能救 primary,能跨机器,还统一了日志和监控。在 k8s 里通常干脆不用 cluster,一个容器跑一个进程,靠多副本吃满多核(Week 16–17 会实操)。
4. **每家分店各自的 Map 缓存一致吗?** 不一致。4 家分店有 4 份互不相识的缓存,同一个用户这次打到 A 店有缓存,下次打到 B 店就没有,甚至会读到不同版本的数据。这说明**多进程/多副本服务应当是无状态的**,共享状态(缓存、会话、限流计数)要放到外部存储里,比如 Redis(Week 8)。

## 📒 我的理解笔记(做题时的讨论/顿悟,随时记)

- 实测数据:ex1 exec 6MB 当场 `maxBuffer length exceeded`,spawn 829 块共 6.2MB,rss 只涨约 6MB;ex2 主进程算 fib(42) 约 3s,期间心跳 0 下,fork 后心跳 17 下,但总耗时反而多约 350ms;ex3 4 家分店 round-robin 轮流接单,杀掉一家后服务不中断。
- 一句话总结:**多进程换来的是隔离和不卡场,不是单任务更快。** 想要单任务更快,得把活拆开并行算。

### ⚠️ ex3 预测 2 的补充

实验里杀掉 worker 后**等了 800ms** 才发请求,所以没有失败。真实生产中,**正在被那家分店处理的请求**会随着它倒闭而断开(客户端看到 `ECONNRESET`)。所以上线时要做**优雅关闭**:收到 SIGTERM 后先停止接新单、做完手上的单再退出(Week 14 Docker 周会讲 PID 1 和 SIGTERM)。
