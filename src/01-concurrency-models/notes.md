## 1. 并发和并行有什么区别?用面馆的例子说明。

并发: 同一时间段, 是一个时间段内. 应付多件事——一件事没做完可以先搁下,去做另一件。像一个人一边回微信一边烧水,水开了先去关火。
并行: 指的是真的是在同一时间点, 是一个时刻. 在做两个事情,左手炒菜, 右手刷完, 左手右手同时开工

## 2. 为什么 Node.js 特别怕 CPU 密集任务,而 Java/C# 的多线程模型相对不怕?Go 又是怎么"两头占便宜"的?

1. Node.js 怕CPU计算任务是因为, 你的业务代码在Node.js上是单线程, 如果耗时, 那么会卡住其他的任务执行. Node擅长做等待性任务, 就是分配任务给其他人,自己Node的进程等消息就行了, 不要什么都放到Node.js进程中.
2. Java/C# 是多线程,可以开另一个线程去做计算性任务, 但是每个线程都是高级版(一个线程栈约 1MB), 比较占内存, 开多了就会吃内存, 服务器崩溃。现代写法不是来多少开多少, 而是用**线程池**(固定 200 个服务员轮班)配合 async/await 让出线程。所以它们不是不怕堵, 是"堵一个线程只损失一个服务员"; 它们真正怕的是**线程池被打满**。
3. GO 的 goroutine 是**协程, 不是线程**: Go 调度器把成千上万个 goroutine 映射到少量几个真线程上轮流跑。goroutine 便宜(初始栈几 KB)所以能开海量并发, 但"人手便宜"不代表"计算免费"——磨面粉还是要花那么多力气。"两头占便宜"的准确含义: **写法上**像多线程那样直白(同步风格从上往下写), **成本上**像事件循环那样能开海量并发; 主要好处是等待型任务也能用直白写法, 而不是计算任务变便宜。并行度永远被物理核心数封顶。

## 📒 我的理解笔记:await 和 .then() 是同一件事的两种写法

(来自做 ex2 时的讨论,原话记录)

**核心理解:`await` 是一道分界线。它之后的所有代码(一直到当前函数结束),会被整体打包成"纸条",挂到被 await 的那个 Promise 的铃铛后面执行。**

```ts
const p = readFile(BIG_FILE, "utf-8"); // 递单,先不等
console.log("B 递完单子,服务员马上去招呼下一桌了 🏃");
await p;
// 下面三行概念上等价于被打包扔到了 p 之后执行:
console.timeEnd("B 异步读文件");
console.log("B 读完了 🎉");
await cleanupFile();

// 等价于:
p.then(() => {
  console.timeEnd("B 异步读文件");
  console.log("B 读完了 🎉");
  return cleanupFile();
});
```

要点:

1. `.then()` 和 `await` 在 event loop 眼里完全一样:都是「递单 + 注册铃铛(回调) + 服务员继续往下跑」。`.then()` 把回调写在明处;`await` 让编译器帮我把后面的代码自动包进回调。
2. `await` **看起来**像堵住服务员,实际暂停的只是这个 async 函数自己;服务员(主线程)照常绕圈服务别人。**await 暂停的是函数,不是服务员。**
3. 打包范围是「到当前函数末尾」——函数外的代码不会被包进去,函数会提前 return 一个 Promise,外面的人照常往下跑。
4. 链式 await 就是纸条套纸条:第二个 `await cleanupFile()` 会把它后面的代码再挂到 cleanup 的铃铛上。**写法是直线的,执行是链式的** —— 这就是 await 治好 callback hell 的原因。
5. 真实项目偏爱 await:多层异步不塌陷、`try/catch` 统一错误处理、跨语言通用(C#/Python/Kotlin/Swift 都有 async/await,写法几乎一样)。

## 订正区(对完答案后把说错的地方写在这)

- **Java/C# 不是"不怕堵"**: 我原来只说线程占内存, 漏了关键机制——现代 Java/C# 用**线程池**(固定数量轮班)+ async/await 让出线程。堵一个线程只损失一个服务员, 真正的灾难是**线程池被打满**。
- **goroutine 是协程不是线程**: 我原来写成"低内存占用的线程", 错了。goroutine 由 Go 调度器映射到少量真线程上跑; 它便宜(几 KB)指的是"人手便宜", **计算本身不免费**。"两头占便宜" = 写法直白(像多线程)+ 并发成本低(像事件循环), 不是"计算任务变便宜"。10 万个 goroutine 同时算题, 8 核机器同一时刻还是只有 8 个在真跑。

## ✅ 自测清单答案(Day 1 收官四问)

**1. 向不懂技术的人讲清 event loop**

面馆只雇了一个服务员, 他有条铁律: 绝不站着等。给客人点完单, 单子递给后厨, 立刻去下一桌; 后厨出餐按铃, 他听到铃声再回来端菜。event loop 就是这个服务员——你的代码全跑在他一个人身上, 慢活(读文件、查数据库)外包给后厨(libuv 线程池), 靠"铃铛"(回调)通知他回来收尾。一个人能应付上万桌, 因为大部分桌 90% 的时间都在等后厨。

**2. 三种并发模型各一个优缺点**

| 模型 | 优点 | 缺点 |
|---|---|---|
| 多线程/线程池(Java/C#) | 堵一个线程只损失一个服务员, 写法直白从上往下 | 线程贵(每个约 1MB 栈), 人多餐馆装不下, 怕线程池打满 |
| 事件循环(Node.js) | 一个服务员应付上万桌, I/O 密集场景成本极低 | 唯一的服务员被 CPU 任务拖住(磨面粉), **全场**停摆 |
| 轻量协程(Go) | 写法像多线程一样直白, 成本像事件循环一样低(几 KB 一个) | 只是"人手便宜", 计算不免费; 并行度照样被物理核心数封顶 |

**3. 为什么 setTimeout(fn, 1000) 不保证恰好 1 秒后执行**

1000ms 只是"**最早**响铃时间": 1 秒后系统才把你的回调放进取餐铃区排队。但如果那一刻服务员正被别的活占用(比如一个 3 秒的 while 循环在磨面粉), 他腾不出手, 铃铛只能超时等待。所以 setTimeout 保证的是"不早于 1000ms", 不是"恰好 1000ms"——ex1 实验里铃声迟到约 2 秒就是证据。

**4. async/await 在 Node 和 C# 里的一句话差别**

写法几乎相同, 差别在底层让出的东西: C# 的 await 让出的是**线程池里众多线程之一**(堵了只损失一个服务员), Node 的 await 让出的是**唯一的主线程**(所以 Node 对阻塞更敏感)——也因此, I/O 写成同步在 C# 是浪费, 在 Node 是灾难。
